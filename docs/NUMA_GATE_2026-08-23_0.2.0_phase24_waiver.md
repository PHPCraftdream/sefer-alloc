# NUMA gate Phase 2/4 risk acceptance — numa-shim 0.2.0 — 2026-08-23

## What this record is

A dated, explicit owner risk acceptance at release time. It is NOT a
gate-run report (nothing was run for this record), NOT an amendment of
the gating policy, and NOT a judgment that Phases 2 and 4 are
unnecessary. It records that `numa-shim` 0.2.0 publishes with two of the
four phases `docs/NUMA_RELEASE_GATE.md` requires still outstanding, that
the owner knows this, and that the owner chose to publish anyway.

## The decision

- **Decision:** publish `numa-shim` **0.2.0** with **Phase 2 (real Linux
  kernel / QEMU `-numa` VM)** and **Phase 4 (real multi-socket cloud
  instance)** outstanding.
- **Decided by:** the repository owner, 2026-08-23; recorded by task
  #1290 (docs-only — no code, tests, or gate runs in that task).
- **Release/tag commit:** **`cb5d35107ddb883672c7e262affa1b4075285dce`** (task #1262, version-bump commit, 2026-08-25) — the commit where `crates/numa-shim/Cargo.toml`'s `version` field was set to `0.2.0`. This binds the acceptance to the exact tree that publishes as 0.2.0.
- **Reason — infrastructure, not judgment:** the development environment
  can provide neither phase: no Linux kernel for Phase 2's QEMU `-numa`
  runbook, and no multi-socket metal cloud instance (AWS `c5n.metal` /
  Azure HBv4) or cloud credentials for Phase 4. Both gaps were recorded
  as observed facts by the original gate run
  (`docs/NUMA_GATE_RUN_2026-08-23_task1270.md`, "Phase 2 — DID NOT RUN"
  / "Phase 4 — DID NOT RUN") and re-confirmed unchanged by the task
  #1279 Phase-1 re-run. No synthetic, fake, or simulated substitute for
  either phase was attempted, per the original audit's explicit warning.

## What is and is not verified for 0.2.0

From the two gate-run records (`NUMA_GATE_RUN_2026-08-23_task1270.md`,
`NUMA_GATE_RUN_2026-08-23_task1279_phase1_rerun.md`):

- **Phase 1 (mock dispatch): PASS** — 31/0 passed/failed at `c427dd6`
  (task #1279, superseding the earlier 28/0 at `356fb44`). Known-stale
  per item 102's finding E1: `41af0fd` (#1275) and `813d9e7` (#1277)
  touched `crates/numa-shim/src/lib.rs` after that measurement, so the
  FINAL Phase-1 re-run is still owed on the final pre-tag revision, run
  LAST, after the version bump (E1's ordering rule, folded into #1262's
  task description). **This record does not waive Phase 1.**
- **Phase 3 (Windows virtual NUMA): PARTIAL** — single-NUMA-safe suites
  pass on the host kernel (numa_seam 5/5, numa_segment_id 2/2,
  single-node-host numa_alloc 2/2, corroborating only); the actual
  in-guest Hyper-V procedure never ran. **This record does not waive
  completing Phase 3** — its in-guest remainder stays outstanding, so
  release notes must not imply more verification than happened.
- **Phases 2 and 4: NOT RUN — waived by this record, for the 0.2.0
  release only.**

## What this decision overrides — and what it does not

- Both gate-run reports close with the standing caution "do NOT cut a
  0.x.y release touching `crates/numa-shim/**` on the strength of this
  run alone", and the ninth independent audit's F8 (P1) finding (open
  item 100 in `docs/correctness-open-items/TRACKED_publish_readiness.md`)
  was filed against exactly this gap. For Phases 2 and 4 only, the owner
  has explicitly overridden that caution for 0.2.0. This is a knowing,
  recorded risk acceptance — not a silent skip.
- It does NOT amend `docs/NUMA_RELEASE_GATE.md`'s policy for any future
  release: any future release touching `crates/numa-shim/**` still owes
  Phases 1-4 whenever the infrastructure can be obtained, and the gate
  doc's "What they don't validate" list (real multi-socket page
  placement, real cross-socket latency, BIOS/firmware topology quirks)
  stands unchallenged.
- It does NOT waive item 102's other owner-gated conditions: C1 (push +
  confirm CI green on the landing SHA) and the E1 final Phase-1 re-run
  remain owed, in that review's §7 order.

## Downstream consequence (mirrored in `crates/numa-shim/CHANGELOG.md`)

This release's real-multi-socket and real-Linux-kernel NUMA binding
behavior has NOT been independently verified beyond mock-dispatch and
single-node host-level testing. Users on genuine NUMA hardware should
independently validate node-binding correctness before relying on it in
production.
