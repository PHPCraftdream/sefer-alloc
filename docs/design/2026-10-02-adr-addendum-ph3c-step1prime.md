# ADR addendum — Ph3c: шаг 1′ (пересдача шага 1 после дефекта карвинга B3)

Дата: 2026-10-04. Решение консультанта-владельца (`@om`) по запросу оркестратора.
Основание: `docs/design/2026-10-02-adr-addendum-ph3c-escalation.md` (§4 пределы и протокол, §5 конечная
точка (б)), приёмка спайка B3 (`worktrees/ph3c-b3s`, коммит `093c9d23`, tree `f0504322`).
Файл фиксирует правила ДО правки кода и ДО замеров; пороги не пересматриваются после просмотра чисел.

## 1. Факт и классификация

Приёмка спайка нашла, что carve спайка (`b3_carve_start`, один общий bump на сегмент + привязка
4 KiB под-листа к классу первого карвинга + «карвинг другого класса не может стартовать в чужом
под-листе → прыжок к следующему под-листу») при ЧЕРЕДОВАНИИ классов сжигает хвост под-листа на каждую
смену класса. Диагностическая проба (AllocCore, 40 000 аллокаций, без free; база = main + патч S):

| размеры | база | спайк B3 |
|---|---|---|
| 16..128 Б по кругу | 1 сегмент | 2 сегмента (×2) |
| те же, сгруппированно | 1 сегмент | 1 сегмент |
| 16..2048 Б по кругу | 6 сегментов | 7 сегментов (+16.7%) |

Дизайн спайка (`docs/perf/PH3C_B3S_SPIKE_DESIGN.md:60`) обещал хвост ≤ 49 × 4 KiB ≈ 4.8% — это верно
только для карвинга по классам; реализованный общий bump этого не обеспечивает. **Классификация:
явный дефект относительно пред-регистрированного дизайна** (а не тюнинг под результат). Измеренный
бинарник не реализовал дизайн, плюс идентичность измеренного дерева ≠ финального (ревью агента) —
вердикт шага 1 аннулируется как INCONCLUSIVE (аналог «один перезапуск» из escalation §3).

## 2. Правило решающих замеров (уточнение)

1. **Решающий замер** — тот, чей исход выбирает между (а) и (б): их ровно два — шаг 0 (PG-3r, PASS)
   и шаг 1. Приёмка полной интеграции — не третий решающий замер; в escalation §5 она «любой гейт
   полной интеграции → (б)» и имеет нулевой бюджет итераций.
2. **Шаг 1′ заменяет шаг 1** (не добавляется): первый замер измерил несоответствующую дизайну сборку без
   неизменяемой идентичности. Правка ровно одна — per-class курсоры по спецификации §3, без подбора
   параметров.
3. Перемеры: шаг 1′ — 1 сборка, 1 замер; повтор допустим только при провале контроля A/A
   (escalation §4.2), один раз. Приёмка интеграции — так же.
4. Критерий останова: любой гейт красный сверх шума A/A → сразу путь (б). Запрещены: вторая правка
   carve, смена размера под-листа, «ещё одна попытка».
5. Пределы не меняются: hot Ir и EstCycles ≤ 1.02; refill/flush EstCycles ≤ 1.10 И Ir ≤ 1.20;
   фрагментация C/B ≤ 1.10; прочие — escalation §4.1.

## 3. Спецификация правки (единственная)

- Per-class курсор карвинга: массив `[u32; SMALL_CLASS_COUNT]` (смещение «следующего свободного
  start» внутри текущего пробега класса) в `AllocCore` (или owner-only метаданных сегмента),
  сбрасывается при смене `small_cur`.
- Блок класса берётся из текущего пробега класса. При исчерпании пробега класс берёт с общего
  bump-фронтира **непрерывный пробег из k под-листов** (k минимально, чтобы потеря
  `k·4096 mod block_size` была мала), все k под-листов привязываются к классу, абсолютное
  выравнивание `off % block_size == 0` сохраняется (start внутри пробега = `align_up(start, block_size)`).
  Классы > 4 KiB — спан из bump фронтира (как сейчас).
- ОБЯЗАТЕЛЬНО (иначе дефект корректности): блок не должен пересекать границу пробега класса —
  иначе соседний под-лист достанется другому классу с фронтира, и блоки перекроются. Поэтому
  граница пробега — граница блока, а потеря хвоста пробега — часть бюджета.
- Арифметика потерь (в бюджет заранее, не открывать на W3): при k = 1 класс 1536 Б теряет 1024 Б из
  4096 (25%), 2560 Б теряет 1536 Б (37.5%), 3072 Б — 1024 Б (25%), 80 Б — 16 Б (0.4%); выбор k для крупных
  классов — по минимуму потери (k ≤ несколько под-листов), без подбора под замер.
- Худший хвост: ≤ 49 неполных пробегов на сегмент (≈ 4.8% при k = 1; для k > 1 пересчитать и записать).
- Подсказка по стоимости: проверка привязки/пробега нужна только при взятии нового пробега
  (≈ раз на 4 KiB), а не на каждый блок как в `b3_carve_start`; per-class курсор должен быть дешевле
  текущего кода (запас EstCycles refill в спайке: +7.6% при пределе +10%).
- Сопутствующие пункты (ревью): убрать мусор в `src/alloc_core/alloc_core/lifecycle.rs`; обосновать
  или снять допадинг `B3Free::FOOTPRINT` до 12 KiB (иначе зафиксировать причину и стоимость);
  идентичность измеряемого дерева — неизменяемый SHA/tree до замера.
- Тесты: proptest «любое чередование классов даёт потерю ≤ одного неполного пробега на класс на сегмент»;
  тест пересечения границы под-листа; Miri paused на 4 клетках (production/alloc-global × SB/TB);
  мутант `write_next` краснеет в `node.rs`; r1_04 — release (Windows-host стек).

## 4. Протокол фрагментации (пред-регистрируется до кода)

- Точка входа: настоящий `#[global_allocator] SeferAlloc`, `--features production`, `Profile::default()`;
  счётчик сегментов на уровне AllocCore — только оракул, не метрика гейта.
- Изоляция: отдельный процесс на плечо, 1 поток; обратное чтение resolved config, `config_conflicts_total`
  delta = 0.
- Нагрузки (запрошенные размеры; живой набор ≈ 64 MiB, чтобы гранулярность 4 MiB не доминировала):
  - W1: классы 16..128 Б по кругу, без free, до 64 MiB живых — худший случай магазинного чередования;
  - W2: все мелкие классы 16..2048 Б по кругу, без free, 64 MiB;
  - W3 (гейт ADR): log-uniform 16..4096 Б (LCG с фиксированным seed), заполнение до 64 MiB, затем
    10 M операций «free случайного живого + alloc случайного размера», замер в конце;
  - W4 (контроль): те же классы сгруппированно; ожидание C/B ≈ 1.00.
- Метрика: `(RSS_end − RSS_empty) / live_requested_bytes` (VmRSS в WSL); commit — вторичный столбец.
  Гейт читается как отношение **C/B** (кандидат к базе main+S) по медиане, ≤ 1.10 на каждой из W1–W3
  (абсолютное «≤ 1.10» недостижимо даже для базы: 1.456).
- Прогоны: 5 чередующихся прогонов на плечо в свежих процессах, медиана; A/A (B против B) < 1%;
  таблицы/CSV строит скрипт с assert (правила CLAUDE.md).
- Оракулы на плечо: число reserve сегментов, число привязанных под-листов, байты потерянных хвостов.
- Предсказание на ТЕКУЩЕМ спайке (до замера): W1 ≈ 2.0 (FAIL), W2 ≈ 1.17 (FAIL), W4 ≈ 1.00. Если W1
  ≤ 1.10 — стенд невалиден как оракул.

## 5. Порядок и критерий ухода в (б)

1. Этот файл — до кода (≈ 0.25 дня).
2. Стенд фрагментации; замер базы против ТЕКУЩЕГО спайка (диагностика, не решающий): фиксирует FAIL
   и валидирует стенд (≈ 1 день).
3. Правка по §3 + пункты ревью + тесты (≈ 1.5–2 дня).
4. Шаг 1′ на неизменяемом SHA: iai по escalation §4.1 (hot, refill/flush, оракул ≥ 95%), A/A, Miri,
   фрагментация §4 (≈ 1–1.5 дня).
5. При PASS — полная интеграция (2–3 недели), затем одна финальная приёмка всех гейтов ADR на итоговом SHA.

В (б) отправляет любой из пунктов (на шаге 1′ или на приёмке): hot Ir или EstCycles > 1.02 на любом из
4 hot-бенчей; refill/flush EstCycles > 1.10 или Ir > 1.20; фрагментация C/B > 1.10 на любой из W1–W3;
активация refill из free-структуры < 95%; Miri красный не в `node.rs` или мутант зелёный; A/A провален
дважды; на приёмке дополнительно — RSS > 1.05 (и > +1 MiB), remote merge > 1.00 Ir/блок, `bench:table`,
larson/mstress сверх пределов.

## 6. Отклонённые альтернативы

- Мягкая привязка (смешанный под-лист): требует поблочного off-body учёта класса — семейство N,
  закрытое по RSS (escalation §1.3), и новую геометрию, запрещённую §5.
- Под-лист 1–2 KiB: новая геометрия, ломает совпадение с 4 KiB `ClassLeaves` и 4 слова `alloc_bitmap`
  на 4 KiB; классы до 2048 Б не помещаются в 1 KiB; патологию чередования лишь уменьшает.
- Карвинг целого под-листа на refill с остатком в бит-маску free: запасной, не основной (остаток теряет
  статус virgin → calloc платит обнуление, искажается оракул ≥ 95%, лишние записи маски на refill).
