# Поэтапный план фундаментального рефакторинга `sefer-alloc/src` (XS / Sol 6 Extra)

Дата плана: 2026-10-01, Europe/Berlin. База синтеза: `abd95856db692f24ed48b82dee99c872092b7076`. Это **план и перечень условий для будущих решений**, не разрешение начать реализацию, не новое полное ревью `src`, не измерение и не release GO. Изменений исходников, тестов, CI и версий в этом исследовании нет; сборки, тесты и бенчмарки не запускались.

## 1. Основание и текущая граница

Полностью сопоставлены три независимых исследования: [причинная история волн](../reviews/2026-10-01-110129-src-wave-root-causes-hs-sol.md), [архитектура границ полномочий](../reviews/2026-10-01-110129-src-foundational-refactoring-hs-sol.md), [система доказательств и цены](../reviews/2026-10-01-110129-src-proof-and-cost-system-hs-sol.md), а также [protected-Box консультация](../reviews/2026-10-01-r11-protected-box-advice-xxs-sol.md), [фактический отказ приёмки](../reviews/2026-10-01-0945-r11-terminal-box-acceptance-sol-codex.md) и [R11 manifest](../perf/round-manifests/SRC_REVIEW_R11_MANIFEST.md). HS-исследования сделаны на `cae3333b`; их ссылки исправлены на текущей базе коммитом `abd95856`. Корпус исторических отчётов изучался **выборочно**: не все ~175 root/companion-крейт ревью прочитаны построчно. Старые номера строк и severity не переносятся на нынешний код без новой проверки.

**Установленные факты.** R11 P3-1/2/3 приняты отдельными изменениями (`4a0c0bc4`, `e8843374`, `fe65746d`). Полный native-набор зафиксирован как 772 passed / 6 ignored; это свидетельство только выбранного native-набора. Реальный `#[global_allocator]` с приостановленным внутри `Box::drop` producer после terminal RMW всё ещё получает exit 1 в строгих Stacked Borrows **и** Tree Borrows: strict owner trim пишет intrusive `next` в user payload через root 4-МиБ reservation (`Node::write_next`, `reclaim_sidecar_record`). Это открытый P1 acceptance blocker в [ACTIVE.md](../correctness-open-items/ACTIVE.md), а не доказанный native crash и не нормативный вердикт о языке Rust. Пока установленный shipping-путь красный, ни одно структурное переименование или обычный зелёный test suite не даёт GO.

**Изолированные кандидаты, не готовая реализация.** W+1 (producer освобождает exact `System` object) и W+2 (owner освобождает его по перенесённому исходному pointer) дали положительные isolated-witness результаты для размеров 1–7, двух раундов, при паузе внутри реального `Box::drop`; root-derived запись 1 и 8 байт осталась отрицательным контролем. Они **не** проходили полный shipping Sefer lifecycle. W+3 — повторная выдача по удержанному exact-layout capability без физического dealloc — не проверен. Отдельные System-объекты здесь лишь исследовательский proof baseline: их CPU, RSS, contention и системные вызовы не измерены; объявлять этот backend постоянным выбором или сохранять красный slab как «быстрый fallback» нельзя.

## 2. Корневая причина и целевой инвариант

Повторялась не одна неисправленная ошибка, а **разрыв между локальными доказательствами**: принадлежность адресу принималась за provenance, terminal bit/credit — за право писать в payload, состояние `FREE` — за гарантию будущего consumer, успех scalar — за успех batch/fallback/teardown, модель/нижний слой/подокно бенча — за свойство установленного `GlobalAlloc`. После корректностных исправлений стали видны иные cost-оси: полный обход фона, исторический high-water, затем все живые Large при Small refill, storage на route и first-touch registry scan. Исторический новый finding не объявляется регрессией старого фикса автоматически.

Проектная цель — сделать три права *раздельными и проверяемыми*:

1. **Route/identity:** числовой адрес — только ключ; counted descriptor, generation/incarnation и pin дают право найти живой route, но не читать тело объекта.
2. **State/ownership:** подготовка → выдача credit → terminal publication → retirement → unlink → release имеют одного ответственного исполнителя и определённые rollback/progress правила. `hint`, active-index и cursor — ускоряющие кандидаты, не authority.
3. **Object access:** конкретный pointer capability, допустимый диапазон, первоначальный `Layout` и lifetime отдельно оправдывают zero/copy/reuse/physical free. Ни route pin, ни `credit == 0`, ни сохранённый reservation root этого не доказывают.

Типизированные transitions (A) и переносимый exclusive domain lease (B) могут сократить число независимых реализаций, но **не устраняют** сами по себе protected-`Box` P1. Физическая граница allocation/provenance (C) должна быть выбрана по реальным gates, а не по красивому типу. Это направленное предложение, не доказательство достаточности комбинации A+B+C для всех будущих дефектов.

## 3. Правило для каждой фазы

Одна фаза — один изолированный worktree и ответственный HS; два HS не редактируют одни и те же файлы одновременно. Координатор до объединения лично читает весь diff, проверяет реальные positive и mutation-negative witnesses, обрабатывает падения в том же цикле и делает **отдельный локальный коммит** только принятой фазы. Общие `Cargo.toml`, `src/lib.rs`, CI, README, инвентарь unsafe, реестр обязательств и манифест — зона интегратора после source-фаз, не скрытая зона конкурирующих HS. Ни одна стадия плана не разрешает push, изменение версий или неограниченную искусственную нагрузку. Если обязательный gate красный, фазу не сливать; сохранить receipt и вернуться к ближайшему ещё не решённому дизайну. Откат к нынешнему красному shipping `Box`-пути не считается production GO.

Каждое обещание должно иметь независимый оракул: правильный *entry point*, точные features/ОС/toolchain/profile и source/binary identity, фактический activation marker, ожидаемый postcondition и отрицательную мутацию, которая ломает именно его. `BUILD_ONLY`, `CFG_EXCLUDED`, `NOT_RUN`, `PASS`, `FAIL`, `INCONCLUSIVE` и `CONDITIONAL` не сворачиваются в один «зелёный». Модели Loom не доказывают pointer provenance; Miri проверяет конкретный исполняемый путь в экспериментальной модели; native проверяет конкретную ОС/ветку; бенчмарк подтверждает только измеренный режим.

## 5. Решения владельца и явные стоп-линии

1. Требуется ли безусловный autonomous ownerless reclaim, если никто больше не вызывает allocator и `start_maintenance()` не был успешен? Если да, кто гарантирует worker/progress при startup failure; если нет — какая **явно условная** гарантия публикуется? Это нельзя вывести из переносимого lease.
2. Обязателен ли owner-side physical free во время paused producer frame или допустим producer-side exact free до terminal event? Положительный isolated W+2 не даёт автоматически shipping-owner-free; при его красном shipping gate нельзя выбирать его по предпочтению.
3. Какие конкретные performance/RSS пределы определяют пригодность backend, на каком одинаковом workload/profile/OS и с какой метрикой? Числа не подставлены этим планом; их задаёт владелец **до** A/B verdict. Per-object `System` — отправная точка доказательства, не заявленное ускорение.
4. Какие feature/OS комбинации и какие гарантии `Box`/`GlobalAlloc`, fallible OOM, worker/fallback обязательны к публикации? Ломать совместимость допустимо лишь после отдельного решения о новой публичной поверхности; приватные tickets/lease не должны становиться `pub unsafe` только ради удобства миграции.

До этих решений и успешного физического gate нельзя выбирать production backend. До реального installed-Box SB/TB, error-path/OS matrix и измерения нельзя заявлять release GO. Этот план уменьшает будущие места разрыва доказательства; не обещает искоренить все новые находки и не заменяет независимые ревью следующих волн.
