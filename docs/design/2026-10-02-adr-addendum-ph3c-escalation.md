# ADR addendum — Ph3c: эскалация после провала B3, шаг 0 (PG-3r), путь (а) и конечная точка (б)

Дата: 2026-10-02. Решение владельца ADR (`@ox`) по эскалации §6
`docs/design/2026-10-02-adr-addendum-ph3c-decisions.md` после провала фильтра
3c-1b (`docs/perf/PH3C_B3_PROTO_IAI.md`, коммит `cbceb311`). Файл фиксирует
правила, пределы и конечную точку ДО первой строки кода патча S и до интегрированного
спайка B3. Пороги ниже не пересматриваются после просмотра чисел.

## 1. Что видно из уже закоммиченных данных (новых прогонов нет)

### 1.1. Регрессия PG-3 — артефакт скана, а не цена off-body учёта

- `drain_segment_sidecar` (`src/alloc_core/small/alloc_core_small/find_segment.rs`) и
  курсор в `src/alloc_core/alloc_core/sidecar_drain.rs` сканируют pending-bitmap от
  слова 0 до `high_water` (`src/alloc_core/segment/remote_bitmap/sidecar_bitmap.rs`):
  по одному `swap(0, AcqRel)` на каждое слово, включая пустые; одно слово покрывает
  1 KiB payload.
- Спайк положил 1 MiB NextTable в метаданные перед payload. `high_water` вырос на
  1 MiB, и каждый drain стал проходить на 1024 слова больше: ≈ 1024 × 12 Ir = 12 288 Ir
  на проход.
- Проверка по `docs/perf/PG3_OFFBODY_SPIKE_IAI_summary.csv` (перепроверено
  оркестратором 2026-10-02 по всем 85 строкам): ненулевая ΔIr (ir_spike − ir_base) на
  односегментных бенчах группируется у целых кратных 12 288 — k ≈ 1, 2, 4, 16, 32, 64, 68
  (k = ΔIr / 12 288 лежит в пределах ≈0.5% от целого; не «ровно» кратна —
  остаток мал и объясняется прочими незначительными различиями). 48 из 85 строк
  ненулевые.
- Остаток после вычета скана: hot от −0.003% до +0.017%, cold/recycle от −1.10% до
  −0.38% — спайк по Ir даже чуть дешевле базы. D1 read-miss +128 в обоих
  атрибутированных бенчах = 1024 × 8 B / 64 B.
- Вывод: интегрированная цена off-body операции по Ir ≈ 0. §1.3, §1.5 дизайна
  `docs/design/2026-10-02-ph3c-offbody-geometry-design.md` и раздел «Механизм» отчёта
  `docs/perf/PG3_OFFBODY_SPIKE_IAI.md` подлежат поправке задним числом (append-only).

### 1.2. B3: вердикт фильтра остаётся, объяснение механизма — другое

- Построение модели L3 стоит +23 225 Ir (sparse_1: 57 542 против 34 317) и попало в
  замеряемое тело. Если вычесть у каждого плеча собственное построение, отношения
  только по операциям: churn_one_class ×0.944, refill_cold_16 ×0.846, churn_mixed
  ×1.025, drain_dense ×1.189 (у N — ×1.190), drain_sparse_64 ×2.12.
- Dense и sparse всё равно выше порогов (1.10 / 1.25), поэтому §4 предыдущего аддендума
  не пересматривается и новых микро-итераций нет. Вердикт B3 не меняется.
- У N на dense такое же ×1.19, а интегрированно N по остаткам не дороже базы: ось dense
  drain эмуляции не предсказывает интеграцию (эмуляция — только фильтр).

### 1.3. Семейство N (NextTable, в т.ч. «локализованный») закрыто по RSS и commit, а не по Ir

- 4 B на каждый 16-байтовый слот = 25% нарезанного payload; таблица лежит в метаданных,
  коммитящихся сразу (`reserve.rs:180-207`), то есть +1 MiB commit на сегмент.
  Даже u16 даёт ≥ 12.5%. Меньше только при регионах одного класса, а это кандидат A,
  отклонённый в §2 дизайна по той же арифметике.
- N далее — только зонд, не кандидат. У пути (а) один кандидат: B3 в интеграции.

## 2. Решение

Сначала дешёвый шаг 0 (PG-3r), затем путь (а) с B3; путь (б) записан как конечная
точка. Переход к (б) сейчас преждевременен: по §6 предыдущего аддендума (б)
допустим, только если у (а) нет кандидата, а кандидат есть.

## 3. Шаг 0 — PG-3r (0.5–1 день)

- Что: worktree от `7c0c796b` (база) и от `8a028616` (спайк). На обеих сторонах
  патч S: скан начинается с первого слова payload (`payload_start / (MIN_BLOCK × 64)`
  с округлением вниз) — и в `drain_segment_sidecar`, и во всех сбросах курсора в
  `sidecar_drain.rs`.
- Идентичность: временные measurement-коммиты + sha256 патча S (до замера).
- Замер: WSL, `perf_gate_iai`, 85 бенчей, features `production bench-internals
  internals`, приватный `CARGO_TARGET_DIR` на каждый worktree, доказательство свежести
  как в 3c-1b (`.d`-манифест, одна строка `Compiling sefer-alloc`).
- Смоук на обеих сторонах: `r6_terminal_owner_drain`, `r8_owner_sidecar_miss`,
  `r8_terminal_global`.
- Предсказание (записано до замера): ΔIr ≤ +0.5% на 4 hot-бенчах ADR и на
  `cold_alloc_free_256x{16,64}b`, `recycle_alloc_free_256x{16,64}b`.
- Правило решения (только Ir):
  - к шагу 1, если hot ≤ 1.02, указанные 4 refill-бенча ≤ 1.10 (исходные пределы ADR),
    mimalloc-плечо ΔIr = 0.000% и свежесть доказана;
  - иначе сразу (б);
  - гейты прошли, предсказание нет → атрибуция частичная, шаг 1 всё равно делается;
  - INCONCLUSIVE → один перезапуск, потом как FAIL.
- EstCycles и `multiseg_cold_256k` — только в отчёт (разброс по 1 MiB таблице есть
  только у N).

## 4. Шаг 1 — путь (а): интегрированный спайк B3 (6–8 дней + 1–2 дня замер и Miri)

### 4.1. Цена корректности — фиксируется до первого кода, привязана к SHA этого аддендума

| ось | предел |
|---|---|
| refill/flush: `cold_alloc_free_256x{16,64}b`, `recycle_alloc_free_256x{16,64}b`, `multiseg_cold_256k` | EstCycles ≤ 1.10 И Ir ≤ 1.20 |

Удвоение исходного запаса (5% и 10%). Обоснование — ценность, а не данные: закрываются
P1 и подмена freelist через UAF, но reissue при живом кадре остаётся красным
(MODEL-LIMIT), поэтому платим умеренно. Без изменений: hot Ir и EstCycles ≤ 1.02; RSS;
фрагментация; remote merge; zeroed/realloc; `bench:table`; larson/mstress; накопительно
к B0 = `7d80d7e1` те же пределы.

### 4.2. Протокол

§5 предыдущего аддендума дословно, плюс: база — `main` на SHA создания worktree, патч S
на обеих сторонах; ≥ 95% refill из free-структуры; Miri paused зелёный на `production`
и `alloc-global` (SB strict-provenance и TB); мутант с возвращённым `write_next`
краснеет в `node.rs`; клетки C4 краснеют только на reissue/release.

Правило одной сборки: до замера чинятся только явные дефекты; после замера никакого
тюнинга; перемер допустим один раз и только если провалился контроль A/A.

### 4.3. Подсказки для дизайна

Существующий `alloc_bitmap` уже даёт ровно 4 слова на 4 KiB, переиндексация не нужна;
класс под-листа совпадает с 4 KiB `ClassLeaves` у route — использовать его, не заводить
параллельный заголовок. PASS спайка даёт полную интеграцию (2–3 недели) с теми же
пределами.

## 5. Конечная точка — путь (б)

Когда: провал шага 0, провал спайка или любого гейта полной интеграции. Решающих
замеров максимум два; новых геометрий в рамках этого ADR не будет. Переоткрытие только
по внешней причине: нормативное решение Rust о протекторах `Box`; нативное
воспроизведение; новое решение владельца с новой ценой.

Что записывается в (б):

- ADR: решение 1′ — production = slab с интрузивными связями free-list, off-body учёт
  отменён по результатам замеров; G1 переписать без слов «без доступа к телу»; P1
  переименовать в **P1-box** (не путать с гейтом прогресса P1), статус — принятый
  известный дефект, не MODEL-LIMIT; стоп-линии «не возвращать красный slab» (ADR) и
  «откат ≠ GO» (план §3) заменить на: «release GO не заявляет SB/TB-чистоту
  установленного `Box` при паузе producer'а; формулировка "Miri-clean" без этой
  оговорки запрещена».
- README и rustdoc `SeferAlloc`: «Known defect (P1-box): free-list links live inside
  freed small blocks. If a block is freed through a by-value `Box` whose receiving
  frame is still executing when the allocator links it into a free list (owner reclaim
  of a cross-thread free, or a later magazine flush), Miri's Stacked Borrows and Tree
  Borrows report undefined behaviour (protector violation). No native crash or
  miscompilation is known; the aliasing models are experimental, and this is not a
  guarantee that none exists. Re-issuing those bytes while the freeing frame is live is
  a separate model limit shared by any allocator on a shared reservation.» Для
  `alloc-global` без `fastbin` — добавить: дефект срабатывает уже внутри own-thread
  `dealloc` (PG-1, набор B).
- Paused-witness и CI: KNOWN-DEFECT с проверкой причины (не `ignore`, не MODEL-LIMIT).
  Вместо двух шагов CI — четыре: {`production`, `alloc-global`} × {SB strict, TB}.
  Каждый шаг проверяет exit ≠ 0, сообщение протектора, первый кадр — `node.rs`
  (`Node::write_next`), вызывающий — `reclaim_sidecar_record`, `flush_run` или
  `dealloc_small`; зелёный результат роняет шаг («снять обёртку»), красный в другом
  месте тоже роняет («новый дефект»).
- Реестр дефектов: карточка P1-box в
  `docs/correctness-open-items/TRACKED_correctness_residuals.md` со статусом
  «OPEN — ACCEPTED KNOWN DEFECT» и тремя триггерами переоткрытия; item 162 остаётся про
  ownerless reclaim.
- Фазы: Ph3c — CANCELLED (не BLOCKED); Ph4a — начинать сразу, база B_4a = SHA `main`
  при создании worktree, Loom-модели на текущем API drain; Ph4b/Ph4c без изменений;
  Ph5a — CANCELLED; Ph5b/Ph5c — упрочнение slab (C2/C3/C5/C6/C7 обязаны быть PASS,
  C1 = KNOWN-DEFECT, C4 = MODEL-LIMIT); Ph6 — без A/B смены backend; Ph7 — статус
  KNOWN-DEFECT с сигнатурой причины. Трудоёмкость (б): 1–1.5 дня.
