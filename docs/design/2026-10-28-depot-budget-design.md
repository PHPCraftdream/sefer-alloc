# G1-K7 — бюджетный склад магазинов как настройка аллокатора (дизайн)

Статус: проект на ревью (@oh, ревьюер rush). Основание: P0
(`docs/perf/G1_IDEAS.md` §9 в PR #124 — потолок «перенос = 0» на bulk16k,
отношение времени 0.5705 за вычетом null), консультация C5 (§10, ответы
`g1_pmu/c5/`), решения владельца:

- бюджет удержания — настройка, которую пользователь задаёт при создании
  аллокатора; по умолчанию 1 МиБ сверх пола K5;
- в README подробно описана каждая настройка: на что влияет, замеры;
- приём: любой выигрыш против mimalloc на главном судье без проигрышей на
  других ядрах и без потерь в безопасности.

## 1. Что меняется

Склад K5 (`src/registry/heap_core/state/depot.rs`) остаётся полом: те же
`DEPOT_K` по классам 0..17 (16..1024 Б), те же массивы в слоте реестра,
241 408 Б блоков на поток.

Сверх пола — **переполнение склада**: полный магазин любого класса склада,
который не помещается в пол, паркуется в ленивое хранилище, пока сумма байтов
блоков в переполнении не превышает бюджет E. Если E исчерпан или хранилище
недоступно — прежний путь (flush половины магазина в список сегмента).

Алгоритм парковки и перезагрузки тот же, что у пола и у P0: копирование 16
указателей; блоки остаются в состоянии MAG, кредиты сегмента не снимаются.

## 2. Настройка

`LargeCacheConfig::depot_budget_bytes(bytes)` (тот же конфиг, что уже
передаётся в `SeferAlloc::with_config`; рядом с `pool(...)` для малого пула):

- `None` (по умолчанию) → 1 МиБ;
- `Some(0)` → переполнения нет, поведение K5;
- `Some(n)` → бюджет n байт, округлённый вниз до байтов целого магазина
  наименьшего класса (16 × 16 = 256 Б), с верхним пределом 64 МиБ
  (ограничение размера резервирования).

Без `alloc-decommit` (конфига нет) действует значение по умолчанию.
Разрешённое значение хранится в `HeapCore` и участвует в
`live_config_matches` (правило R26-4: повторный claim слота с другим
бюджетом — конфликт конфигурации, счётчик `config_conflicts_total`).
Чтение назад: `HeapCore::dbg_depot_budget()` (чистый наблюдатель,
`bench-internals`).

`Profile` получает ту же ось позже, если замеры покажут, что пресетам нужны
разные значения; в этой задаче — только явная настройка.

## 3. Хранилище переполнения

Новый файл `src/registry/heap_core/state/depot_overflow.rs`, тип
`DepotOverflow` (только владелец, как `Depot`):

- резервирование виртуальной памяти при первой парковке в переполнение через
  `aligned_vmem::reserve_aligned_lazy` (уже используется в `alloc-core`,
  без вызова `GlobalAlloc`, без рекурсии); размер — под худший класс
  (16 Б): `R = E / 256` записей по 128 Б плюс массив связей `u32` на запись;
  для E = 1 МиБ это 4096 × 128 Б + 16 КиБ ≈ 528 КиБ виртуальной памяти;
- коммит постранично по водяной отметке (`commit_range`), только когда
  нужна новая запись; на Unix страницы тронуты лениво ОС;
- записи раздаются из списка свободных записей, затем по водяной отметке;
  на класс — стек записей (голова `u32` в `DepotOverflow`, число записей —
  в `PerClass::parked` вместе с полом: `parked` расширяется до `u16`,
  смещение 2, как в P0);
- учёт: `overflow_bytes` (байты блоков в переполнении) ≤ E;
- отказ резервирования или коммита → парковка не выполняется (обычный
  flush), счётчик отказов; резервирование не повторяется до trim.

Указатель на `DepotOverflow` живёт в `Depot` (слот реестра), сама структура —
в начале резервирования. Слот реестра не растёт на 128 КиБ, как в P0.

## 4. Затухание и возврат памяти

- **Эпоха** — `G = 256` холодных событий кучи (парковка, перезагрузка,
  пополнение магазина из сегмента). Часы не читаются.
- На класс хранится нижняя отметка числа записей переполнения за эпоху. В
  конце эпохи из переполнения класса сбрасывается половина нижней отметки:
  магазины по одному через существующий `flush_class_internal` (L-4
  защита сохраняется). Класс, который каждый раз опустошает переполнение
  (bulk16k: нижняя отметка 0), не затухает.
- **trim / выход потока / recycle слота**: `flush_all_tcache` опустошает пол
  и переполнение (тот же цикл перезагрузки), после чего закоммиченные
  страницы хранилища возвращаются ОС (`decommit`), резервирование остаётся
  за слотом до следующего использования.
- Поток без единого холодного события держит переполнение до trim или
  выхода (как страницы mimalloc без `mi_collect`). Это записывается в README.

## 5. Инварианты и защиты

- Байт состояния: блоки в переполнении — MAG (как в магазине и в поле
  склада). И1–И5 не меняются; double free отвергается точным сравнением
  LIVE; interior / never-issued / foreign — без изменений.
- Remote free и reclaim из sidecar отвергают MAG, как сейчас.
- Сегмент не освобождается, пока его блоки на складе (кредиты не сняты):
  сброс сегмента идёт только при live = 0.
- Ghost: `depot/owner-only-access` — добавить пути переполнения и
  затухания в `allowed`; новое правило для `DepotOverflow` (только
  владелец, инициализация один раз), фикстура с мутантом; мутант «затухание
  не сбрасывает» в тестах; P12 (`depot/flush-reloads-parked`) — цикл
  teardown покрывает переполнение.
- Kani: `depot_park_respects_capacity` / LIFO-харнессы переписать на пол +
  бюджет (модель переполнения без ОС).

## 6. Тесты (в `tests/`)

- бюджет 0 → поведение K5 (переполнение не используется, счётчики 0);
- бюджет E: парковка до E, следующий магазин — flush; перезагрузка отдаёт
  только освобождённые тестом блоки, без дублей, LIFO;
- затухание: при нижней отметке h сбрасывается h/2 магазинов за эпоху;
  bulk-цикл не затухает;
- trim / выход потока опустошает переполнение, страницы возвращены
  (счётчик decommit хранилища), повторное использование слота работает;
- отказ резервирования (fault injection aligned-vmem) → старый путь;
- конфиг: разрешённое значение читается назад; повторный claim с другим
  бюджетом увеличивает `config_conflicts_total`.

## 7. Замеры (предрегистрация отдельным файлом до прогонов)

Скорость, J1′ v2 (20 процессов × 2000 блоков):

1. Абляция против K5 (null-копия), все 11 ядер + два новых ядра судьи:
   `bulk64k` (когорта 4 МиБ > E) и `bulk16k_256` (16 384 блока по 256 Б).
   Пороги (по C5, @oh): bulk16k эффект ≤ −42 (75 % P0) и верх CI ≤ −35;
   контроли pair16/pair64/pair_rt верх CI ≤ +0.5, остальные ≤ +1.0;
   bulk64k ≤ +1.0; bulk16k_256 ≤ −20.
2. Главный судья против mimalloc: ни одно допущенное ядро не хуже K5 вне
   его A/A-полосы; bulk16k t_mi/t_sefer выше K5 (приём владельца: любой
   выигрыш без проигрышей).
3. Оракул (счётчики `bench-internals`): парковки в переполнение,
   перезагрузки, отказы по бюджету, сбросы затухания, вызовы flush.

RSS — отдельный судья (подпроцесс на плечо, K5 / K7 / mimalloc; Windows —
PrivateUsage и WorkingSet, Linux — RSS): пик bulk16k; удержание после
всплеска N ∈ {16k, 64k, 1M} × 64 Б → после 10³ / 10⁵ посторонних операций →
после выхода потока; T = 1 / 4 / 16; коммит чанка реестра без изменений.
Свип E ∈ {0, 512 КиБ, 1 МиБ, 2 МиБ} — для README.
