## 1. Findings

### F1 — **P2** — the loser-wait contract is stated as a positive bound ("exactly as long as the winner's `init` closure takes") that is **false** for the two asynchronous re-entry vectors the `#[global_allocator]` niche makes concrete: `fork()` and a signal handler that allocates. Neither is mentioned anywhere in the crate

**Where:** `crates/racy-ptr-cell/src/lib.rs:57-69` ("The spin-wait" section,
especially `:61-63`), `:71-97` (the "Using this inside a
`#[global_allocator]`" caller-obligation list added by `ccee5cd`), `:420-431`
(`get_or_try_init`'s own reentrancy paragraph),
`crates/racy-ptr-cell/README.md:50-51`. Mechanically verified absent:
`grep -rn -i "fork|signal handler|async-signal|sigaction|pthread_atfork"
crates/racy-ptr-cell/` returns **zero matches**.

The section under audit lists four caller obligations and one caller-bug
class. Every one of them is a rule about what the caller's `init` closure
*does*. The two vectors below need no misbehaving `init` at all — they break
the cell from **outside** the closure, and the section's framing ("hard rules
that are the CALLER's to keep") does not reach them.

**Failure scenario A — `fork()` in a multithreaded process.** Thread B is
inside `GlobalAlloc::alloc` → `RacyPtrCell::get_or_try_init` → has won the
CAS at `src/lib.rs:475-492` → is running `init` (say, one `mmap`). Thread A
calls `fork()`. The child gets thread A only, plus a memory image in which
the cell holds `SENTINEL_INITIALIZING`. Thread A's first allocation in the
child enters `get_or_try_init`, fails the CAS, and enters the loser spin at
`:564-585`, where it observes `a == SENTINEL_INITIALIZING` **forever**, at
100 % CPU, because the only thread that could publish or roll back does not
exist in the child. `get()` (`:384-393`) returns `None` forever too, so a
caller that treats `None` as "not ready yet, retry" loops just as long.

This is the classic malloc-after-fork deadlock. What makes it worth a
finding rather than a shrug is three things:

1. **The doc does not merely omit it — it states the opposite.** `:61-63`
   says "a loser waits for **exactly as long as** the winner's `init`
   closure takes". In the forked child there *is* no winner and no running
   `init`; the wait is unbounded and the stated bound is false, not loose.
   The three documentation-honesty defects the previous three reviews found
   were all of exactly this shape: a true-sounding positive claim whose
   counterexample was reachable.
2. **The crate offers no recovery API, and the one candidate is
   structurally unable to help.** `dbg_rollback_reenterable`'s entry CAS
   (`:680-687`) requires the cell to be `null`; on a sentinel-holding cell
   it returns `None` and touches nothing — by design, and correctly so for
   its documented purpose. So even in the child, where a force-reset would
   be single-threaded and provably safe, there is no way to perform one.
   glibc mitigates the same hazard with `pthread_atfork` handlers that
   reinitialise the arena locks; this cell has no equivalent and no
   documented substitute.
3. **The in-repo consumer is exactly this shape.**
   `src/registry/bootstrap.rs:579` puts 64 `RacyPtrCell<RegistryChunk>`
   cells directly on the bootstrap path of the root crate's
   `#[global_allocator]`.

**Failure scenario B — an allocating signal handler.** Same shape, one
thread, no `fork()`. Thread B holds the sentinel and is inside `init`. A
signal is delivered to B. The handler allocates (directly, or transitively —
any `format!`, any `Vec`, any panic-hook path). The global allocator reaches
the same cell, the CAS fails, and the handler spins at `:564-585` on a
sentinel owned by the very thread it interrupted and suspended. Single-thread
self-deadlock at 100 % CPU, unrecoverable. The existing rule at `:420-423`
("must not itself call back into `get_or_try_init` on the SAME cell") does
not cover this: the caller wrote no re-entrant `init`; the re-entry is
asynchronous and not visible in any call graph. Note this is *not* the
transitive two-cell lock-order hazard `d4f16e8` documented at `:425-431`
either — that one is also lexically visible in the caller's code.

**Suggested fix (documentation only, no algorithm change).**

1. Correct `:61-63` / `README.md:50-51`: the loser waits for as long as the
   winner's `init` takes **provided a winner is running at all**; a cell
   whose `INITIALIZING` owner has ceased to exist is waited on forever.
2. Add one bullet to the `#[global_allocator]` section, e.g.: "**The cell is
   neither fork-safe nor async-signal-safe.** `INITIALIZING` is owned by a
   specific thread. A `fork()` that copies a cell mid-`init`, or a signal
   handler that allocates while this thread holds the sentinel, yields a cell
   whose owner cannot run — every subsequent caller spins forever, and there
   is no reset. In a forking process, either publish every cell before the
   first `fork()`, or `fork()` only from a thread you know holds no cell and
   treat `exec()` in the child as mandatory. Do not allocate in a signal
   handler."
3. Optional, and a genuinely new API surface rather than a doc fix, so it is
   a separate decision: an `unsafe fn reset_after_fork(&self)` (contract:
   caller guarantees single-threaded exclusive access, e.g. a
   `pthread_atfork` child handler) would make the fork case recoverable
   instead of merely documented. If it is ever wanted, adding it before
   0.1.0 is cheaper than adding it after.

### F2 — **P3** — the same latency sentence understates the wait even with a perfectly-behaved `init`: under OOM a loser can be made to wait through an unbounded *number* of successive inits, not one

**Where:** `crates/racy-ptr-cell/src/lib.rs:60-64`,
`crates/racy-ptr-cell/README.md:50-51`.

**Failure scenario.** Memory pressure — i.e. precisely the regime the crate's
headline differentiator from `OnceLock` exists to serve. Winner 1 wins the
CAS, `init` returns `None`, the sentinel rolls back (`:550-551`). Loser L
observes `null` at `:572-584`, `break`s, and re-races via the outer `loop`
at `:464`/`:586`. It loses again to winner 2, spins through winner 2's
`init`, which also OOMs, and so on. L's total wait is `Σ` over as many
rounds as other threads keep winning and failing; the process terminates for
L only when L itself wins a round. Nothing bounds the number of rounds, and
the workload most likely to produce many of them (many threads racing one
cell while the OS is out of memory) is exactly the one the OOM-rollback
design targets.

The text at `:61-63` describes a single round ("exactly as long as the
winner's `init` closure takes"). Combined with F1, this is the second way
that one sentence is stronger than what the code guarantees.

**Suggested fix.** One clause: "… as long as the winner's `init` takes —
and, if that winner reports OOM, again for each successive winner until one
succeeds or this thread wins the race itself."

### F4 — **P3** — the claim-CAS's `Acquire` success ordering is load-bearing for a case its own "open perf question" note does not consider, and **no test would catch downgrading it to `Relaxed`**

**Where:** `crates/racy-ptr-cell/src/lib.rs:475-492`, in particular the
comment at `:485-488` added by `eab098a`.

**Measured in this audit:** patching only `Ordering::Acquire` →
`Ordering::Relaxed` on the CAS **success** ordering leaves **all 7 loom
tests green** (and all 7 native tests, which never touch the multi-attempt
path concurrently).

The comment is now correct about what the `Acquire` *does* — "synchronises-
with the `Release` rollback store … of a PREVIOUS winner that abandoned the
cell" — and correctly retracts the pre-`eab098a` claim that it paired with a
future publish. But it then poses the open question with a premise attached:
"(a rollback leaves no payload state to acquire)". That premise is not
generally true, and the crate's own contract is what makes it untrue.

**Failure scenario.** A previous winner's `init` is arbitrary caller code
that ran to some length before returning `None` or unwinding. It may
legitimately have left observable side effects that the *next* winner's
`init` reads — an arena bump pointer or reservation-bookkeeping word the
failed attempt advanced, a partially-populated caller-side table it intends
the retry to reuse, a `bool` recording "the OS refused a 2 MiB page, ask for
4 KiB next time". None of these are exotic in a bootstrap path; the whole
point of OOM-rollback-and-retry is that the retry is a *continuation*, not a
fresh start. Under today's `Acquire` those non-atomic writes are ordered
against the rollback's `Release` store (`:551`, or the guard's `Drop` at
`:299`) and the next winner sees them. Under a `Relaxed` claim CAS they are
not, and the retry can read torn or stale bytes — a data race introduced
into the *caller's* code by an ordering change in this crate, with no
diagnostic.

Neither suite would notice: every `init` closure in `tests/cell_unit.rs` and
`tests/loom_racy_ptr_cell.rs` is side-effect-free across attempts (they
either `Box::leak` a fresh payload or return `None`), which is why the
mutation above is green.

**Suggested fix.** Keep `Acquire`, and replace the parenthetical premise
with the reason it is not free to relax: a failed attempt's `init` may leave
caller-visible state that the next attempt's `init` reads, and the rollback
`Release` / claim `Acquire` pair is what orders it. If the perf question is
ever genuinely pursued (it is real — `casa` vs `cas` on AArch64; free on
x86-64, where the CAS is a full barrier regardless), it must first be given
an oracle: a loom model whose failed `init` writes a non-atomic word that
the successful `init` reads. Measuring against the current suite would be
measuring against a suite that cannot detect the regression the change
enables — the same "invalid oracle" shape this repo's CLAUDE.md
path-activation rule exists to prevent.

### F5 — **P3** — `RollbackGuard`'s doc explains away its own known coverage gap with a loom-specific reason, but the missing test does not need loom

**Where:** `crates/racy-ptr-cell/src/lib.rs:251-266`.

The doc is admirably honest about the gap: `panicking_init_rolls_back_and_
subsequent_call_succeeds` proves "a SUBSEQUENT call on an already-quiescent
cell succeeds", not "a loser thread that was ALREADY spinning inside
`get_or_try_init` at the moment the winner's `init` unwinds is released" —
and the second is the property the guard's own first paragraph
(`:238-245`) says the guard exists for. It then gives the reason the gap is
open: "Not closed by a loom test here: loom's deterministic scheduling model
and `std::panic::catch_unwind` do not compose cleanly … and the ROI did not
justify building a bespoke harness for it in this round."

**The stated reason does not match the missing test.** The property is a
plain two-thread liveness property; nothing about it needs an interleaving
explorer. It needs: thread W wins and panics inside `init` *after* thread L
is known to be spinning, and an assertion that L returns within a bounded
time. The file already contains every ingredient — `std::thread::spawn`, an
`mpsc` channel and the `recv_timeout(Duration::from_secs(5))` bound at
`tests/cell_unit.rs:110-114`, and `catch_unwind` at `:73-77` — used for the
*weaker* property. Roughly 25 lines with a `std::sync::Barrier`, no loom, no
bespoke harness. A timeout-based liveness assertion is also failure-safe in
the right direction: if the ordering is not achieved on some run, the test
passes spuriously rather than hanging the suite.

**Why it is worth fixing rather than leaving documented.** The doc itself
names the future change that would silently reintroduce the bug — "a future
change that made the rollback conditional (e.g. skipping it when a loser is
observed waiting) could pass the existing test while reintroducing the
spin". A gap with a named reintroduction path and a 25-line closure should
be closed, not annotated. At minimum, replace the stated reason with the
real one, so a future maintainer does not read "loom can't do it" and
conclude the property is untestable.

### F6 — **P3** — a loser that has *already read the sentinel* still issues a guaranteed-failing `compare_exchange`, stealing the cache line from the very winner it is waiting for

**Where:** `crates/racy-ptr-cell/src/lib.rs:464-492`.

The fast path loads `p` at `:466`. If `!is_ready(p)`, `p` is either `null`
(UNINIT) or the sentinel (INITIALIZING) — those are the only two other
states. When it is the sentinel, the `compare_exchange` at `:475-492`
**cannot succeed**: it is a strong CAS whose expected value is `null` and
whose observed value is `1`. It is nevertheless a read-modify-write — a
`lock cmpxchg` on x86-64, an exclusive load/store pair on AArch64.

The cost is not the ~20 cycles of the instruction. It is that the RMW takes
the cache line into Exclusive/Modified state **on the loser's core**, and
that line must then be stolen back before the winner can perform its
`Release` publish at `:533`. With N losers arriving during one `init`, that
is N extra coherence transfers on exactly the line the winner is about to
write — the loser population actively slows down the thread it is waiting
for. The same wasted RMW is paid again on every re-race after an OOM
rollback.

**Suggested fix** (behaviour-identical, no ordering change, ~3 lines):
after the fast-path load, if `p.addr() == SENTINEL_INITIALIZING`, jump
straight into the spin loop instead of attempting the CAS. Both existing
counterfactuals still apply unchanged. This composes with — and is
independent of — cycle-1 F6's two still-open suggestions (relaxed spin with
one `Acquire` on exit; `#[cold] #[inline(never)]` outlining of the slow
path). On the relaxed-spin half I can now add a receipt the cycle-1 report
did not have: the loom suite **does** police it — mutating the spin load to
`Relaxed` without an acquire on exit makes `real_exactly_once_two_threads`
and `real_exactly_once_three_threads` fail with loom's causality violation

### F7 — **P3** — the `OnceLock` comparison, corrected by `4ea840b`, is now wrong in the opposite direction and internally self-contradictory

**Where:** `crates/racy-ptr-cell/src/lib.rs:49-55`.

> "`OnceLock::get_or_try_init` does NOT poison the cell on `Err`, and a
> failed or panicking initialiser leaves it uninitialised and retryable
> (`std` drives it through `Once::call_once_force`, which deliberately
> ignores poisoning)."

**Ground truth, read from the active toolchain**
(`…/lib/rustlib/src/rust/library/std/src/sync/once_lock.rs:533-556`,
rustc 1.97.0):

```rust
        // Ignore poisoning from other threads
        // If another thread panics, then we'll be able to run our closure
        self.once.call_once_force(|p| {
            match f() {
                Ok(value) => { unsafe { (&mut *slot.get()).write(value) }; }
                Err(e) => {
                    res = Err(e);
                    // Treat the underlying `Once` as poisoned since we
                    // failed to initialize our value.
                    p.poison();
                }
            }
        });
```

`OnceLock::initialize` **does** poison, explicitly, on the `Err` arm. What
makes the cell retryable is the *other* half — `call_once_force` ignores
poisoning — which the crate's own parenthetical already states. The two
clauses therefore contradict each other: if nothing is poisoned, there is
nothing for `call_once_force` to ignore.

**Why report a nuance this small.** This sentence is not incidental prose.
It exists *as a correction*, it advertises itself as one ("since this
crate's earlier docs got it wrong"), and it is the load-bearing paragraph of
the "Why not `OnceLock`?" section — the crate's entire justification for
existing. A maintainer who checks it against std's source finds a line of
code that says the opposite, in a paragraph whose whole point is being
checkable. That is the third round-trip on this one comparison; getting it
exactly right ends the cycle.

**Suggested fix.** "std *does* poison the underlying `Once` on `Err` — but
the cell stays retryable, because `OnceLock` drives initialisation through
`Once::call_once_force`, which deliberately ignores poisoning. A failed or
panicking initialiser therefore leaves the cell uninitialised and the next
caller runs the initialiser again."

**Also verified while there, and correct as written:** "its
`get_or_try_init` is still unstable (`once_cell_try`)" —
`#[unstable(feature = "once_cell_try", issue = "109737")]`, `once_lock.rs:396`
on 1.97.0. And "Both also PARK the losing threads" is accurate for both
`Once` backends.

**Where:** `crates/racy-ptr-cell/Cargo.toml:30-37`,

`exclude` can be added in 0.1.1 — but the 0.1.0 tarball is immutable, and
0.1.0 is what a first-look user downloads.

## 5. Verdict: **CONDITIONAL GO**

The primitive is publish-ready and I could not break it. Every gate is green
on the current tree — 7/7 native, 7/7 loom against the **real** type with
both non-vacuousness counterfactuals still firing, clippy `-D warnings`
across all targets, `rustdoc -D warnings`, `fmt`, a clean 12-file package
with both licences and zero normal dependencies, MSRV 1.88 verified directly
across lib + tests + bench + dev-dep, and — new this round — **miri clean
under `-Zmiri-strict-provenance`**. Beyond re-running the gates I executed
six source mutations against a private out-of-repo copy of the crate and
established, for the first time in six reviews, that **both** of the README's
headline verification claims genuinely bite on the real type, and that the
probe-clobber regression test is non-vacuous at its stated preemption bound.
**There is no P1 finding: no UB, no soundness hole, no lost happens-before,
no ABA break, no reachable sentinel collision, no double-init.**

What holds it back from an unconditional GO is **one** thing, and it is a
paragraph of prose:

- **F1.** The crate's headline niche is "usable inside a
  `#[global_allocator]`", and it now carries a dedicated section enumerating
  the caller's hard obligations — added specifically because run-2 found my
  own cycle-1 attempt at this section insufficient. That section still omits
  the two ways the cell is broken from *outside* the `init` closure —
  `fork()` in a multithreaded process, and an allocating signal handler —
  each of which leaves an ownerless `INITIALIZING` cell that every
  subsequent caller spins on forever with no reset API. And the module doc
  does not merely omit them: at `:61-63` it makes the positive claim that a
  loser "waits for exactly as long as the winner's `init` closure takes",
  which in both cases is false rather than loose. That is the identical
  shape as the three documentation-honesty defects the previous three
  reviews found, in the one section this crate has now revised twice, for a
  hazard that is textbook for the exact niche being advertised — and the
  root repo's own `#[global_allocator]` puts 64 of these cells on its
  bootstrap path.

**F3 (the missing miri row) is the one I would fix in the same commit but
would not block on**: it is a CI line, it can land any time, and the run it
would automate is green today. The six P3s are all genuine and none needs to
precede the first upload.

**Close F1 — one corrected sentence plus one bullet, no algorithm change,
no API change — and this is a GO.** After that, the things that would have
to *newly* break to move it off GO are, concretely: a change to the publish
`store`'s `Release` or the loser-spin exit `Acquire` (both now proven to
fail the suite if wrong); a change to the claim-CAS success ordering (which
the suite would **not** catch — F4); removal or `debug_assert!`-downgrade of
the sentinel-collision `assert!` at `:524`; making `RollbackGuard`'s
rollback conditional (which the current tests would **not** catch — F5); a
change to `get()`'s readiness predicate (which the current tests would
**not** catch — the confirmed vacuity in §3); or any edit to the
`#[global_allocator]` section that re-widens a guarantee the cell does not
own. Three of those six are places where the suite is currently blind, and
each has a named, cheap closure above.
