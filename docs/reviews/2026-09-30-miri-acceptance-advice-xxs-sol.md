# Miri acceptance of installed SeferAlloc: bounded source-only advice (XXS / Max Sol6)

## Verdict and evidence boundary

**Yes, a `harness = false` integration test with its own `main`, or an explicitly run example/bin, is a legitimate Miri acceptance vehicle for the installed `SeferAlloc`**. Cargo removes libtest in the first form; it does not replace the allocator, the `Box` destructor, or the crate's allocation paths. Prefer a named `[[test]]` target so CI can select it directly. This is a proposal, **not a reported pass** or a guarantee that the resulting interpreter process fits memory. A green *minimal-feature* target must be named for those features, not called a full-`production` Miri pass.

Scope is source inspection at `85ca6e45`, the user-supplied run summaries, and the official [Cargo target/harness contract](https://doc.rust-lang.org/cargo/reference/cargo-targets.html#the-harness-field) and [Miri usage/flag documentation](https://github.com/rust-lang/miri#using-miri). No Rust or production code was changed for this review; no build, Miri, test, benchmark, load, or new diagnostic experiment was run. This is a narrow provenance/acceptance consultation, not a whole-crate soundness proof or an unmeasured performance GO.

The old `std::alloc` aperture recursion was evidenced for the earlier task and has been replaced by paired `System.alloc`/`System.dealloc` (`crates/aligned-vmem/src/os/miri.rs:14-40`, commit `e5a76ee6`). Five focused member Miri and 49 native member cases reportedly passed. The later root task `e1bb4cd7-ac28-4cb1-8e85-38ad996ac711` exited 134 after 820 s with host `memory allocation of 32768 bytes failed`, followed by Node heap OOM, before libtest reported its first test. **Those symptoms do not identify recursion, a Sefer UB, or a specific failed allocation.** The temporary CountingGlobalAllocator+System fixture's Stacked-Borrows failure inside Windows `System.dealloc` during libtest teardown is a separate control result; it neither proves nor clears `SeferAlloc`. Full native production/internals/bench-internals/batch-api and all-target clippy passes are valuable but do not substitute for the missing root Miri result.

## Startup, lifetime, and cost trace

1. `#[global_allocator] static GLOBAL: SeferAlloc = SeferAlloc::new()` is const/lazy (`src/global/sefer_alloc/core.rs:119-165`), but it becomes the allocator for **runtime and libtest allocations before any selected `#[test]` body**. `--exact` selects a test function after harness startup; it does not remove libtest's collection, capture, threading, or teardown. A smaller test body alone cannot solve a pre-test failure.
2. The first serviceable `GlobalAlloc::alloc` goes through `current_heap` → TLS first bind → `HeapRegistry::claim` (`src/global/sefer_alloc/global_alloc.rs:30-47`, `src/global/tls_heap.rs:344-353,400-468`, `src/registry/heap_registry/claim.rs:171-265`). A pre-TLS or torn-down TLS call may instead initialize the process-lifetime fallback heap (`src/global/fallback.rs:1-37`). A foreign dealloc-only thread does **not** bind a heap (`src/global/tls_heap.rs:290-327`); preserve that distinction in the witness.
3. First claim can materialize one chunk of 64 `HeapSlot`s, not all 4096. Its byte size is `align_up(size_of::<RegistryChunk>(), PAGE)`, feature-dependent because slots inline `HeapCore` (`src/registry/bootstrap/chunk.rs:56-106`). `ensure_chunk_slow` uses `aligned_vmem::leak_zeroed_pages`, process-lifetime storage; under Miri that makes a direct `System.alloc` and explicitly writes the entire chunk to zero (`src/registry/bootstrap/ensure.rs:67-120`, `crates/aligned-vmem/src/api/leak_zeroed_pages.rs:31-54`). This is a genuine lower bound, not a suggested production tuning knob.
4. First materialized `HeapCore` reserves a 4 MiB primordial segment (`src/registry/heap_slot.rs:28-40`, `src/alloc_core/platform/os.rs:85-100`, `src/alloc_core/alloc_core/bootstrap.rs`). The `cfg(miri)` aperture selects the Miri backend even on Windows (`crates/aligned-vmem/src/os/mod.rs:3-23`): its lazy reserve allocates the **whole** span eagerly via `System`, and Miri-specific initialization touches bitmap/hash/free-list storage because `System.alloc` promises no zeroing (`crates/aligned-vmem/src/os/miri.rs:80-90`, `src/alloc_core/alloc_core/bootstrap.rs`). A Small/Primordial route also prepares an independent zeroed sidecar before issue (`src/registry/segment_route/directory.rs:42-95`): 4096 `AtomicU64` pending words = 32 KiB, plus 262,144 `AtomicU8` class cells = 256 KiB (`src/alloc_core/segment/remote_bitmap/sidecar_bitmap.rs:17-24`). Miri's interpreter, borrow tracking, and allocation backtraces add host-side cost not equal to those guest byte counts. The observed 32 KiB host failure happens to equal one bitmap field's size; that numerical match is **not** attribution.
5. Materialized registry chunks, fallback heap, and owned heap slots survive for process lifetime/slot recycling; ordinary `Box` payloads and route registrations follow their own issue/free/release lifecycle. Removing libtest can eliminate unrelated interpreted activity, but it cannot erase this real allocator bootstrap or justify changing `SEGMENT`, `CHUNK_SLOTS`, sidecar cardinality, zeroing, or ownership policy merely to turn Miri green.

## Minimal acceptance vehicle

Use one tiny, explicit `[[test]]` with `harness = false`, `required-features = ["alloc-global", "internals", "bench-internals"]`, and `fn main()`; alternatively an explicitly named example/bin driven by `cargo miri run`. Cargo documents that `harness = false` omits libtest and requires `main`, and Miri documents that `cargo miri test/run` accept Cargo's flags. Keep the current `tests/r8_global_box_provenance.rs` or faithfully relocate its two witnesses; do not replace them with a counting wrapper, `System` as the installed allocator, a model allocator, `Box::into_raw`/`from_raw`, or direct `GlobalAlloc::dealloc`.

The acceptance body must retain: `#[global_allocator]` **SeferAlloc**; `Box<u8>` and `Box<Tiny([u8; 7])>` with real narrow `&mut` payload accesses; an actual move to a foreign thread and ordinary `drop(Box)`; the two issue → foreign Drop → owner-trim rounds/reissue check; and the separate actual-Box producer paused **after successful terminal publication while still inside `Box::drop`/`GlobalAlloc::dealloc`**, with owner trim and retirement assertion before resume/join (`tests/r8_global_box_provenance.rs:13-136`). One scenario per process is reasonable if it reduces cumulative footprint, but its own counterfactual assertions must stay intact. The existing Miri-only gate is static, pre-warmed before Drop, address-targeted, and waits after the terminal RMW (`src/registry/segment_route/terminal_publication_gate.rs:16-111`; `src/registry/heap_core_xthread/routing.rs:47-73`). Do not move the pause before publication or reallocate/log/retag from inside the paused free path. Resume on every failure path so a failed assertion does not strand a producer; do not substitute a timing sleep for the handshake.

The target should return successfully only after both witnesses have actually reached their assertions; a missing `cfg(miri)` body, zero-test selection, or skipped scenario must fail the gate. `--exact` and libtest's `test ... ok` line cease to apply to a custom `main`: the current CI steps at `.github/workflows/ci.yml:2814-2837` and the `running [1-9] test`/exact sentinel in `scripts/miri.mjs:205-224` would need a target-specific exit-status/explicit-completion rule. A plain exit code from an accidentally empty `main` is not evidence; review the target and require a scenario-completed witness. Keep Stacked Borrows/default borrow tracking plus `-Zmiri-strict-provenance`, and a **separate** run with `-Zmiri-tree-borrows` and strict provenance, against the same target, feature set, and target triple. Do not use `-Zmiri-disable-validation`, `-Zmiri-disable-stacked-borrows`, altered retag policy, or an ignored test as an acceptance shortcut. The [Miri flag docs](https://github.com/rust-lang/miri#miri--z-flags-and-environment-variables) explicitly say disabling validation/borrow tracking can miss UB.

If the cost budget permits, repeat this same installed-allocator witness with the *actual* `production,internals,bench-internals` feature set. If not, the defensible claim is only: Windows-target Miri exercised the real installed `alloc-global` route under the named **minimal feature profile**. `production` additionally enables `alloc-decommit`, `fastbin`, `alloc-segment-directory`, and `primordial-lazy-commit` (`Cargo.toml:170-198,412`); do not silently infer their Miri execution from the minimal run. Existing native full-profile tests and OS-release oracle remain separate acceptance legs. Under `cfg(miri)` even a `production`-feature Miri run does **not** execute Windows `VirtualAlloc`/`VirtualFree`, lazy commit, or physical unmapping: those require native Windows evidence.

## Non-negotiable backend/provenance obligations

- **Allocator independence and pairing.** Every bootstrap, chunk, route descriptor/sidecar, and reservation allocation reachable beneath installed `GlobalAlloc::alloc` must avoid calling that global allocator. Miri's `System.alloc` is direct, with original pointer and exact `Layout(size, align)` carried to `System.dealloc`; native Windows keeps its own original VM release token. In particular biased Large payload/root alignment must not replace the underlying token/alignment used to release (`crates/aligned-vmem/src/os/miri.rs:14-40`, `src/alloc_core/platform/os.rs:167-210,548-565`, `src/alloc_core/large/alloc_core_large.rs:628-697`). The Miri backend's eager/no-op commit/decommit modeling cannot be described as physical Windows release proof.
- **Narrow pointer is only identity.** A caller's typed `Box` pointer supplies a numeric address key and validated offset, never authority to read a whole segment header or write its slack. Own-path canonicalization recovers a stored table root, then derives a block from that root (`src/alloc_core/alloc_core/mem/mem_impl.rs:22-42`). Foreign lookup uses `ptr.addr()` under shard lock, returns a counted descriptor/sidecar pin, and drops the lock before publication (`src/registry/segment_route/directory.rs:469-507`). `map_addr` alone would preserve a *narrow* provenance, not widen it to the whole segment; an integer membership check is not a dereference permission. Post-free test queries likewise must use address-only lookup or allocator-owned roots, never dereference the stale `Box` pointer.
- **Issue, terminal commit, and owner cut.** Registration and sidecar preparation precede user-visible issue (`src/alloc_core/segment/segment_table/segment_table_impl.rs:346-397`). Owner writes class/credit before handoff; each valid foreign current instance publishes exactly once via Small `fetch_or(AcqRel)` or Large `LIVE(g) → PENDING(g)` CAS (`src/alloc_core/segment/remote_bitmap/sidecar_bitmap.rs:47-71`, `src/registry/segment_route/pin.rs:37-62`). The producer must touch only the independent descriptor/sidecar after that terminal point; its still-live stack frames are not reservation-lifetime credits. Owner scan takes one fixed high-water, single `swap(0, AcqRel)` per visited word; post-cut publications retain credit for a later pass; detached records and unpublished valid allocations block premature finalization. Owner uses stored roots, consumes a record once, and unlinks/reclaims only after the relevant cuts (`src/alloc_core/alloc_core/sidecar_drain.rs:7-66`, `src/alloc_core/small/alloc_core_small_reclaim.rs:21-67`). A pin must remain valid through unlink via its independent refcount, but must not keep/reconstitute reservation authority (`src/registry/segment_route/directory.rs:124-205`).
- **Exclusive owner lifecycle.** TLS `LOCAL` is stamped TORN before recycle; only a winning slot/maintenance CAS may create mutable heap access; fallback is independently locked (`src/global/tls_heap.rs:43-85`, `src/registry/heap_registry/claim.rs:344-420`, `src/global/fallback.rs:23-37`). Do not manufacture a second `&mut HeapCore`, use a foreign producer to inspect owner metadata, or relax these rules to shorten a run. `trim_current_thread` is owner-side logical retirement and follows cache/decommit policy; an assertion that a route vanished is not by itself an OS-release oracle.

## Separating failure classes without allocating inside the allocator

Use the **call graph and phase order** first. Recursion needs a demonstrable cycle back into installed `GlobalAlloc::alloc` while an earlier allocation frame is still live. The old aperture had such a cycle; the current `System.alloc` edge removes that particular edge. Search any other bootstrap/registration/fallback allocation edge before claiming it cannot recur. Conversely, large *finite* chunk zeroing, 4 MiB aligned eager reservations, sidecar initialization, and libtest allocations offer a plausible interpreter-cost story, not proof of the current failure.

For the run owner, non-invasive discrimination is a bounded external process RSS/commit trace and a **coarsely sampled** Miri `-Zmiri-report-progress=<blocks>` stack trace (documented in [Miri flags](https://github.com/rust-lang/miri#miri--z-flags-and-environment-variables)), streamed directly to a capped/file-backed log instead of accumulated in a Node string. Repeated, deepening `GlobalAlloc → bootstrap → GlobalAlloc` frames would support recurrence; progressing finite initialization frames with rising host memory would support cost/geometry. Neither exit 134, elapsed 820 s, a 32 KiB failed host request, nor a later Node heap OOM distinguishes them. If allocation-backtrace bookkeeping itself dominates, Miri documents `-Zmiri-disable-leak-backtraces` as a memory-saving option that leaves the leak *check* enabled but loses leak backtrace detail; record this trade-off separately, never replace it with `-Zmiri-ignore-leaks` for a green gate. An optional temporary `cfg(miri)` **fixed static atomic** depth/phase guard, if the existing evidence remains ambiguous, may fail closed before formatting or global allocation; it must be removed or shown non-perturbing before acceptance, and a process-global depth signal must not mistake concurrent calls for same-thread recursion. Do not `println!`/`format!`/`Vec`/`Box` in `GlobalAlloc` or its bootstrap to debug a possible recursion. The other worktree's current dynamic diagnosis should own any such experiment; this document does not reproduce it.

If a reduced `System`-only Windows control also fails in std teardown, classify that as a possible toolchain/stdlib-model boundary and produce a minimal upstream reproducer; it is **not** permission to suppress Stacked Borrows for Sefer. A Linux-target Miri pass may supply supplemental evidence, but [Miri itself notes Windows support differs](https://github.com/rust-lang/miri#supported-targets), and cross-target green is not a Windows-target pass. A genuine Sefer-frame UB must be fixed in the backend/provenance invariant; a host OOM or unsupported operation leaves acceptance **open**.

## Acceptance rule and residual risk

Record exact source revision, target triple, nightly/Miri build, features, flags, per-scenario completion and exit code for **both** borrow models. Require the real installed allocator, actual Box witnesses, terminal pause before owner trim and resume afterward, and no checker-suppression flags. Keep native production/Windows OS release evidence alongside, without merging its claim into Miri's. If either model cannot reach the witness or reports UB/OOM, the Windows Miri provenance gate is **not closed**. Even both passes establish only those concrete executions and interleavings: Miri does not prove allocator soundness for all callers, schedules, feature combinations, or native Windows VM behavior ([Miri limitations](https://github.com/rust-lang/miri#limitations)). No speed/RSS improvement is asserted without measurement.
