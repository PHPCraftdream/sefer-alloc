## 1. Findings

### F1 — **P2** — `460191f`'s new clause asserts that all three of the panic sites the same paragraph enumerates carry a bare `&'static str` message; one of the three is *"an unwinding `init`"* — caller code, arbitrary message — and it is the only one the whole section exists to warn about. Measured: 0 / **2** / 0

**Where:** `crates/racy-ptr-cell/src/lib.rs:157-159` (the parenthetical),
against its own antecedent at `:127-133`; `crates/racy-ptr-cell/README.md:101-103`
against `:78-82` (same text, shorter).

The paragraph opens by enumerating the panic inventory (`src/lib.rs:127-130`):

> There are **three** panic sites in total: that sentinel-collision
> `assert!`, **an unwinding `init`**, and the `align_of::<T>() >= 2` check in
> [`RacyPtrCell::new`] / [`RacyPtrCell::default`] …

and closes, thirty lines later, with the clause `460191f` added
(`src/lib.rs:156-159`):

> Only a panic whose message is a bare `&'static str` **(as this crate's own
> three panic sites are)** is fully covered by the `set_hook` mitigation.

**The parenthetical is false under both of its possible readings, and the
reading it forces is the damaging one.**

- Read "three" as binding to the enumeration above (the only antecedent for
  "three" in the whole document): then it claims that **an unwinding `init`**
  carries a bare `&'static str` message. `init` is caller code with a
  `FnMut() -> Option<NonNull<T>>` signature; its panic message is whatever
  the caller writes. Measured (§0.1 probe A, the crate's own recommended
  recipe applied in full — `panic = "abort"` plus a hook that only loads two
  atomics and exits):

  ```
  site 1  crate's sentinel-collision assert!            -> 0 allocations before the hook
  site 3  crate's align_of assert! (via default())      -> 0 allocations before the hook
  site 2  unwinding init, message = "reservation failed"        -> 0
  site 2  unwinding init, message = panic!("… {}", <runtime u32>) -> 2
  site 2  unwinding init, message = Result::expect("mmap failed") -> 2
  ```

  Two of the three are 0 by construction; the third is 0 or 2 depending
  entirely on what the caller wrote.
- Read "this crate's **own**" as excluding the caller's `init`: then the
  count is **two**, not three (`src/lib.rs:398` and `:594` in a non-loom
  build; `:419` and `:594` under `--cfg loom`), and the parenthetical
  contradicts the enumeration it points at.

**Why this matters more than an off-by-one.** The site the parenthetical
mis-covers is not an arbitrary one of three. It is:

1. the **only** site the reader controls;
2. the **only** site the entire "Using this inside a `#[global_allocator]`"
   section exists to warn about (every other bullet in it — no allocation, no
   blocking, no cell cycle, no sentinel return — is about what `init` does);
3. the site cycle 4's own probe C proved **hangs end-to-end** (`exit 124`,
   `timeout` fired) with `panic = "abort"` plus the recommended hook, when
   the message is formatted.

So the sentence that decides whether a reader's configuration is covered
tells them that the one case they are being warned about is already covered.
The very next sentence — "**The only mitigation that covers a formatted
message is an `init` that cannot panic at all.**" — then says the opposite.
A reader who stops at the first sentence (it is the one containing the word
"covered") concludes they are done.

**Concrete failure scenario.** A `std` consumer reads the paragraph, applies
`panic = "abort"` and the non-allocating `set_hook`, then reads "Only a panic
whose message is a bare `&'static str` (as this crate's own three panic sites
are) is fully covered" and checks it off: the three sites listed above are all
the crate's, all static, all covered. Their `init` does
`reserve().expect("mmap failed")`. That is site 2, it is formatted, it costs
2 allocations before the hook, and inside their `#[global_allocator]` the
first of those two re-enters the cell this same thread left `INITIALIZING`,
fails the claim CAS at `src/lib.rs:545`, and enters the loser spin at
`:634-655` on a sentinel it owns itself. 100 % CPU, no diagnostic, no abort.
They implemented the documented mitigation, read the documented exception,
correctly concluded it did not apply to them — and got the documented failure.

**Regression note.** Cycle 4's suggested text read "(as this crate's own three
`assert!`s are)". The landed edit changed `assert!`s → **panic sites**, which
is precisely what binds the claim to the enumeration containing the caller's
`init`. The substitution made the clause wrong; the original suggestion was
merely imprecise about the count.

**Suggested fix (one parenthetical, both files).** Bind the claim to the
crate's own asserts and say what that excludes:

> Only a panic whose message is a bare `&'static str` is fully covered by the
> `set_hook` mitigation. The crate's own two `assert!`s (the sentinel-collision
> check and the `align_of::<T>() >= 2` check) are of that shape and measure 0
> allocations before the hook; **the third panic site above — an unwinding
> `init` — is your code, and its message is whatever you wrote**, so it is
> covered only if you keep it a bare literal. **The only mitigation that covers
> a formatted message is an `init` that cannot panic at all.**

While in this paragraph, `:131`'s "All three go through the panic runtime" is
also loose for site 3: the `static` form the same sentence names is a
**const-eval failure**, which reaches no panic runtime at all.

**Why CI cannot see this.** `ci.yml:1802` is the crate's only bare-metal row
and it names `thumbv7em-none-eabi`, which has CAS — so the row is green and
will stay green. The comment above it (`:1770-1781`) states the row's purpose

it proves, because Cortex-M0-class targets are precisely the ones that fail.

**Precedent inside this repository, at this severity, twice.** Both sibling
crates state the requirement and fail fast:

- `crates/tagged-index-stack/src/lib.rs:135-144` — `#[cfg(not(target_has_atomic
  = "64"))] compile_error!(…)`, plus a "Portability limit" crate-doc section
  (`:110-125`) and a README section (`README.md:58`). Its own doc gives the
  rationale verbatim: *"A build on an unsupported target fails fast with an
  explicit `compile_error!` naming the requirement, rather than the more
  cryptic 'cannot find function/no `AtomicU64` in `core::sync::atomic`' error
  a bare unresolved import would otherwise produce."* That is exactly the
  error class measured above.
- `crates/sefer-region/src/lib.rs:58-65` — `#[cfg(not(target_has_atomic =
  "ptr"))] compile_error!(…)`, i.e. **the identical predicate this crate
  needs**. Its message even records that this class already produced a
  documented overclaim here once: *"riscv32imc (no `A` extension) is NOT
  supported despite any earlier documentation suggesting otherwise."*

`racy-ptr-cell` — the one crate of the three that is *itself* a pointer-CAS
primitive, and the one whose module doc names "bare-metal bootstraps" as a
target audience (`src/lib.rs:39-41`) — has neither the guard nor a single
sentence of portability text anywhere in `src/lib.rs`, `README.md`,
`CHANGELOG.md` or `Cargo.toml`.

**Failure scenario.** A Cortex-M0+ firmware author browsing crates.io's
`no-std::no-alloc` category — the category this crate lists itself in — finds
a cell that says "`no_std` and allocation-free … the cell itself is one
`AtomicPtr`; it never touches the heap … Used by … bare-metal bootstraps".
`cargo add racy-ptr-cell` then produces three `E0599`s pointing into a
dependency's source at a method they never called, with no statement of what
is missing. Nothing in the crate tells them that the answer is "your target
has no pointer-width CAS and this crate cannot work on it".

**Why P2 and not P3.** It is a documented-guarantee divergence, not a style
nit: the published category and the "bare-metal bootstraps" sentence become
permanent at first publish (a crates.io category listing and a frozen 0.1.0
docs.rs page), the failure mode is a compile error with no diagnosis, CI is
structurally blind to it, and the repository has already decided twice that
this exact gap is worth a `compile_error!`. The fix is ~8 lines and touches
neither the algorithm nor the API.

**Suggested fix.** Mirror `sefer-region`'s guard verbatim in shape:

```rust
#[cfg(not(target_has_atomic = "ptr"))]
compile_error!(
    "racy-ptr-cell requires a target with pointer-width atomic \
     compare-and-swap (target_has_atomic = \"ptr\"): the whole cell is one \
     AtomicPtr driven by compare_exchange. Targets with load/store atomics \
     but no CAS -- thumbv6m-none-eabi (Cortex-M0/M0+), \
     riscv32imc-unknown-none-elf (no `A` extension), msp430-none-elf -- are \
     NOT supported, despite this crate being no_std and allocation-free."
);
```

plus one "Portability limit" paragraph in the module doc and the README
(mirroring `tagged-index-stack`), and — optionally, since it is one line —
a second CI cross-build row proving the guard fires, or simply switching
nothing and letting the `compile_error!` be the contract.

### F3 — **P3** — the measured figures inside `460191f`'s own new clause: `Result::unwrap = 2` reproduces exactly, `assert_eq! = 4` does **not** (I measure 3 across five shapes on the named toolchain and platform), and the clause's own list names `unwrap` unqualified while `Option::unwrap` allocates **0**

**Where:** `crates/racy-ptr-cell/src/lib.rs:152-156`; `README.md:97-101`.

The clause (`src/lib.rs:152-156`):

> so `unwrap`/`expect`/`assert_eq!`/`panic!("{}", …)` allocate before any hook
> runs, whether or not the hook itself allocates — measured: 2 allocations for
> `Result::unwrap`, 4 for `assert_eq!`, with the same non-allocating hook that
> reaches 0 for a bare-`&'static str` panic.

Measured on the toolchain and platform the *preceding* sentence names (rustc
1.97, `x86_64-pc-windows-msvc`, `--release`, `panic = "abort"`, the same
non-allocating hook), §0.1 probe B:

| shape | allocations before the hook |
| --- | --- |
| bare `&'static str` panic | **0** |
| `Option::unwrap()` on `None` | **0** |
| `Option::expect("…")` | 1 |
| `Result::unwrap()` on `Err` | **2** ✓ matches |
| `Result::expect("…")` | 2 |
| `panic!("… {}", <runtime u32>)` | 2 |
| `assert_eq!(a, 999)` — no message | **3** |
| `assert_eq!(a, 999, "mismatch")` | **3** |
| `assert_eq!(a, 999, "…")` | **3** |
| `assert_eq!(a, b)` — both operands runtime | **3** |
| `assert_eq!(a, "zzz")` — `&str` operands | **3** |
| `assert_eq!(a, 999, "mismatch {}", <runtime>)` — *formatted* message | 4 |
| `assert_eq!(a, 999, "<130-char message>")` | 5 |

Two distinct defects:

**(a) `4 for assert_eq!` does not reproduce.** Every ordinary shape measures
3; 4 appears only when the *custom message itself* is formatted, and 5 when it
is long enough to force an extra `String` growth. The published figure is
therefore not a property of `assert_eq!` — it is a property of one unstated
source shape. This is the same class cycle-4 F3(a) closed for the neighbouring
figure (a number published against a configuration it was not measured in);
`460191f` fixed that one and added two more without the source shape that
would make them reproducible. Under CLAUDE.md's derived-numbers rule, a
figure a reader cannot regenerate from what the document states is not a
usable citation.

**(b) `unwrap` is listed unqualified, and one of the two `unwrap`s allocates
nothing.** `Option::unwrap` panics through `core::panicking::panic` with a
bare `&'static str` ("called `Option::unwrap()` on a `None` value"), reaches
`StaticStrPayload`, and measures **0** — it is fully covered by the
`set_hook` mitigation, exactly as the criterion stated two sentences later
predicts. Only `Result::unwrap` (which formats the `Err` with `Debug`)
allocates. The list therefore contradicts the criterion the same paragraph
gives, in the direction of over-warning: a reader is told to avoid the single
most common `unwrap` in Rust for a reason that does not apply to it.

The error direction is safe (over-caution, not under-caution), which is why
this is P3 and not P2.

**Suggested fix.** Either drop the counts and keep the robust claim ("a
formatted message allocates before any hook runs; a bare `&'static str`
message does not"), or state the shapes: "`Result::unwrap` 2,
`Result::expect` 2, `Option::expect` 1, `assert_eq!` 3 (more if the custom
message is itself formatted); `Option::unwrap` is a bare-`&'static str` panic
and allocates 0 — measured under `panic = "abort"`, `--release`, rustc 1.97,
`x86_64-pc-windows-msvc`, with a provably non-allocating hook."

I would have liked to break the pattern and return an unconditional GO. I
cannot honestly do so, and neither of the two reasons is a re-argument of an
old point:

- **F1** is in the sentence `460191f` added, and it is the same failure mode
  as cycle 3 and cycle 4: the paragraph's own statement about what its
  remedy covers is wrong. The clause tells the reader that all three of the
  panic sites enumerated thirty lines above carry a bare `&'static str`
  message. One of those three is *"an unwinding `init`"* — caller code,
  arbitrary message. Measured with the crate's full recommended recipe
  applied: the crate's own two `assert!`s reach the hook at **0**
  allocations, but the same site 2 costs **2** with `Result::expect` or
  `panic!("…{}", x)` — and cycle 4 already proved that exact case **hangs**.
  So the one panic site the reader controls, and the only one the entire
  `#[global_allocator]` section is about, is the one the sentence tells them
  is already covered. Cycle 4's suggested wording said "three `assert!`s";
  changing that to "three panic sites" is what made it wrong.
- **F2** is new, novel to all nine reviews, and measured on the *packaged*
  tarball: `racy-ptr-cell` does not compile on any `no_std` target without
  pointer-CAS — `thumbv6m-none-eabi` (Cortex-M0/M0+), `riscv32imc`,
  `msp430` — and fails with three bare `E0599`s that never name the missing
  capability. The crate advertises `no-std::no-alloc` on crates.io and names
  "bare-metal bootstraps" as its audience; CI's only bare-metal row is
  `thumbv7em-none-eabi`, which *has* CAS, so the gate is green by
  construction. Both sibling crates in this same workspace already carry the
  guard this one lacks — `sefer-region` with **literally the same predicate**
  (`target_has_atomic = "ptr"`), and `tagged-index-stack` whose own doc gives
  the rationale word for word ("fails fast with an explicit `compile_error!`
  naming the requirement, rather than the more cryptic … error a bare
  unresolved import would otherwise produce"). Category listings and the
  0.1.0 docs.rs page freeze at upload; the fix is eight lines and one

Both fixes are cheap and neither touches the algorithm or the API: F1 is one
parenthetical in two files, F2 is one `compile_error!` plus a portability
