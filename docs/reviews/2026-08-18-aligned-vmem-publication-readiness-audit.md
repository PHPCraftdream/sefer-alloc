# Аудит готовности `aligned-vmem` к публикации

Дата: 2026-08-18  
Ревизия: `a61c582dbb1d80db436ef35d3aafe7eb34960c91`  
Пакет: `crates/aligned-vmem`, версия `0.2.0` (`Unreleased`)

## Вердикт

**NO-GO: публиковать текущую ревизию не следует.**

В безопасном публичном API `LazyReservation` есть обход его главной гарантии:
`as_reservation()` возвращает `&Reservation`, через который можно вызвать безопасные
методы, меняющие состояние отображения в ОС, не обновив watermark. На Windows это
может оставить `committed_len()` указывающим на уже decommit-нутые страницы и привести
к `STATUS_ACCESS_VIOLATION` у кода, который полагается на документированную гарантию.

После устранения H1 крейт выглядит близким к публикации. Перед релизом также следует
исправить неверный публичный контракт huge pages для Android (M1), а затем запустить
обычные релизные проверки — в рамках этого аудита они намеренно не запускались.

Сводка новых/оставшихся замечаний:

| Уровень | Количество | Публикация |
|---|---:|---|
| HIGH | 1 | блокирует |
| MEDIUM | 1 | исправить до публикации |
| LOW | 3 | желательно исправить до публикации |
| INFO | 1 | можно отложить |

Новых доказанных ошибок освобождения ресурсов, арифметики отображений или FFI ABI в
просмотренных путях не найдено. Это результат статического, ограниченного одним
контекстом аудита, а не доказательство их отсутствия.

## Findings

### H1 — `LazyReservation::as_reservation()` безопасно обходит watermark

**Уровень:** HIGH, релиз-блокер  
**Класс:** нарушение безопасного контракта / рассинхронизация состояния ОС и метаданных

Места:

- `crates/aligned-vmem/src/lazy_reservation.rs:17-18` — watermark определён как
  точное разбиение на committed/uncommitted диапазоны;
- `crates/aligned-vmem/src/lazy_reservation.rs:26-32` — документация утверждает, что
  `&mut self` заставляет сериализовать изменения;
- `crates/aligned-vmem/src/lazy_reservation.rs:34-42` — `committed_len()` объявлен
  гарантией доступного для записи префикса;
- `crates/aligned-vmem/src/lazy_reservation.rs:44-51` — утверждается, что обход
  требует raw pointer и обращения к отдельно названным raw-примитивам;
- `crates/aligned-vmem/src/lazy_reservation.rs:163-166` — `as_reservation(&self)`
  возвращает `&Reservation` якобы для read-only queries;
- `crates/aligned-vmem/src/reservation.rs:563,628,696,732,750,781,799` —
  `decommit`, `try_decommit`, `decommit_lazy`, `recommit`, `try_recommit`,
  `commit_range` и `try_commit_range` являются безопасными методами с `&self`.

Следовательно, никакой raw API для рассинхронизации не нужен:

```rust
let reservation = reserve_aligned_lazy(size, align, initial_commit)?;
reservation.as_reservation().decommit(0, page_size);

// Остаётся прежним, хотя состояние отображения уже изменено.
assert_eq!(reservation.committed_len(), initial_commit);
```

На Windows успешный `MEM_DECOMMIT` делает страницы недоступными до recommit. При этом
`committed_len()` продолжает обещать, что префикс доступен для записи. Обратный обход
тоже возможен: `commit_range`/`recommit` через borrowed `Reservation` меняет состояние
за пределами watermark. Само разыменование указателя остаётся `unsafe`, но безопасный
тип публикует ложную границу, на которую вызывающий код вправе опираться при проверке
диапазона перед записью.

Это также опровергает закрывающую запись item 66 в
`docs/CORRECTNESS_OPEN_ITEMS.md`: там причина введения `LazyReservation` описана
верно — мутаторы `Reservation` используют `&self` — но затем пропущено, что
`as_reservation()` снова предоставляет к ним доступ.

Покрытие недостаточно: `crates/aligned-vmem/tests/lazy_reservation.rs:66` использует
`as_reservation()` только для `len()`. Оракула, который проверял бы невозможность
доступа к state-mutating методам через borrowed inner handle, не найдено.

**Исправление:** до первого релиза `0.2` удалить или сузить `as_reservation()`.
Нужные read-only запросы лучше напрямую проксировать на `LazyReservation` либо вернуть
отдельный read-only view, тип которого вообще не содержит OS-state mutators. Простая
правка комментария не исправит нарушение гарантии.

**Регрессия:** добавить compile-time/API-оракул, подтверждающий отсутствие безопасного
borrowed-пути к decommit/recommit/commit, и Windows-контрпример для прежней формы API.
Обновить закрывающую запись item 66 и changelog после изменения поверхности API.

### M1 — публичный huge-page контракт забывает Android

**Уровень:** MEDIUM  
**Класс:** расхождение документации и реального платформенного поведения

Места:

- `crates/aligned-vmem/src/api/reserve_aligned_huge.rs:29-35` говорит об особом
  требовании кратности 2 MiB только на Linux;
- `crates/aligned-vmem/README.md:65-66,120-123` повторяет Linux-only формулировку;
- `crates/aligned-vmem/src/os/unix.rs:83-91` применяет проверку и к Linux, и к Android;
- `crates/aligned-vmem/tests/huge_pages.rs:109-175` корректно считает контракт
  Linux/Android-общим.

На Android с feature `huge-pages` запрос, который соответствует обычной странице, но
не кратен 2 MiB, будет отвергнут как invalid argument, хотя опубликованная документация
обещает это исключение только Linux. В crate-level документации и changelog Android уже
учтён, то есть это локальный, но пользовательски заметный drift.

**Исправление:** во всех контрактных формулировках заменить “Linux” на “Linux and
Android” там, где cfg и backend используют оба target OS. Желателен статический
doc-drift guard для этой пары, потому что Android не исполняется в CI.

### L1 — документация `fault-injection` неверна в комбинации с mock cfg

**Уровень:** LOW  
**Класс:** feature/cfg composition, неверная документация

`crates/aligned-vmem/src/fault_injection.rs:3-10` утверждает, что
`try_commit_range` всегда вызывает настоящий per-OS backend. Однако строки 108-120
этого же файла документируют обратное: при `aligned_vmem_mock` единственный real-path
call site скомпилирован, а fault-injection hook не используется. CI намеренно собирает
mock-конфигурации вместе с features, поэтому комбинация не является чисто
теоретической.

**Исправление:** явно написать, что `fault-injection` действует только без
`aligned_vmem_mock`, а при совместном включении mock backend и его собственный fault
script имеют приоритет. Если сочетание не поддерживается публично, лучше выразить это
проверяемым cfg-контрактом.

### L2 — успешный address-zero `mmap` классифицируется как «OS refusal»

**Уровень:** LOW  
**Класс:** модель ошибок / диагностическая точность

`crates/aligned-vmem/src/os/unix.rs:963-977` корректно освобождает успешное отображение
по адресу ноль и не читает stale `errno`. Но затем возвращается
`VmemError::os_refusal_unknown_code()`. Документация этого конструктора в
`crates/aligned-vmem/src/error.rs:75-84` одновременно называет случай “genuine OS
refusal” и признаёт, что `mmap` успешно выполнился и ни один syscall ничего не
отклонил.

Утечки и поддельного errno здесь больше нет, однако публичная классификация и Display
сообщают неверную причину. Это затруднит диагностику на экзотической платформе, где
адрес ноль действительно может быть выдан.

**Исправление:** пока версия ещё `0.2.0`, рассмотреть отдельный внутренний/публичный
вид ошибки вроде `unsupported_address` или более нейтральное имя третьего состояния.
Минимальная правка — перестать документировать этот вариант как обязательный отказ ОС.

### L3 — README обещает больше Unix-целей, чем компилирует backend

**Уровень:** LOW  
**Класс:** заявленная поддержка платформ

`crates/aligned-vmem/README.md:238` заявляет намерение поддерживать полные семейства
`cfg(unix)` и `cfg(windows)`. При этом `crates/aligned-vmem/src/os/unix.rs:605-648`
преднамеренно содержит `compile_error!` для неизвестных Unix-семейств и MIPS. MIPS в
README перечислен отдельно, но итоговая blanket-формулировка всё равно шире реального
контракта.

**Исправление:** обещать поддержку перечисленных OS/архитектурных семейств и явно
отделить “reasoned-from-spec” от “CI-verified”. Не использовать `cfg(unix)` как
синоним фактической матрицы поддержки.

### I1 — `LazyReservation` не реализует `Debug`

**Уровень:** INFO  
**Класс:** API ergonomics

`Reservation` имеет ручной `Debug` (`reservation.rs:104`), а публичные parts-типы
derive-ят его. У `LazyReservation` реализации нет, хотя watermark — важнейшее состояние
для диагностики ошибок lazy commit.

**Исправление:** добавить ручной `Debug`, показывающий как минимум inner reservation и
`committed_len`, не раскрывая ничего сверх уже публично наблюдаемого состояния.

## Производительность и архитектурные возможности

Новых доказанных hot-path регрессий не найдено. Значимые возможности уже честно
зафиксированы в `docs/perf/OPEN_ITEMS.md` и не должны маскироваться как новые дефекты:

1. На 64-bit Unix обычный aligned reserve обычно удерживает `size + align` виртуального
   адресного пространства; для hugetlb при `align > 2 MiB` это может временно и/или
   постоянно увеличить charge huge-page pool. Это измеряемый кандидат на оптимизацию,
   а не безопасная механическая правка (items 48/53).
2. Huge exact path и fallback могут повторять попытку отображения при нулевом адресе;
   редкость события и сложность семантики делают измерение обязательным (item 52).
3. Безымянные tuples на границе backend усложняют сопровождение lifecycle-инвариантов;
   переход к именованному внутреннему результату полезен при следующем крупном
   рефакторинге, но сам по себе не блокирует релиз (item 54).
4. Локальные package gates в CI идут после части root-проверок, поэтому ранний root
   failure способен скрыть результат именно для `aligned-vmem` (item 50). Это вопрос
   времени обратной связи и release-process, не runtime-производительности библиотеки.

Не рекомендуется добавлять кеширование или новые fast paths без профиля: системные
вызовы здесь обычно находятся на границе крупных операций с виртуальной памятью, а
ошибка в редком platform path дороже небольшого выигрыша.

## Готовность пакета и release gates

Статически выглядит хорошо:

- package metadata, license, README, repository и docs.rs metadata присутствуют;
- runtime-зависимостей нет;
- changelog содержит секцию `0.2.0 - Unreleased`;
- CI содержит all-features real/mock конфигурации, release mock self-check,
  page-size override, i686 GNU/musl compile checks, rustdoc `-D warnings`, Miri,
  Windows/macOS rows, weekly feature powerset и `cargo publish --dry-run`;
- основные предыдущие замечания по mock capability, stale errno, platform semantics,
  page-size test contract, benchmark counters и reservation pointer oracle в текущем
  дереве исправлены или явно оформлены как принятые ограничения;
- semver-проверка для перехода `0.1 -> 0.2` объективно ограничена правилами Cargo:
  для `0.x` minor является breaking boundary. CI это прямо оговаривает, но такая
  проверка не доказывает отсутствие непреднамеренных API-изменений.

Перед публикацией после исправления H1/M1 нужно фактически выполнить и сохранить
результаты как минимум:

1. package tests для default, all-features и поддерживаемых cfg-вариантов;
2. rustdoc с warnings-as-errors;
3. Miri-наборы real и feature combinations;
4. `cargo publish --dry-run -p aligned-vmem`;
5. Windows real-backend regression для watermark и platform matrix из CI.

Этот отчёт не утверждает, что перечисленные gates зелёные: они присутствуют в CI, но
по требованию read-only/no-tests в ходе аудита не запускались.

## Итог

Главная архитектура — RAII-владение полным mapping, явные platform capability queries,
закрытые FFI boundaries и детализированные decision records — выглядит зрелой. Однако
H1 находится ровно на центральной безопасной абстракции нового lazy API и опровергает
её заявленную гарантию без использования `unsafe` для изменения OS state. Поэтому
текущая ревизия **не готова к публикации**.

Минимальный путь к GO:

1. закрыть безопасный mutating-доступ через `LazyReservation::as_reservation()` и
   добавить API-регрессию;
2. исправить Linux/Android huge-page контракт в rustdoc и README;
3. желательно привести в порядок L1-L3 до заморозки `0.2` API/документации;
4. прогнать существующие release gates на итоговом commit.
