## P3-1. Однородный fill скрывает систематические ошибки копирования realloc

Места: `crates/globalalloc-model/src/drive.rs:101`, `:172`, `:485`, `:491`;
`crates/globalalloc-model/tests/oracle_negative.rs:697`.

Весь блок заполняется одним байтом. Проверка realloc сравнивает каждую позицию
префикса с тем же `l.fill`. Поэтому аллокатор, который вместо копирования
префикса заполняет новый блок первым байтом старого, проходит проверку для
всех данных, которые этот драйвер способен подготовить.

Конкретный дефектный realloc: выделить корректный новый диапазон, прочитать
`old[0]`, заполнить новый диапазон этим байтом, освободить старый и вернуть
новый указатель. Все чтения/записи могут быть полностью определёнными. Для
реального буфера `[1, 2, 3, ...]` такая реализация разрушает содержимое; для
буфера драйвера `[f, f, f, ...]` совпадёт каждая проверяемая позиция.
Перестановки байтов внутри однородного префикса также неразличимы.

Это **пробел покрытия класса ошибок**, а не ложный результат сравнения:
на выбранных драйвером данных выход действительно совпадает с входом.
Существующий `ReallocNoCopy` проверяет потерю префикса в пользу нулей,
но не случай неверного алгоритма копирования, сохраняющего однородный fill.
Описание ограничений обсуждает межблочные коллизии после 255 присваиваний,
однако этот случай возникает уже на первом realloc одного блока.

Рекомендация: использовать воспроизводимый шаблон, зависящий от идентификатора
заполнения и смещения байта. Ожидаемые данные можно вычислять на лету, без
хранения второй копии payload. Добавить отрицательные аллокаторы для
`repeat_first_byte`, сдвига копии и перестановки участков, а также положительные
grow/shrink/in-place случаи. Стоимость шаблонного заполнения относительно
`write_bytes` нужно отдельно измерить; выигрыш в диагностике не означает
ускорение. Даже новый шаблон должен честно описывать оставшиеся коллизии.

## P3-2. Release-workflow не требует успеха нового globalalloc-model workflow

Места: `.github/workflows/release.yml:324`, `:376`, `:432`;
`.github/workflows/globalalloc-model.yml:31`, `:68`, `:86`, `:176`.

Проверка перед публикацией обращается только к
`actions/workflows/ci.yml/runs?head_sha=...`. Отдельный workflow
`globalalloc-model.yml` в release-файле вообще не упоминается.
Локальный release test gate запускает default и all-features, но не повторяет
всю новую матрицу, i686, проверку извлечённого пакета и docs.rs-конфигурацию.

Следовательно, возможна последовательность: общий `CI` зелёный, новый
`globalalloc-model` красный, default/all-features release-тесты зелёные,
после чего workflow продолжает публикацию. Конкретный контрфактический пример —
возвращение `1usize << 63` в интеграционный тест: нативные 64-битные тесты,
64-битный Miri и bare-metal сборки одной библиотеки этого не поймают, а новый
i686-job упадёт на компиляции теста. Его failure не проверяется перед publish.

Это анализ зависимости проверок, не утверждение, что такой красный удалённый
прогон уже произошёл. В этом ревью GitHub Actions не запускались.

Рекомендация: для `NAME=globalalloc-model` проверять успешное завершение обоих
workflow для того же SHA. Отсутствующий, незавершённый, отменённый и неуспешный
прогон не должны разрешать публикацию. Сохранить текущую явную семантику dry-run.
Отдельно проверить сценарии: оба success; новый workflow failure; queued;
нет запуска; success относится к другому SHA.

## P4-1. Резерв модели пропорционален всей истории, а не пику живых блоков

Место: `crates/globalalloc-model/src/drive.rs:243`–`:250`.

`Vec::with_capacity(ops.len())` резервирует место под каждую операцию, хотя
`Dealloc` и `Realloc` не добавляют live-записей. Для истории из миллиона
чередующихся Alloc/Dealloc пиковая живость равна единице, но резерв делается
на миллион записей. Для истории только из Dealloc резерв также делается,
хотя модель всё время пуста.

Обозначим длину истории M, пиковое число живых блоков K. Дополнительная память
модели сейчас O(M), хотя достаточна O(K), независимо от памяти входного `ops`.
Можно одним дешёвым предварительным проходом вычислить пик: Alloc и
AllocZeroed увеличивают счётчик, Dealloc уменьшает непустой, Realloc его не
меняет. Для успешно выполняемой истории это точный пик; остановка на ошибке
требует не больше памяти. Такой проход сохраняет одну начальную аллокацию
модели и отсутствие последующих перемещений её Vec.

Альтернатива — ленивый рост Vec, если важнее избежать предварительного прохода.
Он добавит realloc/copy bookkeeping. Выбор сравнить на длинном churn с K=1,
пустых dealloc-историях и накоплении большого K. Не уменьшать резерв до
произвольной константы с обещанием отсутствия realloc.

## P4-2. Проверка overlap имеет квадратичную худшую сложность

Место: `crates/globalalloc-model/src/drive.rs:80`.

Каждый Alloc/AllocZeroed и успешный Realloc просматривает весь live Vec.
Для M последовательных аллокаций выполняется ровно M(M−1)/2 сравнений
диапазонов: при M=2048 — 2 096 128. Это счёт по коду, не измерение времени.

Если B — суммарное количество проверяемых/записываемых байтов, текущая верхняя
оценка работы — O(MK+B), в худшем случае O(M²+B). Для маленьких стандартных
историй простой последовательный scan может оставаться самым быстрым.

При подтверждённой нагрузке с большим K добавить индекс непересекающихся
интервалов по начальному адресу. После поиска позиции достаточно проверить
предшественника и преемника: ранее принятые интервалы уже непересекаются.
`BTreeMap` позволяет приблизить работу к O(M log(K+1)+B), но добавляет память
и аллокации узлов. Сохранить live Vec для семантики `i % live.len()` и
`swap_remove`; замена его упорядоченным контейнером изменит выбор блоков.
При realloc исключить старый диапазон, сохранить соседства и обработку null.

Нужны положительные adjacent/in-place тесты и отрицательные overlap с обоих
краёв, после remove/reinsert и после swap_remove. Без профиля большого K
это возможность оптимизации, не обязательная замена простой модели.

## P4-3. Boxing стратегии размера добавляет аллокации при генерации и shrinking

Места: `crates/globalalloc-model/src/strategy.rs:15`, `:20`, `:66`–`:72`.

`size_strategy` возвращает `BoxedStrategy<usize>` и вызывается отдельно для
Alloc, AllocZeroed и Realloc. В разрешённом proptest 1.11.0 `Strategy::boxed`
создаёт Arc-обёртку, а `BoxedStrategyWrapper::new_tree` — отдельный
`Box<dyn ValueTree>` на каждое дерево размера. Это не только три холодные
аллокации при построении фабрики: цена повторяется при materialization деревьев
размеров и ленивых альтернатив во время shrinking.

Рекомендация: оценить конкретный возвращаемый тип стратегии вместо стирания
типа, например компактный enum стратегии/дерева или union однородных диапазонов
с корректной заменой отключённой shrink-альтернативы. Нельзя просто вернуть
старый union с weight=0: shrinking снова получит доступ к запрещённой ветке.
Существующий тест отключённой small-ветки должен остаться красным при такой
регрессии. Считать аллокации отдельно при создании фабрики и при new_tree/shrink;
одного времени `op_strategy()` недостаточно.

Основание: исходники proptest 1.11.0, `src/strategy/traits.rs:516`, `:703`,
`:773`–`:781`. Подсчёт не включает внутренние аллокации других стратегий.

## P4-4. Стратегия alignment материализует два ненужных Vec

Места: `crates/globalalloc-model/src/strategy.rs:29`, `:31`, `:66`, `:68`.

Список `[1, 2, 4, ...]` строится с ростом Vec и передаётся `sample::select`.
Это делается дважды на одну фабрику операций. Все значения однозначно задаются
показателем степени; хранить список в куче не требуется.

После `Config::validate` можно генерировать показатель из
`0..=max_align.trailing_zeros()` и отображать его в `1usize << exponent`.
Валидный max_align ограничивает показатель ниже ширины usize, поэтому
недопустимого сдвига не возникает. Проверить тот же набор значений и shrinking
к меньшим alignment, включая 1 и наибольший допустимый alignment на 32/64 битах.
Это устраняет storage списка; аллокации самого proptest в целом не исчезнут.

## P4-5. Ошибки и остаточные неточности документации

Это одна группа редакционных замечаний, не несколько скрытых P3:

- `src/config.rs:38`, `:54`: большой верхний предел не означает, что каждая
  операция получит огромный размер и гарантированно вернёт null. Например,
  `small_max=isize::MAX`, `small_weight=1`, `large_weight=0` сохраняет size=1
  в диапазоне генерации. Рекомендация: писать о возможных больших запросах и
  допустимом отказе аллокатора. Аналогичное преувеличение осталось в
  `tests/config_validate.rs:57`.
- `src/arbitrary_stream.rs:5`–`:6` обещает, что один input не запросит
  гигабайты. Теперь config-aware путь намеренно умеет выдавать размеры выше
  u32, и это закреплено тестом. Ограничение размера зависит от Config; общий
  предел MAX_OPS ограничивает количество операций, но не суммарные байты.
  README здесь уже честнее исходного module doc.
- `src/drive.rs:239`: не каждое сообщение содержит индекс операции. Run-end
  и teardown передают `block_idx` в параметр `step` (`:508`, `:524`);
  после swap_remove это вообще не номер исходной операции. Уточнить обещание
  или хранить идентификатор последней операции, установившей fill.
- `src/drive.rs:139`, `:165`: ссылка словами на crate-level `Limitations`
  устарела; актуальный раздел называется `Safety and oracle limits`.
- `src/drive.rs:279` и `tests/oracle_negative.rs:958`: null для одного байта
  назван безусловным дефектом аллокатора. GlobalAlloc разрешает отказ из-за
  нехватки памяти или неподдержанного alignment; это политика данного теста,
  а не доказательство нарушения allocator-контракта.
- `src/strategy.rs:57`: раздел Panics описывает только Config. Пустой
  `len_range`, например `4..4`, также вызывает panic в `proptest::collection::vec`.
  Указать требование к диапазону длины.

Семантика отказа и realloc сверена с
[официальным контрактом GlobalAlloc](https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html).

## P4-6. Shrink-тест копирует всю историю на каждом шаге; Miri получает лишнюю работу

Места: `crates/globalalloc-model/tests/system_proptest.rs:96`, `:103`,
а также `:20`, `:21`, `:38`.

`tree.current()` возвращает новый Vec из 32 операций на каждом шаге полного
shrink-обхода. Для S шагов тест создаёт S векторов и копирует O(32S) элементов.
Сам предмет проверки — невозможность попасть в отключённый диапазон размеров —
не требует такой длины и shrinking alignment до 4096.

Кроме того, property под Miri уменьшает число случаев и длину, но продолжает
использовать размеры до 128 KiB из Config::default. Arbitrary smoke уже уменьшает
и size bounds. Драйвер после последнего исправления выполняет больше полных
чтений перед уничтожением блоков, поэтому прежняя граница только cases/length
не учитывает текущую стоимость байтовых операций.

Рекомендация: минимизировать детерминированный shrink-контрпример и ненужные
оси, обязательно сохраняя наблюдение size-bearing операции; для Miri отдельно
ограничить size bounds, сохранив small/large, grow/shrink, zeroed/dealloc пути.
Нативный диапазон оставить полным. Не ослаблять тест до простого создания дерева
или ограниченного числа шагов без достижения важного перехода. Свежих измерений
времени в этом ревью нет.

## Подтверждённые сильные стороны и ограничения

- Null, alignment и overlap проверяются до dereference новых результатов.
- Все размеры, переданные через blanket GlobalAlloc, ненулевые и помещаются
  в Layout с учётом alignment. Недопустимый align отклоняется до деления.
- Старый указатель после успешного realloc не используется для чтения/записи;
  при null модель сохраняет прежнюю запись.
- Проверки перед dealloc, shrink-realloc и teardown закрывают ранее найденную
  потерю наблюдения. Их отрицательные тесты соответствуют механизму.
- Сумма двух весов теперь вычисляется в u64; размер получает отдельный draw.
  Нулевая ветка запрещена при generation и shrinking.
- Настройки RNG воспроизведения больше не ломают entropy-тест.
- Собственные payload-копии в reference model не хранятся: Live содержит
  указатель, layout-параметры и marker. Копирование небольшого Live не выглядит
  приоритетнее устранения резервов, дерева boxing и повторных scans.
- Нельзя объявить весь run-end sweep избыточным и просто удалить его: более
  ранний teardown dealloc может изменить ещё не проверенный блок. Нельзя
  автоматически удалить refill после realloc: смена marker участвует в
  диагностике поколений данных.
- Panic-leaks и недиагностируемость нарушений extent/provenance/initializedness
  явно описаны. Произвольный RAII-dealloc suspect pointers не является безопасной
  универсальной заменой. DoubleFreeOk по-прежнему требует соблюдения unsafe
  предусловия; он не является runtime-проверкой способности аллокатора.

## Предлагаемый порядок

1. Привязать release к обязательным результатам нового workflow и добавить
   adversarial realloc с позиционно различимыми данными.
2. Исправить неточности документации.
3. Снизить резерв модели до peak-live и убрать векторы alignment.
4. Измерить аллокации стратегии и большие live-set сценарии; только затем
   выбирать замену boxing и линейного overlap scan.

Числа времени, процентов ускорения и сокращения машинных инструкций здесь
не заявлены: вычислительная сложность доказана по коду, wall-clock эффект
предложений ещё требует отдельного измерения.
