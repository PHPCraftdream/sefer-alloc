## Находки

### P2-1 — BLOCKER: контракт выравнивания путает делимость stride с выравниванием адреса

**Где:**

- `crates/size-classes/src/lib.rs:4-10` — обещание classifier, который «honours alignment»;
- `crates/size-classes/src/lib.rs:575-584` — fit predicate и объяснение через `max_class`-aligned span;
- те же обещания в `crates/size-classes/README.md` и package description.

Документированный predicate:

```text
block_size >= max(size, align)
block_size % align == 0
```

достаточен для выбора stride, но сам по себе не гарантирует выравнивание адресов. Для блока `n`:

```text
address(n) = base + n * block_size
```

Если `block_size % align == 0`, то:

```text
address(n) % align == base % align
```

То есть stride лишь **сохраняет** выравнивание базы. Он не исправляет неверно выровненную базу. Например, при базе `0x...0080`, `align = 512` и `block_size = 512` все адреса блоков останутся равны `128 mod 512`.

Фраза о «natural offset within a `max_class`-aligned span» проблему не закрывает: generic `max_class` не обязан быть степенью двойки или кратным каждому допустимому `align`. В используемой SEFER-схеме геометрический максимум до extras равен 258752 и не кратен 512. Само понятие адресного alignment также обычно требует степень двойки, тогда как максимальный класс arbitrary-схемы может ею не быть.

**Почему это существенно:** крейт позиционируется как строительный блок аллокатора. Интегратор может принять заявленную alignment-гарантию буквально и вернуть указатель, нарушающий `Layout::align()`. В Rust allocator-контексте это уже не просто неоптимальный выбор класса: downstream-код вправе полагаться на правильное выравнивание.

**Почему текущий `sefer-alloc` не сломан:** его small segments резервируются с базой, выровненной на `SEGMENT = 4 MiB` (`src/alloc_core/os.rs:65,152,207` и NUMA-аналог). Поддерживаемые small-path power-of-two alignments делят 4 MiB, поэтому интеграция удовлетворяет неявному предусловию. Гарантию предоставляет потребитель, не `size-classes`.

**Рекомендуемое исправление без сохранения обратной совместимости:** сделать семантику явной в API до публикации.

Предпочтительный минимальный контракт:

1. назвать результат `class_for` выбором размера/stride, а не самодостаточной гарантией адресного alignment;
2. документировать обязательное предусловие: `base % align == 0` для каждого запроса, либо более сильный инвариант arena/slab — базовый адрес выровнен на общий alignment, кратный всем обслуживаемым alignment;
3. переписать объяснение fit predicate как: делимость `block_size` гарантирует, что **при правильно выровненной базе** выровненными будут все блоки;
4. синхронно исправить crate docs, README и package description;
5. добавить compile-time policy, если нужна самопроверяемая гарантия: например, хранить `base_align` в `Params`, требовать power-of-two и возвращать `None`, когда `align > base_align` или `base_align % align != 0`.

Вариант с `base_align` сильнее и лучше соответствует цели «совершенство без боязни breaking changes»: он превращает скрытое внешнее предусловие в проверяемую часть схемы. Если крейт принципиально не должен знать адресную политику, минимальный документированный контракт тоже достаточен, но тогда маркетинговые формулировки должны строго говорить о stride/divisibility, а не об абсолютном выравнивании адреса.

### P3-1 — пример рекомендует `const` для большого значения, хотя нужен `static`

**Где:**

- `crates/size-classes/README.md:46` — `const SC: SizeClasses<...>`;
- `crates/size-classes/benches/size_classes_bench.rs:37` — `const SEFER_SC`;
- `crates/size-classes/src/lib.rs:468-472` — «intended use is a `const`/`static`».

Снятие `Copy` устраняет случайное value-копирование, но не меняет модель const items: `const` подставляется в место использования и для большой структуры с LUT может создавать дублирование данных/материализацию значения. Сам `sefer-alloc` уже осознанно держит экземпляр как `static SC`; комментарий в `src/alloc_core/size_classes.rs:175-194` прямо фиксирует защиту от `.rodata` duplication и `large_const_arrays`.

**Рекомендация:** в публичном README и benchmark использовать `static SC`, а rustdoc рекомендовать `static` для `SizeClasses`; `const` оставить для `Params`, таблицы и вычисляемых размеров либо для намеренно локальных маленьких схем. Это одновременно точнее обучает пользователя и делает benchmark ближе к production-размещению.

### P4-1 — документация standalone LUT ссылается на недоступный путь через `class_for`

**Где:** `crates/size-classes/src/lib.rs:355-363`.

`build_size2class` публично принимает hand-built table и корректно описывает возможность класса, недостижимого через bucket lookup. Но текст называет это недостижимостью через `class_for`, тогда как публичного конструктора `SizeClasses` из arbitrary table/LUT нет: поля приватны, а `SizeClasses::build` всегда вызывает `build_table`, чьи классы кратны `min_block`.

**Рекомендация:** заменить ссылку на «documented bucket lookup / direct LUT lookup». Если поддержка `class_for` поверх hand-built table является реальной целью API, добавить проверяемый `from_parts`/builder; сейчас документация связывает две публичные части сильнее, чем позволяет API.

### P4-2 — generic-документация выдаёт SEFER-специфичную границу `512` за универсальную

**Где:** `Cargo.toml:7`, `README.md:20-22`, `src/lib.rs:26-28`, `CHANGELOG.md:62-65`.

У arbitrary-схемы нет универсальной границы `align >= 512`: она зависит от `min_block`, набора классов и consumer policy. Число 512 корректно как история мотивирующего бага SEFER, но не как свойство generic classifier.

**Рекомендация:** явно назвать это примером из motivating allocator («в исходной SEFER-схеме eligible requests с align >= 512…») либо убрать число из краткого package description. Это особенно важно рядом с P2-1: package metadata должна обещать ровно ту гарантию, которую API способен обеспечить.

### P4-3 — доказательство widened arithmetic стоит сделать машинно явным

**Где:** `crates/size-classes/src/lib.rs:270-288`.

На текущих Rust targets (`usize <= 64`) выражения в `u128` безопасны: произведение двух `usize` помещается в `u128`, а доступный запас до `u128::MAX` достаточен и для последующего `+ mask`. Текущий комментарий, однако, доказывает только произведение; addition остаётся неочевидной частью ручного доказательства, а код не самодокументируется для гипотетической 128-bit pointer width.

**Рекомендация:** поскольку это builder/const-eval, а не query hot path, использовать `checked_mul` и `checked_add` в `u128` с точными panic messages либо дописать полный bound. Практического ускорения здесь не требуется; цель — убрать скрытую зависимость proof от pointer width.

## Общая оценка реализации

### Корректность и API

- `build_table` валидирует power-of-two `min_block`, denominator, длину, порядок/кратность extras, дубликаты и арифметический выход за `usize`.
- Sorted merge корректно поддерживает extras до, внутри и после геометрической последовательности.
- `build_size2class` строится линейным monotone-pointer проходом, проверяет строгую монотонность и теперь корректно поддерживает полный диапазон 256 `u8`-индексов.
- `class_for` корректно выбирает минимальный подходящий класс относительно своего stride predicate. Jump slow path монотонно продвигается, защищён от wrap при вычислении следующего кратного и эквивалентен линейному поиску по таблице.
- `align` как power-of-two — явное предусловие с `debug_assert!`. Это оправдано для hot path при использовании `Layout`, хотя public API сознательно даёт неверный результат для release-mode нарушения контракта.
- `size == 0` не является заявленным входом; при корректном `align >= 1` фактическая арифметика остаётся определённой через `need = max(size, align)`.
- `SizeClasses` не `Copy`, поля приватны, mutation API отсутствует; после построения инварианты нельзя разрушить safe-кодом.

### Производительность

- Query fast path — одна LUT-индексация и несколько scalar операций.
- Для большого alignment jump path перескакивает заведомо неподходящие диапазоны через ту же LUT; деление заменено корректной power-of-two mask-проверкой.
- Builder выполняется в `const`-контексте или однократно; `u128` не находится на основном пути запросов.
- Production-зависимостей, аллокаций, виртуальных вызовов и синхронизации нет.
- Новых алгоритмических возможностей ускорения hot path не найдено. Наиболее практичное performance-улучшение — P3-1 (`static` вместо публично рекомендуемого большого `const`).
