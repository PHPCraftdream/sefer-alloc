## 3. Новые находки

### P3

**F1 — комментарий extreme64-теста содержит фактически неверное утверждение о const-eval overflow, прямо противоречащее двум соседним комментариям того же крейта; из него выведено неверное «no test can fail against it there».**
Где: `tests/builder.rs:499-511` (тест `build_size2class_bucket_need_overflow_clamps_to_last_class`, добавлен run-2 фиксом `e6ed779`).
Комментарий утверждает: «Release const-eval wraps too (const-eval overflow checks follow the profile for const-fn bodies, unlike literal expressions such as `const X: u8 = 255 + 1`, which error in every profile)» — и на этом основании заключает, что при откате клампа под `--release` «no test can fail against it there» (:499-500).
Это противоречит двум другим комментариям ЭТОГО ЖЕ крейта, написанным раньше и корректным: `tests/builder.rs:399-401` («`const` evaluation already traps on overflow regardless of profile») и `src/lib.rs:322-327` (#701: «in `const` context this was ALREADY a hard compile error either way (const-eval traps on overflow regardless of profile)»). Одна из двух версий обязана быть ложной — противоречие файлово-локально и проверяемо чтением.
По существу права СТАРАЯ версия: CTFE в rustc всегда проверяет overflow независимо от профиля — интерпретатор const-eval принудительно чтит Assert-терминаторы overflow-класса, которые codegen выбрасывает при выключенных overflow-checks (машинный хук CTFE вида `ignore_optional_overflow_checks → false`, «for CTFE we can neither optimize nor get rid of overflow checks»); детерминизм const-значений между профилями — публично заявленное свойство const-eval. Следствие: при откате клампа `const EXTREME64_SC` — это E0080 и в release тоже, т.е. `cargo test -p size-classes --all-features --release` (CI-строка :1851) падает НА КОМПИЛЯЦИИ — откат ловится и в release, лучше, чем тест сам о себе заявляет. Ошибка «в безопасную сторону» (занижение покрытия), но: (a) она уже ввела в заблуждение run 3, который дословно завизировал «в release наблюдаемо эквивалентен» (§1 F1 отчёта 1510); (b) будущий автор overflow-тестов, поверив ей, станет городить лишние runtime-обходы там, где const уже даёт гарантию. Runtime-половина анализа комментария (release-wrap на `extreme64_scheme_runtime()`-пути и его наблюдаемая эквивалентность для Params-схем) — корректна и остаётся в силе; третий тест (hand-built, release-flip) этим не задет вовсе.
Фикс: поправить оба предложения комментария (:499-500 и :507-511), приведя их в согласие с `builder.rs:399-401`/`lib.rs:324-326`; исполнителю фикса — 2-минутная эмпирическая проверка направления (release-сборка трёхстрочного `const` c переполняющимся `const fn`), поскольку данный аудит read-only и семантику rustc цитирует по знанию, не по прогону.

### P4

**F2 — третий заход того же класса формулировки: два doc-места lib.rs всё ещё описывают паники как const-only.**
Где: `lib.rs:83-88` (`Params::extras` field doc: «...is a `const`-evaluation panic (compile error) in `build_table`») и `lib.rs:546-548` (`SizeClasses::build`: «a mismatch is a `const`-evaluation panic (compile error)»).
Оба SUT — `pub const fn`, вызываемые и в runtime (extreme64-модуль вызывает `SizeClasses::build` в runtime буквально в этом же репозитории — `extreme64_scheme_runtime()`), где та же проверка — runtime-паника. Ровно то занижение, которое run-2 F7 починил в трёх `# Panics`-заголовках, а run-3 F4 — в README/CHANGELOG; каждый раз правились только НАЙДЕННЫЕ места. Рекомендация: закрыть классом, а не точкой — `grep -n "compile error" crates/size-classes/src/lib.rs` (сейчас ровно два содержательных попадания: :548 и внутри :83-88; :324 — корректное историческое) и привести оба к формуле «identically in `const` evaluation (compile error) and at runtime».

**F3 — публичная `SegmentLayout::class_for` не документирует pow2-precondition; после P-1 non-pow2 там впервые может дать false-accept; плюс два устаревших предложения в шиме.**
Где: `src/alloc_core/segment_layout.rs:75-83` (реэкспортирована как public API в `src/lib.rs:411`), `src/alloc_core/size_classes.rs:212-213`.
(a) Док `SegmentLayout::class_for` называет контракт `size >= MIN_BLOCK`, но НЕ pow2-требование к `align` и не упоминает debug_assert (недокументированная debug-паника публичной safe fn). До P-1 slow path с non-pow2 `align` в release мог только overshoot'ить/вернуть ложный `None`; после P-1 добавился false-accept (класс, НЕ кратный `align`) — крейт это задокументировал (run-3 F2), публичная поверхность потребителя — нет. Не soundness-дыра (чистая арифметика, никаких записей метаданных), но контрактная рассинхронизация crate↔public-shim. (b) Парентетика «This is the O(1) lookup (`SIZE2CLASS[(size-1) >> MIN_BLOCK_SHIFT]`)» описывает только fast path, тогда как форвардится полный классификатор с jump-веткой. (c) `size_classes.rs:212-213`: «clamped ... by the only caller (`AllocCore::alloc`)» устарело — вызывающих минимум четыре (`alloc`, `alloc_zeroed`, `:1901`, realloc-пара `:2252-2253`, diag `:648`); все клампят, инвариант жив, но цитата каллера ложна. Фикс — три предложения документации.

**F4 — `.rodata`-дубликат lookup-таблицы в шиме: `static SIZE2CLASS` + копия внутри `static SC`.**
Где: `src/alloc_core/size_classes.rs:176-177` и `:188`.
`SC` (инстанс крейтового `SizeClasses`) по конструкции ВСТРАИВАЕТ собственные копии `table` и `size2class`; рядом шим держит отдельный `static SIZE2CLASS` (единственный потребитель — реэкспорт `SegmentLayout::SIZE2CLASS`, тестовая поверхность) и `const SIZE_CLASS_TABLE`. Итог: два идентичных экземпляра `[u8; S2C_LEN]` в бинаре — ~16 173 B в дефолтной сборке, ~64 KiB× 2 под `medium-classes` (L = 65 537), ~112 KiB×2 под `medium-classes-wide` (L = 114 689). Комментарии шима аккуратно закрывают смежный класс (`clippy::large_const_arrays`, дублирование ПО ССЫЛКАМ), но межстатичный дубликат остаётся. Дрейфа нет (обе копии const-выведены из одних PARAMS) — цена только в размере бинаря. Варианты: превратить `SegmentLayout::SIZE2CLASS` из `pub const` в `pub fn size2class() -> &'static [u8]`, читающий `SC.size2class()` (семвер-факт для тестовой поверхности), либо принять и задокументировать цену на месте. Не срочно.

## 4. Ответ на вопрос кампании

**Готов ли крейт к публикации?** Да — **GO**, четвёртый цикл подряд без P0-P2, и первый, где насквозь проверен реальный production-потребитель: цепочка crate → shim → `classify`/realloc → `Layout`-домен корректна и контрактно замкнута. Оба свежих фикса чисты и новых дефектов в КОД не внесли; единственная P3 — комментарий теста (внесён run-2 фиксом `e6ed779`, пропущен run 3), правится двумя предложениями. P4 — по желанию, до или после релиза.

Границы уверенности: аудит статический, read-only; F1 опирается на знание семантики rustc CTFE (не на прогон) — противоречие комментариев файлово-доказуемо в любом случае, направление разрешения рекомендовано подтвердить 2-минутной сборкой при фиксе. Зелёность CI-гейтов на HEAD должна подтверждаться самим CI.
