### 1.2 R18-3 (`912740f`, task #330) — the one code change, and its actual scope

`src/registry/heap_core_free.rs` branch (A)'s `#[cfg]` is narrowed from bare
`medium-classes` to the exact promotion predicate (`medium-classes &&
(!exact-span-large || (large-reserved-capacity && !numa-aware))`), and a
runtime gate `cfg!(feature = "hardened") || layout.size() >=
MEDIUM_REALLOC_PROMOTION_THRESHOLD` is added before the `kind_at` read.

- **Under plain `production`:** branch (A) never compiled before this change
  and still never compiles after it — **zero effect**, confirmed by the
  commit's own iai numbers: `small_churn_16b 8,051 Ir`, `large_alloc_free_cycle
  3,308 Ir` — "byte-identical to the pre-R18-3 baseline."
- **Under opt-in `production,medium-classes`:** branch (A) DID already compile
  in (via R17-4), and unconditionally read `SegmentHeader::kind_at(base)` on
  *every* small-classified free, including tiny 16/32/64 B frees that
  structurally cannot reach the promotion path. R18-3 adds a size gate so
  those sub-256-KiB frees skip the `kind_at` load. This is a real,
  well-reasoned micro-optimization, but it is scoped to an opt-in feature
  combination the project does not ship by default, and **no A/B delta is
  reported** — the commit records `medium_class_dealloc_churn_16b: 8,275 Ir`
  as "the FIRST established baseline for this configuration," not a
  before/after comparison. I cannot independently confirm the size of this
  win from what is committed; only that a real unconditional load was removed
  for the common case (sub-threshold sizes) under this opt-in build.
- **Under `hardened`:** the size gate is deliberately bypassed
  (`cfg!(feature = "hardened") || ...`), so `hardened` builds pay the
  unconditional check. This is a correctness requirement, not a missed
  optimization — see §3.1 below for the soundness check.

**Verdict on R18-3: sound, narrowly-scoped correctness/cfg-hygiene fix with a
plausible but unmeasured micro-optimization for one opt-in build; zero effect
on `production`.**

## 3. What needs improving in the code?

### 3.1 R18-3's `hardened`-bypass soundness — I agree it is necessary and correctly placed

I read the diff and the regression test independently
(`tests/regression_hardened_large_kind_own_free.rs`). The test frees a 2 MiB
Large allocation via a 64-byte layout (`LARGE_SIZE = 2 * 1024 * 1024`,
`small_layout = Layout::from_size_align(64, 8)`) under `--features "...
hardened"`. Since `64 < MEDIUM_REALLOC_PROMOTION_THRESHOLD (256 * 1024)`, a
naive unconditional size gate (`layout.size() >= THRESHOLD` with no
`hardened` bypass) would skip the `kind_at` check for this test's exact
scenario, letting the mismatched free alias into the small magazine — this
is precisely the counterfactual the commit message claims and the test is
built to catch it. **The placement of `cfg!(feature = "hardened") || ...`
is correct**: the soundness argument for skipping `kind_at` below the
threshold ("a legitimate promoted Large block's dealloc layout is always ≥
threshold") only holds for a *contract-compliant* caller; `hardened` exists
specifically to catch contract *violations*, which by definition can present
any layout size, so the size-based shortcut must not apply there. This is
sound reasoning, correctly implemented, and non-vacuously tested.

I also traced branch (A)'s new `#[cfg]` against the pre-existing
`MEDIUM_REALLOC_PROMOTION_THRESHOLD` const's own `#[cfg]` at
`src/registry/heap_core_free.rs:68-74` (established by R15-3, task #305,
predating this round) — the two predicates are textually identical
character-for-character. This is good hygiene: the promotion-reachability
predicate now has exactly one canonical shape reused at three sites (the
const's gate, branch (A)'s gate, and the call site further down), rather
than three independently-drifting copies.

### 3.3 `tests/race_repro.rs` watchdog (R18-1, `dc95d1a`) — sound, one design note

I read the full 524-line file. The mechanism:
- `exit(124)` replaces `abort()`, with a clear rationale (Windows/MSVC
  `abort()` → `__fastfail` → `STATUS_STACK_BUFFER_OVERRUN`, i.e. exactly the
  crash signature two prior "unexplained" incidents showed) — this
  reasoning is disclosed as INFERRED, not OBSERVED, and the file's own header
  is careful to say so explicitly (a rare and good practice — most write-ups
  would state this as fact).
- `RACE_REPRO_DEADLINE_SECS` overrides `DEADLINE_SECS` via `deadline_secs()`
  (lines 142-148), parsed with `.filter(|&n| n > 0)` — guards against a `0`
  or negative override silently making the watchdog fire immediately or
  never; reasonable.
- `Watchdog::drop` (lines 193-215) now joins the watcher thread and surfaces
  a panic payload via `eprintln!` instead of swallowing it silently — a real
  improvement; previously a panicking watchdog thread would have been
  invisible.
- Because `Watchdog::drop` runs on unwind as well as normal return, a test
  panic (not just success) still correctly signals `done` and joins the
  watcher — I did not find a leak/hang path here.

One residual design point, not a bug: the watchdog is a *last-resort*
diagnostic distinguisher, not a fix for the underlying "why does this
occasionally take >20s under heavy load" question — the file itself is
explicit about this (the header's own "Refutation test NOT performed"
paragraph). This is honest scoping, not an omission I am flagging as
incomplete work — the task was specifically to make the failure mode
identifiable, and it is now identifiable (nonzero exit 124 vs. a signal/
`__fastfail` crash), which is what was asked.
