## P2-1. Linux: выход главного потока лишает живой процесс метрик

Место: `src/lib.rs:260`, `:263`, `:240`.

`/proc/self` разрешается в TGID — идентификатор лидера группы, не TID
вызывающего worker. Это видно в [Linux proc_self_get_link](https://raw.githubusercontent.com/torvalds/linux/v6.12/fs/proc/self.c).
Главный поток POSIX-программы вправе завершиться через `pthread_exit`, оставив
остальные потоки работающими; для Rust-крейта это в том числе корректный сценарий
использования из многопоточного native host. Это не завершение всего процесса
через `exit`. Такое использование прямо описано в [pthread_exit(3)](https://man7.org/linux/man-pages/man3/pthread_exit.3.html).

Цепочка отказа:

1. Лидер завершает поток. Linux `exit_mm` очищает его `task->mm`, хотя другие
   потоки ещё удерживают общее адресное пространство. См. [kernel/exit.c](https://raw.githubusercontent.com/torvalds/linux/master/kernel/exit.c).
2. Worker вызывает `try_snapshot()`. Крейт читает status именно лидера.
3. `proc_pid_status` получает `get_task_mm(task)` и печатает `task_mem` только
   при ненулевом mm. Файл существует, но в нём нет `VmRSS`/`VmSize`/`VmHWM`.
   См. [proc_pid_status](https://raw.githubusercontent.com/torvalds/linux/master/fs/proc/array.c)
   и [get_task_mm](https://raw.githubusercontent.com/torvalds/linux/master/kernel/fork.c).
4. Строка 263 возвращает `Malformed`, а `snapshot()` превращает его в default.
   Живой процесс с реальной памятью выглядит неизмеримым или освободившим всё.

Это обычное состояние настоящего ядра, не поддельный procfs и не требование
поддержать повреждённый файл. Повторное чтение того же leader status проблему
не исправляет. В первом раунде этот сценарий не был замечен; исходный выбор пути
предшествует текущей волне, а новый fallible API дополнительно называет его
ошибкой формата.

Направление исправления: получать общие memory-поля из status живого вызывающего
task, например через `/proc/<tid>/status`. Кандидат без явного формирования TID —
`/proc/thread-self/status`; его доступность после выхода лидера следует отдельно
закрепить на поддерживаемых ядрах, а не предполагать по имени: symlink ведёт
через `<tgid>/task/<tid>`. См. [реализацию thread-self](https://raw.githubusercontent.com/torvalds/linux/v6.12/fs/proc/thread_self.c)
и [документацию thread directories](https://man7.org/linux/man-pages/man5/proc_pid_task.5.html).
Не суммировать RSS по потокам: они разделяют mm, и такое суммирование умножит память.

Нужен изолированный Linux lifecycle-сценарий: leader завершился, worker после
этого успешно читает память. Продумать нативную границу fixture, не проводить
`pthread_exit` через произвольные Rust frames. **Сам сценарий здесь не запускался**;
основание находки — приведённая цепочка в коде ядра и крейта.

## P3-1. Bytes parser принимает числовой префикс вместо целого значения

Места: `src/status_parse.rs:116`, `:124`, `:129`; `src/lib.rs:176`, `:263`.

`field_value` находит первую цифру, проверяет пробелы перед ней, затем отрезает
всё начиная с первого нецифрового байта. Ни граница числового токена, ни единица
измерения после него не проверяются. Поэтому по текущему коду:

| Строка | Результат `read_kib_field` |
| --- | --- |
| `VmRSS: 12oops kB` | `Some(12)` |
| `VmRSS: 12.5 kB` | `Some(12)` |
| `VmRSS: 1e6 kB` | `Some(1)` |
| `VmRSS: 12 MB` | `Some(12)`, затем трактуется как KiB |

Это расходится с «plain ASCII integer» в parser docs и описанием `Malformed`.
Прежний `split_whitespace().next()?.parse::<u64>()` хотя бы отвергал `12oops`,
`12.5` и `1e6`; новая реализация стала более разрешительной именно на этой границе.
Тест `malformed_values_are_none_rather_than_a_guess` проверяет только отсутствие
цифр и мусор ДО них, поэтому регрессия проходит незамеченной.

Исправление: определить грамматику `ASCII whitespace + unsigned integer +
ASCII whitespace + kB + trailing whitespace` и отвергать нарушение целиком.
Если отсутствие единицы намеренно разрешено, зафиксировать это отдельно; неверную
единицу нельзя молча интерпретировать как KiB. Добавить suffix/unit fixtures.

Калибровка: штатный Linux печатает здесь целые kB, поэтому это P3 — дефект
валидации и обещанного error-контракта, а не заявление, что обычное ядро выдаёт
дробный RSS, и не удалённая уязвимость.

## P3-2. Новый scale oracle всё ещё не доказывает множитель 1024

Места: `tests/platform_contract.rs:135`, `:176`, `:196`, `:308`, `:376`.

Широкая полоса между двумя живыми чтениями — разумная smoke-проверка порядка
величины, но не точный oracle преобразования. Конкретные контрпримеры:

- Для `kb=4096` значение `4096*2048` проходит кратность 4096, `actual > kb` и
  полосу `kb*64 ..= kb*16384`. Замена backend-множителя 1024 на 2048 не ловится
  при сопоставимых соседних readings. Ошибка двукратная, а не шум округления.
- Для `kb=4096` также проходит `4096*1000=4_096_000`: оно кратно 4096 и внутри
  полосы. Вообще x1000 проходит гранулярность при `kb`, кратном 512, — это вполне
  допустимые размеры. Поэтому утверждение, что leg 1 ловит x1000, не универсально.
- Negative control для x1000 берёт `kb=12_345`, не кратный даже 4 KiB-странице
  в KiB. На этом же входе oracle отверг бы и правильное `12_345*1024`.
  Такой пример особенно плохо подтверждает защиту для реальных page-granular данных.

Решение: вынести production-преобразование `status bytes -> Result<MemStat, ...>`
в закрытый тестируемый seam и проверять точные значения из одного immutable fixture,
включая разные числа во всех полях и границы преобразования. Не копировать
множитель в тестируемый дубль функции. Живую проверку оставить availability/smoke,
без обещания точности, которого её допуск не обеспечивает.

Тесты с `#[path]` и без расширения public API для этого подходят. Возвращать
прежний ±25% допуск не предлагаю: два чтения процесса действительно не обязаны
показывать одинаковое VmSize. Простое увеличение допуска лечит конкретное
падение, но не заменяет детерминированный тест конверсии.

## P3-3. Защита от возврата UTF-8 бага и error-контракт проверяются в обход нужного пути

Места: `tests/status_parse.rs:52`, `:57`, `:66`; `tests/fallible_api.rs:47`;
`src/lib.rs:260`, `:263`, `:319`, `:410`.

Тест `the_utf8_route_this_parser_replaced_would_still_lose_every_field` утверждает
в комментарии, что возврат к `read_to_string` не сможет пройти suite. Но он
проверяет `String::from_utf8` над собственным fixture и отдельно вызывает parser;
производственный reader в проверке не участвует.

Контрфактическая регрессия: вернуть в Linux backend чтение через `read_to_string`,
передать его `.as_bytes()` тому же parser, больше ничего не менять. На обычном
ASCII-имени test binary живые tests проходят; fixture tests по-прежнему напрямую
кормят parser байтами. Старый реальный баг вернулся, заявленный guard зелёный.

Аналогичный пробел у `try_snapshot`: `Os`/`Malformed` создаются в tests как значения
enum для проверки Display, но отказ reader/OS и malformed RSS не проходят через
настоящую обработку ошибки. Мутация `Err(Os)` в `Err(Malformed)` в backend не
проверяется happy-path тестом поддерживаемой платформы. `snapshot_is_try_snapshot...`
к тому же сопоставляет ДВА вызова: успешность одного не доказывает успешность другого.

Исправление: один проверяемый путь приобретения bytes, разбора и выдачи
`MemStat`/ошибки, с управляемыми результатами чтения в тестах; отдельно Linux
subprocess с не-UTF-8 именем task, чей status выбран backend. Для wrapper проверять
`Ok`, `Os`, `Malformed`, `Unsupported` по одному заранее заданному результату,
не выводить причинную связь из двух последовательных обращений к ОС.
Текущие pure parser fixtures полезны — их не нужно удалять или объявлять бесполезными.

## Неблокирующие замечания P4

### P4-1. Checked parsing заканчивается до потенциально переполняющего преобразования

Места: `src/lib.rs:265`, `:266`, `:270`; `src/status_parse.rs:145`.

`u64` decimal parser отказывает при переполнении, но последующее `kib * 1024`
не проверено. `18_014_398_509_481_984` KiB (=2^54) успешно разбирается как u64,
а преобразование в bytes даёт 2^64: panic при overflow checks либо wrap в 0 без них.

Это **защитное усиление**, не доказанный достижимый размер памяти обычного
Linux-процесса. Не повышаю до release blocker и не называю remote DoS.
При строгом malformed-input контракте дешевле замкнуть всю конверсию через
`checked_mul(1024)` и fixtures `u64::MAX/1024`, затем следующее значение,
чем оставлять разные отказы на двух последовательных числовых границах.

### P4-2. SAFETY у cached Mach port неполно описывает момент записи

Место: `src/lib.rs:381`.

Комментарий утверждает, что значение записывается только при
`libSystem_initializer`, до любого user code. Apple также вызывает
`mach_init_doit()` из `_mach_fork_child()`: это повторная инициализация в child
после fork. См. [Apple mach_init.c](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/libsyscall/mach/mach_init.c).

Сам getter по-прежнему выглядит корректным: читать cached port по значению
не означает приобретать или освобождать send right. Исправить именно доказательство:
startup плюс однопоточная child-side реинициализация до возврата к обычному
исполнению. Из отсутствующего упоминания fork не следует найденная data race.

### P4-3. «Непаникующий» Drop всё ещё содержит паникующую диагностику

Место: `tests/monotonicity.rs:168`, `:176`.

При ошибке VirtualFree guard вызывает `eprintln!`. Rust документирует panic
этого макроса при ошибке записи stderr. См. [eprintln! — Panics](https://doc.rust-lang.org/std/macro.eprintln.html#panics).
При уже идущем unwind это может скрыть исходную assertion failure за abort.

Калибровка: нужны одновременно неуспешное освобождение и неисправный вывод;
это аварийный путь тестового fixture, не нормальный путь библиотеки.
Убрать диагностику из fallback Drop либо использовать явно не паникующую запись
фиксированного сообщения с обработкой ошибки. Happy-path проверку VirtualFree
сохранить. Само введение RAII и процессной изоляции — правильное исправление.

### P4-4. Fused helper обещает эквивалентность для более широких входов, чем поддерживает

Места: `src/status_parse.rs:50`, `:80`, `:107`.

Для status `VmRSS: 7 kB` и prefixes `[b"VmRSS:", b"VmRSS:"]` два независимых
поиска дают `[Some(7), Some(7)]`, fused — `[Some(7), None]`: после первого
совпадения срабатывает `break`. Аналогичное ограничение возникает у перекрывающихся
префиксов. Фраза «a line matches at most one prefix» не обеспечивается сигнатурой
и не задана как предусловие.

Текущие три `FIELDS` уникальны и не перекрываются; production вообще не вызывает
fused helper. Поэтому это не порча текущих метрик и не опровержение уже записанного
эксперимента. Достаточно сузить helper до конкретных трёх ключей либо явно задать
предусловие, или действительно сохранить общую эквивалентность и добавить fixture.
Отвергнутый кандидат удобнее хранить у benchmark/test support: тогда он не требует
`allow(dead_code)` в production parser и не выглядит недоделанной функцией backend.

### P4-5. Измерение полезно, но не подтверждает несколько сопровождающих формулировок

Места: `examples/status_scan_cost.rs:89`, `:138`, `:198`;
`docs/perf/PROC_MEMSTAT_P4_2_SCAN_COST_summary.csv`.

Прочитаны сохранённые raw log и CSV. Результат не перемерялся. Оставить простой
reader при малой ожидаемой экономии — разумное решение. Ограничения свидетельства:

- Измерены две parse-only петли и отдельно прежний полный `snapshot()`, а не
  два полных backend A/B. `saved_parse / old_snapshot` — оценка доли устранимой
  работы, не измеренное ускорение нового `snapshot()`. В одной петле участвует
  импортированный через `#[path]` parser, в denominator — библиотечная функция.
- В CSV `samples=200000/20000` означает число итераций одного timed batch,
  не независимые timing samples. Порядок arms фиксирован; разброс внутри run
  и неопределённость оценки не записаны. Assert в строке 199 заново вычисляет
  ту же формулу из тех же переменных — не проверяет ни вывод, ни перенос в CSV.
- Последняя CSV-строка говорит «the parse is 2.0%». По её же данным полный
  three-scan parse — примерно 3.17% (`543.2 / 17125.3`), а около 2.0% —
  **экономия** (`335.8 / 17125.3`). Эти величины не взаимозаменяемы.

Не нужен новый большой performance-проект ради этого замечания. Достаточно
обозначить результат как оценку, назвать iterations правильно и исправить
parse-share / saved-share. При возвращении к вопросу ускорения — парные полные

## Безопасность, сложность и возможности ускорения — общий итог

- **Windows FFI:** форма PROCESS_MEMORY_COUNTERS соответствует SDK — два u32 и
  восемь SIZE_T, 40 bytes на 32-bit / 72 на 64-bit; cb заполняется, BOOL проверяется,
  поля читаются только при успехе. PagefileUsage действительно commit charge.
  Источник: [Microsoft PROCESS_MEMORY_COUNTERS](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters).
- **macOS FFI:** MachTaskBasicInfo имеет правильные поля и offsets, размер 48 bytes,
  count 12 четырёхбайтовых единиц; более сильное выравнивание Rust-буфера не меняет
  эти offsets. Неверной ссылки на function symbol больше нет. Источник структуры:
  [Apple task_info.h](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/osfmk/mach/task_info.h).
  Native linking в этом проходе не выполнялся.
- **Linux:** bytes/ASCII разделены правильно, digit accumulation checked,
  индексы срезов выводятся из их же границ; нового OOB/UB здесь не найдено.
  Три поиска — O(L), не O(L²); размер временного Vec — O(L), результат MemStat —
  фиксированный Copy value без heap-владения. Лишних глубоких clone на runtime
  пути нет. Fused helper с переменным N не имеет независимой от N сложности,
  но в его единственном измеряемом случае N фиксировано и равно трём.
- **Главный ещё не измеренный ресурсный кандидат:** убрать свежий heap buffer
  на Linux, если крейт нужен для частых чтений или около allocator hook.
  Решение NO-GO по объединению поисков этого не исследовало. Возможны caller-owned
  scratch и потоковый ASCII parser с O(1) временной памятью и O(L) чтением.
  Нельзя молча обрезать status первыми 4/8 KiB; нужно проходить длинные ненужные
  строки и корректно переносить границы значимых строк между chunks.
- **Не оптимизировать наугад:** не кэшировать открытый `/proc` fd без решения
  lifetime/fork-привязки к конкретному task; не добавлять тяжёлую dependency ради
  трёх ключей; не менять backend на smaps/getrusage, не определив другую семантику,
  точность и стоимость. Запрос на ускорение не оправдывает ухудшение измерения.
- **CI:** собственные three-OS gates теперь есть. Отдельного member MSRV/Miri
  прогона новая job не добавляет; это оставшаяся граница покрытия, не обнаруженный
  compile defect. Miri с нынешним cfg проверит parser/stub, но не native FFI.
