## Подтверждённые находки

### R5-01 — P2: обычный межпоточный drop теряет освобождение при alloc-global без alloc-xthread

Адреса: src/global/sefer_alloc/global_alloc.rs:129–153; src/registry/heap_core/free/dealloc.rs:219–230; src/alloc_core/alloc_core/mem/mem_impl.rs:188–203. Feature-граф: Cargo.toml:199 (alloc-global не включает alloc-xthread), Cargo.toml:427 (production включает оба).

Достижимый сценарий: приложение устанавливает SeferAlloc как глобальный аллокатор с одним лишь feature alloc-global. Поток A создаёт Box/Vec и передаёт владение потоку B; B штатно уничтожает значение. На B GlobalAlloc::dealloc получает его собственный HeapCore, cfg-ветка без alloc-xthread вызывает dealloc_own_thread, а AllocCore::dealloc видит отсутствующий в своей таблице base и немедленно возвращает управление. Это легальный безопасный Rust-код, а не неверный указатель или двойное освобождение. Тот же feature-режим возвращает null для realloc чужого сегмента (src/registry/heap_core/free/realloc.rs:448–452), поэтому рост переданного Vec может завершиться ошибкой выделения.

Последствие: блок остаётся логически живым для исходного heap, сегмент не возвращается в оборот; повторяющийся producer/consumer трафик накапливает память до OOM. Счётчик этой ветки увеличивается только с alloc-stats, поэтому обычная конфигурация не даёт обязательного сигнала. Ограничение описано в комментариях к API, но обычный публичный feature допускает этот режим GlobalAlloc.

Направление исправления: сделать alloc-global зависимым от alloc-xthread либо явно отделить/назвать однопоточный allocator-режим так, чтобы многопоточное применение не выглядело поддерживаемым; добавить узкий регрессионный сценарий передачи владения между потоками для минимального feature-набора. Пока — считать связку без alloc-xthread неподходящей для многопоточного использования.

### R5-02 — P3: публичный диагностический setter возвращает устаревшему handle доступ к новому значению

Адреса: src/concurrent/epoch/epoch_region.rs:627–630 (публичный метод без internals/bench-internals), src/concurrent/epoch/hand.rs:180–199 (проверяется только вакантность), src/concurrent/epoch/hand.rs:335–347 (install сохраняет generation), src/concurrent/epoch/hand.rs:395–403 (MAX не удаляется). Доступность типа при experimental: src/lib.rs:397–398,480–484.

Достижимый сценарий без unsafe: создать EpochRegion<i32> вместимостью 1, вставить значение и сохранить handle h, удалить h, вызвать _set_slot_generation_for_tests(0, 0) на вакантном слоте, вставить другое значение. Старый h снова совпадает по region/index/generation и get_cloned(h) читает уже другое значение; remove(h) удаляет его. Отдельно setter принимает u32::MAX: последующий insert выдаёт handle с MAX, который try_evict_at всегда отвергает, так что значение невозможно удалить обычным API. Название и документация объявляют метод тестовым, но он доступен как safe public API в обычной experimental-сборке.

Последствие: нарушение заявленной неизменной tombstone/no-ABA гарантии и возможная адресация/удаление чужого логического объекта; для MAX — неустранимое занятое место до уничтожения региона. Это не доказательство UB. Направление исправления: убрать мутацию из публичной experimental-поверхности (тестовый cfg/отдельный недоступный в обычной сборке канал); при сохранении публичного метода не разрешать откат generation и выдачу MAX, обновить тестовый контракт и проверить оба сценария.

### R5-03 — P4: переполнение вместимости LockFreeRegion проверяется после крупного резервирования

Адрес: src/concurrent/lock_free/lock_free_region.rs:238–257.

Достижимый сценарий при достаточной памяти для начального Vec::with_capacity: with_pages(67_108_864) проходит проверку page_count → u32, но произведение total_pages * 64 равно 2^32 и вычисляется без checked_mul уже при построении первой страницы. В debug это panic после крупного резервирования; в release произведение оборачивается в ноль, поэтому условие построения next_free работает неверно (если весь астрономический объём страниц удалось бы создать). На обычной машине OOM вероятнее этой дальнейшей ветки; это низкоприоритетная граничная ошибка, а не установленный практически достижимый путь повреждения памяти.

Направление исправления: один раз до Vec::with_capacity вычислить checked_mul(page_count, PAGE), потребовать индексируемую ёмкость не выше u32::MAX и использовать проверенный результат в цикле; проверить пограничные числа без выделения миллиардов слотов.

Итого: P0=0, P1=0, P2=1, P3=1, P4=1; всего 3 подтверждённые находки.

## Неподтверждённые риски и границы контракта

- src/concurrent/pinning.rs:122–141: конструкторы возвращают Some с нулём workers, если core_affinity::get_core_ids выдаст Some(empty). Возможность такого ответа на поддерживаемых платформах здесь не проверялась; без неё это не баг. При подтверждении лучше возвращать None.
- src/concurrent/epoch/epoch_region.rs:339–375,573–588: remote_free_pending использует Relaxed как hint перед mutex. Кодовое рассуждение покрывает гонки push/drain, но полный weak-memory/liveness вывод в этом статическом обзоре не доказан; нужен направленный loom-модельный тест, прежде чем утверждать потерю индекса.
- src/global/sefer_alloc/core.rs:94–107 явно исключает использование аллокатора в ребёнке после многопоточного fork до exec. Это ограничение поддержки, не новая подтверждённая уязвимость в заявленном контракте.
- Внешние unsafe-реализации aligned-vmem, once-ptr-cell, tagged-index-stack и numa-shim находятся вне запрошенной папки; их внутренняя корректность этим обзором не сертифицирована.

## Идеи для измеряемой оптимизации

- src/concurrent/lock_free/lock_free_region.rs:104–113,358–370,431–465: каждая запись копирует весь Vec указателей страниц snapshot, хотя копия данных ограничена одной страницей. Для больших регионов сравнить текущую O(число страниц) публикацию с более сегментированной/персистентной таблицей на репрезентативных write/read пропорциях; улучшение не утверждается без измерения.
- src/global/sefer_alloc/diag.rs:66–80 и src/registry/heap_registry/counters.rs:290–305: с alloc-stats каждый stats() обходит материализованные слоты для hit-сумм. Если scrape частый и слотов много, рассмотреть процессные агрегаты; сопоставить стоимость чтения со стоимостью дополнительных атомарных обновлений на alloc-hot-path.
- src/concurrent/epoch/epoch_region.rs:573–589: каждый удалённый evict блокирует общий Mutex<Vec<u32>> своей очереди. Для высокой доли remote removal сравнить пакетирование/ограниченную MPSC-очередь с нынешней реализацией, отдельно измерив конкуренцию, аллокации и задержку drain.

## Вердикт

NO-GO для безусловного утверждения, что вся доступная feature-матрица пригодна для многопоточного GlobalAlloc: режим alloc-global без alloc-xthread теряет корректные освобождения. Для production (где alloc-xthread включён) в просмотренных путях статически не найден блокирующий дефект, но это не положительный сертификат безопасности: исполнение, межпоточные расписания, ОС-ветви, extreme-size режимы и внешние unsafe-crates не проверялись. Никаких исходников и настроек этот обзор не меняет.
