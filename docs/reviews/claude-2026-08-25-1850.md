## 1. Findings

### F1 — **P2** — the crate's own recommended `std` mitigation, `panic = "abort"`, does **not** do what the sentence recommending it says it does: the panic runtime still allocates, and following the advice inside a `#[global_allocator]` converts a loud `assert!` into a silent self-deadlock

**Where:** `crates/racy-ptr-cell/src/lib.rs:127-136`;
`crates/racy-ptr-cell/README.md:78-85` (identical text).

The paragraph, verbatim (`src/lib.rs:131-136`):

> All three go through the panic runtime, **which allocates in a `std`
> build. Make them fatal instead** — and note these are **different
> mechanisms for different link environments, not two halves of one
> recipe**: a `std` binary sets `panic = "abort"` in its profile (the panic
> runtime belongs to `std`, so no crate can supply its own
> `#[panic_handler]` there); a `no_std` binary supplies a non-allocating
> `#[panic_handler]` itself.

The sentence names a hazard (**the panic runtime allocates**), issues an
imperative offered as the remedy for it (**"Make them fatal instead"**), and
then presents two per-environment mechanisms as parallel answers. The
`no_std` mechanism — a non-allocating `#[panic_handler]` — genuinely solves
the stated hazard. **The `std` mechanism does not.** `panic = "abort"`
changes what happens *after* `rust_panic_with_hook` returns; it does not
remove the hook, and the default hook allocates before it can print
anything (`std::io::stderr()` must construct its `LineWriter` buffer on
first use).

**Measured, not argued** (§0.2, probe A):

```
[profile.release] panic = "abort"
#[global_allocator] → std::process::exit(42) on any alloc after the panic began
$ ./panic-abort-probe.exe ; echo "EXIT CODE: $?"
EXIT CODE: 42
```

and, with a counting allocator, `RUST_BACKTRACE=0`, `--release`:

```
ALLOCATIONS DURING THE FIRST PANIC: 3
```

**Failure scenario.** A consumer does exactly what `src/lib.rs:133-135`
tells them: `[profile.release] panic = "abort"`. Their `init` panics — or the
release-active sentinel `assert!` at `:552-555` fires, which the crate
documents as a *supported, reachable-from-safe-code* path — while their
thread holds the `INITIALIZING` sentinel inside `GlobalAlloc::alloc`. Then:

1. `panic!` → `rust_panic_with_hook` → default hook → `std::io::stderr()`
   → heap allocation (measured above; 3 of them).
2. That allocation re-enters their `#[global_allocator]`, which reaches the
   same cell, fails the CAS at `:503`, and enters the loser spin at
   `:592-613`.
3. The sentinel it spins on is owned by **this very thread**, which is
   suspended inside the panic hook. Unrecoverable single-thread
   self-deadlock at 100 % CPU — structurally identical to the
   allocating-signal-handler case the crate now documents at `:116-121`.
4. `abort()` is never reached. The consumer was promised "fatal"; they get
   a hang.
5. The `assert!`'s diagnostic never reaches stderr either: the allocation
   that would have printed it *is* the one that deadlocked. The whole reason
   task #707 made this check release-active (`:533-551`: "with no diagnostic
   anywhere") is defeated in the exact configuration the crate recommends.

**Why this is worth a P2 rather than a shrug.** This is the third revision of
this same paragraph. Cycle-1 F1 (`870001e`) added the qualification; run-2 F1
(`ccee5cd`, task #1369) split the conflated `std`/`no_std` recipe and added
the `GlobalAlloc`-no-unwind rule; both revisions corrected the *taxonomy* of
the recipe and neither checked its *efficacy*. The result is a mitigation
that is correctly attributed to the right link environment and still does
not achieve the thing the preceding sentence asks for. That is the same
documentation-honesty shape the previous four reviews found, in the one
section this crate has now revised three times.

**Suggested fix (documentation only; no algorithm, no API change).** Say
what `panic = "abort"` does and does not buy, and give the `std` reader a
mitigation that actually closes the allocation hazard:

> `panic = "abort"` removes the *unwind* (which is the UB when the frame
> below is `GlobalAlloc::alloc`) — it does **not** stop the panic runtime
> from allocating: the default hook allocates before it prints (verified:
> 3 allocations on the first panic with `RUST_BACKTRACE=0`). Inside a
> `#[global_allocator]`, that allocation re-enters the very cell that is
> mid-`init` and the thread deadlocks on its own sentinel instead of
> aborting. A `std` consumer therefore needs `panic = "abort"` **and** a
> `std::panic::set_hook` that goes straight to `libc::_exit`/
> `std::process::abort()` without formatting — or, better, an `init` that
> cannot panic at all. Only the `no_std` recipe (a non-allocating
> `#[panic_handler]`) closes this on its own.

### F2 — **P2** — `--cfg loom` set anywhere in a downstream build silently makes `RacyPtrCell::new` non-`const`, breaking the crate's own documented headline usage; the README advertises the flag and never says so

**Where:** `crates/racy-ptr-cell/src/lib.rs:191-194` (the atomics alias),
`:350-352` vs `:374-376` (the two `new` bodies), `:337-338` (the only
mention of the consequence anywhere in the crate);
`crates/racy-ptr-cell/README.md:23-32` (the headline example) and `:98-111`
(where the flag is advertised, with the run command at `:110`).

**Reproduced, not inferred** (§0.2, probe C). A scratch consumer crate with
this crate's own README example:

```rust
pub static CHUNK: RacyPtrCell<Chunk> = RacyPtrCell::new();
```

```
$ RUSTFLAGS="--cfg loom" cargo build
error[E0015]: cannot call non-const associated function
              `RacyPtrCell::<Chunk>::new` in statics
 --> src\lib.rs:7:40
  = note: consider wrapping this expression in `std::sync::LazyLock::new(|| ...)`
```

**Failure scenario.** `--cfg loom` is a *global* `RUSTFLAGS` cfg: it applies
to every crate in the build, not only to the one whose loom suite you meant
to run. The population that sets it is precisely this crate's target
audience — people writing concurrent data structures. Two concrete paths in:

1. A consumer runs their **own** loom suite (`RUSTFLAGS="--cfg loom" cargo
   test`) in a workspace that also contains a `static CELL: RacyPtrCell<T>
   = RacyPtrCell::new();`. Their unrelated static stops compiling.
2. A consumer follows **this crate's README instruction verbatim**
   (`README.md:110`: `RUSTFLAGS="--cfg loom" cargo test --release --test
   loom_racy_ptr_cell`) from their own workspace root — the command carries
   no `-p racy-ptr-cell` — and gets the same break.

The README sells the `--cfg loom` aliasing as a *feature* ("the crate
aliases its atomics to `loom::sync::atomic` under `--cfg loom`",
`:99-100`) and never mentions the cost. The only place the cost is stated is
a subordinate clause inside `new()`'s rustdoc (`:337-338`), phrased as an
internal implementation note ("loom's atomics have no const constructor"),
not as a consumer hazard — and rustdoc renders only the `#[cfg(not(loom))]`
copy on docs.rs, i.e. the one whose reader is *not* in the failing
configuration.

**The repository already paid the price and priced it.** The crate's only
existing consumer, the root `sefer-alloc` crate, carries a ~200-line
hand-written `#[cfg(loom)] mod loom_shim`
(`src/registry/bootstrap.rs:224-523`) built for exactly this: its own
comment at `:206-218` states that under `--cfg loom` "`RacyPtrCell::new` is
NOT `const` … and sefer's `static REGISTRY: Registry = Registry::new()`
would fail to const-evaluate". That shim is a duplicate of the cell's whole
protocol which two prior reviews (run-1 F2, run-2 F5) had to audit for
drift. Every downstream consumer with a `static` faces the same bill, with
none of that context.

**Why it is a P2 and not a P3.** It breaks the *documented primary usage
form*, for the crate's *most likely* audience, following the crate's *own*
published instruction — and both surfaces that could warn (README text; the
0.1.0 docs.rs render) are frozen at upload. It is, honestly, the weaker of
the two P2s here: the failure is a loud compile error with a rustc note, not
a runtime hazard, and the correct information does exist in `new()`'s
rustdoc for someone who thinks to look there.

**Suggested fix, cheapest first.**

1. **Documentation (sufficient on its own).** One paragraph in the README
   next to `:98-111`, and one sentence at `src/lib.rs:191-194`: "`--cfg
   loom` is a global `RUSTFLAGS` cfg — it applies to every crate in the
   build. Under it this crate's atomics become `loom::sync::atomic`, so
   `RacyPtrCell::new` is **not** `const` and a `static CELL:
   RacyPtrCell<T> = RacyPtrCell::new();` will not compile. Scope the flag
   to this crate (`cargo test -p racy-ptr-cell …`), or supply a
   `#[cfg(loom)]` const-capable stand-in in your own crate — see
   `src/registry/bootstrap.rs`'s `loom_shim` in the upstream repository for
   a worked example."
2. **Optional, and a real one-way door, so decide it now rather than later.**
   Gate the aliasing on `#[cfg(all(loom, feature = "loom"))]` so a
   downstream `--cfg loom` build that has not opted in keeps `core` atomics
   and a `const fn new`. This crate's own loom job would then run
   `RUSTFLAGS="--cfg loom" cargo test -p racy-ptr-cell --features loom …`
   (one line in `.github/workflows/ci.yml:2293` and one in `README.md:110`).
   Note it does **not** help F4 — an optional dependency is still resolved
   into every consumer's `Cargo.lock` — and it changes observable behaviour
   for anyone who later relies on the bare-`--cfg loom` aliasing, which is
   why the window is now. `bytes` solves the same problem the other way
   (`#[cfg(all(test, loom))]`, so the aliasing never escapes its own unit
   tests); this crate cannot copy that, because CLAUDE.md's
   "tests live in `tests/`" rule puts its loom harness in an integration
   target that links the library *without* `cfg(test)`. Worth recording as
   the reason the cheap option is unavailable here.

### F3 — **P3** — `panic = "abort"`, the same recommended `std` profile, also silently disables `RollbackGuard` — an advertised headline feature — and nothing says so

**Where:** `crates/racy-ptr-cell/src/lib.rs:263-294` (`RollbackGuard`'s doc),
`:318-330` (its `Drop`), `:131-136` (the recommendation);
`crates/racy-ptr-cell/CHANGELOG.md:54-57` ("**Panic-safe init**");
`crates/racy-ptr-cell/README.md:56-57`, `:80-85`.

`-C panic=abort` means no unwinding, and therefore no destructors on the
panic path. `RollbackGuard::drop` (`:318-330`) is reachable *only* via
unwinding — the two non-unwinding exits both `defuse()` first (`:564`,
`:578`). So under the profile the crate recommends for `std` consumers, the
guard is dead code and the "the cell is left in `UNINIT` (not wedged in
`INITIALIZING`)" contract at `:480-484` does not hold.

In isolation this is harmless — the process aborts, so nobody observes the
wedged cell. It stops being harmless when composed with **F1**: if the panic
runtime's allocation deadlocks before `abort()` is reached, the process does
*not* die, and the cell now genuinely is wedged in `INITIALIZING` forever
with the guard that exists to prevent that compiled out. That is the
complete chain, entirely from following the crate's own documented advice.

**Suggested fix.** One clause in the panic-strategy paragraph and one in
`RollbackGuard`'s doc: the guard is an **unwinding**-only mechanism; under
`panic = "abort"` it never runs, and the "panic-safe init" property is
supplied by the abort itself, not by the guard. (This also makes the
CHANGELOG's "Panic-safe init" bullet honest about its precondition.)

### F5 — **P3** — the new fork mitigation names the wrong thread, and the section's general claim is paired with an allocator-only rule

**Where:** `crates/racy-ptr-cell/src/lib.rs:102-125`;
`crates/racy-ptr-cell/README.md:62-76`. Both added by `0835d8d`.

The hazard is correctly and precisely stated: "If one thread holds the
sentinel (running `init`) when **another** thread calls `fork()`…"
(`:108-110`). I re-derived it and the `dbg_rollback_reenterable`
no-reset-API claim at `:112-115` from the code — both accurate. The
signal-handler bullet at `:116-121` is accurate. Two residual imprecisions:

1. **The mitigation checks the forking thread, not the sentinel-holding
   ones.** `:122-125` / `README.md:74-76`: "`fork()` only from a thread you
   know holds no cell and treat `exec()` in the child as mandatory." What
   the forking thread holds is nearly irrelevant — a `fork()` from *inside*
   `init` is actually the safe case, because that thread survives into the
   child and can still publish or roll back. The dangerous state is what
   **other** threads hold, which the forking thread cannot know. The
   conjunction is not *unsafe* (the `exec()` half is sufficient on its own,
   and is the real POSIX rule), but a reader who takes the first clause as
   the operative safety condition and `exec()` as good hygiene draws exactly
   the wrong conclusion — and the first clause is the one phrased as an
   action they can take.
2. **The section opens with a claim about the cell and closes with a rule
   about allocators.** `:106-107` states, generally, "**The cell is neither
   fork-safe nor async-signal-safe**"; the mitigation at `:125` is "Do not
   allocate in a signal handler." The crate's own intro invites
   non-allocator users ("hand-rolled allocators, runtimes, and bare-metal
   bootstraps", `:40-41`), and for them the rule is different and stricter:
   *never call `get_or_try_init` from a signal handler* — `get()` is a pure
   `Acquire` load and is fine; `get_or_try_init` is the one that can spin on
   a sentinel owned by the interrupted thread.

**Suggested fix.** Replace the first clause with the property that actually
matters and state the general rule alongside the allocator one: "Either
publish every cell before the first `fork()`, or treat `exec()` in the child
as mandatory — you cannot make a `fork()` safe by choosing *which* thread
calls it, because the hazard is what the threads that do **not** survive
into the child were holding. Never call `get_or_try_init` from a signal

### F6 — **P3** — no `Debug` impl (Rust API Guidelines C-COMMON-TRAITS)

**Where:** `crates/racy-ptr-cell/src/lib.rs:232-240` — `RacyPtrCell<T>`
implements `Default` (`:754-758`), `Send`, `Sync`, and nothing else.

A consumer holding a `RacyPtrCell` in their own struct cannot
`#[derive(Debug)]` it. C-COMMON-TRAITS asks for `Debug` on essentially every

readable from one `Acquire` load, with no dereference of `T`).

Reported for completeness of the publish checklist, **not** as a blocker:
adding a trait impl is a purely additive change, so unlike F2 and F4 this
window does not close at upload. It is the lowest-value item in this report
and is here because no prior review covered the common-traits checklist at
all.

The primitive is publish-ready and I could not break it. Every gate is green
on the current tree — 7/7 native, 7/7 loom against the **real** type with
both non-vacuousness counterfactuals firing, 7/7 miri twice (including

P1 finding: no UB, no soundness hole, no lost happens-before, no ABA break,
no reachable sentinel collision, no double-init.** Both of cycle 2's
findings are genuinely closed: `0835d8d`'s fork/signal section is accurate
against the code and its general "owner has stopped running" framing covers
more of the class than the two examples it names, and `b84b312`'s CI job
parses, is ungated, and runs two commands I verified green.

What holds it back from an unconditional GO is **two** findings, and — for
the first time in this crate's review history — both are things I
**measured** rather than argued:

- **F1.** The crate tells `std` consumers to set `panic = "abort"`, in a
  sentence whose stated purpose is that "the panic runtime … allocates in a
  `std` build". It does not stop the allocation: a binary with
  `panic = "abort"` and an allocator that traps re-entry exits **42** — the
  global allocator *is* re-entered before the abort, and a counting
  allocator measures **3 allocations on the first panic** with
  `RUST_BACKTRACE=0` in release. Inside a `#[global_allocator]`, that
  re-entry reaches the same mid-`init` cell and the thread deadlocks on a
  sentinel it owns itself: the consumer was promised "fatal" and gets a
  100 %-CPU hang, with the release-active `assert!`'s diagnostic — the whole
  point of task #707 — never reaching stderr, because the allocation that
  would have printed it is the one that deadlocked. This is the third
  revision of that paragraph; the two prior revisions fixed which
  environment gets which recipe and never checked whether the `std` recipe
  works.
- **F2.** `RUSTFLAGS="--cfg loom"` — a global flag, advertised by this
  crate's own README at `:110` — makes `RacyPtrCell::new` non-`const`, so
  the README's own headline form `static CHUNK: RacyPtrCell<Chunk> =
  RacyPtrCell::new();` fails with `E0015` in any downstream build that sets
  it. Reproduced in a scratch consumer. The audience that sets `--cfg loom`
  is precisely this crate's audience, the repository already paid ~200 lines
  of duplicated protocol (`bootstrap.rs`'s `loom_shim`) for exactly this,
  and the only place the crate says so is a subordinate clause in the
  rustdoc of the `new()` copy that docs.rs renders — i.e. the one whose
  reader is not in the failing configuration.

Both fixes are prose. F1 is a corrected paragraph (plus, optionally, F3's
one clause about the guard being unwind-only). F2 is one README paragraph
and one line in `src/lib.rs` — with an *optional* second half (feature-gating
the loom aliasing) that is a genuine one-way door and is therefore worth
deciding now rather than in 0.1.1. F4 is one CHANGELOG sentence and F5 is
one replaced clause; both are cheap enough to fold into the same commit. F6
is additive and can wait indefinitely.

**Close F1 and F2 — no algorithm change, no API change — and this is a GO.**
For the record, the things that would have to *newly* break to move it off GO
after that are unchanged from cycle 2 and are still six, three of which the

making `RollbackGuard`'s rollback conditional (**not** caught — cycle-2 F5);
