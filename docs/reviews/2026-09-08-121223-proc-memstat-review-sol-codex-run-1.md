## P2-1. MacOS: C-макрос объявлен как внешняя C-функция

Места: `crates/proc-memstat/src/lib.rs:202`, `:224`.

Крейт объявляет `extern "C" fn mach_task_self() -> u32`. Но публичный
Mach API задаёт `mach_task_self()` как макрос чтения глобального
`mach_task_self_`, а не как эту функцию:

```text
#define mach_task_self() mach_task_self_
```

Определение приведено в [заголовке Apple mach_init.h](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/libsyscall/mach/mach/mach_init.h).
Rust libc реализует одноимённый Rust helper чтением extern static, а не
FFI-вызовом функции. [Исходник libc](https://raw.githubusercontent.com/rust-lang/libc/0.2.186/src/unix/bsd/apple/mod.rs).

Нынешнее объявление требует от линкера функциональный символ
`_mach_task_self` вместо штатного data symbol `_mach_task_self_`.
Ожидаемый результат на стандартном SDK при линковке использующего snapshot
бинарника — unresolved symbol. **Нативная линковка здесь не выполнялась**;
вывод основан на объявлении SDK и форме binding, не на собственном build log.
Один `cargo check` или сборка rlib такой импорт не подтверждают.

Исправление: привязаться к штатной cached-переменной и прочитать значение
через небольшой корректно обоснованный unsafe helper либо использовать
проверенный binding. Не заменять это на произвольный Mach trap с иной
семантикой прав. Cached self-port не надо освобождать как вновь полученное
право. После правки нужен реально линкуемый macOS consumer, вызывающий snapshot.

## P2-2. `commit` означает разные, несопоставимые величины

Места: `src/lib.rs:8`, `:36`, `:67`, `:101`, `:234`; `README.md:16`.

Поле обещает память, charged against the system commit limit. Windows
PagefileUsage действительно описан как commit charge.
[Microsoft PROCESS_MEMORY_COUNTERS](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters).
Linux VmSize и macOS virtual_size — размер виртуального адресного
пространства, не тот же счётчик. Apple прямо называет поле virtual memory
size. [Apple task_info.h](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/osfmk/mach/task_info.h).

Контрпример для Linux: большое read-only file mapping увеличивает VmSize,
но его стоимость в overcommit accounting равна нулю. Аналогично сам объём
зарезервированных адресов нельзя приравнивать к памяти, за которую взято
commit-обязательство. [Правила Linux overcommit](https://docs.kernel.org/mm/overcommit-accounting.html).
В измерении reserve/commit/decommit такое смешение может изменить смысл
вывода: удержанное адресное пространство будет названо удержанным commit.

Linux-оговорка в lib.rs и macOS-комментарий признают total VM, но не
исправляют тип/API, безусловную документацию поля и основной README.
«Ближайший аналог» не делает метрики взаимозаменяемыми.

Рекомендация: отдельные `virtual_size` и `commit_charge`, с отсутствием
последнего там, где выбранный API его не даёт; либо обязательное явное
описание вида возвращённой метрики в данных. Не подставлять phys_footprint
или VmSize под названием commit charge без изменения контракта. Единая
единица «байты» не означает единую измеряемую величину.

## P2-3. Linux: не-UTF-8 Name обнуляет даже корректные числовые поля

Место: `src/lib.rs:98`.

Весь status читается через `read_to_string`. Между тем имя task — байтовая
строка с ограничением длины, а не гарантированная UTF-8 строка. PR_SET_NAME
ограничивает её байтами и может обрезать длинное имя; даже исходно валидный
UTF-8 может быть оборван посреди символа. [Linux PR_SET_NAME](https://man7.org/linux/man-pages/man2/PR_SET_NAME.2const.html).
В `proc_task_name` ядро экранирует специальные символы, но не преобразует
всё имя в гарантированный UTF-8. [Linux array.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/proc/array.c).

Например, имя main thread с байтом FF создаёт невалидный UTF-8 в Name,
хотя строки VmRSS/VmSize/VmHWM остаются обычными ASCII-числами.
`read_to_string` возвращает ошибку; `unwrap_or_default()` заменяет весь
файл пустой строкой, и snapshot становится `{0, 0, None}`.
[Условие ошибки read_to_string](https://doc.rust-lang.org/std/fs/fn.read_to_string.html).
Это допустимый процесс/данные procfs, не требование поддержать поддельный
файл с искусственно повреждёнными счётчиками.

Читать bytes и разбирать только ASCII memory fields. Проверка UTF-8
нерелевантного имени не должна определять доступность измерения. Добавить
байтовый fixture с таким Name и точными ожидаемыми числовыми результатами.
Живой процесс с изменённым именем в этом ревью не создавался.

## P3-1. Один вызов не обеспечивает обещанный атомарный same-instant snapshot

Места: `src/lib.rs:55`, `:78`; `README.md:3`, `:12`; description в Cargo.toml.

Ядро Linux прямо предупреждает, что RSS accounting асинхронный и может
быть неточным. [Документация procfs](https://docs.kernel.org/filesystems/proc.html).
В реализации `task_mem` anon/file/shmem и total_vm читаются отдельными
операциями; комментарий явно допускает inconsistent snapshots.
[Исходник task_mem](https://raw.githubusercontent.com/torvalds/linux/master/fs/proc/task_mmu.c).

Следовательно, один MemStat и одно чтение файла уменьшают временной разрыв,
но не доказывают, что все цифры соответствуют единственному моменту.
На уровне std чтение файла также не равнозначно одному системному вызову.
Обещание из заголовка и описания типа сильнее выбранного механизма.

Документировать best-effort observation из одного источника/сборки отчёта,
а не атомарность. При необходимости предложить отдельный более дорогой
режим RSS с явно описанными ограничениями; не объявлять его атомарным
только из-за более точного источника. В текущем Linux task_mem неравенство
VmHWM >= VmRSS формируется из общего total_rss — само по себе оно не
ошибка; оно просто не доказывает same-instant свойство всех полей.

## P3-2. Тесты влияют на общепроцессные счётчики друг друга

Места: `tests/monotonicity.rs:30`, `:72`, `:107`, `:155`.

В одном test binary два теста трогают по 16 MiB, третий на Windows
проверяет, что нет роста RSS на 16 MiB. Изоляции или общего lock нет;
libtest по умолчанию запускает тесты параллельно.
[Cargo test](https://doc.rust-lang.org/cargo/commands/cargo-test.html).

Допустимое расписание без дефекта snapshot:

1. Windows commit-test читает before.rss и выделяет нетронутые 64 MiB.
2. Два соседних теста успевают затронуть свои 16 MiB каждый и ещё не
   освободили буферы.
3. Commit-test читает after.rss и падает на ограничении роста менее 16 MiB,
   хотя собственную committed область действительно не трогал.

В обратную сторону освобождение чужого буфера между before/after может
компенсировать рост RSS в touching_memory_grows_rss. Увеличивать N для
лечения такого флейка неправильно. Изолировать сценарии в fresh processes
или как минимум сериализовать все тесты, влияющие на процессную память.
Даже после изоляции OS trimming и неточность RSS нужно отличать от ошибки
парсера; наиболее строгие unit assertions должны проверять детерминированные
данные/контролируемый backend. Это статический контрпример, не выполненный прогон.

## P3-3. Монотонность не проверяет byte-scale и доступность peak

Места: `tests/monotonicity.rs:12`, `:54`, `:86`; `src/lib.rs:100`.

Если в Linux backend убрать все множители 1024, три Linux-теста сохранят
отношения `after > before`, `peak >= rss`, `peak_after >= peak_before`.
То есть значения в KiB вместо bytes прошли бы suite. Аналогично постоянный
`peak_rss: None` не провалит peak-тест: `(None, None)` принимается без
проверки, что это действительно stub platform. Linux commit вообще не
сверяется с независимым ожидаемым числом.

Нужны exact-value parser fixtures с разными числами для трёх полей,
missing/malformed cases и не-UTF-8 нерелевантным полем. Реальный platform
smoke должен отдельно подтверждать ожидаемую доступность counters.
Проверить layout/count константы FFI по SDK также полезно. Не расширять
обычный public API только ради доступа тестов к закрытому парсеру.

## Неблокирующие улучшения P4

### P4-1. Ошибка/отсутствие данных неотличимы от числового нуля

Места: `src/lib.rs:82`, `:98`, `:167`, `:229`, `:248`.

Fallback явно документирован, поэтому это не скрытое нарушение текущего
контракта. Но API не даёт пути получить ошибку: до/после с неудавшимся
вторым чтением способен выглядеть как полное освобождение памяти.
Полезны `try_snapshot`/Result и явная доступность метрик; best-effort wrapper
можно оставить отдельно. Возврат ошибки не означает panic и не требует
останавливать измеряемый процесс.

### P4-2. Linux snapshot выделяет память и повторно сканирует status

Места: `src/lib.rs:98`, `:100`, `:112`.

read_to_string создаёт новый heap buffer на каждый вызов; три поиска
повторно сканируют строки от начала до нужного поля. Это O(L) времени,
с тремя независимыми поисками, не O(L²),
и O(L) временной памяти. Сам сбор данных может менять измеряемую память,
особенно на первом вызове. В allocation hook такой путь способен
рекурсивно войти в allocator; не стоит обещать безусловное «probe never
takes the process down» без оговорок об аллокациях/reentrancy/OOM.

Приоритет — bytes-парсер из P2-3, один проход и возможность caller-owned
scratch buffer/потокового чтения. Не заменять это безусловным чтением первых
4/8 KiB: длинные поля, например список Groups, могут предшествовать memory
fields. Частичные строки и большие status нужно обрабатывать корректно.
Выигрыш не измерен; дополнительные зависимости ради трёх полей не обязательны.

### P4-3. Windows fixture не освобождает VM при panic

Место: `tests/monotonicity.rs:134`.

VirtualFree находится после assertions. При падении любого из них
64 MiB committed памяти остаются до завершения test process и могут
ухудшить соседние проверки. Нужен владеющий RAII guard: явное освобождение
с проверкой на happy path и не паникующий cleanup на unwind. Комментарий
«при null пропускаем assertions» также неверен: код сейчас делает assert.

### P4-4. Stub/Miri пути выполняют бессмысленные большие allocations

Места: `tests/monotonicity.rs:30`, `:61`, `:72`.

Cfg ограничивает только assertions, не создание/запись 16-MiB буферов.
На Miri и unsupported targets обе большие операции остаются, хотя snapshot
не наблюдает реальную память. В первом тесте результаты затем просто
отбрасываются; во втором допускается `(None, None)`.
Гейтировать весь OS-dependent сценарий, а stub проверять маленьким
контрактным тестом точного `{rss: 0, commit: 0, peak_rss: None}`.

### P4-5. README и field docs не синхронизированы с Linux-исправлением

Места: `README.md:29`; `src/lib.rs:64`, `:69`; package description.

Реализация уже читает только status, но README и field docs продолжают
называть statm. Исправление page size принимается: kB * 1024 действительно
не зависит от base page size. Синхронизировать все поверхности, а обещания
commit/same-instant исправить по P2-2/P3-1. «Zero crate dependencies»
точнее, чем «no C libraries»: native OS APIs всё равно используются.

## Что в текущем коде выглядит корректным

- Windows PROCESS_MEMORY_COUNTERS соответствует форме SDK: два u32 и восемь
  SIZE_T, то есть 40 B на 32-bit и 72 B на 64-bit. cb задаётся размером,
  BOOL проверяется до использования результата. Pseudo-handle текущего
  процесса не требует CloseHandle.
- MachTaskBasicInfo имеет нужные поля/offsets и 48 B размера, COUNT=12
  четырёхбайтовых единиц. Более сильное выравнивание Rust-буфера не означает
  mismatch этих полей. Замечание к macOS — binding self-port, не найденный
  overflow выходного буфера. Сырые out-структуры полностью zero-initialized;
  при ошибке backend значения не используются.
- Linux-переход 583cd8f устранил жёсткое умножение page counts на 4096.
  Сам шаг touch=4096 в тесте не воспроизводит тот старый conversion bug
  на 16/64-KiB страницах: там он просто делает несколько записей на страницу.
- MemStat — небольшой Copy value, без владения чужими указателями,
  кэшей и ручных Send/Sync. FFI ограничен платформенными модулями;
  dependency-free seam сам по себе разумен.

## Рекомендуемый порядок

Сначала исправить macOS binding, Linux byte parsing и назвать метрики
строго по их смыслу. Затем убрать недостижимую гарантию атомарного снимка,
изолировать реальные OS-тесты, добавить exact-value оракулы и подключить
crate-specific CI. После этого оптимизировать Linux reader по измерениям,
не подменяя точность более быстрым, но усечённым разбором.
Реализация и исполняемая проверка этих исправлений в этот read-only проход
не входили.
