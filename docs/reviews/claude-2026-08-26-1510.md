## 1. Верификация четырёх фиксов run 2 — все закрывают заявленное

**F1 (`e6ed779`, task #1423) — regression-тесты на две незапиненные P2-1 точки. ЗАКРЫТО, тесты не вакуумны.** Модуль `extreme64_overflow` (`tests/builder.rs:449-621`) перепроверен арифметически с нуля:

- Схема `min_block = 1<<62`, `geo_count = 1`, `extras = [2<<62, 3<<62]` легальна (extras кратны min_block, строго возрастают, ≥ min_block; geo_count=1 не достигает геометрического шага) → таблица `[1<<62, 2<<62, 3<<62]`, `L = 4`. Ровно рецепт run 2 F1.
- `build_size2class_bucket_need_overflow_clamps_to_last_class`: bucket k=3 вычисляет `4·2^62 = 2^64` → overflow → кламп-ветка. Пересчитал все четыре bucket'а: `[0, 1, 2, 2]` — совпадает с оракулом теста (reference клампит МНОЖИТЕЛЬ до умножения, поэтому сам переполниться не может — корректный независимый оракул). Контрфактуальность честно ограничена: тест сам документирует, что при откате фикса он падает дважды в debug (E0080 на const + panic на runtime-пути), но в release наблюдаемо эквивалентен — и объясняет почему (для любой `Params`-собранной схемы `L·min_block = small_max + min_block = 2^64` wrap'ается ровно в 0, а `need = 0` не двигает monotone-pointer назад). Это не изъян теста, а свойство домена; закрыто третьим тестом ниже.
- `build_size2class_bucket_need_overflow_flips_the_release_answer_for_a_hand_built_table` — ключевое дополнение сверх рецепта run 2, дающее **release-контрфактуальность**: hand-built таблица `[1<<62, 2<<62, (3<<62)+2, (3<<62)+5]` (легальна для standalone `build_size2class`, run 2 F9) делает need предпоследнего bucket'а (`3<<62`) строго меньше `small_max`, так что pointer останавливается на классе 2 ДО переполняющегося bucket'а; при откате фикса в release wrapped `need = 0` оставляет `s2c[3] = 2` вместо правильного 3 — молчаливо неверный ответ без паники, ровно исходный класс бага P2-1. Пересчитал оба варианта вручную: fixed `[0,1,2,3]`, reverted-release `[0,1,2,2]` — совпадает с заявленным в комментарии. u128-оракул скана переполниться не может. Тест генуинно различает fixed/reverted в release.
- `class_for_next_multiple_overflow_returns_none`: `class_for(3<<62, 1<<63)` — seed = класс `3<<62` (не кратен `2^63`), `(3<<62) | (2^63-1) = usize::MAX`, `checked_add(1)` → `None`. Пересчитал: верно. Позитивный контроль `class_for(2<<62, 1<<63) == Some(1)` тоже верен (`2^63 & (2^63-1) == 0`). При откате в release тест не падает, а **виснет** (wrap → 0 → `(0-1)>>62 = 3`… нет: `s2c[(0-1)>>shift]`, wrap индекса → тот же seed → бесконечный цикл) — commit message это честно называет; CI-таймаут такой откат всё равно поймает.
- Гейт `#[cfg(target_pointer_width = "64")]` покрывает ВЕСЬ модуль, включая все консты со сдвигами `<< 62`; вне модуля 32-bit-опасных сдвигов не осталось (проверено: два overflow-теста используют портабельный `1usize << (usize::BITS - 1)` и корректно панируют и на 32-bit — пересчитал оба сценария для usize=u32).

## 2. Свежий полный обзор — проверено и признано корректным

- **`build_table`**: ленивая генерация + two-pointer merge; шаг за последним geo-классом не вычисляется (нет ложных overflow); `cur == extras[ei]` → extra первым → дубликат ловится финальной проверкой монотонности с именованным сообщением; все документированные panic-причины сверены с кодом 1:1.
- **`build_size2class`**: monotone-pointer корректен (`need` и таблица неубывающие); `class_idx` не может достичь `N` (need ≤ small_max = table[N-1]), значит `as u8` при `N < 256` без усечения; кламп overflow-ветки математически обоснован (истинное произведение заведомо > small_max).
- **`class_for`**: seed-индекс всегда в границах (`(need-1)>>shift ≤ L-2`); терминация slow path строгая (`next_mult > block` ⟹ следующий индекс строго больше — таблица строго возрастает и кратна min_block, поэтому lookup по `next_mult` точен, без переокругления мимо кандидата); хвостовой `None` после `while i < N` — недостижимый защитный код (s2c-элементы всегда < N, цикл покидается только через return) — приемлемая оборонительная форма для const fn, не дефект.
- **Тесты**: оракулы независимы (hand-derived golden против циркулярности; u128/клампящий-множитель reference против самопереполнения оракула); exhaustive sweep `size × align` до `SEFER_MAX+1`; proptest на трёх схемах с jump≡walk≡scan; `#[should_panic]`-подстроки взаимно не пересекаются между chokepoint'ами. Пробелов покрытия уровня P3 не нашёл.
- **32-bit портабельность тест-сьюта**: после F6 полная (все `<<62/63` под cfg-гейтом или в портабельной форме; оба overflow-теста пересчитаны для usize=u32 — панируют с тем же сообщением).
- **CI**: publish-dry-run job (`ci.yml:711-734`), clippy `--all-targets -D warnings` + rustdoc `-D warnings` (:1865-1866), test debug+release `--all-features` (:1850-1851; release-строка нужна именно из-за `debug_assert`-гейтированного теста), msrv `check` + `test --no-run` (:2065-2066), no_std thumbv7em build (:1832). Согласованно, без дублей.
- **Публикационные метаданные**: без изменений с run 2, повторно сверены (keywords/categories валидны, лицензии на месте, README-пример ```text-фенс, `MAX_CLASS = 258_752` арифметически верен — пересчитан заново). ## 3. Новые находки

### P3

**F1 — сообщение коммита `a8236e7` содержит фактически неверное заявление, и его R30-12-классификация `perf(opt-in)` от этого неверна: должно быть `perf(runtime)`.**
Коммит обосновывает выбор префикса так: «Not a production-default change (size-classes is not yet published/wired into sefer-alloc's production feature set)». Половина «not yet published» — правда. Половина «not wired into production» — **ложь**, проверяемая тремя строками корневого репозитория:
- `Cargo.toml:419`: `production = ["alloc-global", …]`; `:191`: `alloc-global = ["alloc-core", …]`; `:160`: `alloc-core = […, "dep:size-classes"]`; `:920`: `size-classes = { path = "crates/size-classes", … }`.
- `src/alloc_core/size_classes.rs` — «Thin compat shim over the `size_classes` crate» (его собственный module doc, :4): `static SC: SizeClassesImpl<…> = SizeClassesImpl::build(PARAMS)` (:188) и `SizeClasses::class_for` → `SC.class_for(size, align)` (:216) — прямой форвард в ИЗМЕНЁННУЮ функцию.
То есть изменённый slow path — это alignment-классификатор production-аллокатора: любой `--features production` билд компилирует именно этот код, и любой in-contract запрос с `align > 16` (например `#[repr(align(64))]`-тип через `Layout`) исполняет заменённую инструкцию. По таксономии R30-12 (CLAUDE.md) это ровно определение `perf(runtime)`: «a hot-path algorithm changed while remaining in `production`'s always-on scope». Семантика in-contract сохранена и изменение полезное — дефект не в коде, а в записи: `git log`-читатель (та самая аудитория, ради которой R30-12 существует) сделает вывод «production runtime не тронут», что неверно; будущий round-manifest (правило R34-24 классифицирует каждый коммит по префиксу, «derived from git log») унаследует ошибку и неверно отчитается «Runtime improvements this round: 0».
Что НЕ нарушено: композиция `production` в Cargo.toml не менялась, поэтому обязательство «re-run bench:table + iai» из CLAUDE.md формально не срабатывало.
Рекомендация (без переписывания истории — non-retroactive-позиция репозитория): зафиксировать исправление классификации записью — в round-manifest текущего раунда классифицировать `a8236e7` как `perf(runtime)` с пометкой о неверном самоописании, и/или строкой в `docs/CORRECTNESS_OPEN_ITEMS.md`-процесс-record. ### P4

**F2 — `a8236e7` сделал неполным перечень failure-mode'ов для non-pow2 `align` в `# Preconditions` у `class_for`.**
Где: `lib.rs:663-671` (перечень) vs `:711` (новый mask test).
Док перечисляет для slow path только два режима отказа при out-of-contract non-pow2 `align`: overshoot round-up'а («skipping a class that would actually have fit») и ложный `None`. До P-1 это было полно: `is_multiple_of` был честной проверкой делимости, и slow-path `Some(idx)` ВСЕГДА удовлетворял `block % align == 0` даже вне контракта. После P-1 появился третий режим — **ложное принятие**: mask test может вернуть класс, НЕ кратный `align`. Проверяемый пример (release, схема SEFER): `class_for(20, 24)` → need=24 → seed = класс 32; `32 & 23 == 0`, но `32 % 24 == 8` — возвращается класс, нарушающий fit-предикат. Вводная фраза («BOTH paths can silently violate the fit predicate») остаётся генерически верной, испорчен только детальный перечень механизмов. Однострочное дополнение дока; поведения in-contract не касается, `debug_assert` в debug по-прежнему срабатывает раньше.

**F3 — дублирование связанных констант между бенчем и его оракулом/параметрами.**
(a) Пары `(1025, 256)` / `(2049, 1024)` захардкожены дважды: `benches/size_classes_bench.rs:73,80` и `tests/builder.rs:171`. Оракул пинит свойство «seed не кратен align» для СВОИХ литералов, а не для тех, что реально стоят в бенче: изменение пары в бенче без синхронного изменения теста молча возвращает F2-инертность для изменённой строки, и оракул продолжит зеленеть. Смягчено перекрёстными комментариями (каждый файл называет второй). (b) Аналогично `is_huge`-строки бенча используют литерал `4 * 1024 * 1024` (:120,125,130) независимо от того же литерала в `SEFER_PARAMS` (:31) — изменение huge_threshold схемы молча уводит строки с границы. Вариант фикса при случае: общий именованный const / включение фактических bench-пар в один разделяемый const, на который смотрят оба файла (в пределах одного крейта это одна `pub`-константа тестового hелпера или просто named const в каждом файле с комментарием-ссылкой).

**F4 — остаток F7-класса в README и CHANGELOG: const-only формулировка паник-контракта.**
`README.md:13` («so violations are compile errors, not accepted input») и `CHANGELOG.md:24-26` («a violation is a `const`-evaluation panic, i.e. a compile error at the consumer's table definition») сохраняют формулировку, которую run 2 F7 счёл занижением контракта и починил в трёх `# Panics`-заголовках lib.rs («identically in `const` evaluation and at runtime»). Оба утверждения не ложны (в const-контексте это действительно compile error), но недоговаривают runtime-release половину — ту самую, ради которой существовали P2-1 фиксы. Однострочная правка в двух файлах, если хочется полной согласованности; можно и осознанно оставить (README/CHANGELOG описывают типичное const-употребление).

**F5 — `derive(Copy)` на `SizeClasses<N, L>` — многокилобайтный Copy-тип; решение стоит зафиксировать ДО первой публикации.**
`lib.rs:530-539`: для реалистичного SEFER-инстанса структура ≈ 16.6 KiB (`table` 392 B + `size2class` 16 173 B + скаляры). `Copy` делает случайную передачу по значению молчаливым memcpy такого размера (все методы берут `&self`, ничто Copy не требует; предназначение — const/static, где Copy безвреден). Дилемма семверная: снять `Copy` ПОСЛЕ публикации — breaking change, оставить — навсегда. Оба решения защитимы (plain data без interior mutability; прецедент — сам sefer держит его в `static SC`); находка в том, что решение должно быть осознанным и записанным до `cargo publish`, а не унаследованным по умолчанию. Рекомендация-минимум: одна строка в rustdoc типа («deliberately `Copy`: plain const data; note the value is ~L bytes — pass by reference») — тогда выбор задокументирован.

## 4. Ответ на вопрос кампании

**Готов ли крейт к публикации?** Да — **GO**, третий цикл подряд без P0-P2. Четыре фикса run 2 закрывают заявленное по существу (включая release-контрфактуальный тест для клампа, которого не было даже в рецепте run 2), и сами новых дефектов в код не внесли. Единственная новая P3 — процессная (запись/классификация коммита `a8236e7`), закрывается одной записью в манифесте раунда/индексе, не правкой кода. P4 — по желанию, до или после релиза. Обязательный остаток перед `cargo publish` — прежний F5 run 2: дата в CHANGELOG, проверка имени на crates.io, `npm run check` + зелёный CI на landing SHA.

Границы уверенности: аудит статический, read-only; корректность подтверждена чтением, диффами и независимой ручной арифметикой (SEFER-таблица до 258 752, обе jump-трассы бенча, все bucket'ы обеих extreme64-схем, оба 32-bit сценария), но не исполнением. Зелёность существующих CI-гейтов на текущем HEAD должна подтверждаться самим CI.
