## P3-1. Сдвиг между разными fill-id даёт коллизию уже на двух блоках

Места: `crates/globalalloc-model/src/drive.rs:54`–`:68`, `:225`, `:538`;
описание ограничений: `src/lib.rs:61`, `README.md:182`.

Новый шаблон:

```text
pattern(f, offset) = (f + offset) mod 256
```

Из этого следует не только описанный период 256, но и равенство:

```text
pattern(1, offset + 1) == pattern(2, offset)
```

То есть соседние идентификаторы дают один и тот же шаблон со сдвигом фазы.
Для ошибки чтения из другого allocation такая корреляция особенно опасна.

Контрпример без UB в тестовом аллокаторе:

1. `Alloc { size: 65, align: 8 }` создаёт A с fill-id 1.
2. `Alloc { size: 64, align: 8 }` создаёт B с fill-id 2.
3. `Realloc { i: 1, new_size: 64 }` обрабатывается дефектно: аллокатор
   создаёт новый отдельный, непересекающийся диапазон C, копирует в него
   64 байта из **A+1**, а не из B, корректно потребляет старый B и возвращает C.

Все адреса и размеры могут удовлетворять минимальному `RawAllocator` contract.
A+1 имеет 64 доступных и инициализированных байта. C не пересекается с A,
поэтому overlap guard не помогает. Каждый байт C совпадает с ожиданием для B:
`A[1..65] == expected_B[0..64]`. Prefix oracle проходит, C получает новый fill,
а последующие проверки видят корректные шаблоны A и C. Возврат **самого A+1**
не является этим контрпримером: его поймал бы overlap guard.

Арифметическая проверка в этом ревью подтвердила равенство всех 64 позиций.
Первые байты A: `[1,2,3,4,5,6]`; B и ошибочная копия A+1:
`[2,3,4,5,6,7]`. До изменения шаблона A состоял из единиц, B — из двоек,
и такой wrong-source realloc не прошёл бы первую проверяемую позицию.

Таким образом, это отдельная регрессия покрытия, не повторное замечание о
периоде 256 и не случай reuse одного идентификатора после 255 присваиваний.
Идентификаторы разные, сдвиг равен одному, блоков только два.

Рекомендация: шаблон должен смешивать идентификатор и позицию так, чтобы
смена идентификатора не сводилась к фиксированному сдвигу того же массива.
Можно регенерировать ожидаемые слова из seed и номера слова без хранения
второй копии payload. Не обещать отсутствия любых коллизий у байтовых шаблонов.
Добавить отрицательный `realloc_from_other_block_shifted` и сохранить три
нынешних отрицательных теста и честные grow/shrink/in-place контроли.

Классификация P3 относится к качеству продукта-оракула: на выбранных данных
нынешнее сравнение математически правильно, но систематически не выявляет
ошибочный выбор источника копии.

## P4-1. `peak_live_count` скрыт из rustdoc, но остался экспортом обычной сборки

Места: `crates/globalalloc-model/src/lib.rs:171`–`:177`,
`src/peak_live_count.rs:21`.

Комментарий называет функцию test-only/internal, однако вокруг `pub use`
нет cfg. Внешний потребитель обычной сборки может импортировать и вызвать
`globalalloc_model::peak_live_count`; `#[doc(hidden)]` управляет отображением
документации, а не видимостью или наличием символа.
[Источник: rustdoc book](https://doc.rust-lang.org/rustdoc/write-documentation/the-doc-attribute.html#hidden).

Это не проблема memory safety. Но технически API стал шире, и refactor
внутреннего prepass может затронуть потребителей скрытой функции.
Если это намеренный нестабильный helper, назвать его статус точно, не
приравнивая hidden к test-gated. Если нужен действительно закрытый API,
использовать явно включаемый тестовый cfg либо проверять внутренний алгоритм
без безусловного публичного re-export. Не менять ради этого корректную формулу
peak-live и не терять её интеграцию с `drive`.

## P4-2. Две проверки alignment опираются на недостаточные или неверные предпосылки

Места: `crates/globalalloc-model/tests/system_proptest.rs:263`, `:288`,
`:292`–`:297`, `:305`.

1. `align_strategy_exponent_is_width_correct_at_the_isize_ceiling` вообще
   не вызывает `op_strategy`. Она проверяет арифметику самого usize и
   default alignment. Ошибка production mapping только на большом alignment
   не изменит результат этого теста. Нужен вызов реального генератора с
   граничным Config и проверка полученных alignment; допустимо отдельно
   оставить compile-time арифметическое доказательство с честным названием.
2. `align_strategy_shrinks_toward_one` сначала отбирает `op_size(op).is_some()`,
   а затем считает Realloc недостижимым. Но `op_size(Realloc)` возвращает
   `Some(new_size)`. Тест сейчас зависит от того, что полное shrinking
   конкретной стратегии/seed оставляет только другие варианты. Это не
   следствие его собственного предиката. Отбирать надо операции, имеющие
   alignment, и отдельно требовать хотя бы одну такую операцию.

Первый тест не доказывает заявленную связь с production, второй способен
дать ложный panic при допустимом изменении формы shrinking. Сам новый
exponent mapping выглядит корректным: валидация ограничивает показатель
значением `usize::BITS - 2`.

## P4-3. Исправление `fill_op` пока не имеет контрпримера, отличающего его от позиции

Места: `crates/globalalloc-model/src/drive.rs:34`, `:373`, `:434`, `:555`,
`:572`, `:592`; `tests/oracle_negative.rs:1011`, `:1079`.

Код теперь хранит правильный источник fill и использует его в run-end/teardown.
Однако существующие тесты сообщений оставляют соответствующий блок в позиции,
совпадающей с исходной операцией: повреждённый первый блок имеет индекс 0,
а второй survivor в teardown — индекс 1. Подмена `fill_op` обратно на
позицию в этих примерах не обнаруживается.

Достаточен небольшой тест с уже имеющимся fault:

```text
op 0: Alloc A, 64 bytes
op 1: Alloc B, 32 bytes
op 2: Dealloc(0), с ClobberAtOnDealloc(64)
```

После swap_remove B находится в live[0], но его fill относится к op 1.
Run-end panic должен называть именно 1. Также нужен пример после успешного
realloc, чтобы проверять обновление `fill_op`, а не только первоначальную запись.
Это пробел регрессионного покрытия; в текущем коде неправильного значения
`fill_op` не найдено.

## P4-4. Приоритет новой оптимизации — стоимость позиционного fill/verify

Места: `crates/globalalloc-model/src/drive.rs:130`, `:149`, `:185`, `:214`.

Заполнение изменилось с одного `write_bytes` на цикл отдельных записей.
Проверки выполняют вычисление ожидания и условие для каждого байта. При
небольшом K и больших блоках именно эти проходы могут доминировать над overlap
и prepass. Коммит сообщает наблюдения времени тестов, но они не доказывают
контролируемый коэффициент замедления: необходимо зафиксировать stream, seed,
профиль, аллокатор и машину.

После выбора шаблона, закрывающего P3, сравнить побайтовую и порционную
генерацию/проверку. Возможны небольшие stack-буферы ожидаемых слов/байтов и
проверка подробного byte offset только в несовпавшем участке. Сохранить
поддержку произвольного alignment, точный первый несовпавший байт и
инициализацию каждого проверяемого байта. Не вводить невыравненное чтение u64
через обычное разыменование и не заменять диагностику одной контрольной суммой.

Это предложение для измерения, не подтверждённое ускорение. Не удалять
проверки перед уничтожением блока или весь run-end sweep ради меньшего времени:
они обнаруживают разные последовательности повреждений.

## P4-5. Ранее известный линейный overlap scan остаётся O(M²) в худшем случае

Место: `crates/globalalloc-model/src/drive.rs:105`.

Формула из раунда 2 не изменилась: M последовательных аллокаций требуют
M(M−1)/2 сравнений диапазонов. Prepass улучшил память, но не эту сложность.
При пике K и суммарной работе с байтами B верхняя оценка — O(MK+B).

Замена на индекс непересекающихся интервалов по адресам может дать
O(M log(K+1)+B), сохраняя Vec для выбора блока по индексу. Цена — дополнительная
память, аллокации дерева и более сложная обработка realloc. Правильно, что
этот пункт пока не реализован без профиля большого K. Не считать его новым
дефектом исправляющего коммита.

## P4-6. Ранее известные boxed size strategies всё ещё выделяют деревья в куче

Место: `crates/globalalloc-model/src/strategy.rs:15`–`:24`.

Alignment Vec устранён, но `size_strategy` по-прежнему возвращает
`BoxedStrategy<usize>` для трёх размерных веток. В proptest 1.11.0 это
Arc-обёртка стратегии и Box для получаемого ValueTree. Стоимость остаётся
при материализации размерных деревьев и shrinking, а не только при создании
фабрики. Снижение длины Miri-сценария уменьшает её частоту, но не устраняет.

Профилировать отдельно constructor, new_tree и shrinking; затем выбирать
конкретный тип/enum стратегии, если цена существенна. Обязательный регрессионный
критерий — zero-weight ветка не должна вновь появиться при shrinking.
Это второй сознательно отложенный performance-пункт прошлого раунда.

## Проверка безопасности, сложности и документов

- `peak_live_count`: счётчик совпадает с динамикой длины модели; выбор
  индекса при Dealloc/Realloc на длину не влияет. Для завершившегося без
  panic потока предсказан точный пик; преждевременная остановка требует не
  больше. `live += 1` ограничено длиной существующего среза ненулевых Op.
- Дополнительная память модели теперь O(K), хотя сам входной `ops` занимает
  O(M). Новый `fill_op` расширяет отдельную Live-запись; это оправданная цена
  диагностического идентификатора, но не обещание уменьшения памяти для
  истории, где K=M.
- Область указателей не расширена: новые циклы пишут только offset<size,
  prefix reader работает на min(old,new), null/align/overlap проверяются до
  доступа к новым результатам. Старый указатель после успешного realloc
  не используется для чтения или записи.
- Новый guard действительно проверяет отдельный globalalloc-model workflow
  (`release.yml:432`), SHA (`:486`), завершение и success (`:512`); missing и
  ошибочные API-ответы не разрешают публикацию. Guard ограничен нужным крейтом
  и исключает dry-run. Предыдущее P3 по зависимости workflow закрыто.
- Новый тестовый файл peak_live_count добавлен в обе Miri-строки общего CI.
  Отдельный i686 job продолжает запускать все интеграционные targets.
- README и crate rustdoc явно указывают период 256 и reuse fill-id. Не
  считаю сам известный период новым замечанием; проблема P3 — дополнительная
  корреляция разных fill-id со сдвигом меньшим 256.
- CHANGELOG всё ещё описывает старую схему словами о cycling fill bytes,
  не объясняя позиционную составляющую так же точно, как README. При правке
  P3 стоит синхронизировать эти описания в одном изменении.
- Panic-leaks и пределы диагностики при нарушении RawAllocator остаются
  явно документированными. Не предлагается освобождать suspect pointers
  универсальным Drop или заменять unsafe-контракт runtime-проверками,
  которые не способны установить provenance/initializedness.
