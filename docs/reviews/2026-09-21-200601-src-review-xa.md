### Что не следует ошибочно считать найденным UB

- Raw-address casts сами по себе не объявлены UB: exposed-provenance round-trip отличается от `without_provenance_mut`.
- Намеренно некорректные вызовы unsafe dealloc/realloc с double-free, неправильным Layout, unmapped/foreign pointer не выданы за safe-code exploit.
- Process-lifetime registry chunks, remote atomic sidecars и fallback не приравнены к standalone owner-sidecar leak XA-10.
- Acquire/Release publication once-ptr-cell, TORN перед recycle и slot-resident counters рассмотрены как реальные защитные механизмы, а не проигнорированы.
- Отсутствие фона для cache decay, per-heap retention, ограниченный remote overflow с окончательным отказом и отсутствие remote reclaim без alloc-xthread уже документированы. Их нельзя называть вновь найденной скрытой гарантией.
- Loom shim прямо использует core atomics и не доказывает реальные registry interleavings. Kani ring-wrap harness проверяет ограниченную арифметику occupancy, не все interleavings и не отсутствие ABA после полного оборота счётчика.

## 3. Замечания P1

### XA-01 — P1: segment_bases возвращает итератор без lifetime владельца; safe use-after-free

**Место:** `src/alloc_core/segment/segment_table/mod.rs:678`, `SegmentTable::bases`, чтение raw slot на строках 679–686.
Публичные выходы: `src/alloc_core/alloc_core/state.rs:173`, `AllocCore::segment_bases`; `src/registry/heap_core/core.rs:714`, `HeapCore::segment_bases`.
**Конфигурация:** alloc-xthread либо alloc-global, включая production. internals не нужен.

Возвращаемый `impl Iterator<Item = *mut u8>` захватывает только копии raw `slots` и `count`, не заимствование таблицы. В edition 2021 lifetime `&self` не захватывается автоматически в таком inherent-method RPIT, если его нет в bounds. Это именно случай, оговорённый [Rust Reference: automatic capturing](https://doc.rust-lang.org/reference/types/impl-trait.html#automatic-capturing).

Статический свидетель, не запускался:

```rust
let mut bases = {
    let core = sefer_alloc::AllocCore::new().unwrap();
    core.segment_bases()
}; // Drop освобождает primordial reservation с массивом slots.
let _ = bases.next(); // Сам next читает освобождённую память.
```

В вызывающем коде нет unsafe. Не требуется разыменовать возвращённый пользователю base: разыменование выполняет closure итератора через Node::read_struct. Аналогично можно продолжать обход после уничтожения core в иной точке.

**Последствие:** UAF/UB из safe API, нарушение собственной lifetime-мембраны. `#[doc(hidden)]` ничего не меняет.

**Исправление:** вернуть `impl Iterator<Item = *mut u8> + '_` на всех трёх уровнях либо явно использовать `use<'_>` с корректными captures; предпочтительно дополнительно захватывать сам `&SegmentTable`, а не только raw pointer. Если внешнему API обход не нужен, сделать методы `pub(crate)`, но lifetime внутреннего итератора всё равно исправить. Комментарий о необходимости `pub` для доступа между модулями одной crate ошибочен: `pub(crate)` достаточно.

**Нужная проверка:** compile-fail на escape за пределы жизни AllocCore и на drop/mutable access при живом итераторе; Miri regression исходного сценария. Не исполнялись.

### XA-02 — P1: foreign epoch handle может удалить vacant slot; defer_destroy(null) не является no-op

**Место:** `src/concurrent/epoch/epoch_handle.rs:25` (только index/generation), `src/concurrent/epoch/epoch_region.rs:316` / `369`, `src/concurrent/epoch/hand.rs:338`, `357`, `391`.
**Конфигурация:** experimental; также ShardedRegion/pinning/batch-api через feature composition.

У EpochHandle отсутствует идентификатор региона. `remove` проверяет только индекс и CAS поколения. Новый vacant slot имеет generation=0, как и первый live handle другого региона. Поэтому:

```rust
let a = sefer_alloc::EpochRegion::with_capacity(1);
let b = sefer_alloc::EpochRegion::with_capacity(1);
let foreign = a.insert(7_u32).unwrap();
let _ = b.remove(foreign);
```

CAS в b выигрывается, хотя b никогда не содержал значение. Value swap возвращает null; код вызывает `guard.defer_destroy(old)`, уменьшает нулевой len и повторно добавляет уже свободный индекс в freelist.

Safety-комментарий `hand.rs:382` утверждает, что defer_destroy(null) — no-op. В локальном crossbeam-epoch 0.9.20 `Guard::defer_destroy` (guard.rs:268) откладывает `ptr.into_owned()`; `Shared::into_owned` (atomic.rs:1530) имеет только debug_assert против null, затем создаёт Owned. Это не nullable destructor. Upstream [исходник Guard](https://docs.rs/crossbeam-epoch/latest/src/crossbeam_epoch/guard.rs.html) подтверждает deferred ownership conversion.

**Последствие:** deferred panic в debug или недопустимая ownership reconstruction/UB в release; повреждение len/freelist происходит сразу. Foreign handle на занятом slot также читает/удаляет чужой объект. ShardedHandle тоже не несёт instance id; LockFreeHandle имеет ту же межэкземплярную логическую коллизию, хотя его реализация на safe Arc не создаёт этот null-reclaim UB.

**Исправление:** добавить неповторяемую identity региона в handles всех трёх concurrent tiers и проверять её до любого доступа/изменения. Для epoch дополнительно не планировать destruction null и не изменять accounting/free-list, если occupancy не была реально захвачена. Простая проверка null после уже выигранного generation CAS не заменяет корректный vacant/live protocol при гонке install.

**Нужная проверка:** foreign handles против пустого/занятого/повторно использованного региона; перенос между shards через split_handle; инвариант len≤capacity; отложенное reclamation после null-сценария. Не исполнялись.

### XA-03 — P1: epoch reclamation допускает T без Send и 'static

**Место:** `src/concurrent/epoch/epoch_region.rs:143` (`impl<T>`), `274` / `316`; `src/concurrent/epoch/hand.rs:391`.
**Конфигурация:** experimental, наследуется ShardedRegion.

Ограничения `T: Send + Sync` стоят только на manual Send/Sync самого AtomicSlot (`hand.rs:461,471`). Они запрещают перенос region между потоками, но **не запрещают локально создать EpochRegion<Rc<_>> и вызвать remove**. Remove передаёт сам T глобальному epoch collector, который может выполнить destructor в другом потоке и после уничтожения региона.

Равным образом допускается T с borrowed данными и Drop, читающим эти данные. Внешний pinned guard может удержать grace period до тех пор, пока локальный referent и регион уже уничтожены; затем deferred Drop читает истёкшую ссылку. Drop региона обрабатывает только всё ещё live pointers и не забирает уже отложенные T обратно.

У `defer_unchecked`, используемого внутри defer_destroy, требования к переносимости и длительности жизни возложены на unsafe caller; [upstream Guard source](https://docs.rs/crossbeam-epoch/latest/src/crossbeam_epoch/guard.rs.html) явно предупреждает о другом потоке выполнения.

**Последствие:** Rc/non-atomic state data race либо UAF в deferred destructor, достижимые через safe region API без переноса самого региона.

**Исправление:** в минимальном варианте требовать `T: Send + 'static` для epoch-owning type и операций, отдающих T collector; сохранить Sync там, где выдаётся shared access между потоками; протянуть ограничения в ShardedRegion/PinnedRunner. Если нужны borrowed/!Send значения, нужен другой reclamation design, возвращающий их в owner-thread и гарантированно завершающий destruction до окончания borrow lifetime. Один только !Send у контейнера этого не обеспечивает.

**Нужная проверка:** compile-fail для Rc и borrowed-Drop T; отдельные controlled-reclamation сценарии с внешним guard и destructor thread-id. Не исполнялись.

### XA-04 — P1: безопасный setter поколения разрушает доказательство уникального reclamation

**Место:** `src/concurrent/epoch/epoch_region.rs:425`, `_set_slot_generation_for_tests`; `src/concurrent/epoch/hand.rs:156`.
**Конфигурация:** experimental; не требуется internals.

Safe `&self` метод произвольно переписывает generation. Проза «только vacant slot / production MUST NEVER» не является unsafe-контрактом и не проверяется. После insert→remove можно вернуть generation к значению сохранённого handle и вызвать remove ещё раз: он снова выиграет CAS по уже vacant slot. Получаются null deferred destruction, двойная выдача индекса и underflow len. При конкурентной установке/удалении setter также разрушает no-reinstall premise из safety proof.

**Это независимо от XA-02:** добавление region identity не закрывает setter на том же регионе.

**Исправление:** убрать из обычной сборки; сделать unsafe hook с формальным контрактом отсутствия действующих handles/readers/конкурентных операций и корректного состояния, либо заменить safe конструктором свежего никогда не публиковавшегося тестового slot с выбранным начальным поколением. Одного `&mut self` или одного `#[doc(hidden)]` недостаточно: старые Copy handles могут сохраниться.

**Нужная проверка:** отрицательная compile surface без internals; stale-handle replay после setter; saturation с сохранением корректного freelist. Не исполнялись.

### XA-05 — P1: safe diagnostics проверяют адрес, но разыменовывают caller pointer без provenance

**Основное место:** `src/alloc_core/alloc_core/alloc_core_core_diag/header_diag.rs:27`, `dbg_kind_byte_of`, разыменование на строке 34.
Другие примеры: тот же файл `:116,135,152,170,250`; `table_diag.rs:28,52,186`; `src/alloc_core/small/alloc_core_small_pool/mod.rs:716`; `src/alloc_core/small/alloc_core_small_diag.rs:52,76,228`; `src/registry/heap_core/diag/queries.rs:30`.
**Конфигурация:** alloc-core + internals и соответствующие дополнительные features.

Пример полностью safe:

```rust
let mut core = sefer_alloc::AllocCore::new().unwrap();
let p = core.alloc(std::alloc::Layout::from_size_align(16, 16).unwrap());
assert!(!p.is_null());
let forged = std::ptr::without_provenance_mut::<u8>(p.addr());
let _ = core.dbg_kind_byte_of(forged);
```

`segment_base_of_ptr` сохраняет provenance аргумента; `contains_base_ro` лишь сравнивает адрес с таблицей. Совпадение успешно, но оно не заменяет forged pointer каноническим указателем reservation. Node::offset/read затем обращаются к памяти с отсутствующим provenance. Это прямо запрещено контрактом [without_provenance_mut](https://doc.rust-lang.org/std/ptr/fn.without_provenance_mut.html).

**Последствие:** safe-code UB даже при реально живом адресе, без dangling/unmapped memory. Address membership — не доказательство происхождения указателя.

**Исправление:** safe diagnostics должны искать по адресу и **возвращать/использовать canonical base из собственной таблицы**, а не dereference исходного аргумента; либо эти методы должны быть unsafe с явным provenance/liveness/aliasing контрактом. Предпочтителен первый вариант для действительно безопасных query API. Применить системно ко всем `dbg_*_for`/forwarders, а не к одному методу.

**Нужная проверка:** Miri strict provenance для no-provenance pointers, соседних живых allocations с совпадающей маской, null/foreign pointers; обычные canonical queries должны продолжать работать. Не исполнялись.

### XA-06 — P1: batch-free не учитывает Large representation после medium realloc promotion

**Место:** `src/registry/heap_core/free/dealloc_batch.rs:192`, `239`, `297`, `320`.
Связь: `src/registry/heap_core/free/realloc.rs:261`, `540`; правильный scalar dispatch — `src/registry/heap_core/free/dealloc_own_base.rs:204`.
**Конфигурация:** fastbin + batch-api + medium-classes и достижимый promotion predicate; например production + batch-api + medium-classes без exact-span-large.

Realloc может перевести Small allocation в **настоящий Large segment**, сохраняя новый Layout в medium/small class диапазоне. Например рост от 64 KiB до 256 KiB с alignment 8 проходит promotion, а новый Layout классифицируется Small из-за medium-classes.

Scalar free явно проверяет Large kind для такого случая. Batch-free классифицирует только Layout, затем считает любой owned base Small. Без hardened он читает и пишет `magazine_bitmap`/`alloc_bitmap` по small-metadata offsets **внутри пользовательского payload Large allocation**. Payload вправе содержать неинициализированные байты; чтение их как u8 oracle уже нарушает memory safety. Даже на заполненном payload возникают ложные double-free решения и неправильное помещение Large pointer в small magazine. С hardened ветка просто `continue` для всякого Large и гарантированно теряет законно переданный promoted allocation.

Контракт batch API допускает любое live allocation этого allocator с правильным Layout, а не только pointers, первоначально полученные именно alloc_batch; realloc-result под него попадает.

**Последствие:** на non-hardened — некорректное чтение payload как metadata, включая UB на uninitialized bytes; на hardened — leak корректного allocation. Это не caller double-free или неправильный Layout.

**Исправление:** до всех bitmap accesses маршрутизировать Large kind в scalar/kind-aware deallocation; использовать один общий promotion-aware eligibility predicate для scalar и batch paths. Для hardened отличать легальный promoted Large от действительно неверного Layout.

**Нужная проверка:** alloc→realloc promotion→dealloc_batch, пустая/полная magazine, uninitialized payload, mixed batch, с/без hardened; medium-classes-wide и large-reserved-capacity. Не исполнялись.

### XA-07 — P1: safe HeapOverflow hook способен создать обращение к null sidecar в release

**Место:** `src/registry/heap_overflow.rs:806`, `dbg_reserve_unpublished_for_test`; последующее `slot` на строках 492–512; `src/registry/bootstrap/overflow_sidecar.rs:282`.
**Конфигурация:** alloc-global + alloc-xthread + internals, native release, не miri.

Полностью safe последовательность: создать `HeapOverflow::new_boxed_for_test()`; вызвать `dbg_fill_and_drain_inline_tier_for_test()` (head=tail=64, sidecar ещё null); вызвать `dbg_reserve_unpublished_for_test()`; затем `drain(|_, _| {})`.

**Исправление:** сделать setter unsafe и документировать quiescence/capacity/backing state либо превратить в safe checked operation, который не изменяет tail при нарушении предусловий и корректно материализует нужный tier. **Нужная проверка:** именно native release regression. В `cfg(miri)` HEAP_OVERFLOW_CAP=64 и SIDECAR_CAP=0, поэтому приведённый native tier-crossing механизм обычный Miri target **не моделирует**; нужен test representation с ненулевым sidecar или соответствующий production-layout Miri shim. ### XA-08 — P2: корректность ring зависит от неограничиваемой паузы потока меньше полного оборота u32

### XA-14 — P2: cross-thread remove ошибочно обещан lock-free

### XA-15 — P2: документация подменяет GlobalAlloc no-unwind контракт наблюдением о compiler shims

**Место:** `src/global/sefer_alloc/mod.rs:123`, абзац «Panic-in-GlobalAlloc is abort, not UB»; связанные tripwires `:65`.
**Конфигурация:** alloc-global; документационный дефект safety boundary.

Текст универсально утверждает, что panic любого GlobalAlloc метода гарантированно abort и не UB благодаря `__rust_*` nounwind shims. Публичный normative контракт trait по-прежнему запрещает unwind как UB: [GlobalAlloc, Safety](https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html#safety). Кроме того прямой `GlobalAlloc::alloc(&allocator,...)` не обязан идти через эти shims.

Наличие конкретного abort в сгенерированном коде не превращает unwind в допустимый контракт на всех поддерживаемых toolchains/call paths. Panic hooks выполняются до eventual abort и могут аллоцировать/reenter. Здесь **не заявляется**, что перечисленные инвариантные expect сегодня достижимы при корректном production state; ошибочен безусловный safety-вывод.

**Последствие:** неверная предпосылка для будущих изменений unsafe impl и downstream direct callers; ложное оправдание добавления panic на allocator path.

**Исправление:** записать нормативное «allocator methods не должны unwind», отдельно описать фактическое поведение проверенного toolchain как наблюдение. Если нарушение инварианта должно завершать процесс, использовать явный allocation-free abort-path, а не доказывать безопасность panic наличием shims. Сохранить доказательства недостижимости каждого tripwire и учитывать debug/config-conflict paths отдельно.

**Нужная проверка:** статический no-unwind audit всех reachable paths; после разрешения запусков — subprocess direct-call/global-shim, panic strategies и MSRV. Не исполнялась.

- `src/concurrent/lock_free/lock_free_region.rs:140–147`: retirement при достижении u32::MAX, тогда как remove на строках 351–358 ещё раз помещает slot generation=MAX в freelist; его окончательно retiring remove происходит позже. Wrap не происходит, но сформулированный threshold неверен.

- `src/alloc_core/platform/sidecar.rs:1`: ссылка на несуществующий OwnedSidecar; `src/concurrent/sharded/sharded_region.rs:16`: ссылка super::hand после переразбиения модулей.
- `src/lib.rs:45`: безусловная O(1)-подобная характеристика stats расходится с alloc-stats slot walks; детальный метод описывает их отдельно.

**Механизм:** исторические абзацы, оправдания старых фиксов и абсолютные «единственный / всегда / невозможно / proven» пережили изменения кода. Повторение safety rationale не заменяет актуальную проверяемую предпосылку. Сомнительные рекламные формулы вроде «concurrent crown jewel» не дают технического контракта.

**Последствие:** повышается вероятность ошибочного следующего unsafe изменения; broken links и противоречивые API обещания затрудняют аудит.

**Исправление:** оставить в исходнике короткое актуальное правило и конкретный caller/lifetime/publication proof; историю и perf rationale вынести в design docs с относительными ссылками. Устранить перечисленные фактические расхождения. Не приравнивать качество/объём комментария к доказанной безопасности.

**Нужная проверка:** rustdoc для minimal/production/all relevant features и private items с broken-link errors; ручное сравнение safety prose с cfg. В этом проходе rustdoc не запускался.

## 6. Межмодульные связи и feature/platform выводы

### Ownership/reclamation цепочки

1. **AllocCore → SegmentTable → primordial reservation.** Таблица размещена внутри owned VM allocation, поэтому любой её lazy iterator обязан держать lifetime core (XA-01).
2. **HeapCore realloc promotion → GlobalAlloc/batch dealloc.** Layout class и физический SegmentKind — разные признаки. Promotion делает возможным сочетание Small class + Large backing; все free paths обязаны согласоваться (XA-06).
3. **EpochRegion → AtomicSlot → crossbeam collector.** Автотрейты контейнера не ограничивают поток/время отдельного deferred destructor (XA-03); generation без identity не доказывает владение slot (XA-02).
4. **Registry count → chunk publication → stats.** Count — выдача индекса, не completion flag chunk init (XA-09).
5. **Owner-only sidecar → AllocCore::drop.** Process-lifetime allocation strategy недопустимо автоматически переносится на временный standalone owner (XA-10).
6. **Dirty notification после ring publish.** Текущий resolve-before-publish/apply-after-publish хранит slot-resident target; повторное чтение уже потенциально unmapped segment после publication не используется. Это важное положительное свойство, которое нужно сохранить.
7. **TLS teardown → recycle → следующий owner.** TORN ставится до publication FREE; HeapCore/remote state не уничтожаются. Не обнаружено самостоятельного доказанного нарушения именно этого handoff.

### Feature-матрица, рассмотренная статически

| Группа | Вывод |
|---|---|
| default/std; no-default | Реэкспорты sefer-region; allocator не включён; отдельная верификация dependency всё ещё нужна |

В src собственных extern declarations/экспортированного C ABI нет; настоящие OS вызовы делегированы aligned-vmem/numa-shim. Проверены роли reservation_ptr/reservation_len, alignment и publication на границе вызовов. Полная ABI/errno/platform реализация companion crates здесь заново не сертифицировалась. Releasing default Segment и NUMA reservation должен сохранять точные параметры исходной reservation, а не использовать usable length как замену.

Manual unsafe traits в src: GlobalAlloc (`global/sefer_alloc/global_alloc.rs:29`), HeapSlot::Sync (`registry/heap_slot.rs:531`), Registry::StackStorage (`heap_registry/stack.rs:125`), AtomicSlot::Send/Sync (`concurrent/epoch/hand.rs:461,471`), loom-shim OncePtrCell::Send/Sync (`bootstrap/loom_shim.rs:42,44`). Области ответственности проверены отдельно. Unbounded marker impl у pointer-only shim не означает передачу T само по себе; фактическое dereference/ownership должно доказываться потребителем. Для AtomicSlot проблема не в отсутствии Sync bounds, а в deferred destruction вне bounds методов.

## 7. Дополнительные возможности упрощения/ускорения — не отдельные подтверждённые дефекты

Эти предложения не входят в число 20 и не основаны на исполненных измерениях:

- `ShardedRegion::MY_SHARD` хранит единственный id на thread для всех instances. Это уже документированная one-region-per-pool политика, а не новый скрытый баг. Если расширять use case, добавить region-keyed binding; не навязывать HashMap/TLS allocation горячему пути без нужды.
- `src/registry/heap_core/alloc/hot.rs:551,612`: при non-virgin small alloc_zeroed class вычисляется, затем alloc вычисляет его снова. Общий classified entry point может убрать повтор; проверить реальное codegen и горячий путь, не обещать speedup только по исходнику.
- `src/alloc_core/small/alloc_core_small_magazine.rs:265–268`: `issued_so_far.contains` внутри drain callback даёт O(batch × drained) проверок. Для действительно больших batch-api workloads рассмотреть ограниченный membership structure/bitmap, сохранив запрет повторной выдачи. Обычная magazine=16 сама по себе не оправдывает новую структуру.
- `src/alloc_core/alloc_core/lifecycle.rs:416`: Drop собирает массив из 4096 пар (64 KiB на 64-bit). Можно освобождать non-primordial reservations потоково, primordial последним, без такого stack scratch; нужно сохранить валидность table при обходе и исправить XA-01.
- `src/global/fallback.rs:333`: contended CAS-spin непрерывно модифицирует общую cache line. Test-and-test-and-set/backoff способен уменьшить contention, но важнее сохранить no-allocation и teardown semantics. Не обещать общий throughput выигрыш без отдельного fallback режима.
- `src/alloc_core/platform/size_classes.rs:229,272`: есть SC и отдельная копия SIZE2CLASS. Следует проверить binary footprint wide-medium конфигурации и возможность одного canonical массива/ссылки, сохранив const API. Linker/codegen дедупликация статически не измерена.
- Большие исторические комментарии, повторные diagnostic forwarders и повторение cfg promotion predicates усложняют проверку. Извлекать общий eligibility/ownership protocol полезнее, чем сокращать количество строк ради количества строк.

## 8. Проверки, необходимые перед следующим release — НЕ ЗАПУСКАЛИСЬ

### Первая очередь: закрытие P1

1. Compile-fail lifetime surface для segment_bases на edition 2021/MSRV; Miri safe iterator UAF.
2. Epoch foreign-instance handles для пустого/занятого/переиспользованного slot и каждого concurrent tier.
3. Deferred Drop non-Send/borrowed T, длительный внешний guard, destructor в другом потоке; negative type-bound tests.
4. Safe-hook surface: произвольный epoch generation setter должен стать недоступен/unsafe; safe API не должен ломать ownership.
5. Strict-provenance diagnostics с `without_provenance_mut`; корректные canonical pointers и invalid-address negative cases.
6. Scalar alloc/realloc → batch dealloc promotion matrix; uninitialized payload и hardened on/off; all live allocations освобождаются ровно один раз.
7. Native release HeapOverflow inline→sidecar boundary; Miri вариант должен сохранять эту топологию.

### Concurrency и lifecycle

8. Реальная или faithful reduced-width модель RemoteFreeRing с delayed cached-head publication и tail ABA; wrap safety отдельно от power-of-two indexing.
9. Pause после registry count increment до chunk init; stats не должен материализовать память или ждать init.
10. Одновременные TLS teardown, fallback contention, slot reuse и поздние remote frees; dirty notification после освобождения segment.
11. Panic/error cleanup: callbacks в test rings, OOM chunk/core/sidecar/commit, old allocation сохранён при failed realloc.
12. Standalone AllocCore Drop ledger, owner sidecars, cache entries, table holes, primordial-last release.
13. NUMA 9+ ids, bucket reuse/unknown promotion, node cache invalidation на recycled heap.
14. Pinning runner с другим числом shards; queue progress guarantee и устойчивость poison recovery.

### Feature/platform/build gates

15. Default/no-default/std, alloc-core, alloc-global, xthread, fastbin, production по отдельности; затем рискованные пары/тройки, а не только all-features.
16. Отдельно production+medium+batch с/без hardened; exact-span+reserved-capacity; NUMA+exact/reserved; virgin-zero-skip+lazy+batch; extended cache с budget=0 и finite budgets.
17. MSRV 1.88 и актуальный stable; debug/release, поддерживаемые panic strategies, direct GlobalAlloc calls и shims.
18. Native Windows x64 (reserve/commit/decommit), Linux x64, macOS arm64/16 KiB pages, native ARM weak memory и Linux 64 KiB pages. QEMU не считать полным ARM memory-model доказательством.
19. 32-bit compile gates после определения политики; allocator target_has_atomic предпосылки и явно неподдерживаемые OS.
20. Rustdoc minimal/production/relevant feature sets, включая private items для broken internal links; cargo-semver-checks с baseline после согласования API tightening.
21. Cargo audit/deny и точная версия toolchain/security advisories — отдельно от этого статического source review; прочитанный lockfile не является advisory scan.

### Измерения после correctness fixes

22. Независимый VM ledger для reconciliation и decommit-vs-release counters; не использовать ошибочный счётчик как oracle для самого себя.
23. Allocation/refcount counters для stale LockFreeRegion::remove и remote queue steady state.
24. Batch membership complexity, fallback contention, class reuse в alloc_zeroed, sidecar/binary footprint.
25. Сопоставимые A/B с одинаковыми features/compiler/target; deterministic counters для CI, native timing как trend. В этом отчёте нет performance receipts.

## 9. Очерёдность исправлений и условия изменения вердикта

1. Закрыть XA-01–XA-07, не заменяя unsafe proof отключением теста/ослаблением oracle.
2. Согласовать поддерживаемые target/feature contracts и queue progress/wrap политику.
3. Исправить stats/reconciliation/VM счётчики до любых новых release/perf заявлений, опирающихся на них.
4. Устранить resource lifecycle gaps и добавить регрессии на конкретные witnesses.
5. Затем оптимизировать COW/queue/cold paths, сверяя не только время, но и allocations/retention.
6. Обновить safety docs по фактическому механизму и повторить независимое ревью затронутых взаимосвязей.

Исходный код и конфигурация этим ревью не менялись. Исправления только предложены. Статический вывод NO-GO не подменяет проверку выполненного исправления: вердикт может быть пересмотрен после закрытия блокеров и получения перечисленных применимых результатов.
