## P4-1. SKIP перенесён через child capture, но остаётся под parent capture

Места: `tests/non_utf8_name.rs:126`, `:128`, `:262`;
`.github/workflows/ci.yml:1091`.

Parent теперь получает содержимое result-файла, однако run_scenario_alone
вызывается из обычного успешного `#[test]`. Его println на строке 128 тоже
попадает в libtest capture. CI запускает `cargo test -p proc-memstat --all-targets`
без показа stdout успешных tests.

Поэтому даже при успешно записанном и прочитанном SKIP-файле обычный запуск
по-прежнему показывает `... ok`, не объясняя, что реальные assertions child
не выполнялись. Это не гипотеза об ошибке файловой системы: достаточно
штатного NotFound→skip на legacy kernel и штатного capture. Поведение описано
в [Rust Book: Showing Function Output](https://doc.rust-lang.org/book/ch11-02-running-tests.html#showing-function-output).

Есть реальное улучшение относительно раунда 4: теперь `--show-output` или
`--nocapture` у parent позволит увидеть перенесённый текст. Раньше текст
терялся ещё внутри child, и одних внешних флагов было недостаточно. Но фраза
«visible ... unconditionally» пока сильнее того, что гарантирует обычный runner.

Довести отображение до последнего уровня: например, закрепить показ результатов
успешных tests для этого target в CI либо доставлять notice через явно
неперехватываемый/структурированный канал. Не превращать legitimate skip в
failure. Для проверки нужен сценарий именно всего parent/child протокола с
наблюдением конечного вывода, а не только наличия result-файла.

Замечание относится к наблюдаемости покрытия, не к работе библиотечного
fallback. Best-effort запись маркера и её возможная потеря дополнительно
оговариваются самим кодом; найденная проблема capture существует и без ошибок записи.

## P4-2. Любая ошибка создания non-UTF-8 fixture ослабляет проверку

Места: `tests/status_read.rs:171`, `:181`, `:186`.

При любом Err от fs::write тест объявляет, что filesystem отказалась от
non-UTF-8 имени, и вместо чтения точных bytes проверяет только `result.is_err()`.
Но fs::write объединяет создание файла и запись: ошибка может означать отсутствие
прав, недоступный каталог или другую проблему подготовки, а не свойство
кодировки имени. См. [std::fs::write](https://doc.rust-lang.org/std/fs/fn.write.html).

Контрпример для этого отдельного теста: существующий каталог позволяет поиск
файлов, но не создание новых файлов текущим пользователем. Создание fixture
отказывает; primary и fallback отсутствуют; reader возвращает Err; assertion
проходит без единого успешного чтения не-UTF-8 файла. Это не утверждение, что
весь suite при такой среде будет зелёным: другие файловые tests способны
отдельно обнаружить проблему. Дефект в том, какое свидетельство даёт именно
новый regression test и как он диагностирует отказ.

Для действительно несовместимой с такими именами filesystem ослабленная
проверка отсутствия panic допустима, но её следует отличать от общего setup
failure. Ограничить downgrade подтверждённым случаем неподдерживаемого имени
либо явно сообщать отдельный «fixture недоступен», не выдавая это за полную
проверку чтения. Ошибки подготовки вне этого случая должны оставаться видимыми.

Также Err от записи не доказывает, что файла нет: после неудачной записи уже
созданный файл может остаться. Фраза assertion «with no fixture file on disk»
поэтому тоже требует подтверждения предпосылки. Код в таком случае способен
упасть, а не ложно пройти; здесь не заявляется утечка или порча данных библиотеки.
Сам переход reader на Path и успешную ветвь fixture принимаю.

## Общий обзор кода и контрактов

### Linux

Reader получает Path без Unicode-конверсии и читает bytes. Успешный primary
сразу возвращается; только NotFound разрешает обращение к legacy fallback;
прочие ошибки не подменяются. Path::new над константами не требует создания
новых строк или передачи владения путём.

Parser остаётся безопасным Rust: диапазоны выводятся из границ входного среза,
decimal accumulation checked, единица kB и хвост проверяются. Первый совпавший
prefix определяет результат, как документировано. Tri-state сохраняет отсутствие,
ошибку и значение до conversion. В ней все три memory-поля проходят checked
×1024, включая optional; ошибочное optional не становится None.

Политика ошибок и единицы не изменились: ошибка доступа — Os, непригодное
содержимое — Malformed, неизвестный backend — Unsupported; best-effort wrapper
сводит Err к default. Новый Path API — внутренний, public API не расширялся.
Доступ к памяти после выхода leader, отличия commit_charge от virtual_size,
пределы точности RSS и ограничения legacy-пути сохраняют уже проверенный смысл.

### Windows, macOS и unsafe

Windows хранит output в корректной base PROCESS_MEMORY_COUNTERS, устанавливает
cb и проверяет BOOL перед использованием полей. Структура состоит из двух u32
и восьми SIZE_T; все поля допускают zero-init. Pseudo-handle не требует закрытия.
Mach buffer сохраняет размер 48 bytes, правильные offsets и count 12; cached
task-port читается по значению, без приобретения или освобождения права.
Обоснование startup/fork реинициализации не изменилось.

Новых unsafe-блоков в production, raw-pointer входов в public API, ручных
Send/Sync или lifetime-преобразований не появилось. Native fixture использует
собственный child, а не завершает поток вызывающего приложения. Неизвестные
SYS_EXIT остаются явным ограничением покрытия, не угадываемым syscall number.
Native linking и исполнение этих ветвей в данном ревью не выполнялись.

### Tests, docs и артефакты

Exact-value fixtures по-прежнему обращаются к production conversion и ловят
потерю множителя, ×1000/×2048 и ошибки соответствия полей. Отдельно проверяются
absence, malformed и оба вида overflow. Новый Path fixture имеет правильную
предпосылку `path.to_str().is_none()` и проверяет точные bytes при успешном
создании; это сильнее обычного валидного Unicode-имени. Код не меняет глобальный
TMPDIR в многопоточном test process.

README и описание полей сохраняют явные ограничения native RSS, включая
Windows large pages/AWE и Linux explicit HugeTLB, и не обещают атомарный снимок.
CSV сохраняет исправленное экранирование. Исторические perf-числа привязаны к
`3119719`, не считаются измерением текущей реализации. Изменений CI/release
workflow в рассматриваемом диапазоне нет; прежние три OS-ряда и downstream
link-and-call не выдаются за выполненные здесь проверки.

## Ускорение, сложность, копирования и аллокации

- **Асимптотика:** три поиска остаются O(L), не O(L²), где L — длина status.
  Обработка каждого выбранного числа ограничена его строкой; промежуточные
  коллекции не создаются. В собственном runtime-коде крейта не найдено
  вложенного роста O(n²) или неограниченного retry-loop.
- **Память:** Linux выделяет Vec под файл, то есть O(L) временной памяти.
  Смена str на Path новой аллокации не добавляет. Conversion берёт срез из
  существующего Vec, MemStat — небольшой Copy value без heap-владения.
  Windows/macOS используют стековые output buffers.
- **Перспективный вариант при частом опросе:** переиспользуемый scratch или
  streaming parser с O(1) временной памятью. Требуются корректные partial reads
  и перенос строк между chunks; фиксированное отсечение первых 4/8 KiB остаётся
  неверным из-за потенциально длинных строк до memory fields. Выигрыш здесь
  не измерялся; старый NO-GO для fused scan не исследовал этот вариант.
- **Маленькая экономия только в tests:** вместо
  `String::from_utf8(status_bytes.clone())` подходит проверка заимствованного
  среза через `str::from_utf8`. Для SKIP можно рассмотреть более простой
  протокол, не требующий временного файла и дополнительных файловых операций;
  важна различимость pass/skip/failure и конечная видимость сообщения.
  Ни один из этих пунктов не является заявлением об ускорении библиотеки.

Для редких snapshot нынешний простой путь разумен. Не предлагаю усложнять
публичный API, добавлять зависимости или кэшировать procfs fd без решения
его task/fork-привязки ради непроверенной микроэкономии.
