## P2-1. Real-stdout тест ложно падает при последовательном child libtest

Места: `tests/protocol.rs:250`, `:270`, `:290`, `:299`, `:305`.

Child запускается с `--exact ... --nocapture`, но формат вывода и число потоков
не заданы. При `RUST_TEST_THREADS=1`, унаследованном дочерним процессом, libtest
использует последовательный pretty formatter. Аналогичное условие возникает,
когда доступный parallelism равен одному.

В Rust 1.88, то есть уже на заявленном MSRV, formatter перед тестовым телом
печатает `test <name> ... ` **без перевода строки**. Получается такая схема
stdout — это иллюстрация по исходникам, не захваченный вывод:

```text
test real_emit::real_stdout_emit_family_exact_bytes ... RESULT arm=sefer
RESULT rss_kib_max=18446744073709551615
...
```

Первый assertion `stdout.contains(EXPECTED_BLOCK)` проходит: ожидаемый блок
присутствует как подстрока. Затем `.lines().filter(|l| l.starts_with("RESULT "))`
отбрасывает первую метрику, потому что её строка начинается с `test `. Сравнение
с полным списком ожидаемых метрик падает, хотя все функции напечатали правильные
байты. Число потоков не влияет на корректность emitter, но влияет на его оракул.

Механизм проверен по [PrettyFormatter Rust 1.88](https://github.com/rust-lang/rust/blob/1.88.0/library/test/src/formatters/pretty.rs#L156),
[выбору is_multithreaded](https://github.com/rust-lang/rust/blob/1.88.0/library/test/src/console.rs#L277)
и [get_concurrency](https://github.com/rust-lang/rust/blob/1.88.0/library/test/src/helpers/concurrency.rs#L5).

Важно: одного `--test-threads=1` у внешнего cargo/libtest недостаточно для этого
контрпримера — его argv не пересылаются child. Здесь условие именно наследуемый
`RUST_TEST_THREADS=1` или один доступный поток.

Отделить служебное framing от проверяемых байтов: например, явно использовать
terse formatter для обычного child-теста либо отдельный helper без libtest.
В [TerseFormatter](https://github.com/rust-lang/rust/blob/1.88.0/library/test/src/formatters/terse.rs#L193)
имя заранее выводится для padded benchmark, не для обычного test. Нужен
регрессионный сценарий с последовательным child. Не убирать проверки лишних
метрик и не подменять исправление принудительным увеличением числа потоков.

## P3-1. Drift guard проверяет substring, а не актуальный контракт runner

Места: `tests/protocol.rs:381`, `:429`, `:432`, `:570`;
`scripts/paired-ab-runner.mjs:253`.

Проверка `runner_src.contains(RUNNER_REGEX_SRC)` подтверждает только наличие
текста тела regexp где-нибудь в файле. Node затем исполняет заново собранную
копию этого тела с жёстко заданным `.trim()`, а не функцию из runner.

Два конкретных изменения production parser останутся незамеченными:

- Добавить flag `i` к regexp. Substring остаётся, реальный runner начинает
  принимать lowercase prefix/uppercase key, а тестовый `new RegExp(parsed.regex)`
  по-прежнему не имеет flags. Даже существующие соответствующие negative
  fixtures тестируют старую семантику и не обнаружат рассогласование.
- Убрать `.trim()` перед `.exec()`. Substring остаётся, Node-проверка продолжает
  сама применять `.trim()` и пропускает изменение handling внешних пробелов.

На текущем HEAD regex body и вызов действительно совпадают — это полезная
проверка движка, и исправление Unicode-ошибки первого раунда принимаю.
Неверно именно обещание в комментарии, что изменение parse contract заставит
guard упасть: flags и preprocessing не входят в проверяемое свидетельство.

Лучшее решение — общий side-effect-free parser/helper, используемый runner
и interop-тестом. Не импортировать текущий runner целиком: его top-level `main`
запускает работу. Если остаётся source guard, проверять активный callable,
flags и preprocessing, а не произвольное вхождение фрагмента. Оба указанных
изменения должны стать отрицательными контролями.

## P3-2. Ошибки запуска Node превращаются в скрытый успешный SKIP

Места: `tests/protocol.rs:419`, `:439`, `:441`, `:442`, `:521`;
`.github/workflows/ci.yml:1231`, `:1239`; `CHANGELOG.md:90`.

Комментарий различает отсутствующий Node и настоящую ошибку среды, но любой
`Err` от первого `Command::output()` попадает в skip. Например, найденный
исполняемый путь без права выполнения даст PermissionDenied — проверка corpus
не состоится, а test вернёт успех. Ошибки создания процесса по другим причинам
также не означают, что optional инструмент просто не установлен.

Дополнительно оба skip-сообщения — `eprintln!` внутри успешного `#[test]`.
Обычный libtest захватывает их, а CI не запрашивает вывод успешных tests.
Наличие успешной строки с именем Node-теста поэтому не доказывает, что Node
вообще исполнял corpus. Завершающий `println!` с verdicts тоже захватывается.
Общий путь `_eprint -> print_to -> capture` виден в
[stdio Rust 1.88](https://github.com/rust-lang/rust/blob/1.88.0/library/std/src/io/stdio.rs#L1096).

Отсутствие scripts в опубликованном пакете — нормальный повод пропустить
repository-only interop, не предлагаю делать это ошибкой для пользователей
архива. Но обычные spawn failures нельзя классифицировать как «нет Node».
Ограничить permissive skip соответствующим случаем, сделать notice видимым
вне libtest capture, а в repository CI явно требовать выполнения interop-пути
и наличия его зависимостей. Это один дефект политики необязательной проверки
с двумя механизмами потери свидетельства: классификацией и отображением.

## P3-3. Corpus path теряет байтовую идентичность на границе Rust -> Node

Места: `tests/protocol.rs:465`, `:484`, `:537`, `:572`.

Rust создаёт corpus через настоящий PathBuf из `temp_dir`. Затем путь
передаётся переменной окружения, а Node читает его через `process.env` как
JavaScript string и передаёт string в `fs.readFileSync`.

На Unix возможен корректный существующий TMPDIR с raw-байтом FF в компоненте
имени. Rust запишет corpus туда, но строковый путь Node интерпретируется
как UTF-8 и не может адресовать тот же raw-FF путь. Результат — ошибка открытия
corpus и падение теста при исправных parser/emitter. Использование env вместо
argv не устраняет эту границу кодировки.

Вывод основан на [Node: string/Buffer paths](https://nodejs.org/docs/latest-v22.x/api/fs.html#string-paths)
и представлении env value как V8 String в
[Node 22 RealEnvStore::Get](https://github.com/nodejs/node/blob/v22.19.0/src/node_env_var.cc#L116).
В [Node 24.12](https://github.com/nodejs/node/blob/v24.12.0/src/node_env_var.cc#L114)
возвращается тот же строковый вид через ToV8Value. Здесь не требуется
предполагать конкретный символ замены: UTF-8 string-path уже не равен raw FF.

Передавать JSON по stdin либо кодировать нативные path bytes и восстанавливать
Buffer на поддерживающем такой путь Node. Stdin проще: исключает ненужную
файловую операцию, path round-trip и cleanup. Сейчас cleanup расположен после
panicking helper, поэтому при таком сбое corpus ещё и остаётся на диске.
Глобальный TMPDIR в процессе тестов менять не надо; сценарий проверять
изолированным child. В этом ревью такой каталог и процессы не создавались.

## P4-1. Тест fallible-реэкспорта не закрепляет доступность SnapshotError

Места: `tests/protocol.rs:170`, `:175`, `:178`; `src/lib.rs:115`.

Тест вызывает `proc_probe::try_snapshot`, но нигде не называет
`proc_probe::SnapshotError` в коде: тип `e` выводится из результата функции.
Удаление одного `SnapshotError` из re-export не сломает этот тест, хотя
заявленная возможность именовать error через фасад исчезнет.

Комментарий про обязательный wildcard из-за non_exhaustive тоже не описывает
написанный match: разбирается `Result`, а `Err(e)` просто связывает payload,
не сопоставляя варианты SnapshotError.

Добавить явный type/API pin с `Result<proc_probe::MemStat,
proc_probe::SnapshotError>` и функцией реэкспорта. Сам текущий реэкспорт
корректен; замечание к защите его API и пояснению, не к runtime measurement.

## P4-2. Quick start включает измерение RSS и вывод в elapsed_ns

Место: `README.md:10`, `:11`, `:12`, `:13`.

После объявления t0 пример выполняет snapshot, печатает `rss_kib` и только
потом снимает elapsed. В длительность входят OS measurement и первый stdout
emit: lock, форматирование, возможное ожидание вывода. Сам последующий
`emit_ns` туда не входит — elapsed вычисляется до его вызова.

Это не ошибка Instant и не утверждение, что существующие пользовательские
benchmarks уже испорчены. Но quick start измерительной библиотеки задаёт
неудачный шаблон: длительность зависит от инструмента отчётности.
Показать измеряемую работу отдельно, зафиксировать elapsed до snapshot/output,
а затем публиковать оба результата. Если намеренно измеряется стоимость
самой instrumentation, назвать метрику соответственно.

## P4-3. Собственные tests и feature-off не закреплены на MSRV

Места: `.github/workflows/ci.yml:1209`, `:1255`, `:2562`, `:2566`.

Новый job действительно проверяет пакет, но только на stable. Корневой MSRV job
компилирует root test/dev graph; proc-probe достигается как default-feature
dependency, не как пакет со своим `tests/protocol.rs`. Отдельных MSRV-команд
для proc-probe и его bare-metal feature-off конфигурации нет.

Это остаточный пробел матрицы, не заявление о найденном API новее Rust 1.88.
Достаточно добавить явный package-scoped compile-check собственных targets
в обеих конфигурациях и feature-off bare-metal проверку на 1.88. Расширять
весь workspace или вводить новую дорогую matrix ради этого не требуется.

## P4-4. Две небольшие неточности в новых комментариях

Места: `tests/protocol.rs:240`, `:241`, `:337`.

- Внутрипроцессный capture libtest описан как принадлежащий harness pipe.
  На проверенном Rust 1.88 это thread-local capture buffer; OS pipe появляется
  отдельно из `Command::output`. Не смешивать эти два уровня — именно их
  различие существенно для теста. См.
  [OUTPUT_CAPTURE](https://github.com/rust-lang/rust/blob/1.88.0/library/std/src/io/stdio.rs#L18).
- U+2003 подписан EN SPACE, но это EM SPACE; EN SPACE — U+2002.
  [UnicodeData](https://www.unicode.org/Public/16.0.0/ucd/UnicodeData.txt).

Оба пункта исправляются комментариями и не меняют результаты функций.

## Общий обзор кода и возможностей ускорения

Production-слой остаётся пятифункциональным: borrowed key/value или число
поступает непосредственно в std formatting. Собственных String/Vec, clone,
числовых `as`, caches, unsafe или FFI у emitter нет. Новые re-export не
создают обёртки над OS handles и не меняют время жизни данных зависимости.

Стоимость передачи строк — O(K + V) по количеству байтов key/value;
числовая ширина фиксирована, u128 сохраняется без сужения. Снижения
асимптотики в этих функциях не требуется. Замена прямого formatting на
`emit(key, &value.to_string())` добавила бы аллокацию и была бы ухудшением.

Feature-off библиотека теперь действительно не использует std-зависимость.
В tests std доступен от собственного test crate, поэтому Node helper не
доказывает наличие std в feature-off библиотеке и не опровергает no_std fix.
Crate-level docs не оставляют прежние intra-doc ссылки на cfg-удалённые items.

Обвязка получила правильные отрицательные контроли: literal RESULT не зависит
от constant; u64::MAX, i64::MIN и u128::MAX обнаруживают сужение; проверка
verdicts проверяет длину и алфавит до индексирования. Corpus ограничен статическими
строками. JSON escaper обрабатывает quotes, backslash и C0 controls; на его
фактическом bounded input ошибки кодирования или переполнение не найдены.

Основная ненужная работа теперь в тесте, не в runtime API: два Node startup,
материализация JSON, промежуточные строки и temp-file round trip. При исправлении
P3-3 разумно упростить transport; это одновременно уменьшит I/O и число
failure paths. Микрооптимизировать оставшиеся небольшие cold allocations или
добавлять новую formatter dependency оснований нет.

Writer/sink API по-прежнему мог бы уменьшать количество stdout locks для
пакетного вывода, но решение не расширять публичный API без измерений принимаю.
Новых чисел ускорения или гарантий zero-allocation для std/OS здесь нет.

Лицензии не изменились и совпадают с проверенными в первом раунде файлами.
CHANGELOG теперь присутствует и имеет подходящий раздел; регистровое разрешение,
содержимое будущего tarball и linking в этом раунде не проверялись.
Внешние вопросы числового parsing/statistics paired runner из первого отчёта
не переобъявляю дефектами proc-probe: эти scripts не менялись и не были целью.

а не на повторном выставлении уже исправленных P2 первого раунда.
