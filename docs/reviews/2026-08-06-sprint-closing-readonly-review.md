## 1. Метод

Readonly, без `cargo`/`npm` (чтобы не конкурировать за `target/` с параллельным
`npm run check`). Использовано:

- `git log --reverse --format="%H|%s" 42d4206..HEAD`, `git show <sha>` — полный
  diff каждого из 15 коммитов прочитан построчно;
- чтение целевых файлов в текущем состоянии (не только диффов):
  `.github/workflows/release.yml`, `.github/workflows/ci.yml`,
  `tests/regression_free_path_chunk_oom_graceful.rs`, `CONTRIBUTING.md`,
  `SECURITY.md`, `README.md`, `CLAUDE.md`, `CHANGELOG.md`, `Cargo.toml`,
  `scripts/check-all.mjs`, `docs/CORRECTNESS_OPEN_ITEMS.md`,
  `docs/plans/2026-08-05-release-execution-map.md`,
  `docs/checkpoints/2026-08-06-0015.md`;
- перепроверка каждого фактического утверждения из коммит-мессаджей командой:
  `git merge-base --is-ancestor` по 10 цитируемым SHA, `git rev-list --count`,
  `ls`/`grep` по каждому упомянутому файлу/фиче/таргету;
- `node scripts/verify-commit-prefixes.mjs` (единственная разрешённая
  исполняемая проверка).

## 3. Новые находки

### S1 [P2] — CHANGELOG переоценивает результат K5: ручной non-dry publish участника **не** проходит те же гварды, что тег

`CHANGELOG.md:180` утверждает: «re-keyed both on `dry_run != 'true'` …, **so a
real manual publish now clears the same checks as a tag push**».

Фактически:

- `release.yml:178-182` — гвард версии при `workflow_dispatch` немедленно
  `exit 0` («no tag to compare against»). Проверять нечего: `workflow_dispatch`
  не приносит версию ни в каком виде.
- `release.yml:224-233` — CHANGELOG-гвард `exit 0` для любого крейта, кроме
  `sefer-alloc`.

Следствие: `workflow_dispatch` + `dry-run=false` + `crate=aligned-vmem`
проходит **ноль** проверок версии и **ноль** проверок changelog. Остаются
только CI-гвард и тест-гейт. Это строго меньше, чем у тег-пуша, где обе
проверки реально исполняются.

Сам `release.yml` в комментариях честен (`:170-173`, `:208-218` прямо описывают
skip). Переоценка живёт только в CHANGELOG-сводке, где дисклеймер потерян — и
именно CHANGELOG публичен.

**Что делать:** либо переформулировать булет («guards are no longer bypassable
by trigger type; the version guard still has nothing to compare against on
`workflow_dispatch`, and the CHANGELOG guard applies to the root crate only»),
либо закрыть дыру по существу — добавить `workflow_dispatch` input `version` и
сверять его с `cargo pkgid` тем же шагом. Второе дешевле, чем кажется: шаг
`version` уже вычисляет реальную версию.

### S2 [P2] — единственный заявленный способ проверить правки `release.yml` структурно неспособен их проверить

`CHANGELOG.md:180` (конец булета): «a live `workflow_dispatch` **dry-run**
against each crate is still an operator follow-up».

Но все три гварда, которых касался спринт, стоят под
`if: steps.target.outputs.dry_run != 'true'`. **Dry-run пропускает их все по
построению.** Такой follow-up исполнит ровно ноль строк из того, что спринт
изменил, и вернёт зелёный, ничего не доказав — это false-PASS того же класса,
что HS-F1.

Правильный тест сформулирован в самой карте (§Ход C, «Готово, когда»):
запустить `workflow_dispatch` + **`dry-run=false`** при секции `(unreleased)` и
убедиться, что джоба **падает на гварде**. Это безопасно именно потому, что
гвард fail-closed срабатывает до `cargo publish`. Формулировка CHANGELOG
противоречит карте.

Дополнительно: `actionlint` не подключён нигде — `grep -rn actionlint
package.json .github/ scripts/` → пусто. Утверждение «`actionlint` and a YAML
parse both clean on every edit» описывает разовый ручной прогон без артефакта и
без гейта. У `release.yml` сейчас **нулевое автоматическое покрытие**, и это
единственный workflow, несущий `CARGO_REGISTRY_TOKEN`. Стоит добавить
`actionlint` шагом в `ci.yml` (или в `npm run check`) — это дешевле, чем разовые
ручные заявления.

### S3 [P2] — CONTRIBUTING'овская loom-команда после правки стала тихим no-op'ом

`tests/loom_epoch.rs:40` — `#![cfg(loom)]`. CI-джобы loom выставляют
`RUSTFLAGS: "--cfg loom"` (`ci.yml:930`, `:984`, `:1018`).

`CONTRIBUTING.md:83-88` (блок «Mandatory when touching concurrent paths», тот
самый, который `5db488c` правил — из него удалялась строка про несуществующий
`loom_reclaim`) по-прежнему содержит:

```sh
LOOM_MAX_PREEMPTIONS=2 cargo test --test loom_epoch --features experimental
```

Без `RUSTFLAGS="--cfg loom"` весь файл вырезается `#![cfg(loom)]`, бинарь
собирается пустым, вывод — `0 passed; 0 failed`, **exit 0**. Контрибьютор,
выполнивший «обязательную» команду, получает зелёный и уверенность, что
loom-модель прогнана.

Это **хуже**, чем строка, которую спринт из этого блока удалил: несуществующий
`--test loom_reclaim` падает громко, а этот вариант проходит вакуумно. Класс
дефекта — ровно тот, что ловили в F1/HS-F1 (false PASS сканера) и в R33-3
(тавтологичный loom-тест).

**Фикс на одну строку:** `RUSTFLAGS="--cfg loom" LOOM_MAX_PREEMPTIONS=2 cargo
test --release --test loom_epoch --features experimental`.

Соседняя строка того же блока — `cargo +nightly miri test --features alloc-core
-- region_invariants` — использует позиционный фильтр, тогда как `ci.yml:761`
делает `cargo miri test --test region_invariants`; комментарий в самом `ci.yml`
(`:737`) явно объясняет, что это **разные** вещи. Не трогалось спринтом, но
находится в том же блоке и заслуживает той же правки (P4).

### S5 [P3] — «Known limitations» и вся запись спринта структурно вложены в `### BREAKING CHANGE`, а не в релизную секцию

Карта заголовков `CHANGELOG.md`:

```
:8    ## [0.3.0] (unreleased)
:10   ### Round 34 — …
:14     #### Measurement, correctness & tooling
:42   ### BREAKING CHANGE — `AllocCore`'s `dbg_*` … narrowed behind `internals`
:109    #### Post-closing independent review remediation
:120    #### Release-readiness remediation
:137    #### Release-readiness remediation follow-up
:152    #### Release-readiness remediation wave 4
:168    #### Known limitations (as of this release)      ← добавлено спринтом
:175    #### Release-readiness sprint                    ← добавлено спринтом
:188  ### Round 33 — …
```

Между `:42` и `:188` нет ни одного `###`/`##`. Значит все шесть `####`-секций,
включая обе новые, синтаксически принадлежат заголовку **BREAKING CHANGE про
`AllocCore::dbg_*`**, а не Round 34 и не `## [0.3.0]`.

Практическое следствие: читатель release notes, ищущий «Known limitations»
релиза, находит их подшитыми под breaking change о сужении диагностического
API — а обе описанные там оговорки (cross-thread double free, MSRV-гейт) к
этому breaking change отношения не имеют.

Это **тот же класс дефекта**, который волна 4 закрывала как F3+F8 (`ba18071`,
«move BREAKING CHANGE heading out of the Round-34 bullet list»): тогда заголовок
вынесли за пределы списка булетов, но четыре `####`-подсекции, оказавшиеся после
него, так и остались осиротевшими. Спринт добавил в осиротевшую область ещё две.

**Фикс:** поднять `#### Known limitations (as of this release)` до `###` и
поставить непосредственно под `## [0.3.0] (unreleased)` (это релизная, а не
раундовая информация); блок BREAKING CHANGE перенести в конец секции 0.3.0 либо
понизить его до `####` внутри Round 34.

### S8 [P3] — исправление L8 корректно, но его новый комментарий обещает больше, чем даёт мьютекс; самопротиворечивый докстринг оставлен

`Mutex` даёт **взаимное исключение, но не порядок.** libtest не гарантирует, кто
захватит `TEST_LOCK` первым. Если первым войдёт
`oom_injection_flag_is_clean_after_test`, он проверит, что флаг чист на старте
процесса — что верно всегда — и **не докажет ничего** про `OomInjectionGuard`
основного теста. Тест при этом пройдёт (то есть красный CI закрыт по-настоящему),
но заявленный «второй слой уверенности» превращается в подбрасывание монеты.

Новый комментарий (`:67-81`) утверждает: «their correctness relies on sequential
execution … designed to run AFTER». После правки корректность на порядке уже не
завязана (тест проходит в любом порядке) — но и заявленное свойство «AFTER»
по-прежнему не обеспечено.

Одновременно оставлен без изменений докстринг `:155-161`, который противоречит
сам себе в трёх строках:

> This test runs **FIRST** (alphabetical ordering) and asserts the flag is
> clean, then the main test runs … This separate test provides a second layer
> of confidence: run **after** the main test (by name, `chunk_oom_...` sorts
> before `oom_injection_flag_...`).

Спринт правил именно этот файл и именно вопрос порядка — оставить здесь
противоречие странно.

**Дешёвый фикс, дающий заявленное свойство:** `static MAIN_TEST_RAN: AtomicBool`,
который основной тест выставляет в конце, а второй тест проверяет — и либо
ассертит своё условие, либо явно себя скипает с сообщением «main test has not
run yet in this process». Альтернатива — слить оба `#[test]` в один с двумя
фазами (тогда порядок гарантирован структурно, а мьютекс становится не нужен).

## 4. Что проверено и признано корректным (чтобы не перепроверяли)

## 5. Вердикт

**Спринт годится как есть для того, чтобы двигаться дальше, но не годится как
«закрытый» — до DAG-прохода нужно закрыть S1-S4, и до релиза S5-S7.**

Качество работы высокое: 15 из 15 коммитов делают ровно то, что заявляют,
все цитируемые SHA и числа сходятся при независимой перепроверке, два реальных
CI-red дефекта закрыты по существу, K8-гвард спроектирован верно и обходит
неочевидный режим отказа (ci.yml не триггерится на тегах). Ни одного случая
«сделано наспех и сломано» я не нашёл.

Найденное — четыре класса, все в зоне «формулировки и остаточные дыры», а не
«сломанный код»:

1. **Две переоценки в CHANGELOG** (S1, S2) — тот же класс, что F6 «provably the
   ceiling», который этот же спринт исправлял в записи предыдущей волны. Одна из
   них (S2) хуже, чем просто неточность: она задаёт план валидации, который по
   построению не может ничего провалидировать.
2. **Один новый false-PASS** (S3) — loom-команда в CONTRIBUTING, которую спринт
   редактировал, проходит вакуумно без `RUSTFLAGS="--cfg loom"`.

   чекпойнте, но **не заведён ни в TaskList, ни в один из двух OPEN_ITEMS
   индексов**, то есть протоколом старта раунда не поднимется.
