## 1. Findings

### F1 — **P2** — the replacement `std` mitigation in `64060b4` closes the hazard only for a panic whose message is a bare `&'static str`; for any *formatted* message the panic runtime allocates **before the hook is entered**, and no hook can prevent it — reproduced end-to-end as a hang

**Where:** `crates/racy-ptr-cell/src/lib.rs:138-149` (the `std` bullet added by
`64060b4`); `crates/racy-ptr-cell/README.md:86-95` (same text, shorter).

The sentence under audit (`src/lib.rs:146-149`):

> A `std` consumer therefore needs `panic = "abort"` **and** a
> `std::panic::set_hook` that goes straight to `std::process::abort` without
> formatting — or, better, an `init` that cannot panic at all.

Two options are offered as alternatives. **The only scenario in which they
differ is "`init` panics" — and in exactly that scenario the first option
fails whenever the panic message is not a bare `&'static str`.**

**Mechanism, from `std`'s own source** (active toolchain,
`library/std/src/panicking.rs:832-834`):

```rust
        Hook::Custom(ref hook) => {
            hook(&PanicHookInfo::new(location, payload.get(), can_unwind, force_no_backtrace));
        }
```

`payload.get()` is evaluated as an **argument** to the hook call — it runs
before the hook body, on both the `Hook::Default` and the `Hook::Custom` arm.
For a formatted message the payload is `FormatStringPayload`, whose `get()` is
`fill()` (`:629-639`), which materialises a `String`:

```rust
        fn fill(&mut self) -> &mut String {
            let inner = self.inner;
            self.string.get_or_insert_with(|| {
                let mut s = String::new();
                let mut fmt = fmt::Formatter::new(&mut s, fmt::FormattingOptions::new());
                let _err = fmt::Display::fmt(&inner, &mut fmt);
                s
            })
        }
```

There is no hook shape that avoids this: the allocation is upstream of the
hook by construction. (Only the bare-`&'static str` path escapes it —
`StaticStrPayload::get` at `:673-675` returns `&self.0`.)

**Measured, not argued** (§0.1, probes A/B — same binary, same non-allocating
hook, same `panic = "abort"` profile, only the message shape differs):

```
message = "RacyPtrCell: init returned the null/sentinel address"   -> 0 allocations before the hook
message = panic!("init failed with code {}", <runtime u32>)        -> 2 allocations before the hook
Result::unwrap() on an Err                                          -> 2 allocations before the hook
assert_eq!(<runtime u32>, 999, "…")                                 -> 4 allocations before the hook
```

**Reproduced end-to-end, as the hang the paragraph itself describes**
(§0.1, probe C — a real `#[global_allocator]` bootstrapping a
`static CELL: RacyPtrCell<Chunk>`, `panic = "abort"`, plus the recommended
non-allocating `set_hook`, both arms run under `timeout 15`):

```
arm "static" (message is a bare &'static str)  -> exit 50   (hook reached, clean exit)
arm "fmt"    (message has one runtime argument) -> exit 124  (HUNG — timeout fired)
```

The `fmt` arm hangs for precisely the reason `src/lib.rs:142-146` gives for
why `panic = "abort"` alone is insufficient: the `String` allocation re-enters
the `#[global_allocator]`, reaches the cell this same thread left
`INITIALIZING`, fails the claim CAS at `:532`, and enters the loser spin at
`:621-642` on a sentinel it owns itself. The added `set_hook` does not change
that outcome, because the hook is never reached.

**Failure scenario, concretely.** A `std` consumer follows the crate's advice
in full: `[profile.release] panic = "abort"` plus a `set_hook` that aborts
without formatting. Their `init` calls `reserve().expect("mmap failed")`, or
`?`-free `unwrap()`s a `Result`, or `assert_eq!`s a returned size — all of
which lower to a formatted panic. The panic runtime builds the message
`String` before the hook runs; that allocation re-enters their allocator; the
thread deadlocks on its own sentinel at 100 % CPU; `abort()` is never
reached; nothing is printed. They implemented the documented mitigation and
got the documented failure anyway.

**Why P2 rather than a shrug.** This is the *fourth* revision of this
paragraph and the second time the recommended remedy has been found not to do
what the sentence recommending it says. Cycle-3 F1 was rated P2 on exactly
this reasoning ("the sentence names a hazard, issues an imperative offered as
the remedy for it… the `std` mechanism does not [achieve it]"); consistency
requires the same rating here. Both surfaces that carry the claim — the
rustdoc render for 0.1.0 and the README on crates.io — freeze at upload. In
mitigation: the crate's own three panic sites all use static, argument-free
messages, so for *those* the recommended recipe genuinely is complete (probe
A). The gap is confined to the one panic site the crate does not control —
which is also the one its whole `#[global_allocator]` section is about.

**Suggested fix (documentation only, one clause).** Name the constraint:

> …needs `panic = "abort"` **and** a `std::panic::set_hook` that goes straight
> to `std::process::abort` without formatting. **Note the residual limit: a
> hook cannot help if the panic message is formatted.** `std` materialises the
> message (`payload.get()`) as an *argument* to the hook call, so
> `unwrap`/`expect`/`assert_eq!`/`panic!("{}", …)` allocate before any hook
> runs — measured: 2 allocations for `Result::unwrap`, 4 for `assert_eq!`,
> under `panic = "abort"` with a provably non-allocating hook. Only a panic
> whose message is a bare `&'static str` (as this crate's own three `assert!`s
> are) is fully covered. **The only mitigation that covers a formatted message
> is an `init` that cannot panic at all.**

### F3 — **P3** — two residual precision defects inside `64060b4`'s own replacement paragraph: the cited "3 allocations" is a `panic = "unwind"` measurement quoted inside the `panic = "abort"` bullet, and the `no_std` bullet contradicts its own preceding sentence

**Where:** `crates/racy-ptr-cell/src/lib.rs:135-137` and `:140-142`;
`crates/racy-ptr-cell/README.md:84-85` and `:88-90`.

**(a) The measurement was taken in the other panic strategy.** The parenthetical
sits inside the `panic = "abort"` bullet and is offered as that
configuration's evidence:

> A `std` binary's `panic = "abort"` profile setting … does **not** stop the
> panic runtime from allocating: the default hook allocates before it can
> print anything (measured: 3 allocations on the first panic,
> `RUST_BACKTRACE=0`, `--release`).

Measured here on the same host (§0.1, probe D — one binary, one counter, only
the profile's `panic` key changed; allocation #k detected by exiting on the
k-th post-arm allocation):

| Profile | allocations on the first panic, default hook, `RUST_BACKTRACE=0`, `--release` |
| --- | --- |
| `panic = "abort"` | **2** (allocation #3 never happens) |
| `panic = "unwind"` | **3** (allocation #3 happens, #4 does not) |

The one-allocation difference is exactly the payload box the unwinding path
takes and the aborting path never reaches — `StaticStrPayload::take_box`,
`library/std/src/panicking.rs:668-670`, `Box::into_raw(Box::new(self.0))`,
called from `rust_panic(payload)` at `:850`, which `panic = "abort"` replaces
with a bare `abort()`. Cycle 3's own §0.2 table, which produced the `3`,
records the counting probe without a `panic = "abort"` row (only the separate
trap-allocator probe named that profile) — consistent with the number having
come from a default-profile build.

The load-bearing half of the claim ("it does not stop the panic runtime from
allocating") is TRUE and independently confirmed here (2 > 0). The defect is
that a measured figure is published, in permanent rustdoc, against a
configuration it was not measured in — the same regime-mismatch shape
CLAUDE.md's own cost-and-benefit rule exists to prevent, one level down. Note
also that the figure is host- and toolchain-specific and carries no
platform/rustc identification, so it will silently rot.

**Suggested fix.** Either re-state it as `panic = "abort"`'s own number
("measured: 2 allocations under `panic = "abort"`, 3 under `panic = "unwind"`;
`RUST_BACKTRACE=0`, `--release`, rustc 1.97, x86_64-pc-windows-msvc"), or drop
the count and keep the robust claim ("the default hook allocates before it can
print anything").

**(b) "no handler, no allocation" contradicts the sentence it explains.**
`src/lib.rs:135-137` / `README.md:84-85`:

> A `no_std` binary supplies a non-allocating `#[panic_handler]` itself. This
> closes the hazard completely: **no handler, no allocation.**

A `no_std` binary manifestly *does* have a handler — the sentence immediately
before says it supplies one. The intended meaning is "no `std` *hook*"; as
written the summary negates its own premise, in the one bullet a bare-metal
reader will read first. One word ("no `std` hook, no allocation") fixes it.

### F4 — **P3** — `a7cbc6c`'s primary named mitigation, "Always scope the flag to this crate (`-p racy-ptr-cell`)", is neither a scoping of the flag nor a command a crates.io consumer can run

**Where:** `crates/racy-ptr-cell/README.md:120` (the command) and `:123-132`
(the warning paragraph); `crates/racy-ptr-cell/src/lib.rs:205-212` (the
`CONSUMER HAZARD` comment) and `:358-366` (`new()`'s rustdoc).

The hazard itself is now correctly and prominently documented — that half of
`a7cbc6c` is sound and I confirmed the underlying breakage is unchanged
(§0.1, probe E: `E0015` in a scratch consumer built from the actual 0.1.0
tarball). The defect is in the *first* of the two mitigations offered:

> Always scope the flag to this crate (`-p racy-ptr-cell`, as above), or
> supply a `#[cfg(loom)]` const-capable stand-in in your own crate if you need
> to set the flag workspace-wide…

**`-p` does not scope `RUSTFLAGS`.** `RUSTFLAGS` applies to every crate
compiled in the invocation; `-p` selects which *packages* are built/tested.
The repo's own command works only because that selection happens to exclude
every crate holding a `static`. Measured (§0.1, probe F): a consumer who scopes
`-p` to their **own** crate in order to run their **own** loom suite —
`RUSTFLAGS="--cfg loom" cargo test -p app` — still gets

```
error[E0015]: cannot call non-const associated function `RacyPtrCell::<Chunk>::new` in statics
```

That consumer does not think of themselves as "setting the flag
workspace-wide", so the second clause — the only mitigation that actually
helps them — reads as not applying to their case.

**And the command itself is unrunnable outside this repository.** Measured
(§0.1, probe G): from a consumer workspace whose only relation to the crate is
a dependency edge, the README's own instruction fails outright:

```
$ RUSTFLAGS="--cfg loom" cargo test -p racy-ptr-cell --release --test loom_racy_ptr_cell
error: package `racy-ptr-cell` cannot be tested because it requires dev-dependencies
       and is not a member of the workspace
```

This matters slightly more than a stale command, because "Ships executable
loom proofs run against the real type, with `#[should_panic]` counterfactuals"
is the closing sentence of the crate's crates.io `description`
(`Cargo.toml:7`) — a headline selling point — and `tests/loom_racy_ptr_cell.rs`
*is* in the published tarball. A reader who wants to verify that claim with
the command the README gives them cannot, and the README never says the
command presumes a checkout.

**Suggested fix.** Two clauses. (1) Say what `-p` actually does: "run the loom
suite in a checkout of this crate, where the selection excludes any crate
holding a `static` — `RUSTFLAGS` itself cannot be scoped per-package". (2)
Promote the stand-in advice from a conditional afterthought to the mitigation
for the consumer case: "if you set `--cfg loom` for **your own** loom suite,
`-p` will not help — every crate in that build gets the flag, including this
one; supply a `#[cfg(loom)]` const-capable stand-in in your own crate (see
`loom_shim`)". The optional one-way-door alternative cycle 3 raised —
gating the aliasing on `#[cfg(all(loom, feature = "loom"))]` — would remove
the problem outright and is still only decidable before 0.1.0.

### F5 — **P3** — the crate's `unsafe`-seam justification header, which is the *formal* audit surface under CLAUDE.md's Active Rules, contradicts itself twice in four lines and names a non-`unsafe` construct as its `unsafe` surface

**Where:** `crates/racy-ptr-cell/src/lib.rs:176-191`, immediately above the
tier-1 lift `#![allow(unsafe_code)]` at `:192`.

> There is a **SINGLE** documented reason to hold `unsafe` here: constructing
> the never-dereferenced `INITIALIZING` sentinel pointer via
> `core::ptr::without_provenance_mut` (a `const fn` that is safe on modern
> toolchains) **requires no `unsafe`**; the only genuinely `unsafe` surface is
> **the pointer-sentinel comparison discipline plus the caller-facing
> accessors** that hand back the raw pointer. […] The crate body's own
> `unsafe` is confined to **two** audited kinds: `unsafe impl Send/Sync` …
> and `unsafe { NonNull::new_unchecked(p) }` …

Three problems in one block:

1. "a SINGLE documented reason" is asserted and then contradicted by "two
   audited kinds" eleven lines later.
2. The colon introduces the reason and then states the opposite — the named
   reason "requires no `unsafe`". As written, the single reason is a

## 5. Verdict: **CONDITIONAL GO**

The primitive is publish-ready and I could not break it. Every gate is green
on the current tree — 7/7 native, 7/7 loom against the **real** type with both
non-vacuousness counterfactuals firing, 7/7 miri twice (including
`-Zmiri-strict-provenance`), clippy `-D warnings` across all targets, `rustdoc
-D warnings`, `fmt`, and a clean 12-file package that I re-materialised as a
path dependency of a foreign workspace and compiled there. **There is no P1
finding: no UB, no soundness hole, no lost happens-before, no ABA break, no
reachable sentinel collision, no double-init.** That is now five consecutive
independent clean bills on the algorithm.

Both of cycle 3's findings landed their substantive corrections: `64060b4`'s
central claim about `panic = "abort"` is true and I re-measured it, and
`a7cbc6c` put the `--cfg loom` hazard in all three places it needed to be,
including the `#[cfg(not(loom))]` copy docs.rs renders.

What holds it back from an unconditional GO is **two** findings, and — as in
cycle 3 — the first is something I **measured** end to end rather than argued:

- **F1.** The crate tells `std` consumers to add a non-allocating
  `std::panic::set_hook` on top of `panic = "abort"`. `std` materialises the
  panic message (`payload.get()`) as an **argument** to the hook call, so for
  any formatted message the allocation happens before the hook body ever runs
  and no hook can prevent it. Measured on one binary with the crate's full
  recommended recipe applied: a bare-`&'static str` panic reaches the hook
  with **0** allocations; `Result::unwrap` costs **2**, `assert_eq!` costs
  **4**. And the end-to-end chain reproduces: a real `#[global_allocator]`
  bootstrapping a `static RacyPtrCell`, `panic = "abort"` plus the recommended
  hook, `init` panicking — **static message: clean exit 50; formatted message:
  HUNG (timeout 124)**. That is the exact 100 %-CPU self-deadlock the
  paragraph itself warns about, produced by following the paragraph's own
  advice. This is the fourth revision of this text and the second consecutive
  cycle in which the recommended remedy turned out not to do what the sentence
  recommending it says.
- **F2.** The crate has **no rustdoc gate anywhere in CI** — not one of
  `ci.yml`'s eight `cargo doc` rows names it, and the root `docs` job is
  `--no-deps` *and* deliberately drops `-D warnings`. This is not
  hypothetical: `64060b4`, two commits ago, introduced two broken intra-doc
  links into this very paragraph and its own commit message records that they
  were caught by a manual local run. A crate with `#![deny(missing_docs)]`,
  ~175 lines of module rustdoc, eleven intra-doc link targets, and a docs.rs
  page that is frozen per published version should not be one hand-run away
  from shipping dead links. One line of YAML; it passes today.

Both fixes are cheap and neither touches the algorithm or the API: F1 is one
clause of prose (fold in cycle-3 F3's "the guard is unwind-only" clause while
there — it belongs in the same paragraph), F2 is one `ci.yml` row. F3, F4 and
F5 are all prose and are cheap enough to land in the same commit; F4's
optional half (feature-gating the loom aliasing) is a genuine one-way door and
is still only decidable before 0.1.0.

**Close F1 and F2 — no algorithm change, no API change — and this is a GO.**
For the record, the things that would have to *newly* break to move it off GO
after that are unchanged from cycles 2 and 3 and are still six, three of which
the suite is blind to: the publish `Release` or the loser-spin exit `Acquire`
(both proven to fail the suite if wrong); the claim-CAS success ordering
(**not** caught — cycle-2 F4); the sentinel-collision `assert!` at `:581`;
making `RollbackGuard`'s rollback conditional (**not** caught — cycle-2 F5);
`get()`'s readiness predicate (**not** caught — the confirmed vacuity in §3);
