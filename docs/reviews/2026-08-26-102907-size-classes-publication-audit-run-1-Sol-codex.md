## Итог

**NO-GO для публикации в текущем состоянии.**

Архитектура крейта компактная и в основной области применения выглядит качественно: `no_std`, нулевые production-зависимости, `#![forbid(unsafe_code)]`, таблицы строятся в `const`-контексте, lookup строится линейно, а основной `class_for` имеет короткий O(1)-путь. До исправления обоих публикацию не рекомендую. Дополнительно новый benchmark измеряет не заявленную границу, а три почти одинаковых ранних отказа.

## P2-1. Непроверенная арифметика `usize` даёт profile-dependent публичное поведение

**Где:**

- `crates/size-classes/src/lib.rs:150-155` — `size2class_len`;
- `crates/size-classes/src/lib.rs:361-365` — проверка `L` в `build_size2class`;
- `crates/size-classes/src/lib.rs:374-383` — вычисление верхней границы bucket;
- `crates/size-classes/src/lib.rs:585-597` — переход slow path в `class_for`.

`size2class_len` проверяет только степень двойки, после чего делает:

```rust
max_class / min_block + 1
```

Контрпример не нарушает заявленную предусловием форму аргументов:

```rust
size2class_len(usize::MAX, 1)
```

Частное равно `usize::MAX`, поэтому `+ 1` переполняется. В const/debug это panic, но runtime-вызов в обычном release-профиле способен вернуть `0`. Rustdoc при этом обещает panic только для `min_block`, не являющегося степенью двойки. Это не просто недостаток диагностики: одинаковый публичный вызов меняет результат между профилями.

Тот же шаблон повторён непосредственно в `build_size2class`:

```rust
L == small_max / min_block + 1
```

Например, для `N = 1`, `table = [usize::MAX]`, `min_block = 1`, `L = 0` release-арифметика превращает ожидаемую длину в ноль, проверка проходит и функция возвращает пустой lookup. В debug/const тот же вход падает. Таким образом, проверка сама маскирует некорректную конфигурацию в профиле, где должна защищать от неё.

Ещё два родственных места:

1. `(k + 1) * min_block` вычисляется до clamp к `small_max`. При большой допустимой области произведение может переполниться, хотя математически требовалось просто выбрать `small_max`.
2. `(block | (align - 1)) + 1` в alignment slow path переполняется, когда следующего представимого кратного уже нет. Семантически это должен быть `None`, а не release-wrap. Для текущих реалистичных таблиц путь практически недостижим из-за необходимого огромного lookup, но публичная арифметика всё равно должна быть тотальной на заявленном домене.

**Почему P2:** это release-silent semantic bug на публичных функциях, а не только косметика или panic на заведомо неверном входе. Риск для типичных allocator-схем мал, но библиотечный контракт задаётся всем разрешённым `usize`-диапазоном.

**Как исправить:**

- вычислять длину через `checked_add(1)` с единым содержательным panic-сообщением;
- в `build_size2class` не дублировать потенциально опасную формулу либо использовать такую же checked-логику;
- вычислять `need` сравнением/делением до умножения, например сначала определять, достигнут ли верхний bucket, и умножать только в безопасной ветке;
- в `class_for` заменить финальный `+ 1` на `checked_add(1)` и возвращать `None` при отсутствии представимого следующего кратного;
- дополнить `# Panics` точным overflow-контрактом;
- добавить runtime-регрессии именно для release-семантики, а не только const-вычисления.

## P2-2. Standalone `build_table` возвращает таблицу, нарушающую собственный контракт

**Где:**

- обещание: `crates/size-classes/src/lib.rs:158-166`;
- merge: `crates/size-classes/src/lib.rs:231-309`;
- отложенная проверка: `crates/size-classes/src/lib.rs:342-359`;
- существующий тест прямо фиксирует расхождение: `crates/size-classes/tests/builder.rs:184-230`;
- то же утверждение повторено в `crates/size-classes/CHANGELOG.md`.

Rustdoc `build_table` обещает, что merged table остаётся **strictly increasing**. Но функция проверяет только внутреннюю сортировку `extras`; пересечение `extras` с геометрическим рядом не отвергается. На равенстве merge выбирает extra и позже геометрическое значение, создавая дубликат.

Уже существующий тест даёт точный пример: `min_block = 16`, `extras = [16, 32]`. Комментарий теста прямо говорит, что `build_table` самостоятельно принимает этот вход и производит дубликаты; panic появляется лишь после передачи результата в `build_size2class` через `SizeClasses::build`.

Это нарушает контракт отдельной публичной функции. Пользователь вправе вызвать `build_table` без `build_size2class`: crate-level API описывает их как самостоятельные building blocks. Формулировка CHANGELOG «never a silently accepted bad table» также неверна для этого пути.

Есть соседний непроверенный случай: `extras = [0]` проходит требования «кратно `min_block`» и «строго возрастает», после чего нулевой класс оказывается перед первым геометрическим классом. Он недостижим для корректного `Layout` (`align >= 1`), но остаётся в `count`, `table` и `block_size(0)`, хотя `min_block` описан как минимальный quantum. Это либо должно быть явно разрешено и документировано, либо — предпочтительно — отвергнуто.

**Как исправить:**

- проверять строгую монотонность итогового массива непосредственно в `build_table` до возврата;
- оставить проверку в `build_size2class` как defense in depth для таблиц, собранных пользователем вручную;
- запретить `extras[i] < min_block` (или явно определить и покрыть контракт нулевого класса, если это действительно желаемая возможность);
- переписать overlap-регрессию так, чтобы её SUT был непосредственно `build_table`, и проверять его уникальное panic-сообщение;
- синхронизировать rustdoc, README и CHANGELOG с фактическим chokepoint.

## P3-1. Три новых benchmark-сценария измеряют не `huge_threshold`

**Где:** `crates/size-classes/benches/size_classes_bench.rs:69-89`; фактическая политика — `crates/size-classes/src/lib.rs:509-510`.

Benchmark добавляет три строки:

- `near_huge_threshold_below`;
- `near_huge_threshold_at`;
- `near_huge_threshold_above`.

Все вызывают `class_for` около 4 MiB. Но `class_for` вообще не читает `huge_threshold`; этот параметр используется только методом `is_huge`. Для конкретной таблицы `SEFER_MAX` существенно меньше 4 MiB, поэтому все три случая проходят один и тот же ранний путь `need > small_max => None`. Они не измеряют различие «ниже / на / выше huge threshold», несмотря на имена и комментарии, и занимают половину benchmark-набора дублирующимися наблюдениями.

**Как исправить:**

- boundary-сценарии `class_for` разместить около `SEFER_MAX`: `SEFER_MAX - 1`, `SEFER_MAX`, `SEFER_MAX + 1`;
- если важна цена policy check, отдельно измерить `is_huge` ниже/на/выше 4 MiB;
- оставить один явный `above_small_max_rejection`, если нужен только ранний отказ.

До этого benchmark нельзя использовать как доказательство поведения около huge-policy boundary.

## P3-2. `build_table` документирует не все причины panic

**Где:** `crates/size-classes/src/lib.rs:168-174` против checked-операций в `crates/size-classes/src/lib.rs:274-299`.

`# Panics` перечисляет структурные ошибки параметров, но не сообщает, что геометрическая прогрессия может завершиться panic при overflow `checked_mul` или `checked_add`. Регрессии для этих случаев уже существуют (`tests/builder.rs:283-319`), а CHANGELOG подчёркивает loud overflow. Публичная документация функции должна отражать эту намеренную часть контракта.

Также после исправления P2-1 сюда следует включить overflow вычисления длины/границ там, где он остаётся паникой по дизайну.

## P3-3. Обычный CI проверяет не весь публикуемый пакет как самостоятельный crate

**Где:** `.github/workflows/ci.yml:1807-1826`, root-only clippy/doc jobs и отсутствие package-gates для `size-classes`.

Сейчас для `size-classes` есть полезные проверки:

- bare-metal `thumbv7em-none-eabi` build;
- debug и release `cargo test -p size-classes`.

Но перед PR-merge нет отдельного симметричного набора:

- `cargo clippy -p size-classes --all-targets -- -D warnings`;
- `RUSTDOCFLAGS="-D warnings" cargo doc -p size-classes --no-deps`;
- `cargo publish --dry-run -p size-classes`;
- проверки собственного test/dev graph на заявленном MSRV.

Root-scoped clippy/doc команды этого не заменяют: `--no-deps` не документирует dependency crate, а компиляция библиотеки как зависимости не покрывает её собственные integration tests и benchmark target. Это особенно заметно после добавления `size_classes_bench`: обычные test-строки не являются all-target lint/compile gate для bench executable.

Release workflow всё же выполняет cargo publish с verify перед реальной загрузкой, поэтому это P3 process gap, а не ещё один production P2. Но ошибка обнаружится слишком поздно — в момент релизной процедуры, а не в PR.

Дополнительная гигиена: crate manifest не наследует workspace lints через `[lints] workspace = true`, хотя корневой workspace такую политику содержит. Это не отдельный блокер при наличии явного `-D warnings`, но самостоятельный пакетный gate и наследование lint policy сделали бы защиту однозначной.

## Общий обзор реализации

### Корректность и безопасность

- `#![no_std]`, `#![forbid(unsafe_code)]`; FFI, raw pointers, atomics и shared mutable state отсутствуют.
- Production-зависимостей нет, поэтому supply-chain поверхность минимальна.
- `SizeClasses` хранит таблицу и lookup как значения; lifetime есть только у входного `Params::extras` и не протекает в построенный объект.
- Ограничение индекса `< 256` корректно защищает `u8` lookup от truncation.
- Проверка глобальной монотонности в `build_size2class` необходима и полезна для вручную созданных таблиц; проблема лишь в том, что она не выполняет обещание отдельного `build_table`.
- `align.is_power_of_two()` как debug precondition согласуется с доменом `Layout`; публичная документация объясняет последствия нарушения.

### Алгоритмы и производительность

- `build_table`: O(N) merge после O(`geo_count`) генерации, без allocation.
- `build_size2class`: monotone-pointer даёт O(buckets + classes), а не повторный поиск с нуля.
- `class_for`: типичный путь — `max`, одна проверка границы, один lookup и одна ветка; это хороший O(1) hot path.
- alignment slow path перескакивает через lookup к следующему кандидату вместо линейного перебора каждого класса; идея корректная для power-of-two align.
- Locking, syscall, heap allocation и скрытая инициализация отсутствуют.

Очевидного безопасного ускорения production hot path без измерений не найдено. Удалять проверки или усложнять representation ради нескольких полей не рекомендую: объект мал, а const/static-построение уже убирает runtime builder cost. Сначала следует исправить benchmark, затем принимать perf-решения только по валидным измерениям.

### Тестовый дизайн (только чтение)

Сильные стороны:

- есть независимый reference scan для проверки `class_for`, а не только сравнение функции с самой собой;
- есть hand-written golden sequence и exhaustive проход по практической SEFER-схеме;
- property tests покрывают несколько фиксированных схем и разные size/align;
- overflow геометрии защищён адресными regression tests;
- debug/release профили заявлены в CI отдельно.

Пробелы:

- нет boundary tests для `usize::MAX` в `size2class_len`/`build_size2class` и overflow-safe round-up;
- overlap-тест намеренно проверяет только downstream `build_size2class`, поэтому закрепляет расхождение standalone-контракта;
- нет теста на `extras = [0]`;
- property tests варьируют запросы, но не генерируют сами схемы/границы арифметики;
- benchmark boundary oracle неверен.

## Рекомендуемый порядок исправлений

1. Устранить все profile-dependent overflow в `size2class_len`, `build_size2class` и slow-path round-up; добавить release-runtime контрпримеры.
2. Перенести проверку строгой монотонности результата в `build_table`, определить политику для zero/sub-`min_block` extras и сделать прямые regression tests.
3. Исправить benchmark на реальные `small_max`/`huge_threshold` границы.
4. Синхронизировать `# Panics`, README и CHANGELOG.
5. Добавить самостоятельные clippy/rustdoc/package/MSRV gates для пакета и всех targets.

После пунктов 1-2 нужен новый статический проход. Пункты 3-5 желательно закрыть до публикации, чтобы релизные заявления и perf-сигнал были достоверны.

## Ограничения аудита

Никакие команды, которые компилируют, исполняют тесты, benchmarks или package verification, не запускались. Поэтому вывод — результат code review, а не подтверждение зелёного toolchain-прогона.
