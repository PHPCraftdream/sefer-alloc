## 1. Findings

### F1 — **P2** — the "no reentrancy / cannot re-enter the allocator it is bootstrapping" claim is unqualified, but the crate now has a release-active panic path that *does* re-enter

**Where:** `crates/racy-ptr-cell/src/lib.rs:33-37` (module doc),
`crates/racy-ptr-cell/README.md:10-12`,
`crates/racy-ptr-cell/Cargo.toml:7` (`description`, immutable once 0.1.0 is
uploaded — "Safe inside a #[global_allocator] (no std sync, no reentrancy, no
heap)"). The panic itself is `src/lib.rs:438-441`.

**Failure scenario.** A consumer does exactly what all three texts invite: puts
a `static CELL: RacyPtrCell<Chunk>` on the bootstrap path of their
`#[global_allocator]`, in a `std` binary. Their `init` closure has a bug — it
returns `NonNull::new(core::ptr::without_provenance_mut::<Chunk>(1))` (100%
safe code; `tests/cell_unit.rs:130-145` constructs precisely this), or it
simply panics for an unrelated reason (task #706 made an unwinding `init` a
*documented, supported* contract, so this is a designed path, not a
theoretical one). The `assert!` at `:438-441` fires. `core::panicking::panic`
hands off to the `std` panic runtime, which **allocates**: the panic payload is
boxed on the unwinding path, and the default hook allocates again when
backtrace capture is enabled. Every one of those allocations re-enters the
global allocator whose bootstrap cell is at that moment holding
`INITIALIZING` — the allocator's own bootstrap either spins on the sentinel
(its owner is this same thread) or recurses into the panic machinery again.
Result: a hang or a stack overflow inside the panic handler, with none of the
diagnostic the `assert!` was added to provide. The claim that made the
consumer comfortable ("no reentrancy", "cannot re-enter") is stated without
qualification in all three places.

Note the exact shape: this is *caller misuse* triggering it, but the crate's
own guarantee text is what says the crate cannot re-enter, and both panic
paths were added (tasks #706 in `048c657`, #707 in `9b98c7a`) *after* that
text was written, without revisiting it. Prior review run-1 F3 corrected the
adjacent "bounded and short in practice" overclaim by the same mechanism; this
is the one it did not reach.

**Suggested fix, cheapest first.**
1. Qualify the claim in all three places: the cell's own *success* paths use no
   `std` sync primitive and allocate nothing; the two panic paths (the
   sentinel-collision `assert!`, and an unwinding `init`) go through the panic
   machinery, which allocates in a `std` build — so a `#[global_allocator]`
   consumer should treat both as fatal-by-construction and consider
   `panic = "abort"` plus a non-allocating `#[panic_handler]`. `Cargo.toml:7`
   is the urgent one: it is frozen for 0.1.0.
2. Optionally (behaviour change, one test edit): make a sentinel-valued `init`
   result take the *rollback + `None`* path instead of panicking — the exact
   alternative the 2026-08-07 audit listed under §B26 ("or treat a
   sentinel-address init result as an error (roll back to null, return
   `None`)"). That would make the unqualified claim literally true for
   everything except an unwinding `init`, which is unavoidably the caller's.

### F2 — **P2** — `Cargo.toml`'s `lock-free` keyword asserts a progress guarantee the crate's own documentation, corrected four hours ago, says it does not have

**Where:** `crates/racy-ptr-cell/Cargo.toml:12` —
`keywords = ["oncelock", "lock-free", "allocator", "cas", "no-std"]`.

**Failure scenario.** `RacyPtrCell` is *blocking*, not lock-free: a winner
suspended (preempted, page-faulted, descheduled) anywhere inside `init` stalls
every loser indefinitely, because losers busy-spin on `== INITIALIZING` with no
bound, no backoff, and no way to steal the work. `src/lib.rs:42-54` now says
this in as many words ("**There is no bounded-latency guarantee**"), and
commit `7e20a4a` (task #1360) *explicitly declined* to relabel the primitive
"lock-free" for exactly this reason, quoting the run-1 review's caution.
The keyword was not updated in the same pass. A user filtering crates.io by
`lock-free` — the canonical way people search for progress guarantees — lands
here, reads the one-line description (which does not mention spinning), and
adopts the cell in a context (real-time thread, priority-inverted scheduler,
single-core embedded target) where a preempted `init` deadlocks the system.
Keywords are per-version published metadata, so 0.1.0's listing carries this
permanently.

**Suggested fix.** Drop `lock-free`. `spin`, `lazy`, `once`, `atomic` and
`init` are all accurate and at least as discoverable; `oncelock`, `allocator`,
`cas` and `no-std` are already correct. Do it in the same change as F1's
`description` edit, since both are one-way doors at upload time.

### F4 — **P2** — the module doc's "Sentinel encoding" section and the `SENTINEL_INITIALIZING` doc both state, as fact, the property that the crate's own release-active `assert!` exists because it is false

**Where:** `crates/racy-ptr-cell/src/lib.rs:62-64` and `:127-132`.

> `:62-64` — "`1` is not a valid address for any `T` a caller stores here
> (every such `T` has alignment >= 2), so it can never collide with a real
> published pointer."
>
> `:127-132` — "`1` is below the minimum alignment of any `T` stored here
> (asserted at construction), so it can never equal a real published pointer."

**Failure scenario.** Both sentences are false as written, and the crate's own
test suite proves it: `tests/cell_unit.rs:130-145`
(`init_returning_the_sentinel_address_panics`) constructs
`NonNull::new(core::ptr::without_provenance_mut::<Payload>(1)).unwrap()` from
100% safe code for an `align(4)` `Payload` and hands it to `get_or_try_init`.
`align_of::<T>() >= 2` constrains *validly aligned* pointers to `T`; it
constrains nothing about what a caller's closure may synthesise and return, and
`NonNull` rules out only null. The actual defence is the release-active
`assert!` at `:438-441` (task #707), which **neither doc section mentions** —
`:127-132` even attributes the whole guarantee to the *construction* assert
alone.

The concrete harm is to the next maintainer, not to today's user. Someone
auditing the sentinel encoding — the crate's central soundness argument, and
the thing its README sells — reads `:62-64`, concludes the collision case
cannot arise, and later removes or re-`debug_assert!`s the "redundant" runtime
check. That reopens exactly the hole task #707 closed (silent publish of the
sentinel as READY → every reader misclassifies the cell as `INITIALIZING`
forever, no diagnostic anywhere), and the module doc will still be telling them
it was impossible. This is the same class of internal doc-vs-code disagreement
the 2026-08-07 audit filed under §F2 and the 2026-08-09 review under F8 — both
of which were fixed; this instance was not reached because it sits in the
*explanatory* prose rather than in a proof claim.

**Suggested fix.** Reword both to separate the two guarantees:
"an *aligned* pointer to `T` can never have address `1` (`align_of::<T>() >= 2`
is asserted at construction); a *misaligned or synthesised* pointer at address
`1` is possible from safe code and is rejected by the release-active `assert!`
in [`RacyPtrCell::get_or_try_init`] — see its `# Panics`." Two sentences, no
code change.

### F5 — **P3** — no test, native or loom, ever exercises `get()` observing `INITIALIZING`; half of `get`'s documented contract is unverified

**Where:** contract at `crates/racy-ptr-cell/src/lib.rs:310-318`; the gap is
across `tests/cell_unit.rs` and `tests/loom_racy_ptr_cell.rs`.

**Failure scenario.** `get`'s doc promises: "`None` means the cell is `UNINIT`
or `INITIALIZING` right now (neither the sentinel nor null is ever returned as
`Some`)." The `UNINIT` half is covered (`tests/cell_unit.rs:22-27`). The
`INITIALIZING` half is covered nowhere:

- `cell_unit.rs` is single-threaded; there is no way to observe the cell in
  `INITIALIZING` from it (`dbg_rollback_reenterable` restores before
  returning), so no test there can reach the state.
- In the loom suite the *only* `get()` call outside a post-join assertion is
  `tests/loom_racy_ptr_cell.rs:285`, and it runs after that same thread's own
  `get_or_try_init` has already returned — i.e. always on a `READY` cell.
  `real_survives_oom_rollback_two_threads`'s `cell.get()` (`:373`) likewise
  runs after both joins.

Today a mutation to `is_ready` is still caught, because `get_or_try_init`'s
`assert!` shares the same helper — so this is a coverage gap, not a live hole.
The concrete way it becomes a hole: a refactor that gives `get` its own
inlined predicate (or that keeps `is_ready` for the assert but changes `get`),
dropping the `a != SENTINEL_INITIALIZING` half. `get()` then hands a caller
`Some(NonNull)` pointing at address `1` during any concurrent init; the caller
dereferences it — that call is `unsafe` but its precondition ("the cell said
READY") was satisfied — and the process faults on a null-page access. Every
existing test stays green, because none of them ever calls `get()` while
another thread holds the sentinel.

**Suggested fix.** ~8 lines in `loom_racy_ptr_cell.rs`: add a third thread to
`real_exactly_once_two_threads` that only calls `cell.get()` in a loop a
bounded number of times and asserts, for each result,
`r.is_none() || r.unwrap().as_ptr().addr() != SENTINEL`. That closes the last
uncovered arm of the public API under concurrency and costs one more
interleaving dimension in a model that currently runs in 0.37 s.

### F6 — **P3** — the loser spin re-acquires on every iteration, and `get_or_try_init` has no `#[cold]` slow-path split

**Where:** `crates/racy-ptr-cell/src/lib.rs:478-499` (spin loop); `:381-504`
(whole function, no `#[inline]`/`#[cold]` structure).

Two separate, independently applicable micro-optimisations, both
correctness-preserving:

1. **Relaxed spin, acquire on exit.** The inner loop issues
   `self.ptr.load(Ordering::Acquire)` on *every* spin iteration. Only the
   iteration that *leaves* the loop needs `Acquire` (that is the load that
   pairs with the winner's `Release` publish). On x86-64 this is free (both
   lower to `mov`), but on AArch64 `ldar` carries real ordering cost per
   iteration, and this loop is the one place the crate deliberately spins hot.
   The textbook shape — `load(Relaxed)` for the `== SENTINEL_INITIALIZING`
   test, then one `load(Acquire)` (or `core::sync::atomic::fence(Acquire)`) on
   the two exit paths at `:486-493` — is a strict improvement. Both existing
   loom proofs remain the oracle: under `--cfg loom` the extra load is still
   modelled, and `counterfactual_relaxed_publish_loses_happens_before` still
   pins that the *publish* side must not be relaxed.
2. **Outline the slow path.** `get_or_try_init` is one generic function
   containing the fast-path load, the CAS, the spin loop, the `RollbackGuard`,
   and two `assert!` panic strings. Being generic over `F`, it is monomorphised
   into every consumer's CGU, so all of that is inlining-eligible into a hot
   caller. The crate's own in-repo consumer already works around this by hand:
   `src/registry/bootstrap.rs:702-713` does its own `get()` fast path and
   defers to a `#[cold] fn ensure_chunk_slow` (`:906`). Splitting
   `get_or_try_init` into an `#[inline]` fast-path wrapper plus a
   `#[cold] #[inline(never)]` remainder gives every consumer that for free and
   removes the incentive to reimplement the fast path downstream.

*(Run-1's F5 first half — `Ordering::Relaxed` on the CAS **success** ordering —
is still open and not re-argued here; it composes with (1).)*

### F7 — **P3** — the `get_or_try_init/cold` benchmark measures the system allocator and the timer, not the cell, and its per-iteration leak perturbs its own measurement

**Where:** `crates/racy-ptr-cell/benches/racy_ptr_cell_bench.rs:44-50` (the
timed closure), `:41-43` (the comment that acknowledges the leak).

**Measured, on this host, just now** (`cargo bench -p racy-ptr-cell --bench
racy_ptr_cell_bench`, release, iteration counts from the workspace
`bench-iters.txt`):

```
get_or_try_init/cold                 4404261 iters   694.579 ms   157.71 ns/op
get/hot                            270839749 iters  1038.189 ms     3.83 ns/op
get_or_try_init/warm_already_ready 185011429 iters   888.356 ms     4.80 ns/op
```

**Failure scenario (as a measurement).** The cold path's cell-side work is
exactly three atomic operations: one `Acquire` load, one `compare_exchange`,
one `Release` store. `get/hot`'s 3.83 ns/op is the measured cost of that load
in isolation; an uncontended `lock cmpxchg` is ~20 ns. So the cell accounts
for well under 30 of the 157.71 ns. The remainder is (a) `Box::new(Payload)`
inside the timed closure — `leak()` at `:28-30` is called *within* the
`routine`, not the `setup` — and (b) `bench_batched`'s two `Instant::now()`
reads per iteration (bench-scale-tool times each batched iteration
individually; on Windows each read is a `QueryPerformanceCounter`). A "cold
cell publish" figure that is ~80% system allocator and clock is not usable to
detect a regression in the cell, which is the stated reason the file exists
("the hottest primitive in the sefer-alloc allocator's init paths ... no
benchmark coverage existed to track hot-path latency", `:5-7`).

Worse, and not covered by the file's existing caveat: the 4.4 M `Box<Payload>`
allocations are *never freed*, so the process heap grows monotonically across
the measured run and `Box::new` itself slows down as the run proceeds. The
number therefore is not even a stable measurement of "cell + one malloc" — it
drifts within a single run and is not comparable across hosts with different
system allocators. The file's comment at `:41-43` frames the leak purely as an
RAM-exhaustion question ("well below any host-RAM-exhaustion risk"), which is
true and is the wrong axis.

**Suggested fix.** Hoist the payload out of the timed closure. Because the cell
never frees its pointee and each iteration gets a *fresh* cell, **one** leaked
payload can serve every iteration:

```rust
let payload = leak();
h.bench_batched(
    "get_or_try_init/cold",
    RacyPtrCell::<Payload>::new,
    move |cell| { black_box(cell.get_or_try_init(|| Some(payload))); },
);
```

That removes the malloc from the timed region, removes 4.4 M leaked
allocations and the drift they cause, and leaves a number that is actually
about the CAS. (Run-1's F5 second half asked for a "baseline without the cell"
and a contended arm; those remain worthwhile and separate — this fix is the
prerequisite that makes either of them interpretable.)

### F8 — **P3** — the root crate's `#[cfg(loom)] mod loom_shim` is now faithful in *behaviour* but has three `unsafe` blocks with no `// SAFETY:` comment, contradicting `bootstrap.rs`'s own seam header

**Where:** `src/registry/bootstrap.rs:320` (`get`), `:334` (`get_or_try_init`
fast path), `:378` (`get_or_try_init` loser path), against the header claim at
`:187` ("Every `unsafe` block carries a `// SAFETY:` proof below.") which
immediately precedes the tier-1 lift `#![allow(unsafe_code)]` at `:188`.

**Fidelity verdict first, since that is what the task asked.** I diffed the
shim against the real crate line by line. Commit `29c2b2f` closed run-1's F2
correctly, and I found **no new drift**. Present and matching in both:
entry `Acquire` load; CAS `null → sentinel` with `Acquire`/`Relaxed`;
`RollbackGuard` armed across `init()` and defused on both non-unwinding exits;
release-active `is_ready` assert before the publish; `Release` publish;
`Release` OOM rollback with `defuse()` first; loser spin on
`== SENTINEL_INITIALIZING` with `break`-and-re-race on `null`;
`dbg_rollback_reenterable`'s restore gated on its own postcondition CAS; and
the `align_of::<T>() >= 2` const assert with the same message. The only
deviations are the two documented ones: `core::sync::atomic` instead of
`loom::sync::atomic` (the whole reason the shim exists — `const fn new`), and
`core::hint::spin_loop()` instead of the real crate's
`loom::thread::yield_now()`.

**The residual defect.** The three `NonNull::new_unchecked` sites carry no
`// SAFETY:` line, while their counterparts in the real crate all do
(`crates/racy-ptr-cell/src/lib.rs:324-326`, `:389-392`, `:488-493`). These
predate `29c2b2f` (they are context lines in its diff), but `29c2b2f` was the
commit that re-audited this module against the real crate for fidelity and did
not close them. Consequence: a grep-based `unsafe`-hygiene audit of the tier-1
seams — which CLAUDE.md's "Active rules" section makes the *formal* audit
procedure — finds three unjustified blocks in a file whose own header asserts
there are none. Two-line fix; the invariant is identical to the real crate's
(`is_ready`/`a != 0` proved non-null one to three lines above).

**Second-order hazard, worth one sentence in the shim's module doc.** Because
the shim spins with `core::hint::spin_loop()` on `core` atomics, if a future
root-crate loom harness ever *did* reach a chunk cell, loom would not model the
interleaving and the model would **hang** rather than fail. The module doc
asserts "It is NEVER on a loom-modeled interleaving" (`:240-241`) but nothing
mechanically enforces that, and the failure mode of the assertion being wrong
is silent rather than loud.

### F9 — **P3** — the reentrancy warning covers self-recursion on one cell but not a cycle across two cells, which is the shape the crate's own primary use case produces

**Where:** `crates/racy-ptr-cell/src/lib.rs:357-360`.

**Failure scenario.** The doc says `init` "must not itself call back into
`get_or_try_init` on the SAME cell (that would spin forever — the current
thread is the only one able to publish)". Correct, but the narrower half of the
hazard. Take two cells, `A` and `B`, in one allocator bootstrap — exactly the
shape `src/registry/bootstrap.rs` already has (64 per-chunk `RacyPtrCell`s plus
the `alloc-xthread` overflow-sidecar path, whose module doc at `:887-905`
explains why it is a *second* instance of the same protocol). Thread 1 wins
`A`, and `A`'s `init` touches something that lazily initialises `B`. Thread 2
concurrently wins `B`, and `B`'s `init` touches `A`. Thread 1 spins on `B`'s
sentinel, thread 2 spins on `A`'s: two threads at 100% CPU forever, no
diagnostic, no timeout, no deadlock detection — and, in a `#[global_allocator]`,
no way to even print about it. Nothing in the doc warns that the cells compose
into a lock-order graph.

**Suggested fix.** Generalise the sentence: `init` must not, transitively, wait

## 3. Verdict: **CONDITIONAL GO**

The primitive itself is publish-ready and I could not break it. Every gate is
green on the current tree — 7/7 native, 7/7 loom against the *real* type with
both non-vacuousness counterfactuals still firing, clippy `-D warnings` across
all targets, `rustdoc -D warnings`, `fmt`, and a clean 12-file package with
both licences, a CHANGELOG, and zero normal dependencies. The three atomic
orderings that matter are each justified and each pinned by a test that fails
without them; the `RollbackGuard`, the release-active sentinel assert, and
`dbg_rollback_reenterable`'s conditional restore are all correct, complete, and
non-vacuously covered; and the root crate's `loom_shim`, which run-1 flagged as
drifting, is now faithful line by line with no new divergence. **There is no P1
finding: no UB, no soundness hole, no lost happens-before, no ABA break, no
reachable sentinel collision.** What blocks an unconditional GO is a cluster of
four P2s that are all cheap and all sharply worse *after* upload than before
it: two claims that ship as permanent published metadata and are wrong — the
unqualified "no reentrancy" in `Cargo.toml:7` (F1), which the crate's own
task-#706/#707 panic paths falsified after the sentence was written, and the
`lock-free` keyword (F2), which asserts the exact progress guarantee commit
`7e20a4a` had just finished documenting the crate does *not* provide; one
soundness-argument doc that states as fact the very case its release-active
`assert!` exists to catch (F4), which is precisely how a future maintainer
deletes that assert; and one file that ships to crates.io with zero compile
coverage in any gate (F3), reopening the exact CI class the 2026-08-09 review
closed for the file next to it. Close F1-F4 — they are a single small
`Cargo.toml` + doc + one-CI-line commit, with no algorithm change anywhere —
and this is a **GO**; the eight P3s are all genuine but none of them needs to
precede the first upload.
