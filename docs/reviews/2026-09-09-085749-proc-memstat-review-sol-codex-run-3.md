## Вердикт

**NO-GO для полностью готового к публикации пакета: P0=0, P1=0, P2=1, P3=2, P4=4.**

Основные исправления прошлого раунда принимаю. Нового UB или неправильного
расчёта штатных memory counters на основных платформах по статическому анализу

## P2-1. Новый lifecycle target ломает проверку пакета на PowerPC Linux

Места: `Cargo.toml:22`; `tests/thread_leader_exit.rs:152`, `:164`, `:168`.

Target `thread_leader_exit` автоматически входит в тестовый набор. Весь scenario
включён для `target_os = "linux"`, но список архитектур с SYS_EXIT не содержит
`target_arch = "powerpc"` — только `powerpc64`. Для остальных Linux-архитектур
включается `core::compile_error!`.

По условиям cfg на `powerpc-unknown-linux-gnu` этот compile_error неизбежно активен.
Это не гипотетическое имя target: Rust перечисляет PowerPC Linux среди поддерживаемых
платформ с host tools. Источник: [Rust Platform Support](https://doc.rust-lang.org/rustc/platform-support.html).
Библиотечный backend при этом не имеет соответствующего arch-ограничения: он
читает procfs безопасным Rust-кодом.

Следствие: `cargo test -p proc-memstat` / проверка `--all-targets` на этой
архитектуре больше не могут проверить пакет из-за fixture, хотя сама библиотека
не нуждается в этом syscall number. Аналогичный ограничитель затрагивает другие
Linux targets вне списка. **Команды здесь не выполнялись**; вывод следует прямо
из compile_error и полного набора cfg.

Исправить область применимости fixture: либо добавить проверенный номер для
реально поддерживаемых ABI, либо ограничить только native-сценарий его честно
поддерживаемым списком с явным сообщением о пропуске. Нельзя из-за тестового
syscall лишать переносимости обычный parser/backend. Сохранять запрет угадывать
номера правильно; превращать его в запрет собрать весь тестовый пакет — нет.

## P3-1. Native tests безусловно требуют thread-self вопреки legacy fallback

Места: `src/lib.rs:293`, `:313`; `tests/thread_leader_exit.rs:203`;
`tests/non_utf8_name.rs:95`; `README.md:87`.

Production явно поддерживает отсутствие `/proc/thread-self`: при NotFound
читает `/proc/self/status`, сохраняя старый режим на Linux до 3.17. Новые tests
безусловно открывают `/proc/thread-self/status` через `expect`, поэтому на такой
системе проверка падает ещё на подготовке сценария — даже когда библиотека
корректно возвращает reading через предусмотренный fallback.

`/proc/thread-self` появился в Linux 3.17; это указано в
[proc_pid_task(5)](https://man7.org/linux/man-pages/man5/proc_pid_task.5.html).
Минимальное ядро ряда Rust GNU/Linux targets — 3.2, так что такое окружение
не исключается одним выбором Rust. См. [Rust Platform Support](https://doc.rust-lang.org/rustc/platform-support.html).

Согласовать tests с capabilities: на старом ядре проверять работающий legacy
путь при живом leader, а native-сценарий, требующий thread-self, явно считать
неприменимым. Не маскировать произвольные I/O errors как «старое ядро» и не
ослаблять основной Linux 3.17+ regression guard. Полезно отдельно проверить
ветвь NotFound→fallback управляемым acquisition-результатом.

Само ограничение измерения после смерти leader на legacy-пути уже описано во
внутреннем комментарии; не выдаю его за новый регресс production. Дефект здесь —
несовпадение области поддержки библиотеки и обязательных для неё tests.

## P3-2. CSV больше не соответствует собственной схеме из десяти столбцов

Места: `docs/perf/PROC_MEMSTAT_P4_2_SCAN_COST_summary.csv:7`, `:11`, `:12`.

В header десять полей, но три строки содержат по одиннадцать: запятая внутри
`note` не заключена в кавычки. Конкретные места внутри текста:

- `whole snapshot()), not a measured speedup...` — строка 7;
- `real file, so no percent-of-call...` — строка 11;
- `~3.17% of it, see parse_share_real` — строка 12.

Строки 7 и 12 повреждены текущей P4-правкой; дефект строки 11 существовал раньше
и был пропущен мной во втором раунде. Новые слова полезны, но добавленная запятая
становится разделителем столбцов. Строгий reader отвергнет несогласованный размер
record, более разрешительный потеряет часть note либо создаст лишнее поле.
Сами числовые value до note этим не изменены — это дефект формата артефакта,
не опровержение записанных измерений.

Заключить note с запятыми в double quotes с корректным escaping. Правило и
согласованное число полей описаны в [RFC 4180, раздел 2](https://www.rfc-editor.org/rfc/rfc4180.html#section-2).
Если файл дальше генерируется, использовать настоящий CSV writer и проверить
round-trip строк, а не собирать их конкатенацией. В этом ревью reader/validator
не запускался; лишние разделители видны в самом тексте.

## Неблокирующие замечания P4

### P4-1. Ошибочное optional-поле иногда становится None, иногда Malformed

Места: `src/status_convert.rs:55`, `:61`; `src/status_parse.rs:202`, `:233`;
`CHANGELOG.md:109`, `:168`.

`read_kib_field` возвращает один None и для отсутствующего ключа, и для
неправильной единицы, и для decimal overflow. Конвертер уже не может различить
эти причины. Поэтому при корректном `VmRSS: 4 kB`:

| VmSize в том же buffer | Результат conversion |
| --- | --- |
| отсутствует | `Ok`, `virtual_size: None` |
| `VmSize: 12 MB` | `Ok`, `virtual_size: None` |
| `VmSize: 18014398509481984 kB` | `Err(Malformed)` — overflow при ×1024 |
| `VmSize: 18446744073709551616 kB` | снова `Ok`, `virtual_size: None` — overflow раньше, в parser |

Аналогично для VmHWM. Более некорректное значение таким образом может превратить
ошибку обратно в успех. CHANGELOG утверждает, что любое нарушение грамматики
выходит через try_snapshot как Malformed, и приравнивает два overflow-пути;
это шире действительной реализации.

Выбрать явную политику: `None` только для отсутствия, `Err` для найденного
невалидного поля — либо намеренно разрешённые частичные readings с точными docs.
Для первого варианта parser нужен внутренний результат, различающий absence
и invalidity. Не расширять public API только ради этого. Добавить fixtures
неправильных optional-полей, а не только отсутствия и scaled overflow.

P4: обычное ядро такие чрезмерные числа/MB не печатает; это согласованность
защитного error-контракта, не обнаруженный сбой на реальной памяти процесса.

### P4-2. В prctl передаются неназванные по ширине вариадические нули

Место: `tests/non_utf8_name.rs:89`.

В `prctl(15, name.as_ptr(), 0, 0, 0)` у трёх нулей нет ожидаемого Rust-типа от
variadic signature, поэтому используется i32. Для libc wrapper prctl нужны
аргументы правильной машинной ширины; документация специально предупреждает
об этом и приводит `0L`. См. [prctl(2), CAVEATS](https://man7.org/linux/man-pages/man2/prctl.2.html).

Передавать эти значения с явным `core::ffi::c_ulong` (либо соответствующим
документированным C long типом), чтобы переносимость не зависела от заполнения
слотов ABI. Сам name buffer имеет правильные 14 bytes, NUL и срок жизни на call.
PR_SET_NAME не использует эти дополнительные нулевые аргументы в своём действии,
поэтому не заявляю о воспроизведённом падении или порче имени на x86-64: это
небольшое исправление точности FFI в тестовом коде.

### P4-3. RSS нужно явно отделить от всей физической памяти процесса

Места: `src/lib.rs:6`, `:118`; `README.md:53`.

Поле честно читает native RSS/WorkingSetSize, но описание как «physical memory
currently backing the process» легко прочитать как полный physical footprint.
Для allocator-потребителя важны конкретные исключения:

- Windows working set исключает nonpageable allocations, включая large pages
  и AWE. Это прямо указано в [Microsoft Working Set](https://learn.microsoft.com/en-us/windows/win32/memory/working-set).
- Linux Hugetlb учитывается отдельно от обычного RSS; task_mem строит VmRSS
  из anon/file/shmem и отдельно вызывает hugetlb_report_usage. См.
  [Linux task_mem](https://raw.githubusercontent.com/torvalds/linux/v6.12/fs/proc/task_mmu.c)
  и [документацию procfs о Hugetlb](https://docs.kernel.org/filesystems/proc.html).
  Это исключение для explicit HugeTLB, не утверждение, что обычные THP исчезают из RSS.

Реальная большая resident allocation поэтому не обязана дать равный ей рост
этого поля. Не нужно молча прибавлять другие counters к rss: это изменит значение
native метрики. Достаточно явной секции ограничений; отдельную метрику большего
охвата добавлять только с определённой семантикой. Это документационное улучшение,
не новый баг чтения VmRSS или WorkingSetSize.

### P4-4. Остались точные расхождения грамматики и исторических пояснений

Места: `src/status_parse.rs:173`, `:207`; `tests/platform_contract.rs:422`, `:440`;
`examples/status_scan_cost.rs:144`, `:187`, `:221`; `CHANGELOG.md:198`.

1. Грамматика требует leading `ASCII-whitespace+`, но integer_span допускает
   `start == 0`: `VmRSS:12 kB` успешно разбирается. Разрешить `*` в грамматике
   или действительно проверять первый пробел. Это не возврат прежних `12oops`
   или неверных единиц — их новое поведение корректно.
2. Production читает thread-self, тогда как smoke-band повторно читает self;
   утверждение «same file the backend reads» неверно. При живом leader они
   отражают общий mm, что объясняет пригодность smoke, но это не одна task-запись.
   Example также печатает старый self-путь как путь полного snapshot, хотя
   denominator вызывает обновлённый backend. Уточнить источник и labels.
3. CHANGELOG говорит, что fused function не изменилась относительно измеренной.
   Её цикл действительно сохранён, но вызываемый field_value теперь проверяет
   grammar/unit; изменилось и приобретение данных полного snapshot. Числа с
   привязкой к `3119719` остаются историческим свидетельством именно того кода,
   а запуск example на текущем HEAD измеряет уже другой код. Указать revision
   в рецепте исторического воспроизведения и не подавать старую оценку как
   измеренную скорость текущего parser.

Многие необходимые ограничения теперь повторяются в длинной истории внутри
src, tests, example и CHANGELOG; это увеличивает число мест для таких расхождений.
Лучше короткий действующий контракт у реализации и ссылка на один исторический
отчёт. Не предлагаю переписывать историю коммитов или повторять benchmarks
только ради редакционной правки.

## Общий обзор безопасности и стоимости

**Runtime.** Публичных raw-pointer входов нет; MemStat — Copy value без heap
владения, SnapshotError — небольшой non-exhaustive enum. В Linux нет unsafe:
байтовая граница не зависит от имени task, срезы ограничены вычисленными внутри
них позициями, decimal accumulation и перевод в bytes проверяют overflow.
Один read-result идёт в реальную conversion-функцию, которую проверяют fixtures.

**FFI.** Windows сохраняет корректную форму base PROCESS_MEMORY_COUNTERS,
cb и проверку BOOL до использования output. Mach buffer имеет правильные
поля/offsets, 48 bytes и count 12; cached port читается по значению без
приобретения/освобождения права. Новое объяснение fork корректно учитывает
повторную инициализацию. В lifecycle fixture raw SYS_exit сознательно не вызывает
foreign unwind, worker владеет своими данными, а весь child завершается после
результата. PASS-файл действительно защищает от ложного успеха при ошибочном
завершении всего процесса с кодом 0. Это полезные исправления, не повод снова
поднимать закрытые замечания R2.

**Сложность.** Три поиска дают O(L), а не O(L²); временный Vec занимает O(L).
При фиксированных трёх ключах fused reader тоже O(L). Переменное N в его
внутренней сигнатуре не делает его O(L) независимо от N, но текущие callers
используют фиксированный FIELDS. Глубоких копирований на runtime пути нет:
snapshot_from_read забирает Vec и берёт срез без клонирования. Новый слой
conversion сам по себе не добавляет heap allocation.

**Реальная возможность уменьшить стоимость:** для частого опроса Linux —
caller-owned scratch либо streaming parser с фиксированной временной памятью.
Это может убрать свежие alloc/realloc и их влияние на измерение, не меняя поля.
Нужны корректные partial reads и перенос незавершённой строки; длинную Groups
следует пропускать до конца, не обрезая весь файл первыми 4/8 KiB. Такой parser
останется O(L) по чтению, но может иметь O(1) временную память. Скорость здесь
не измерялась; старый NO-GO по объединению поисков не измерял zero-allocation путь.

Не предлагаю ускорять cold probe усложнением ownership, добавлять зависимости
ради трёх полей или кэшировать procfs fd без решения его task/fork-привязки.
Для короткой серии измерений текущий простой путь разумен после закрытия
замечаний. Отдельный no-allocation API был бы иной возможностью, не незаметным
«ускорением» неизменного контракта.

**Покрытие.** Новые exact fixtures, non-UTF-8 end-to-end и проверка настоящего
leader exit существенно сильнее прежних косвенных тестов. CI по-прежнему содержит
