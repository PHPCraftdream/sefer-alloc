## Подтверждённые находки

### R9-01 — P2 — safe diagnostic reader применяет Small-метаданные к Large payload

**Где и доступность:** `src/alloc_core/small/alloc_core_small_diag.rs:70-85,98-104`; оба метода `pub fn` доступны через root `AllocCore` при `alloc-core + internals`, не при одном `production`. Соседний `dbg_live_count_for` уже проверяет `SegmentKind` (`:38-49`), а эти два — нет.

**Валидный сценарий:** создать `AllocCore`, вызвать безопасный `alloc(Layout::from_size_align(2 * 1024 * 1024, 16).unwrap())` и, пока выделение живо, безопасно вызвать `dbg_freelist_head_for(ptr, 0)` либо `dbg_is_free_for(ptr)`. 2 MiB больше `SMALL_MAX` даже с `medium-classes-wide` (`src/alloc_core/platform/size_classes.rs:35-44`), следовательно сегмент Large. `canonical_base_of` подтверждает лишь членство в таблице, не Small-kind. `SegmentMeta::bin_table()` адресует Small bin offset (`src/alloc_core/segment/segment_header/descriptors.rs:277`), а `alloc_bitmap()` — Small bitmap offset (`:285`); в Large это область возвращённого, не инициализированного для этих структур payload. `BinTable::head` читает там `u32` (`descriptors.rs:190` → `src/alloc_core/platform/node.rs:217`), bitmap читает байт (`src/alloc_core/segment/bitmap/segment_bitmap.rs:83`). На обычном свежем OS mapping нули могут сделать лишь бессмысленный диагностический ответ. Под `cfg(miri)` `aligned-vmem` резервирует через `System.alloc`, не `alloc_zeroed` (`crates/aligned-vmem/src/os/miri.rs:14-21`); Large-конструктор пишет header, но не эти Small-структуры (`src/alloc_core/large/alloc_core_large.rs:676-697`). Поэтому указанное чтение попадает в неинициализированные байты при успешной резервации. Это конкретное source-level нарушение unsafe-предусловия за безопасным методом, **не** вывод из отсутствующего Miri-прогона и **не** утверждение об обычном production API.

**Последствие:** на native ложные значения диагностики; на описанном Miri backend чтение uninitialized memory из safe вызова. **Исправление:** для обоих методов после canonical lookup проверять `Small | Primordial`; вернуть `FREE_LIST_NULL`/`false` для Large (или явно изменить API на `Option`); не формировать Small view раньше проверки. **Отрицательный/regression witness:** отдельный тест под `alloc-core + internals` на живом Large pointer, проверяющий sentinel/false, плюс тот же короткий сценарий под Miri после исправления; затем Small positive control, где настоящий head/free-bit по-прежнему наблюдаем. Ничего из этого в данном раунде не запускалось.

### R9-02 — P3 — периодический полный sidecar-scan даже без pending-публикаций

**Где:** `src/global/maintenance_service.rs:144,165`, `src/registry/heap_registry/maintenance.rs:18-40`, `src/registry/heap_core/state/ownership.rs:105-110`, `src/alloc_core/alloc_core/sidecar_drain.rs:12-34`, `src/alloc_core/segment/remote_bitmap/sidecar_bitmap.rs:79-84`, `bitmap_scan.rs:15-22`. Доступность: обычный `production`, **только после** успешного явного `start_maintenance()`.

**Валидный сценарий:** owner-thread выделяет достаточно Small-блоков для нескольких почти полных сегментов, передаёт live-объекты другой нити и завершается. Его registry slot становится `FREE`, но сегменты остаются зарегистрированными из-за живых кредитов; другой поток пока не освобождает блоки. Работник каждые 10 ms вызывает bounded-by-slot-count maintenance, для FREE heap — `trim_for_recycle`, а та — `drain_sidecar_ingress`. Последний посещает каждый non-null slot до high-water и вызывает `scan(high_water)`, выдающий `ceil(high_water / (16*64))` word cuts. `next_cut` делает `AcqRel swap(0)` **для каждого** слова, включая нулевое. Для сегмента с high-water близко к 4 MiB это 4096 RMW за один обход; для `S` таких сегментов — `O(S * 4096)` на каждый визит к heap, даже при нуле публикаций. Это счёт операций по исходнику, не измеренная CPU/latency цифра; interval и slot budget не являются гарантией дешёвого idle.

**Последствие:** при большом числе FREE heaps с остающимися live Small-сегментами maintenance может тратить CPU и создавать атомарный трафик, не выполняя полезного reclaim. **Направление:** проектировать безопасный idle fast-path (например, иерархический pending-summary с доказательством отсутствия потерянной публикации) либо ограниченный word/segment cursor на тик; сохранять правило, что post-cut producer остаётся кредитом для следующего обхода. **Отрицательный/regression witness:** счётчик word-cuts у FREE heap с `S` заполненными сегментами и нулём публикаций должен перестать расти на `4096*S` каждый визит; отдельно проверить гонку publish до/после cut, без потери reclaim. Это пока источник-level cost finding, не заявка на доказанный выигрыш во времени.

### R9-03 — P3 — публичная инструкция `stats()` не компилируется и обещает снятый счётчик

**Где:** `src/global/sefer_alloc/diag.rs:76-86`, `src/global/alloc_stats.rs:56-150`; внешний `SeferAlloc::stats()` доступен с `alloc-global`, включая `production`. В текстовом примере написано `stats.ring_overflows`, но у текущего `AllocStats` такого поля нет; есть `foreign_or_unroutable_frees`. `AllocStats` и `src/global/sefer_alloc/mod.rs:68` также описывают снятый `dealloc_foreign_routing`/ring как текущий путь, тогда как `GlobalAlloc::dealloc` вызывает `publish_foreign` (`src/global/sefer_alloc/global_alloc.rs:64` и `src/registry/heap_core_xthread/routing.rs:27`).

**Сценарий → цепочка → последствие:** downstream пользователь копирует документированный `stats()` пример с `production`; компилятор отвергает обращение к несуществующему полю. Если пользователь ищет «ring overflow» как мониторинговый сигнал, текст направляет его к несуществующей текущей метрике и скрывает фактическую семантику `foreign_or_unroutable_frees`. **Исправление:** заменить пример на существующие поля, убрать сравнение с ring-overflow (это не синоним dropped/foreign frees), обновить описание действующего route-sidecar пути. **Отрицательный/regression witness:** вынести пример в реально компилируемый feature-gated integration/example target и проверять exact `production` set; статически отвергать ссылку на отсутствующее поле. Сейчас fence `text`, поэтому doctest не защищает пример.

### R9-04 — P4 — комментарии инвентаря unsafe/архитектуры называют удалённые модули

**Где:** `src/alloc_core/mod.rs:5-15,29-36` перечисляет `dirty_by_class` и `segment::remote_free_ring` как действующие seams/детали; `src/alloc_core/alloc_core/lifecycle.rs:457` говорит о нынешнем leak `PerClassDirty`; `src/registry/heap_core/alloc/hot.rs:166` содержит rustdoc link к `crate::alloc_core::remote_free_ring`. В текущем `src/` нет соответствующих модулей (`src/alloc_core/platform/mod.rs`, `src/alloc_core/segment/mod.rs` и полный файловый инвентарь), а actual foreign ingress находится в `segment_route`/`remote_bitmap`.

**Сценарий → последствие:** новый ревьюер использует эти комментарии как карту unsafe/teardown и проверяет несуществующий ring вместо текущего route protocol; rustdoc link к удалённому пути не может вести к объявлению. Runtime-дефект из одного комментария не следует. **Исправление:** заменить active-tense инвентарь текущими модулями, исторические механизмы обозначить как историю либо удалить; сверить ссылки с exact `production` rustdoc. **Отрицательный/regression witness:** source-link/identifier guard для актуального дерева и doc-lint точного docs.rs feature set; ни один не запускался здесь.

## Не подтверждено как дефект

- `src/concurrent/epoch/epoch_region.rs:634` безопасный setter поколения может оживить старый handle при `experimental + internals`; это прямо описанный и намеренно открытый тестовый backdoor, а `tests/xxs_r5_02_epoch_generation_setter_gated.rs` проверяет отсечение от plain `experimental`. Не выдаю его за новое нарушение обычного API. Если `internals` предполагается использовать вне тестов, нужен отдельный policy-выбор о более узком gate или об unsafe контракте.
- `src/concurrent/pinning.rs:122-145`: конструктор возвращает `Some` даже если `core_affinity::get_core_ids()` даст `Some(empty)`, и тогда `worker_count() == 0`; не установлено, допускает ли resolved `core_affinity 0.8.3` такой ответ на поддерживаемых платформах. Нужна проверка контрактного поведения зависимости; пока гипотеза, не P-пункт.
- Параллельные owner/producer переходы route-directory, epoch generation CAS и NUMA/backend-only paths требуют dynamic/model/target проверки. Отсутствие такого прогона здесь не считается доказательством Sefer UB. Упомянутые в README per-heap cache headroom и отсутствие гарантированного shutdown/deadline у maintenance — заявленные ограничения, не новые баги.

## Оптимизации для измерения, не «замеренный speedup»

1. `src/registry/segment_route/directory.rs:266-315,388-466`: внутри shard lock бинарный поиск `O(log k)` сопровождается сдвигом sorted pointer array `O(k)` на insertion/removal; grow копирует `O(k)` pointers под lock. При `k` route keys в одном shard, серия вставок в начало — `O(k^2)` суммарных pointer moves. Также каждая регистрация выделяет `Entry` + sidecar через `System` (`:43-92`). Оценить частоты register/unregister, распределение keys, mutex wait и allocation count в реальной конфигурации до выбора hash/segmented структуры; нынешняя сортировка может быть лучшей при маленьком `k`.
2. `src/alloc_core/large/alloc_core_large_cache_eviction.rs:198-247` и `src/alloc_core/alloc_core/mem/mem_impl.rs:347-375`: oldest victim ищется перебором set bits `O(k)`; если budget требует удалить `k` spans, повторная eviction даёт `O(k^2)` slot inspections (`k <= 8`, либо до 40 с `large-cache-extended`). Замерить прежде чем вводить FIFO index/list с новыми инвариантами.
3. `src/concurrent/lock_free/lock_free_region.rs:363-376,439-470,516-563`: legacy `LockFreeRegion` копирует snapshot page vector при каждой успешной записи (`O(P)` page-Arc refs/copies) и одну страницу (`O(PAGE)` slot clones). Это явная цена RCU-read оптимизации, не hidden regression; сравнивать на read/write смеси и отдельно от production allocator.

Приоритеты: сначала kind-gate у R9-01; затем проверить/cost-gate idle maintenance R9-02; документационные R9-03/04 можно закрыть вместе. Все предложенные отрицательные свидетели — задания на проверку после правки, **не** выполненные в этом статическом раунде.
