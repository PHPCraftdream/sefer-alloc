# Почему зелёные локальные доказательства порождали новые находки: proof/cost-контур

Дата исследования: 2026-10-01, Europe/Berlin. Неизменённая база: `cae3333bac50b6a05b93c79695823b3df41edc55`. HS-C, исследование доказательств, процесса и стоимости; не предложение немедленно заменить backend. Все пути ниже относительно репозитория. Исходники, тесты, сборки, Miri, Loom, бенчмарки и скрипты проекта в этом исследовании **не запускались и не менялись**. Результаты прогонов указаны только как уже записанные исторические receipts, не как мои прогоны.

## Вывод

Главный повторяющийся дефект *системы доказательств* — незаметное повышение уровня утверждения. Свойство отдельного предиката, модели, низкого слоя или измерительного окна объявлялось свойством поставляемой композиции `#[global_allocator]` при конкретных feature/ОС/времени жизни. Другой повторяющийся класс — стоимость действительного перехода состояния измерялась в неверной конфигурации, на неверном пути либо при нагрузке, не пересекающей порог политики. Это не означает, что старые исправленные баги вновь живы, и не сводит все находки к одному runtime-дефекту. Примеры из разных периодов: неверно разрешённая конфигурация R25-5→R26-1 (`docs/perf/R25_5_POOL_CAP_SWEEP_GATE.md:390-455`, `CLAUDE.md:634-668`), неверно активированный «virgin» путь R29-16→R30-3 (`docs/perf/R30_3_VIRGIN_ZERO_SKIP_NATIVE_GATE.md:150-201`), неверный слой R30-3→R31-0 (`docs/perf/R30_3_VIRGIN_ZERO_SKIP_NATIVE_GATE.md:472-504`), зелёные ограниченные owner/model проверки на фоне красного real installed-Box frame (`docs/perf/round-manifests/SRC_REVIEW_R11_MANIFEST.md:57-60,101-122`, `docs/reviews/2026-10-01-0945-r11-terminal-box-acceptance-sol-codex.md:7-35`).

Практический рефакторинг здесь — **реестр исполняемых обязательств приёмки**, привязанный к действительным переходам и конфигурациям, плюс разделение логического владения, pointer-permission и физического освобождения в протоколе. Реестр не заменяет архитектурный ремонт открытого Box P1: пока `Node::write_next` пишет в защищённый payload, формально красивый чеклист лишь точнее зафиксирует красный gate. Отдельные HS-A/HS-B рассматривают причинный ledger и архитектурный memory backend; этот документ не выбирает их дизайн.

Я **не запускал** их и не принимаю handoff-логи как свою проверку. Подробную память/descriptor архитектуру должен оценивать HS-B отдельно; по одной изолированной кандидатуре production GO невозможен.

## Почему измерительный контур уже ошибался несколько раз

1. **Подмена конфигурации.** R25-5 подписал строки `pool_segments=8/16/32`, но повторно взятый slot оставался с конфигурацией прежнего arm. R26-1 потребовал fresh process, readback resolved config и нулевой `config_conflicts` delta (`CLAUDE.md:634-668`; `docs/perf/R25_5_POOL_CAP_SWEEP_GATE.md:390-455`). Новая fresh-first registry политика R11 меняет вероятность materialization/reuse; старые RSS цифры не пересаживаются на неё без нового одинакового churn regime.
2. **Подмена кода под меткой.** В R29-16 повторная Criterion-итерация брала recycled freelist вместо virgin carve. R30-3 добавил per-arm path oracle и нашёл собственный первоначальный 16-element batch только на 6.25% intended path (`docs/perf/R30_3_VIRGIN_ZERO_SKIP_NATIVE_GATE.md:150-201`; `CLAUDE.md:675-738`). Path activation должен измеряться *до* принятия результата, а OFF binary с выключенной веткой не может считаться «100% активированным» из счётчика ветки (`docs/perf/R30_3_VIRGIN_ZERO_SKIP_NATIVE_GATE.md:206-224`).
3. **Подмена слоя.** Даже исправленный R30-3 `AllocCore::alloc_zeroed` обходил `HeapCore` magazine; R31-0 нашёл другой реальный virgin fraction на shipping layer (`docs/perf/R30_3_VIRGIN_ZERO_SKIP_NATIVE_GATE.md:472-504`; `CLAUDE.md:830-854`). Для нынешних R11 hot changes нужно мерить `HeapCore`/реальный `GlobalAlloc`, отдельно записывая, что именно нижний `AllocCore` unit case покрывает.
4. **Подмена окна/режима.** R13-9's «21.71×» относилось к inner timer, тогда как тот же Criterion full round давал приблизительно 11% (`docs/perf/R14_3_CLASS_AWARE_DIRTY_FIXED_WORK_AB.md:16-33`), а независимый process judge не устанавливал одну точную full-round цифру (`:158-170`). R30-6's 8×6 MiB request округлился до ровно 64 MiB working set: сравнение headroom64 против256 не пересекло порог; R31-1 зафиксировал 12.5 percentage-point hit-loss при 128/288 MiB (`docs/perf/R31_1_LARGE_CACHE_HEADROOM_CROSSING_REGIME_GATE.md:4-24,50-57`). Порог, page faults, owner drain *после* выбранного inner timer и fallback saturation должны жить в том же arm, для которого заявляется Pareto-вывод.
5. **Подмена количества.** `R29_13_LARGE_CACHE_RETENTION_GATE.md:430-518` фиксирует 63-символьный «sha256» неиспытанного рабочего дерева, категориальную ошибку absolute retention ÷ incremental delta («30×») и простую арифметическую «32×» вместо `256/16=16`; первоначальный примерно 238 MiB idle floor отдельно не опровергнут. Измерительная идентичность должна создаваться до запуска, отношение — вычисляться из сохранённых чисел одной единицы/знаменателя (`CLAUDE.md:752-827`).
6. **Подмена исполняемого артефакта.** R11 integration сперва запустил устаревший default-target selector после переноса файла с сохранённым mtime; isolated target и затем scoped cache cleanup дали согласованный результат (`docs/perf/round-manifests/SRC_REVIEW_R11_MANIFEST.md:74-82`). Это не подтверждённый дефект нового registry алгоритма и не разрешение бесконечно чистить общие caches: acceptance identity должна включать исходный tree, binary hash/время build и фактически исполненный путь.

В текущем R11 OOM-проверка иллюстрирует, что fault injector, привязанный только к «следующему вызову», хрупок: одноразовая ошибка регистрации была законно восстановлена новым full-rescue retry и старый тест больше не достигал NULL; persistent fault budget покрыл обе попытки (`docs/perf/round-manifests/SRC_REVIEW_R11_MANIFEST.md:49-56,114-120`; `tests/r6_route_lifecycle_oom.rs:40-47`). Это *изменение проверяемого перехода*, не повод запрещать rescue или ослаблять rollback assertion.

## Предлагаемый рефакторинг приёмки: контракт на переход, не каталог grep-чисел

Один проверяемый manifest (формат с типизированными полями; YAML/TOML/JSON — выбор владельца) должен порождать матрицу gates и ссылки на receipts. Не копировать магические числа между README, карточкой item 87 и `scripts/verify-ci-sentinels.mjs`: `tests/no_stale_doc_references.rs:2105-2223` уже держит text-anchor `"the guard itself reports **"`, а R11 потребовал его перепривязки после перефразирования (`docs/perf/round-manifests/SRC_REVIEW_R11_MANIFEST.md:61-64`). Литературная редакция не должна определять факт исполнения; машина читает structured record, документы отображают его. Это не требует переписать все Markdown отчёты ретроактивно.

Минимальная схема для **одного обязательства**:

```text
id, owner_transition, precondition, success_postcondition, failure_postcondition
entry_point, exact_feature_set, target_os, toolchain, profile, allocator_layer
source_tree_id, binary_id, test_selector, activation_witness, observed_marker
proof_kind, actual_type_or_shadow_model, scheduling_barrier, negative_mutant
resource_axis, numerator, denominator, measurement_window, workload_regime
status = NOT_RUN | CFG_EXCLUDED | BUILD_ONLY | PASS | FAIL | INCONCLUSIVE | CONDITIONAL
receipt_path, known_limits, decision_scope
```

`source_tree_id` должен фиксировать исполняемую рабочую версию **до** измерения (`git write-tree`/commit/patch hash из сохранённого patch), а `binary_id` и manifest/result receipts подтверждают, что запущен именно этот build; один base SHA плюс незакоммиченный diff недостаточен (`CLAUDE.md:276-301`; R11 default-target incident). Не подразумевать, что `mtime` сам доказывает source identity. `status` различает отсутствие проверки, cfg-empty, build-only, timeout/host-OOM (INCONCLUSIVE) и настоящий красный Miri с stack trace (FAIL). Положительный reduced Loom model записывается с `actual_type_or_shadow_model=shadow`, без автоматического повышения до production.

Каждая строка `activation_witness` должна утверждать *тот механизм*, который изучают: фактическое опустошение magazine, число `base_at` попыток **до** probe, reached-refill/rescue, реальную class-leaf materialization, slot CAS/maintenance lease, OS release token, а не только «тест вернул 0». Для unsafe перехода рядом нужна mutation-negative, которая отключает именно защиту (например, root-derived write в paused-Box frame, early descriptor free при удержанном pin, потеря публикации после cut); отрицательное срабатывание из собственного bug'а harness не является доказательством (исторический tagged-index-stack counterfactual исправлялся отдельно: `CHANGELOG.md:373-381`). Для cost-gate negative — вернуть full scan/скрыть config conflict/держать workload ниже порога, и требовать, чтобы judge отверг такой arm.

Открытый Box P1 требует отдельной строки, объединяющей: `#[global_allocator]`, **настоящий** `Box::drop` кадр, `narrow=1..7`, paused **после** terminal RMW, strict owner trim до resume, Stacked **и** Tree Borrows, реальные Primordial/Small и dealloc/zeroed/reissue варианты, отрицательный intrusive/root control, затем last-pin/OS release. W+1/W+2 остаются кандидатами другого entry point. Считать gate выполненным лишь если selector действительно выбран, маркер после `join`/проверок, exit0, expected-negative проваливается по требуемой причине; не выключать borrow tracking или переносить паузу за Drop frame. `docs/reviews/2026-10-01-r11-protected-box-advice-xxs-sol.md` объясняет, почему даже успешный точный `System.dealloc` сам по себе не лицензирует раннее root-write или чужой zero/copy.

Для tiered verification это даёт отношения, а не ложную эквивалентность: Loom доказывает небольшой interleaving state machine; Miri — доступ/provenance данного runtime пути в текущих экспериментальных моделях; native integration — фактическую композицию и OS-поведение на конкретной платформе; benchmark — только измеренный режим и окно. Source review выявляет сценарии и обязательства, но не подменяет ни один из этих receipts.

### Вводимые критерии без искусственного «доказательства всего»

| Gate | Машинный критерий и отрицательный контроль | Чего не заключаем |
| --- | --- | --- |
| Корректность перехода | Все поддерживаемые `entry×feature×OS` клетки имеют explicit `PASS` или честный `CONDITIONAL` с названным исключением; `FAIL` Box frame блокирует соответствующий release claim. Переходы issue/terminal/retire/unlink/release и rollback с независимым count/token oracle, mutants должны падать по механизму. | Зелёный model или соседний `cfg` не доказывает все interleavings; Miri не является нормативным Rust proof. |
| Fault injection | Fault scope именует `prepare`, `publication`, `post-issue`, `retry`, `rescue`, `release` и число разрешённых попыток; сохраняются credit, block ownership, NULL/partial semantics и последующий retry. Mutation проверяет потерю rollback. | Простое «fail next N calls» не гарантирует, что после рефакторинга тест поразил тот же transition. Переход на named `TransitionFaultScope` — проектное предложение, не уже существующий API. |
| Поддерживаемая матрица | Реальный `GlobalAlloc` на опубликованном feature set и нижние opt-in gates по отдельности; MSRV **runtime** на OS, где TLS destructor registration использует соответствующий std путь; `cargo test --no-run`, `--all-features` и 0-test cfg не засчитываются за отсутствующую клетку. Документный lint exact docs.rs set по `CLAUDE.md:890-940`. | Исторический MSRV abort не объявляем живым после соответствующего исправления; матрица не означает перебор всех теоретических сочетаний features. |
| Стоимость/footprint | Источник и binary pinned; в *одном и том же* workload arm — resolved config, activation %, owner hot probes, foreign-free RMW, cold/worker cut, fallible System bytes+alloc count, actual RSS/commit/reserved/page faults, full-round и inner-window latency, hit/retention. N=малый реальный + независимая логическая граница вместо фейковых тысяч сегментов. | `41,984+256*m` requested bytes не RSS и не универсальный выигрыш: при `m=1024` это 304,128 > старых 294,912 (`ACTIVE.md:164`); CPU/latency не следуют из O(N) счётчиков. |

Порядок применения: сначала устранить текущий real-Box FAIL без отключения oracle; затем стабилизировать конкретные transitions и их counterfactuals, после — matrix execution и только затем сопоставимые perf gates. Каждый gate обязан хранить статус и scope рядом с точным исходным hash; append-only история старых ревью остаётся историей, но текущий GO берётся только из актуальных receipts. Это снижает вероятность *ложного* закрытия и повторной находки на соседнем пути, не обещает отсутствие новых ошибок: новые API, платформы, компиляторы и aliasing-модели расширяют пространство обязательств.

## Покрытие и ограничения этого исследования

Полностью прочитаны `docs/perf/round-manifests/SRC_REVIEW_R11_MANIFEST.md`, `docs/reviews/2026-10-01-0945-r11-terminal-box-acceptance-sol-codex.md`, `docs/reviews/2026-09-30-terminal-cutover-acceptance-xs-sol.md`; точечно прочитаны текущие `Cargo.toml`, `ACTIVE.md`, `CLAUDE.md` (правила evidence/gate), R9/R10 manifests, R9/R11 XS, R10/R11 XXS advice, protected-Box XXS advice, сентябрьские XA/fxx, июльские R14-3/R25-5/R29-13/R30-3/R30-6/R31-1 reports, выбранные test/source швы и `CHANGELOG.md` для counterfactual history. Инвентарь `docs/reviews/` содержит сотни файлов; **не** проводилось полное чтение каждого отчёта July/Aug/Sep, companion-crate corpus или всех строк нынешнего `src/`. Старые координаты привязаны к отчётному snapshot, нынешние — к `cae3333b`; исторические закрытые finding'и не перенесены автоматически в текущий статус. Изолированные W+1/W+2 результаты получены из handoff и чтения их test-source, но их logs и свежий W+3 не перепроверялись в этом исследовании. Любой будущий код/производительность/релизный вердикт требует собственной приёмки.
