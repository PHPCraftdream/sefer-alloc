## P2-1. Self-check передаёт недопустимый new_size в GlobalAlloc::realloc

Места: `crates/globalalloc-model/examples/perf_probe_p4_measurements.rs:190`,
`:208`, `:321`.

После успешного shrink тест имеет живой блок с `layout32 = Layout(32, 8)`.
Затем для проверки отказа вызывает:

```text
CountingAlloc.realloc(p32, layout32, isize::MAX as usize)
```

У GlobalAlloc::realloc новый размер после округления вверх до
`old_layout.align()` обязан оставаться не больше isize::MAX.
Это именно unsafe-предусловие, не ожидаемая причина обычного OOM.
[Контракт GlobalAlloc::realloc](https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html#method.realloc).

Здесь alignment равен 8, а на 32- и 64-битных targets:

```text
isize::MAX % 8       = 7
round_up(MAX, 8)     = MAX + 1 > MAX
max_valid_size(8)    = (MAX / 8) * 8 = MAX - 7
```

CountingAlloc напрямую пересылает запрос в System, не нормализуя его.
`main` безусловно запускает self-check, поэтому на обычном пути с ожидаемым
отказом предыдущего huge alloc выполнение доходит до этого нарушения.
`assert!(null.is_null())` после unsafe-вызова не исправляет предусловие.
Нельзя считать его выполнением корректного negative/OOM теста только потому,
что конкретный backend вернул null и программа продолжилась.

Основной `drive` этой ошибки **не имеет**: в `src/drive.rs:547` размер
ограничивается соответствующим align-зависимым максимумом до вызова realloc.

Минимальное исправление — использовать допустимый размер с учётом alignment.
Более надёжная проверка accounting — backend с управляемым отказом на малом
**валидном** запросе. Не предполагать, что почти-isize::MAX запрос обязан
отказать на каждом target: особенно 32-битный запрос находится в области
реально возможных виртуальных allocations. Такой backend заодно проверит
null без нагрузки на память машины. Проверить сохранность старого блока и
неизменность live/total/peak; затем повторить реальные измерения уже с
корректным self-check. В этом ревью ни опасный вызов, ни предлагаемый тест
не исполнялись.

## P3-1. S3 не воспроизводит управление и время жизни значений TestRunner

Места: `crates/globalalloc-model/examples/perf_probe_p4_measurements.rs:585`,
`:667`, `:670`, `:693`; claims — `src/strategy.rs:93`, `CHANGELOG.md:155`.

### Неверный переход после complicate

Настоящий runner после проходящего/отвергнутого кандидата вызывает complicate
и, если тот успешен, **снова оценивает current восстановленного дерева**.
Следующий simplify выполняется только после нового failure. При false от
complicate runner прекращает этот поиск.
[TestRunner::shrink, proptest 1.11.0](https://raw.githubusercontent.com/proptest-rs/proptest/7f1367f9a4dc8440c47b93166a38ed064f63ea8c/proptest/src/test_runner/runner.rs).

S3 в начале каждой итерации безусловно вызывает simplify. После complicate
он возвращается именно туда, пропуская проверку восстановленного кандидата;
false от complicate отдельно не завершает цикл. Схемы различаются:

```text
runner: PASS -> complicate -> current + predicate -> дальнейшее решение
S3:     PASS -> complicate -> simplify -> current + predicate
```

Даже если финальное минимальное значение случайно совпадает, число
materialization/evaluation, путь и метрики уже не те. Напечатанное число
complicates подтверждает вызовы метода, но не правильность протокола.

### Лишний retained Vec и другой лимит

S3 сохраняет предыдущий принятый `Vec<Op>` в `result`, пока создаётся новый
candidate. Он нужен только последнему black_box. Реальный shrink loop хранит
дерево и причину failure, не постоянную копию последнего `Vec<Op>`; очередное
значение передаётся predicate по владению. Поэтому S3 добавляет лишний
одновременно живой буфер и меняет peak/copy lifecycle.

Кроме того, 16384 названо default max_shrink_iters. В проверенном proptest
1.11.0 без env overrides значение по умолчанию вычисляется как `cases * 4`:
при default cases=256 это **1024**, не 16384. В S3 ещё добавлен собственный
предел последовательных rejects. Пользовательский длинный сценарий допустим,
но это не default runner и не его точная копия.

Рекомендация: для S3 использовать существующий `TestRunner::run_one` с явно
заданным Config и тестовым predicate; он доступен в resolved версии.
Либо точно воспроизвести переходы/освобождение значений, а выбранные лимиты
назвать пользовательскими. S2 оставить как отдельный microbenchmark.
После этого повторить S3 и исправить относящиеся к нему claims. Это не
обнаруженная ошибка `SizeValueTree::complicate`: её делегирование корректно,
а новый lockstep-тест — полезный самостоятельный контроль реализации.

## P4-2. Разница 0.015 → 0.000 объяснена шумом, хотя изменился счётчик

Места: `crates/globalalloc-model/examples/perf_probe_p4_measurements.rs:108`,
`:126`, `:533`, `:907`; `tests/size_strategy_avoids_boxed_value_trees.rs:75`;
`src/strategy.rs:38`, `CHANGELOG.md:134`.

Раньше probe увеличивал ALLOC_CALLS и при alloc, и при realloc. Теперь
realloc прибавляет отдельный REALLOC_CALLS, а `mean_allocs` читает только
ALLOC_CALLS. В counting test override realloc по-прежнему отсутствует:
default реализация проходит через alloc/dealloc wrapper и попадает в
ALLOC_CALLS. Таким образом, тест и probe сейчас считают разные события.

`current()` материализует Vec, рост которого может идти через realloc.
Исключение этих событий из numerator закономерно меняет абсолютную marginal
стоимость, даже при одинаковых seed и полностью детерминированном запуске.
Называть новую абсолютную величину просто run-to-run drift некорректно.

Показанный paired gap около 0.75 и работоспособность порога 0.35 от этого
сами по себе не опровергаются. Нужно одинаково определить метрику в обеих
реализациях измерителя либо явно печатать раздельно alloc/realloc/sum и не
объяснять смену определения шумом. Это также позволит честнее оценивать
уменьшение reallocs и копирования в materialization path.

## P4-3. Runtime Cargo.lock не удостоверяет зависимости запущенного бинарника

Место: `crates/globalalloc-model/examples/perf_probe_p4_measurements.rs:235`.

Новый metadata helper читает lockfiles относительно текущего cwd. Готовый
бинарник может запускаться из другого проекта либо после обновления lockfile;
найденные версии тогда не являются версиями, с которыми он собран.
Надпись `resolved front-ends` сообщает более сильный факт, чем установлен.

Есть и отдельная ошибка объединения: `found` создан до цикла по candidate
paths и между файлами не очищается. Если ближайший Cargo.lock содержит только
proptest, а родительский — только arbitrary, функция соединит эти сведения
и подпишет всю пару именем родительского файла. Не требуется реально менять
зависимости бинарника, чтобы такой вывод стал ложным.

Минимально: не объединять разные lockfiles и назвать результат runtime
lockfile snapshot. Для идентификации измерения брать сведения из resolved
графа **при сборке** и связывать их с артефактом/командой. Обычный канонический
запуск из неизменённого workspace может дать верные версии, но код не
проверяет это условие; текущим числам другую версию здесь не приписываю.

## P4-4. В S1 материализация current не попадает ни в одну временную колонку

Места: `crates/globalalloc-model/examples/perf_probe_p4_measurements.rs:626`,
`:632`, `:641`, `:785`.

Таймер new_tree остановлен на строке 628, а current вызывается на 633.
Таймер walk запускается лишь на 641, причём S1 ничего внутри walk не делает.
Drop дерева измеряется отдельно. В результате затраты current/создания и
освобождения возвращённого Vec отсутствуют во всех трёх timing columns,
хотя S1 назван `new_tree → current → drop` и memory-окно включает эту работу.

Не нужно выводить скорость полного успешного case из суммы этих колонок.
Добавить current/materialization time и/или общий elapsed для всей S1;
сохранить отдельно полезные component timings. Это пробел performance
наблюдения, не дефект байтового учёта или самого `ValueTree::current`.

## Общий обзор, стоимость и принятые решения

- Старое повреждение LIVE_BYTES исправлено в самом wrapper: успешный realloc
  заменяет размер через CAS, а не только вычитает old size из локальной
  переменной; null не меняет bytes. Исправить нужно новый невалидный вызов,
  которым проверяют эту бухгалтерию, а не возвращать старую формулу.
- Ядро `drive` не менялось: guards предшествуют доступу, old block проверяется
  целиком перед shrink/free, при null realloc остаётся live, успешный realloc
  обновляет layout/fill_op, teardown перепроверяет каждый survivor. Новых
  UAF/aliasing/extent дефектов при соблюдении RawAllocator contract не найдено.
- `RawAllocator` явно требует single-object extent, provenance, liveness,
  initializedness и отсутствие racing access. M2 остаётся off-by-default и
  требует unsafe token, запрещённый для blanket GlobalAlloc.
- Генераторы сохраняют полный u64 weight sum в arbitrary, структурное
  исключение zero-weight size arm в proptest, проверку Config до генерации
  и допустимый exponent mapping. Новое имя helper не изменило expression
  tree генератора. Static introspection теперь действительно без создания
  стратегий и скрыта за proptest+internals.
- Рост качества тестов реален: bounded lockstep теперь проверяет bool и
  current при backoff и несёт activation floors. Наличие 1024-step prefix
  не выдаётся за полное исследование пространства. Эта корректностная
  проверка не подменяет отдельную проверку протокола S3.
- Память модели остаётся O(K), prepass — O(M), общая стоимость драйвера
  O(M + MK + B), худшая O(M² + B). Ни новый O, ни устранение копий payload
  эти коммиты не добавили. Выбор enum — компромисс calls/memory; стоимость
  Single и successful draw теперь открыто указана. Автоматический откат enum
  или ordered interval index по результатам этого ревью не требуется.
- Предыдущие ложные repeat/permutation и unwritten-memory обещания убраны.
  Паттерн менять заново не требуется; сценарные ограничения сформулированы
  существенно точнее, чем раньше.
- Feature/package/i686/MSRV/bare-metal/release-profile/Miri wiring по крейту
  сохранены, exact docsrs combination и release guard остаются. Обычная
  сборка example не исполняет его main/self-check; зелёные библиотечные
  тесты поэтому не доказывают отсутствие P2-1. Свежих результатов CI этот
  read-only проход не удостоверяет.

## Порядок исправлений

Сначала устранить нарушение unsafe-предусловия self-check и проверять
allocator failure только на допустимом запросе. Затем заменить неверную
копию runner-протокола S3 и повторить её измерения. После этого синхронизировать
знаки memory-выводов, определения счётчиков и metadata/timing labels.
Тесты и реализация этих исправлений остаются отдельной задачей; здесь выполнено
только ревью и сохранение отчёта.
