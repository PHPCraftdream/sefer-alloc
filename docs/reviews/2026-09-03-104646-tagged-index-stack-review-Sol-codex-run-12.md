## Найденные проблемы

### P3-1 — `with_tag_for_test` молча превращает недопустимый tag в другой

**Места:**

- `crates/tagged-index-stack/src/imp.rs:509-529`;
- `crates/tagged-index-stack/src/imp.rs:1822-1835`.

Оба безопасных конструктора `with_tag_for_test(tag: u64)` обещают создать
голову с «specific tag», но `StackHead::with_tag_for_test` вызывает приватный
`TaggedIndex::pack_truncating` без проверки `tag <= TAG_MAX`. При передаче
`TAG_MAX + 1` значение бесшумно станет нулём; другие старшие биты также будут
отброшены. Это не создаёт UB и не повреждает production-путь, однако способно
сделать будущий тест ложноположительным: тест думает, что моделирует заданную
границу, а фактически получает другую исходную точку.

Поверхность скрыта через `#[doc(hidden)]`, но при feature `test-internals` это
всё ещё безопасный публичный метод, доступный downstream-коду. Текущие
внутренние вызовы корректны: `tag_seal.rs:60,142` использует `TAG_MAX - 2`, а
`loom_aba.rs:1137-1138` — `TAG_MAX - 3`. Именно поэтому дефект сейчас не
проявляется.

**Рекомендация:** в тестовом конструкторе использовать проверяемый `pack` и
явно падать с понятным сообщением при `tag > TAG_MAX`, либо добавить явный
`assert!(tag <= TAG_MAX)` перед `pack_truncating`. Конструктор не находится на
горячем пути, поэтому здесь важнее точный тестовый oracle, чем экономия одной
проверки.

### P3-2 — README смешивает число unsafe-регионов с числом unsafe-сайтов

**Места:**

- `crates/tagged-index-stack/README.md:21-30`;
- авторитетная детализация в `crates/tagged-index-stack/src/lib.rs:256-355`.

README утверждает, что в production source находится «exactly EIGHT audited
`unsafe` sites». В действительности восемь — это число item-scoped
`#[allow(unsafe_code)]` lint-exception **регионов**. Документация crate root
правильно разделяет границы и содержимое: один `unsafe trait`, десять
`unsafe fn` declarations, ноль `unsafe impl` и шесть `unsafe {}` blocks.

Фраза README не меняет safety-контракт, но для аудитора «unsafe site» обычно
означает конкретную декларацию, блок или операцию. В этом смысле заявленное
число фактически неверно и противоречит более точному объяснению в crate docs.
Это типичный риск от многократного дублирования точных счётчиков в длинном
нарративе.

**Рекомендация:** заменить формулировку на «exactly EIGHT audited,
item-scoped `#[allow(unsafe_code)]` lint-exception regions» и отослать к
авторитетному инвентарю crate root. По возможности не дублировать в README
точные operation counts, которые уже подробно и самопроверяемо описаны в
одном месте.

### P3-3 — durability-реестр всё ещё обещает tag wrap и считает pops вместо pushes

**Место:** `docs/DURABILITY.md:34`.

Живая строка реестра для `TaggedIndex` одновременно содержит новое имя теста
`...through_tag_max`, но продолжает описывать счётчик как «monotonic
wrapping» и ресурс как `2^48` **pops**. Оба утверждения не соответствуют
текущему протоколу:

- tag увеличивает только успешный push; pop сохраняет наблюдённый tag, включая
  переход последнего элемента в empty;
- при `TAG_MAX` следующий push возвращает `TagExhausted`; production tag не
  оборачивается, а голова остаётся навсегда sealed для push.

Оценка порядка 89 лет при 100k операций/с остаётся пригодной оценкой времени
до исчерпания, если назвать операции pushes, но это именно lifetime budget до
seal, а не «effectively unreachable» wrap. Текущий текст расходится и с
README, и с crate-level rustdoc.

**Рекомендация:** заменить модель на «strictly monotonic, saturating/sealed at
`TAG_MAX`», считать успешные pushes и описать последствие как permanent push
seal при сохранении возможности pop/drain. В колонке mitigation отметить, что
non-recurrence tag полностью устраняет ABA на доступном lifetime головы.

## Полный обзор production-кода

### Представление и границы

- `TaggedIndex<INDEX_BITS>` статически ограничивает ширину диапазоном
  `1..=16`; tag получает 48–63 бита, а пустой sentinel не пересекается с
  допустимым индексом.
- Публичный проверяемый `pack` отвергает слишком широкие index/tag. Приватный
  `pack_truncating` корректно используется в production после установленных
  границ; единственное замечание к нему — тестовый конструктор P3-1.
- Переход к `TAG_MAX` односторонний: push после исчерпания бюджета возвращает
  `TagExhausted`, pop продолжает дренировать цепочку, API сброса нет.

### Push/pop и memory ordering

- `push_index_impl` проверяет индекс до доступа к backing; проверяет seal до
  `store_next`; записывает link до публикации новой головы; публикует её
  strong CAS с `Release/Relaxed`.
- `pop_index_impl` начинает с Acquire-load головы, загружает и валидирует
  next-link, сохраняет текущий tag при переходе к empty и применяет strong
  CAS с `Acquire/Acquire`.
- При CAS failure используется фактически наблюдённое atomic значение, а не
  повторный load. Порядки failure не обещают публикацию link, но pop уже имеет
  Acquire, а push не читает чужой link перед успешной публикацией.
- Все записи головы остаются RMW/CAS; plain store не добавлен. Поэтому
  документированная release-sequence цепочка от Release push через следующие
  RMW остаётся непрерывной и согласуется с Acquire-only успешным pop CAS.
- H-2 граница — сохранение running tag при снятии последнего элемента —
  реализована; пустая голова не откатывается к bootstrap tag 0.
- Guards против out-of-range next и self-loop активны в release-сборках и
  выполняются до публикации повреждённой головы.

### Unsafe и расширяемость

- `StackStorage` остаётся `unsafe trait` с явными обязательствами по
  уникальности head↔links binding, идентичности backing, непересечению
  достижимых populations, домену индексов, времени жизни и atomic-доступу.
- Все три storage hook являются `unsafe fn` с caller-side safety contracts;
  bridge содержит локальные unsafe-блоки и SAFETY-обоснования.
- `StackOps` предоставляет единый blanket algorithm, поэтому downstream
  implementor не может подменить протокол произвольной реализацией push/pop.
- `ArrayIndexStack` владеет головой и links совместно и намеренно не реализует
  публичный `StackStorage`, что не позволяет безопасно построить конкурирующий
  binding вокруг его приватной головы.
- Production source сохраняет `#![deny(unsafe_code)]` и
  `#![deny(unsafe_op_in_unsafe_fn)]`; разрешения локализованы в восьми
  задокументированных регионах.

Статический поиск не обнаружил production raw-pointer ownership,
`transmute`, FFI, ручных `Send`/`Sync`, async state machines, криптографии или
ресурсного RAII/Drop-протокола, требующих отдельного механизмо-специфического
аудита.

## Производительность

Нового статически доказуемого ускорения не найдено. Горячий путь по-прежнему
минимален: один head atomic, link access и CAS-loop с ограниченным backoff.
Переход с strong на weak CAS ранее отмечен в репозитории как codegen-null, а
перестановка ordering без измерения затрагивает тонкое concurrency-доказательство.

Осмысленные кандидаты уже перечислены в `docs/perf/OPEN_ITEMS.md` (items
61–63): не повторять идентичный `store_next` после CAS failure, измерить
Relaxed link-cell accesses на native ARM64 и отдельно измерить Relaxed success
ordering у pop CAS. Каждый вариант имеет архитектурный или branch/cache
trade-off; по одному чтению нельзя честно назвать его ускорением.

Плотный `ArrayLinks` может создавать false sharing в некоторых workload, но
универсальный padding увеличит footprint, а custom slot-resident storage уже
даёт специализированному allocator возможность выбрать лучший layout.

**Рекомендация:** не менять atomics, backoff и layout без native A/B данных.
Сначала завершить существующие измерительные планы, затем принимать только
выигрыш, подтверждённый на целевой архитектуре и совместимый с формальным
memory-ordering доказательством.
