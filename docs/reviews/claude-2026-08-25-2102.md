## 1. Findings

### F1 — **P2** — `e3e3b93`'s replacement sentence, *"The two that reach the panic runtime allocate in a `std` build"*, is measurably false (three do), and it contradicts the sentence the SAME commit added 25 lines below it, which reports that very site's allocation count *at the hook*

**Where:** `crates/racy-ptr-cell/src/lib.rs:132-134`; `crates/racy-ptr-cell/README.md:94-96`.
Antecedent: `src/lib.rs:127-131` / `README.md:90-93`. Contradicted by:
`src/lib.rs:158-161` / `README.md:115-118`.

The paragraph opens by enumerating the panic inventory (`src/lib.rs:127-134`,
the emphasis and bracketed numbering are mine):

> There are **three** panic sites in total: [1] that sentinel-collision
> `assert!`, [2] an unwinding `init`, and [3] the `align_of::<T>() >= 2` check
> in [`RacyPtrCell::new`] / [`RacyPtrCell::default`] (a const-eval failure in
> the documented `static` form — which never reaches a panic runtime at all;
> **a runtime panic when reached from a non-const context**). **The two that
> reach the panic runtime** allocate in a `std` build, and the two link
> environments need genuinely different mitigations, **not a shared recipe**:

There is no reading of "the two" that is true.

- Bind it to the enumeration (the only antecedent): it names sites 1 and 2 and
  excludes site 3. But the immediately preceding clause of the *same sentence*
  says site 3 is "a runtime panic when reached from a non-const context" — a
  runtime panic **is** the panic runtime. The sentence contradicts its own
  parenthetical, in the same breath.
- Bind it to the two *forms* of site 3 that the parenthetical splits out: only
  one of those two reaches the panic runtime, so "the two" is still wrong.
- Count what actually reaches the panic runtime: **three** (sites 1, 2, and
  site 3's non-const form). The pre-`e3e3b93` text said exactly that ("All
  three go through the panic runtime") and was merely *loose* about site 3's
  const-eval form. The fix replaced a loose-but-substantively-true sentence
  with a precise-sounding false one.

**Measured, both directions** (§0.1 probes A and B, the packaged 0.1.0 tarball,
a real `#[global_allocator]`, `panic = "abort"`, `--release`,
`RUST_BACKTRACE=0`, rustc 1.97, `x86_64-pc-windows-msvc`):

```
WITH the crate's own recommended non-allocating set_hook:
  site 1  sentinel-collision assert!                    -> hook ENTERED, 0 allocations
  site 2  unwinding init, bare &'static str             -> hook ENTERED, 0
  site 2  unwinding init, panic!("… {}", x)             -> hook ENTERED, 2
  site 2  unwinding init, Result::expect("mmap failed") -> hook ENTERED, 2
  site 3  align_of assert! via ::<u8>::default()        -> hook ENTERED, 0
  site 3  align_of assert! via ::<u8>::new() in a fn    -> hook ENTERED, 0

WITH std's DEFAULT hook (k-th-allocation trip):
  control panic!("plain static message")                -> exactly 2   (k=1,2 trip; k=3 does not)
  site 3  align_of assert! via ::<u8>::default()        -> exactly 2   (k=1,2 trip; k=3 does not)
```

Site 3 is **byte-identical to a plain `panic!("literal")`** under the default
hook. It is not a site that "never reaches a panic runtime"; it is a site that
reaches it and allocates exactly as much as any other bare-literal panic.

**Self-contradiction inside the same commit.** `e3e3b93` also added, at
`src/lib.rs:158-161` / `README.md:115-118`:

> The crate's own two `assert!`s (the sentinel-collision check and **the
> `align_of::<T>() >= 2` check**) are of that shape and **measure 0
> allocations before the hook**

A site cannot simultaneously be excluded from "the two that reach the panic
runtime" and have a measured allocation count *before the hook* — reaching the
hook is reaching the panic runtime. Both sentences were written by the same
commit, 25 lines apart, and only one of them can be right. (The second one is;
I reproduced its 0.)

**Concrete failure scenario.** A `std` consumer writes a `#[global_allocator]`
whose bootstrap runs inside `CHUNK.get_or_try_init(|| …)` — so the thread holds
`CHUNK`'s `INITIALIZING` sentinel — and inside that closure lazily constructs a
sub-cell at runtime, `RacyPtrCell::<Sub>::new()` (a fn body, not a `static`).
They read the panic inventory to decide what to mitigate, and take the
sentence at face value: the `align_of` check is compile-time-only and is not
one of the sites that reaches the panic runtime, so it needs no `std` panic
mitigation — only sites 1 and 2 do. `align_of::<Sub>()` is 1 (a `#[repr(C)]`
struct of `u8`s, or a `[u8; N]` header — the exact shape a bootstrap header
often has, and the exact shape the crate's own test uses,
`tests/cell_unit.rs:183`). At runtime the assert panics, the default hook
allocates (measured: 2), that allocation re-enters their allocator, the
allocator reaches `CHUNK` — whose sentinel **this same thread** holds — the
claim CAS at `src/lib.rs:581` fails, and the thread enters the loser spin at
`:670-691` on its own sentinel. 100 % CPU, no diagnostic, no abort: precisely
the self-deadlock this whole section exists to prevent, reached by a reader
who applied exactly the mitigations the section told them applied.

Note the residual is narrower than cycle-5's F1: a reader who applies the FULL
recommended recipe (`panic = "abort"` **and** the non-allocating `set_hook`) is
covered anyway, because site 3's message is a bare literal and measures 0. The
defect is that the sentence tells them site 3 is outside the scope that needs
the recipe at all.

**Regression note.** Cycle 5's F1 flagged, as a secondary remark, that "All
three go through the panic runtime" was *loose* for site 3's const-eval form,
and suggested the paragraph acknowledge that form. `e3e3b93` overcorrected: it
turned a loose true statement into a precise false one, and thereby created a
contradiction with the primary fix it landed in the same commit. This is the
**fourth consecutive cycle** in which this one paragraph is the finding (cycle
3 F1 → cycle 4 F1 → cycle 5 F1 → this), and the **second consecutive** in
which the defect was introduced by the immediately preceding remediation.

**Suggested fix — structural, not another one-clause patch.** Three
single-clause patches to this paragraph have now each introduced the next
cycle's finding. The counting prose ("three panic sites … all three … the two
… the crate's own two … the third panic site above") is what keeps breaking:
every edit has to re-derive which subset a bare numeral refers to. Replace the
enumeration with a table whose cells are independently checkable and which
contains no cross-referencing numerals at all:

| # | Panic site | Whose code | Reaches the panic runtime? | Message shape | Allocations before a non-allocating hook |
| --- | --- | --- | --- | --- | --- |
| 1 | sentinel-collision `assert!` in `get_or_try_init` | this crate | yes | bare `&'static str` | 0 |
| 2 | an unwinding `init` closure | **yours** | yes | whatever you wrote | 0 if a bare literal, ≥ 2 if formatted |
| 3 | `align_of::<T>() >= 2` in `new`/`default`, `static` form | this crate | **no** — const-eval failure, compile time | n/a | n/a |
| 3 | `align_of::<T>() >= 2` in `new`/`default`, non-const form | this crate | yes | bare `&'static str` | 0 |

then keep the two mitigation bullets unchanged below it. The minimal
alternative, if a table is unwanted, is to delete the offending clause and
write: "Every one of these that is reached at RUNTIME goes through the panic
runtime, which allocates in a `std` build; only the `static` form of the
alignment check is a compile-time failure that reaches no panic runtime at
all." Apply to both `src/lib.rs` and `README.md` — they carry the same text.

### F2 — **P3** — `817d8bf`'s own new portability text mis-describes the failure mode it exists to improve on, in two independent ways: it attributes the measured `E0599` to "a bare unresolved import" (measured: nothing is unresolved; an unresolved import is `E0432`), and it classifies `msp430-none-elf` as a "load/store atomics but no CAS" target (measured: `max-atomic-width: 0` — it has no atomics at all)

**Where:** `crates/racy-ptr-cell/src/lib.rs:202-207` (crate doc) and
`:236-243` (the `compile_error!` message itself);
`crates/racy-ptr-cell/README.md:29-33` (same text).

**(a) "a bare unresolved import" is the wrong error class.** The doc says
(`src/lib.rs:204-207`, `README.md:30-33`):

> A build on an unsupported target fails fast with an explicit
> `compile_error!` naming the requirement, rather than the more cryptic "no
> method named `compare_exchange`" error **a bare unresolved import** would
> otherwise produce.

Measured (§0.1 probe D, the real tree, `thumbv6m-none-eabi`): the import
`use core::sync::atomic::{AtomicPtr, Ordering};` **resolves fine** — those
targets do have `AtomicPtr` (it is `Atomic<*mut T>` with the CAS methods
`cfg`'d out). The four errors are the new `compile_error!` plus three
`E0599 no method named compare_exchange found for struct Atomic<T>`. There is
no `E0432` anywhere. An unresolved import produces `E0432 unresolved import`,
never `E0599` — so the sentence names an error class that cannot produce the
message it quotes, and attributes this crate's real failure mode to a
mechanism this crate does not have.

The phrasing is inherited verbatim from `crates/tagged-index-stack`, where it
is *correct*: that crate needs `AtomicU64`, which genuinely does not exist on
its unsupported targets, so its failure genuinely is an unresolved import. The
copy dropped the one word that made it true there.

**(b) `msp430-none-elf` is not a "load/store atomics but no CAS" target.**
Both the crate doc (`src/lib.rs:202-204`) and the `compile_error!` message
itself (`:240-242`) say:

> Targets with load/store atomics but no CAS -- `thumbv6m-none-eabi`
> (Cortex-M0/M0+), `riscv32imc-unknown-none-elf` (no `A` extension),
> `msp430-none-elf` -- are NOT supported

Measured (§0.1 probe E):

| target | `atomic-cas` | `max-atomic-width` | `target_has_atomic="ptr"` | has load/store atomics? |
| --- | --- | --- | --- | --- |
| `thumbv6m-none-eabi` | `false` | (default, `+atomics-32`) | absent | **yes** |
| `riscv32imc-unknown-none-elf` | `false` | `32` | absent | **yes** |
| `msp430-none-elf` | `false` | **`0`** | absent | **no — none at all** |
| `thumbv7em-none-eabi` (CI's row) | `true` | — | present | yes |

msp430 emits no `target_has_atomic*` cfg of any kind. It is the one named
target for which the crate's *actual* failure mode would be an unresolved
import — i.e. (a) and (b) are each true of a different target than the text
assigns them to.

The guard itself is **correct and correctly firing** for all three: they all
lack `target_has_atomic = "ptr"`, which is exactly the predicate. Only the
descriptive prose around it is wrong. P3 because nothing compiles that should
not, and nothing fails that should not — but the `compile_error!` string is a
message a stranded firmware author reads once, at their most confused moment,
and it currently tells them their target has a capability it does not have.

**Suggested fix.** In both files and in the `compile_error!` string:

- replace "rather than the more cryptic 'no method named `compare_exchange`'
  error a bare unresolved import would otherwise produce" with "rather than
  the three bare `no method named compare_exchange` errors an unguarded build
  would otherwise produce" (this crate's measured behaviour), and
- split the target list: "…thumbv6m-none-eabi (Cortex-M0/M0+) and
  riscv32imc-unknown-none-elf (no `A` extension) have load/store atomics but
  no CAS; msp430-none-elf has no atomics at all."

### F4 — **P3** — `817d8bf` added a new hard compile-time requirement to the crate's public contract and documented it in the README and the rustdoc, but not in `CHANGELOG.md`, whose 0.1.0 `### Added` block is the crate's complete first-release inventory and freezes at publish

**Where:** `crates/racy-ptr-cell/CHANGELOG.md:12-79` (the `### Added` block);
the requirement it omits is at `src/lib.rs:195-207` / `:235-243` and
`README.md:23-33`.

The 0.1.0 `### Added` list is written as an exhaustive inventory of what the
crate guarantees — it enumerates the state machine, `get_or_try_init`, the
anti-livelock rule, `get`, `new`'s `const`-ness *and its `align_of` panic*,

Both of cycle 5's findings landed and both are substantively closed.

fires, fires *first*, uses the right predicate for all three named targets,
and leaves the supported bare-metal row and the loom suite untouched; its

I wanted to return an unconditional GO this cycle, and one finding stops me:

- **F1** is, once again, a defect introduced by the immediately preceding
  remediation, in the same paragraph for the fourth consecutive cycle. This
  time it is not the clause cycle 5 asked to be fixed — that one landed
  correctly — but an *unrequested* tightening `e3e3b93` bundled alongside it.
  "The two that reach the panic runtime allocate in a `std` build" is
  measurably false: three sites reach it, and the excluded one measures
  **byte-identically to a plain `panic!("literal")`** — 2 allocations under
  std's default hook, 0 under the crate's own recommended hook. Worse, the
  same commit's own sentence 25 lines below reports that very site's
  allocation count *at the hook*, which is only meaningful if it reaches the
  panic runtime. The two sentences cannot both be true, and the false one is
  the one a reader hits first, in the paragraph that decides which panic
  mitigations a `#[global_allocator]` consumer must apply.

The residual runtime hazard behind F1 is narrower than cycle 5's F1 (a reader
applying the full recipe is covered regardless, because the message is a bare
literal), which is why I am not calling it P1 — but it is a false statement,
self-contradicting, in the crate's safety contract, and it freezes on the
0.1.0 docs.rs page at publish.

One thing this cycle has established that the prior five could not: **the
one-clause patch is the wrong instrument for this paragraph.** Three
consecutive single-sentence fixes to it have each produced the next cycle's
finding, and the mechanism is identical every time — the prose counts subsets
with bare numerals ("three panic sites … all three … the two … the crate's own
two … the third panic site above"), so every edit silently re-binds a numeral
to a different subset. F1's suggested fix is therefore structural: a six-cell
table with no cross-referencing numerals, which cannot regress this way
because each row states its own answer. I would take that over a fourth
one-clause patch even though the one-clause patch is smaller.

**Close F1 — one paragraph, two files, no algorithm change, no API change —
and this is a GO.** F2, F3 and F4 are cheap enough to fold into the same
commit and I would; none of them individually blocks publication, but F3 and
F4 both freeze at first upload (a crates.io landing page and a first-release
changelog), so "later" for those means "0.1.1".
