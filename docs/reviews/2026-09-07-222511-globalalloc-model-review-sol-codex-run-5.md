## Вердикт

**P0=0, P1=0, P2=0, P3=2, P4=4.**

Новых нарушений memory safety или неверной семантики `drive`/генераторов
при соблюдении их контрактов не обнаружено. Исправление allocation guard
по конкретному обходу через failure persistence принимаю. Прежнее объяснение
времени жизни ValueTree исправлено, цена Single-конфигурации теперь признана.

Два P3 относятся к обоснованию performance-решения: ошибочный учёт памяти
в новом измерительном аллокаторе и отсутствие отдельного memory-замера
успешного case без shrinking. До их исправления не считаю опубликованные
выводы о памяти достаточным основанием для безоговорочного GO. Это не
обнаруженная опасность основного allocator oracle и не требование вслепую
откатить enum либо добавить сложный overlap index.

## P3-1. Новый CountingAlloc неверно обновляет LIVE_BYTES при realloc

Места: `crates/globalalloc-model/examples/perf_probe_p4_measurements.rs:39`,
`:53`, `:285`.

Критическое выражение:

```text
live = LIVE_BYTES.fetch_add(new_size) + new_size - old_size
```

`- old_size` исправляет только локальное значение, передаваемое в PEAK_LIVE.
В атомике остаётся **предыдущее LIVE_BYTES + new_size**: старый размер из
состояния никогда не вычитается. Пример при успешных allocator calls:

| Действие | Правильный live | Хранимый LIVE_BYTES |
| --- | ---: | ---: |
| alloc 64 | 64 | 64 |
| realloc 64 → 128 | 128 | 192 |
| dealloc 128 | 0 | 64 |

Это фиктивная утечка только в измерителе. Сам System получает правильные
аргументы; реальная утечка из этого выражения не следует. Следующие alloc
уже используют завышенную базу и способны завысить PEAK_LIVE.

Есть ещё две связанные ошибки того же учёта:

- `TOTAL_BYTES` при realloc вообще не обновляется: не учитывается ни полный
  новый запрос, ни прирост при увеличении. В названии/выводе не оговорено,
  что realloc исключён из total allocated bytes.
- Counters обновляются до результата backend. При null realloc старый
  allocation остаётся прежним, но LIVE_BYTES уже увеличен; отката нет.
  Аналогично alloc прибавляет размер к live до проверки успешного результата.
  [Контракт GlobalAlloc::realloc](https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html#method.realloc).

Рекомендация: разделить attempted-call counters и учёт успешно полученных
диапазонов. На успешном realloc заменить старый размер новым в самом live
состоянии; на null оставить live без изменений. Явно определить семантику
total для realloc. Проверить grow, shrink, failure и итоговый возврат live к
исходной базе после освобождения. Такой счётчик отражает запрошенные живые
байты, не RSS и не невидимый ему временный расход внутри System::realloc.

Калибровка: это доказанная ошибка счётчика, но не доказательство, что каждый
уже опубликованный memory-результат численно неверен. В `draw_metrics`
realloc может не происходить; постоянное смещение до начала окна может
сократиться при вычитании `start_live`. Нужно зафиксировать число realloc
в самом измерительном окне и переснять затронутые результаты. Отдельный
allocation-count guard считает calls другим wrapper и этой ошибки bytes
не наследует.

## P3-2. Memory-вывод для default draw получен из обязательного полного shrinking

Места: `crates/globalalloc-model/examples/perf_probe_p4_measurements.rs:285`,
`:297`, `:306`, `:360`; `src/strategy.rs:76`, `CHANGELOG.md:141`.

`draw_metrics` открывает одно memory-окно перед `new_tree`, затем обязательно
выполняет `while tree.simplify()`, уничтожает дерево и лишь после этого
возвращает total/peak. Вывод помечен `draw: total ... peak-live ...`, а числа
848124/915594 далее обосновывают меньшую память enum при default Config.

Но это память **construction + полного simplify-only обхода**, не отдельного
обычного draw и не успешного property case. Lazy branches делают различие
существенным: при упрощении `TupleUnion` инициализирует предыдущие варианты
и сохраняет их деревья в options. На boxed стороне это создаёт дополнительные
size-Box, которых на успешном case без shrinking не было бы.
[Реализация TupleUnion shrinking](https://raw.githubusercontent.com/proptest-rs/proptest/7f1367f9a4dc8440c47b93166a38ed064f63ea8c/proptest/src/strategy/unions.rs).

Например, изначально выбранный Realloc держит одно size-tree; полный
simplify-проход может дополнительно построить деревья AllocZeroed и Alloc.
Драйвер мог бы принять исходный поток без единого шага shrinking. Большой
inline stride enum оплачивается с самого начала в обоих случаях, а цена
инициализации отложенных boxed-ветвей — нет. Поэтому порядок вариантов по
общему объёму/пику памяти в этих двух режимах нельзя считать одинаковым без
отдельной проверки. Конкретный процент разницы на обычном draw здесь не измерен.

Более того, измерительный цикл не вызывает `current()` на каждом шаге и не
имеет predicate/`complicate`. Настоящий runner материализует текущие значения
и возвращается через complicate, когда кандидат проходит или отвергается.
Для `Vec<Op>` это существенная часть аллокаций и копирования при shrinking.
[Протокол TestRunner::shrink](https://raw.githubusercontent.com/proptest-rs/proptest/7f1367f9a4dc8440c47b93166a38ed064f63ea8c/proptest/src/test_runner/runner.rs).

Нужны отдельно подписанные сценарии:

1. Успешный case: `new_tree → current → drop`, без shrinking.
2. Изолированная механика simplify-only — нынешний полезный microbenchmark.
3. Сценарий shrinking с `current` и возвратами через `complicate`, с явно
   заданным predicate либо через реальный TestRunner.

В каждом разделить память после construction и peak по всей выбранной
траектории; повторить default/Single A/B после исправления счётчика.
Необязательно включать дорогой `drive` в каждый microbenchmark, но исключение
его и материализации Op должно быть явно частью названия/области вывода.
Это вопрос правильной приёмки компромисса, не автоматический запрет enum.

## P4-1. Парный shrink-тест проверяет конечную точку, не заявленную траекторию

Места: `crates/globalalloc-model/tests/size_strategy_avoids_boxed_value_trees.rs:216`,
`:228`, `:239`; `src/strategy.rs:140`.

Два независимых simplify-loop сравниваются только по числу успешных шагов и
последнему `current`. Два разных ряда промежуточных Op могут иметь одинаковые
длину и конец. Ни этот тест, ни существующие явные shrink-walk тесты крейта
не проверяют возврат через `SizeValueTree::complicate`.

Текущая реализация правильно делегирует complicate; дефект делегирования
не найден. Но подмена её тела на постоянный false не изменила бы данный
paired-тест: он ни разу не вызывает этот метод. Основная System property
также не является отрицательным контролем этой ветви, пока все cases проходят.

Улучшение: идти попарно, сравнивая return value и `current` после каждого
simplify/complicate, а не только endpoint. Включить weighted и оба Single
режима. Если полная эквивалентность trajectories не требуется, как минимум
назвать текущий assertion именно проверкой step count/final value.

## P4-2. README всё ещё обещает обнаружение всех repeat/permutation префиксов

Места: `crates/globalalloc-model/README.md:189`, `src/lib.rs:77`.

Оговорка unshifted исправлена, но следующая часть README по-прежнему
категорически исключает совпадение repeated-single-byte и permuted prefix.
Контрпример текущего паттерна:

```text
pattern(66, 0) = pattern(66, 1) = 0x42
```

Двухбайтовый префикс этого fill-id уже однороден: повторение первого байта
или перестановка этих двух байтов неразличимы. Это не новый P3 к алгоритму
и не повод снова заменять hash — конечные байтовые данные не обязаны
различать каждую перестановку. Нужно ограничить формулировку реально
проверенными контрпримерами и убрать общее обещание.

В lib.rs также стоит оставить только «marker не равен нулю», убрав
невозможность спутать его с любой unwritten memory: незаписанные после
данной операции, но ранее инициализированные байты могут иметь любое
совпавшее значение; genuinely uninitialized память вообще не является
безопасно диагностируемым входом, что соседний safety contract уже объясняет.

## P4-3. Probe безусловно маркирует профиль и ширину указателя

Места: `crates/globalalloc-model/examples/perf_probe_p4_measurements.rs:167`,
`:360`; конкретные sizeof-числа в `src/strategy.rs:70` и CHANGELOG.

Строка результатов всегда печатает `release profile`, хотя пример можно
обычно запустить без `--release`. Другая строка безусловно объявляет
двухсловный `Box<dyn ValueTree>` равным 16 B; на 32-битном target это 8 B.
Точные размеры proptest-деревьев также относятся к конкретным target,
feature set и toolchain, а не к переносимому контракту этих типов.

Печатать реальные compile-time размеры и достоверные build/target признаки,
фиксировать команду и resolved dependencies рядом с числами. Если профиль
автоматически достоверно не определён, не подставлять слово release.
Это точность артефакта, не обнаруженный неправильный layout самой библиотеки.

## P4-4. Статическая introspection строит и выделяет реальные стратегии

Место: `crates/globalalloc-model/src/strategy.rs:262`.

`size_strategy_repr_sizes` вызывает `op_element_strategy(config)`, чтобы
передать готовую стратегию в helper, который использует только
`size_of::<S::Tree>()`. Для этого создаются внешние Arc-ветви и, при default
weights, Arc обеих range-ветвей каждого size generator. Ни одного generated
значения для ответа не нужно; результат определяется типами, а не Config.

Можно вывести тип через фабрику, не вызывая её, и вычислить sizeof без
создания объектов. Это небольшое cold-path упрощение и уменьшение ненужных
аллокаций, не обещание заметного ускорения тестов. Нынешний probe вызывает
introspection до измерительных окон, поэтому сам по себе этот вызов не
доказывает загрязнение опубликованных memory-дельт.

## Общий обзор текущего состояния

- Основной `drive` сохраняет null/alignment/overlap guards до доступа к новому
  диапазону, clamping sizes, проверку целого old block перед shrink и
  актуализацию layout/fill_op после успешного realloc. Null realloc оставляет
  старую запись. Нового использования освобождённого указателя не найдено.
- `RawAllocator` явно задаёт extent/provenance/initialization/liveness и
  запрет racing access. M2 off-by-default и требует unsafe token; обычный
  GlobalAlloc не получает разрешение на повторный free из safe Config.
- `peak_live_count` по-прежнему даёт O(M) prepass и O(K) память модели.
  Общая стоимость O(M + MK + B), теперь честно описанная в Cost. Старые
  предложения о более сложном overlap index и hash-fill не дублируются
  как новые баги: их стоит пересматривать под конкретную нагрузку.
- Enum/value-tree delegation и weight dispatch не изменили логики; helper
  `op_element_strategy` извлечён без изменения состава генератора. Zero-weight
  arm отсутствует структурно; arbitrary использует полный u64 weight sum,
  отдельный size draw и ограничение числа decode attempts.
- Новая static introspection доступна только при `proptest + internals` и
  скрыта из документации. Безусловного расширения обычного public API нет.
- Feature/package/i686/MSRV/bare-metal/release-profile/Miri wiring сохранены;
  exact docsrs build и отдельный release workflow guard остаются на месте.
  Новый measurement test под Miri исключён целиком; native paired assertions
  от этого не становятся Miri-проверенными. Свежего зелёного CI этот отчёт
  не удостоверяет.

## Приоритет следующего шага

Сначала исправить бухгалтерию byte counters и добавить отдельный memory-case
без shrinking. Затем усилить paired shrink oracle и поправить подписи/
гарантии в документации. Static introspection — необязательное маленькое
упрощение. Не возвращать uniform fill и не откатывать enum только по числу
замечаний: решение должно опираться на исправленный, правильно названный A/B.
