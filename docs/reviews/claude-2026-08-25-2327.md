## Verdict

**GO.** No P1 and no P2 found. The atomic protocol, the `unsafe` surface, the `Send`/`Sync` reasoning, the rollback/re-race liveness design, and the probe's clobber protection are sound as written; the documentation contract, after ten prior cycles, now matches the code on every load-bearing claim I could check. Everything below is P3 — non-blocking polish, most of it best done before the 0.1.0 API freeze but none of it a reason to hold publication.

Summary of what I verified as sound (not just "didn't look at"):

- **State machine.** `READY` is terminal: the only writers are the claim CAS (`null → sentinel`, `lib.rs:622-639`), the winner publish (`:680`), the two rollback stores (`:698`, guard `Drop` `:439`), and the probe (`:827-867`, every write gated on the probe itself owning the cell via a CAS from `null`). No write can ever follow a published real pointer. All success reads are `Acquire` (`:532`, `:613`, `:712`) against the winner's `Release` publish (`:680`) — the happens-before for the pointee is complete.
- **Rollback liveness.** Losers spin strictly on `== INITIALIZING` (`:711-732`) and re-race on `null`; the OOM path (`:697-699`) and the unwind path (`RollbackGuard`, `:430-442`) both restore `null` with `Release`. The guard is armed exactly across `init()` and defused on both non-unwinding exits — no window in which a panic could fire it after a successful publish (no panic site exists between the `store` at `:680` and `defuse()` at `:683`).
- **Sentinel discipline.** Built via `without_provenance_mut` (`:509-511`), compared by address only, never dereferenced; the `align_of::<T>() >= 2` constructor guard (`:475-479`) and the release-active result `assert!` (`:671-674`) close both reachable collision routes, including the safe-code `NonNull::new(without_provenance_mut(1))` route (regression-pinned by `tests/cell_unit.rs:128-145`).

All hold.

Fast path, CAS orderings (`Acquire`/`Relaxed`), rollback guard arming/defusing order, release-active result assert, `None`-path defuse-then-store order, loser spin shape, `dbg_is_ready`, and the probe's conditional step-4 restore are all behaviorally identical to the extracted crate. **No drift.** (The shim's *surrounding* docs in the same file have drifted — see N2 below — but the shim itself has not.)

## New findings (this run)

### N1 — P3 (doc accuracy) — claim-CAS ordering comment: stale `:544` line reference, and a "the only prior `Release` stores" claim that omits the probe's stores

**Where:** `crates/racy-ptr-cell/src/lib.rs:625-632`.

The comment on the claim CAS's success ordering says the `Acquire` "synchronises-with the `Release` rollback store (OOM at :544, or the unwind guard's `Drop`) of a PREVIOUS winner that abandoned the cell — the only prior `Release` stores that can leave it `null`." Two defects:

1. **`:544` is stale.** The OOM rollback store is at `lib.rs:698` in the current tree (Sol-codex run 3 already measured it at `:666`; three doc commits later it has drifted again — a hard-coded line number in a comment re-rots on every edit above it).
2. **"the only prior `Release` stores that can leave it `null`" is false.** `dbg_rollback_reenterable` performs two further `Release` stores of `null` on the same atomic (`:838` step 2, `:867` step 4). A cell can therefore be observed `null` at the claim CAS because a *probe* rolled it back, not only because a previous winner abandoned it. The synchronization *argument* is unaffected (any `Release` null-store pairs with the CAS's success `Acquire` identically), but the sentence's exhaustiveness claim is wrong, and this crate's whole documentation posture is precision about exactly such claims.

**Fix:** name the stores semantically, not numerically — e.g. "synchronises-with whichever `Release` store returned the cell to `null` (the explicit OOM rollback in this function, the unwind guard's `Drop`, or `dbg_rollback_reenterable`'s rollback/restore stores)". No code change.

### N2 — P3 (doc drift, root crate) — `bootstrap.rs`'s probe-forwarder doc still describes the PRE-extraction `Some(false)` contract, and links a deleted function

**Where:** `src/registry/bootstrap.rs:1020-1025` (contract), `:971`, `:1006`, `:1302` (dead intra-doc links). Root repo, not the published crate — but this audit was explicitly asked to check `bootstrap.rs` for drift.

`dbg_rollback_chunk_sentinel_reenterable` (`:1027-1040`) is now a thin forwarder onto `RacyPtrCell::dbg_rollback_reenterable`, yet its doc still promises:

> Returns … `Some(false)` if the postcondition CAS unexpectedly failed (rollback is broken — the counterfactual this test is designed to catch), or `None` if the chunk was not observed `UNINIT` …

The forwarded cell method makes `Some(false)` **deliberately unreachable** (a failed postcondition CAS maps to `None` — `lib.rs:791-796`, `:864-866`, and the cell's own doc explains why at length). Consequences:

- The root doc describes a return value that can never occur, and mislabels the meaning of `None` (which now covers the postcondition-CAS-failure case too).
- The detection strength the doc advertises no longer exists: the consumer test `tests/regression_bootstrap_oom_sentinel_rollback.rs:98-116` treats `None` as benign "not applicable — nothing to assert", so the specific breakage mode the doc says `Some(false)` "is designed to catch" would today surface as a silently-passing `None` arm, not a test failure. (In the extracted design this is defensible — the probe structurally cannot distinguish "broken" from "legitimately contended" — but the root doc must say that, as the cell's own doc does.)
- Three intra-doc links `[`rollback_chunk_sentinel`]` / `[`super::rollback_chunk_sentinel`]` (`:971`, `:1006`, `:1302`) point at a function the CRATE-P3 extraction deleted (`grep` finds no definition anywhere in `src/`). They survive because the root `docs` CI job deliberately drops `RUSTDOCFLAGS="-D warnings"` (per the comment at `ci.yml:1831-1838`).

**Fix:** rewrite `:1020-1025` to mirror the cell's actual `Some(true)`/`None` contract (copying the cell doc's "deliberately conflated, `Some(false)` intentionally unreachable" language), and replace the three dead links with prose naming the cell's rollback path. Root-crate docs only; no behavior change.

### N5 — P3 (doc precision) — the fork-barrier discipline's phrasing permits two broken protocol readings

**Where:** `crates/racy-ptr-cell/src/lib.rs:190-194`; mirrored at `README.md:83-87`. (This is the text `ea25359` just added to close Sol-codex run-3 F1 — the intent is right; the letter is looser than the intent.)

> Serialize `fork()` against every initializer with a process-wide barrier — acquired before `fork()`, held until no cell anywhere is `INITIALIZING` — so the fork actually happens with the invariant proven …

"Acquired before `fork()`, held until no cell anywhere is `INITIALIZING`" does not state the load-bearing piece: the barrier must be held **across the `fork()` call itself**, and acquisition must **exclude initializers** (initializers hold it shared around `init`; the forking thread takes it exclusively). Read literally, the sentence admits (a) "acquire → wait for quiescence → release → fork" (a new init can start in the release-to-fork gap) and (b) "acquire → fork → keep holding until quiescence" (the child snapshots a live sentinel before quiescence arrives). Both are the exact failure the paragraph exists to prevent. A careful reader recovers the intended protocol from "Serialize `fork()` against every initializer" plus "the fork actually happens with the invariant proven", which is why this is P3 and not P2 — but this specific paragraph family has produced a finding in five consecutive review cycles precisely because its letter kept trailing its intent.

**Fix:** one sentence, e.g.: "initializers hold the barrier (shared) for the duration of every `init`; the forking thread acquires it exclusively — which by construction waits until no cell anywhere is `INITIALIZING` and blocks new inits — calls `fork()` while holding it, and releases it only after `fork()` returns."

### N6 — P3 (API polish) — `get_or_try_init` is the only public method without `#[must_use]`, and it is the one whose discarded result hides an OOM

**Where:** `crates/racy-ptr-cell/src/lib.rs:607`.

`new`, `get`, `dbg_is_ready`, and `dbg_rollback_reenterable` all carry `#[must_use]`; `get_or_try_init` does not. A caller pre-warming a cell with `cell.get_or_try_init(init);` and checking readiness later silently discards the one signal that init reported OOM. The lint would force an explicit `let _ =`, which is exactly the friction wanted for a fallible-by-design API. (Deliberate-looking omissions were considered: a "call for effect" idiom is plausible, but the crate's own posture everywhere else is to make discards explicit.)

**Fix:** add `#[must_use = "None means init reported OOM; the cell is rolled back, not initialised"]`.

## Prior open P3s (Sol-codex run 3, F4–F9) — independently re-derived; I agree these are real and worth doing before the API freeze

Listed for completeness with current line anchors; none is a blocker.

1. **`FnMut` → `FnOnce`** (`lib.rs:607-609`; root shim `bootstrap.rs:328-330` must change in lock-step). Re-verified independently: within one `get_or_try_init` invocation the closure runs at most once — the winner arm returns on every exit (publish `:684`, OOM `:699`, or unwinds through the `assert!` `:671`), and the loser arm never calls it — so `FnOnce` is the accurate bound and admits consuming closures the current API rejects. NLL accepts the move because the consuming arm diverges. Pre-1.0 this is a free correction; post-1.0 it is a breaking change forever. The strongest of the open P3s.
2. **`dbg_rollback_reenterable`'s unreachable `Some(false)`** (`:824`). The doc handles it honestly, but a return type with a documented-impossible inhabitant is a wart to freeze; `bool`-returning or a two-variant enum (`Proven`/`Inconclusive`) states the contract in the type. Note the knock-on: fixing this changes the root forwarder's signature too, which would force the N2 doc fix along the way.
3. **Ordering costs** (success `Acquire` on the claim CAS `:636`; `Acquire` on every loser-spin iteration `:712`) and the monolithic generic `get_or_try_init`. Correctness is fine as-is (over-strong, never under-strong); do not weaken without a loom counterfactual first — the code's own comment at `:633-635` already frames `Relaxed` as an open measured question, which is the right posture.
4. **Bench validity** (`benches/racy_ptr_cell_bench.rs:44-50`): `get_or_try_init/cold` allocates and leaks a `Box` inside the timed closure, so the number is dominated by the system allocator, not the cell protocol; and the loser-spin/contention path — the crate's most expensive scenario — has no baseline at all (the file's own `NOT IMPLEMENTED` note at `:74-84` is honest about it).
5. **Loom-oracle gaps** (`tests/loom_racy_ptr_cell.rs:449`, `:467`, `:512-529`): the property-6 reclaim path round-trips pointers through `expose_provenance`/`with_exposed_provenance_mut` where `cell.get()` after the joins would sidestep provenance entirely (the crate's own `cell_unit.rs:91-101` comment explains precisely this pattern as the fix it already applied elsewhere); and there is no real-type oracle calling `get()` while a live `INITIALIZING` sentinel is held. My one nuance: the second gap is narrower than stated — an `is_ready` regression that classified the sentinel as ready would already fail `real_exactly_once_two_threads` (the fast path would hand a loser address `1`, whose `init_marker` deref loom rejects) — but a direct `None`-during-`INITIALIZING` oracle is still the honest pin.
6. **"Parks" as a mechanism claim about `OnceLock`** (`lib.rs:44`, `README.md:20-21`, `Cargo.toml:7` "instead of being parked, as OnceLock's losers are"): std promises blocking, not parking; "may block losing threads (this crate busy-spins and uses no OS primitive)" is the semver-stable phrasing.
7. **Doc/maintainability hygiene**, all confirmed still present: `#![cfg_attr(not(test), no_std)]` could be a plain `#![no_std]` (`:266` — no `#[cfg(test)]` code exists in `src/`); the type-level doc still quotes the retired claim `"safe inside a #[global_allocator]"` (`:339-340`) where every other occurrence was deliberately weakened to "usable inside"; internal `task #…`/`finding F…` numbers throughout the public rustdoc (`:375`, `:391-406`, `:653`, `:747-767`, `:812-822`) and — most out-of-place for a crates.io landing page — README's references to "the default CLAUDE.md's benchmark-hook rule (2)" and "the root repo's `tests/dbg_hook_safety_tripwire.rs` allowlist" (`README.md:221-229`), artifacts of this repo's internal process a downstream reader cannot resolve; the unsafe-seam header simultaneously claiming a "SINGLE documented reason" and "two audited kinds" (`:248-263` — the inventory is correct, the framing sentence is not); README/rustdoc section-order divergence.

## Checked and deliberately NOT flagged

Recorded so the next cycle does not re-litigate them:

- **The duplicated `| 3 |` row number in the panic table** (`lib.rs:110-111`, `README.md:102-103`): deliberate, not a defect — both rows are the same panic *site* (the alignment `assert!`) in its two forms; review-9 F1's fix intentionally removed ordinal cross-references, and renumbering the second row "4" would recreate exactly the numeral-drift class that produced findings in five consecutive cycles.
- **The msp430 E0432 claim** (`lib.rs:243-246`, `README.md:160-163`): scrutinized because `de7da71`'s commit message shows the thumb targets were rebuilt but msp430 was not. The claim nonetheless holds by rustc's own target spec: `msp430-none-elf` sets `max_atomic_width = Some(0)` (the spec's comment notes the LLVM backend supports neither CAS *nor* atomic load/store there), so `core` defines no `AtomicPtr` at all and the unguarded failure is an unresolved import, exactly as documented. Verified against the `target_has_atomic_load_store` gating reasoning recorded in `de7da71`'s message.
- **"`panic = "abort"` compiles the crate's internal rollback guard out entirely"** (`lib.rs:155-157`): strictly speaking the guard type still compiles and its (defused, no-op) `Drop` still runs on normal exits; what disappears is the armed-drop unwind path. The parenthetical "(it is unwind-only)" conveys the intended meaning; flagging the wording would be pedantry beyond the defect threshold.
- **`Some(false)` conflation in the cell itself**: not a defect — the cell's own doc (`lib.rs:781-796`) explains the deliberate conflation and why the probe cannot distinguish "broken" from "contended". The defect is only in the root forwarder's *stale mirror* of the pre-extraction contract (N2).
- **Loser-spin coherence in `real_fast_path_reentry_same_pointer`**: `get()` after a same-thread successful `get_or_try_init` is guaranteed `Some` by read-read coherence (a later load of the same atomic cannot observe an earlier value in modification order, and the real pointer is final) — the test is not racy.
- **`should_panic` counterfactuals passing vacuously if loom swallowed a child-thread panic**: they cannot pass silently — a `should_panic` test that does not panic *fails* `cargo test`, so the release-mode loom CI row's exit code already pins non-vacuousness even though the grep names only the probe-clobber test.
