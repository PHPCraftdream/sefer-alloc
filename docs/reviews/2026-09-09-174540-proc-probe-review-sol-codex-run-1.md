## Вердикт

**NO-GO для публикации в текущем виде.** Найдены три P2: обещанный режим
без `std` не реализован на уровне зависимостей; тесты не проверяют фактический
вывод библиотеки; отсутствует CHANGELOG, обязательный для publish-workflow.

Количество замечаний: **P0 — 0, P1 — 0, P2 — 3, P3 — 4, P4 — 3**.
P2 здесь — исправить до публикации; P3 — существенные улучшения проверок/API;
P4 — низкоприоритетные уточнения и возможности улучшения.

Нового UB, нарушения владения, ошибочной арифметики в самих `emit*` или
квадратичного алгоритма не обнаружено. Для корректных ключей и значений пять
функций действительно печатают заявленный текстовый формат. Основные проблемы
находятся в обещаниях, проверках и подготовке к публикации, а не в сложности
форматирования чисел.

## P2-1. Отключение `std` не даёт сборку без стандартной библиотеки

Места: `Cargo.toml:15`, `:21`, `:24`; `src/lib.rs:56`, `:58`, `:67`;
`README.md:44`; зависимость — `crates/proc-memstat/src/lib.rs:94`, `:231`.

Feature `std = []` управляет только `extern crate std` и наличием `emit*`.
Зависимость `proc-memstat` обязательная, её реэкспорт тоже безусловный.
Сам `proc-memstat` — std-крейт, в том числе с `impl std::error::Error`.

Поэтому потребитель с `default-features = false`, использующий только
`RESULT_PREFIX`, всё равно получает std-зависимость. Для bare-metal target
вроде `thumbv7em-none-eabi` заявленный путь не может собраться без `std`.
Обычная host-сборка не выявляет эту проблему: на хосте `std` доступен.

Само сочетание `#![no_std]` и std-зависимости допустимо. Ошибка — обещание
потребителю, что отключение feature устраняет требование `std`. Rust Reference
прямо отделяет атрибут от фактического подключения стандартной библиотеки;
Cargo отдельно управляет включением optional dependencies.
[Rust Reference](https://doc.rust-lang.org/reference/names/preludes.html#the-no_std-attribute),
[Cargo: optional dependencies](https://doc.rust-lang.org/cargo/reference/features.html#optional-dependencies).

Рекомендация: выбрать честный контракт. Либо сделать OS measurement dependency
optional и включать её вместе с соответствующим std API, оставив без std
только действительно независимый протокольный слой; либо отказаться от
обещания no_std и от вводящего в заблуждение переключателя. Одного
`default-features = false` у зависимости недостаточно: она не предоставляет
no_std-режим.

## P2-2. Тесты протокола могут пройти при полностью сломанном `emit*`

Места: `tests/protocol.rs:5`, `:19`, `:28`, `:50`, `:113`;
реальные функции — `src/lib.rs:80`, `:86`, `:93`, `:102`, `:112`.

Round-trip тесты строят строку собственной функцией `line()` и проверяют
собственный `parse_result()`. Ни один из этих assertions не получает байты,
которые напечатала библиотека. Единственный вызов настоящих `emit*` — smoke
без проверки вывода.

Два независимых контрпримера, прослеженных статически:

1. Заменить тела всех `emit*` на пустые. Round-trip assertions не меняются,
   smoke по-прежнему не паникует. Главная функция крейта исчезла, оракул молчит.
2. Изменить `RESULT_PREFIX` на `RESULTX`. И тестовый formatter, и тестовый
   parser используют этот же constant; внешний runner жёстко ожидает `RESULT`
   (`scripts/paired-ab-runner.mjs:253`). Тесты принимают новый префикс вместе,
   хотя реальная совместимость потеряна.

Также `ns_from_u128_round_trips` использует число, помещающееся даже в u32:
он не защитит от случайного сужения u128 до u64. Сама текущая реализация
`emit_ns` число не сужает — это пробел защиты, не найденное переполнение.

Нужны проверки stdout настоящих вызовов с независимо заданными ожидаемыми
байтами, включая LF, точный `RESULT`, signed/extreme values и u128 выше u64::MAX.
Подойдёт отдельный child; если он запускается под libtest, необходимо учесть
его capture. Альтернатива — тестировать общий production formatter через sink,
но оставить хотя бы один end-to-end тест привязки к stdout. Дублирование
форматирующего выражения внутри теста этой задачи не решает.

## P2-3. Штатный publish-workflow остановится из-за отсутствия CHANGELOG

Места: каталог `crates/proc-probe/`;
`.github/workflows/release.yml:277`, `:293`, `:295`, `:298`.

В пакете есть README и лицензии, но нет `CHANGELOG.md`. Для реальной публикации
workflow вычисляет каталог выбранного пакета, требует CHANGELOG именно там
и завершает шаг с ошибкой при его отсутствии. До `cargo publish` дело не дойдёт.

Это воспроизводимое по конфигурации препятствие именно существующему release
workflow, а не утверждение, что Cargo/crates.io сами требуют CHANGELOG.
Dry-run пропускает этот guard и поэтому не является свидетельством готовности
реального release-пути.

Добавить содержательный CHANGELOG первого релиза: экспортируемые API,
протокольный контракт, feature/platform ограничения. Guard не следует ослаблять
ради отсутствующего документа. Код workflow в ходе ревью не исполнялся.

## P3-1. Feature-off конфигурация не согласована с тестами и rustdoc

Места: `tests/protocol.rs:112`; `src/lib.rs:17`, `:18`, `:79`.

`emit_smoke_does_not_panic` не имеет `#[cfg(feature = "std")]`, хотя все пять
вызываемых им функций при отключённом feature отсутствуют. Изолированный
`cargo test -p proc-probe --no-default-features` на обычном std-хосте должен
получить ошибки разрешения имён. Это отдельная проблема от bare-metal
зависимости из P2-1: для неё не нужен target без стандартной библиотеки.

Crate-level rustdoc при этом безусловно содержит ссылки на удалённые `emit*`.
Feature-off документация имеет ссылки без доступных items; генерация с deny
для broken intra-doc links должна выявить это. Rustdoc применяет cfg так же,
как компилятор. [Rustdoc: feature-specific information](https://doc.rust-lang.org/rustdoc/advanced-features.html#cfgdoc-documenting-platform-specific-or-feature-specific-information).

Если feature сохраняется, согласовать cfg тестов и документации и проверять
обе конфигурации отдельно. Не смешивать их с root dev-dependencies, которые
могут снова включить default features. Названные команды здесь не запускались.

## P3-2. Тестовый parser не эквивалентен объявленному JavaScript regex

Места: `tests/protocol.rs:23`, `:27`, `:30`, `:44`;
`scripts/paired-ab-runner.mjs:252`, `:253`.

Rust helper использует `char::is_whitespace` и Rust `trim`; runner —
ECMAScript `\s`, `\S` и JavaScript `trim`. Эти множества символов различаются,
поэтому комментарий о семантической идентичности неверен.

Контрпримеры ниже записаны с escaped Unicode code points; подразумеваются
строки с настоящими соответствующими символами, не с буквальным обратным слешем.

| Строка | Rust helper | Настоящий JS parser |
| --- | --- | --- |
| `RESULT k=a\u{FEFF}b` | Принимает | Отклоняет |
| `RESULT k=a\u{0085}b` | Отклоняет | Принимает |

`char::is_whitespace` использует Unicode White_Space: U+0085 входит, U+FEFF
не входит. ECMAScript добавляет U+FEFF, но не относит U+0085 к своим whitespace
или line terminators.
[Rust char](https://doc.rust-lang.org/std/primitive.char.html#method.is_whitespace),
[Unicode PropList](https://www.unicode.org/Public/16.0.0/ucd/PropList.txt),
[ECMAScript White Space](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-white-space),
[ECMAScript CharacterClassEscape](https://tc39.es/ecma262/multipage/text-processing.html#sec-characterclassescape).

Определить точный алфавит протокола и проверять один corpus на реальном
потребителе либо на действительно эквивалентной модели. Добавление обычного
Rust regex само по себе не гарантирует ECMAScript-семантику. На ASCII fixtures
расхождение незаметно; Unicode значения публичный `emit` сейчас не исключает.

## P3-3. Основной CI не запускает собственные проверки proc-probe

Места: `.github/workflows/ci.yml:2140`, `:2160`;
`Cargo.toml:1`, `:86`, `:992` в корне;
`.github/workflows/release.yml:549`, `:560`.

В main CI нет команды, выбирающей `proc-probe` для собственного test/clippy/doc
прохода. Workspace non-virtual, а job `test-workspace` перечисляет другие
пакеты явно. Компиляция proc-probe как dev-dependency корня или через примеры
не запускает `crates/proc-probe/tests/protocol.rs`.
Это соответствует правилам выбора пакетов Cargo.
[Cargo test: package selection](https://doc.rust-lang.org/cargo/commands/cargo-test.html#package-selection).

Упоминание пакета в `scripts/verify-ci-sentinels.mjs:191` — словарь для
статического анализа YAML, не запуск тестов. При настоящем релизе отдельный
test gate действительно выполнит `cargo test -p "$NAME"`; утверждать, что
тесты не запускаются вообще нигде, было бы неверно. Но ошибки обнаруживаются
слишком поздно, а feature-off и собственные rustdoc/clippy targets не покрыты.

Добавить явные проверки пакета в обычный CI: std/default и feature-off,
собственные tests/clippy/rustdoc; bare-metal проверку — только если no_std
остаётся обещанием. Уточнить MSRV-покрытие самого пакета, не полагаться на
название workspace job. Статус последних CI runs по сети не запрашивался.

## P3-4. Однозависимостный фасад не предоставляет fallible измерение

Места: `src/lib.rs:24`, `:67`;
`crates/proc-memstat/src/lib.rs:197`, `:240`, `:278`.

Зависимость уже предоставляет `try_snapshot` и `SnapshotError`, но фасад
реэкспортирует только `snapshot` и `MemStat`. Потребитель с одной заявленной
зависимостью не может вызвать fallible API через `proc_probe`.

Типичный показанный в README путь `snapshot().rss -> emit_u64` при ошибке
измерения напечатает корректную строку с нулём. Для сравнения памяти это может
выглядеть как освобождение памяти вместо отсутствующей выборки. По полной
структуре можно распознать fallback-shape, но нельзя получить причину ошибки.

Рекомендую реэкспортировать fallible пару и показать её в measurement-примере:
нет измерения — нет успешной числовой выборки. Best-effort `snapshot` можно
оставить. Это улучшение фасада и защиты измерений, а не новая ошибка самой
`proc-memstat::snapshot`, которая именно так документирована.

## P4-1. Гарантия формата зависит от непроверяемых входных предусловий

Места: `README.md:27`, `:30`; `src/lib.rs:77`, `:80`, `:84`.

`emit` не проверяет key/value, numeric helpers тоже принимают любой `&str`
ключ. Например, `emit("arm", "x\nRESULT rss_kib=0")` создаёт две строки,
а пустой ключ или значение — строку, которую runner не принимает.

Здесь важна калибровка: значение с newline нарушает уже написанное предусловие
`value` без whitespace. Поэтому это не заявляется как ошибка на допустимом
входе или доказанная security vulnerability. Проблема — чрезмерное обещание
«can never drift» и отсутствие явной политики invalid input у всего API.

Либо валидировать перед первым байтом вывода, возможно через проверенный тип
ключа, либо явно назвать API unchecked и распространить предусловия на все
helpers. Не исправлять недопустимые значения незаметной заменой/усечением:
это превратит ошибку входа в другую метрику.

## P4-2. Sink API позволит управлять I/O errors и стоимостью серии emit

Места: `src/lib.rs:81`, `:87`, `:94`, `:103`, `:113`.

Сейчас каждая функция привязана к `println!`: отдельный stdout lock на вызов,
паника при ошибке записи, нет возможности передать уже удерживаемый writer.
Это свойства выбранного std API, а не предположение о его внутренностях.
[std::println](https://doc.rust-lang.org/std/macro.println.html).

Для большого пакета метрик полезен formatter/emitter с передаваемым sink:
можно удерживать lock один раз, выбирать буферизацию и возвращать `io::Result`.
Он одновременно облегчит P2-2. Для существующих функций как минимум описать
паники при stdout failure; более богатый API — улучшение, не срочный bugfix.

Один только общий lock не устраняет flush на newline при line buffering.
Line buffering stdout описан в [std::io::Stdout](https://doc.rust-lang.org/std/io/struct.Stdout.html).
Для сокращения записей нужна явная пакетная буферизация с проверяемым flush.
Не менять момент доставки данных молча. Для обычных нескольких строк в конце
probe выигрыш может быть несущественен; измерений ускорения в этом ревью нет.

## Общая оценка кода, стоимости и интеграции

В собственной реализации нет `unsafe`, ручного FFI, `Send/Sync`, raw pointers,
фоновых задач, caches или принадлежащих крейту OS handles. Реэкспорт не добавляет
новой unsafe-обёртки. Ошибок освобождения ресурсов внутри этих пяти функций
не найдено; native measurement целиком остаётся обязанностью зависимости.

Вызовы принимают строки по ссылке, числа по значению; `emit_ns` сохраняет u128.
Собственных `String`/`Vec`, `clone`, `collect`, `to_string` или промежуточного
`format!` на production-пути нет. Не следует ради DRY превращать numeric helper
в `emit(key, &value.to_string())`: это добавит ненужную аллокацию.

Для K байт ключа и V байт значения стоимость передачи строки — O(K + V).
Числа имеют фиксированную ширину типа; максимум у u128 — 39 десятичных цифр.
Квадратичных проходов или структур данных, требующих снижения O, здесь нет.
Это не гарантия отсутствия любых аллокаций внутри std/OS: измерений allocator
calls и первичной инициализации stdout не было. Практический кандидат на
ускорение — управление sink из P4-2, не новая библиотека форматирования.

Константа и повторённые пять небольших format strings сами по себе не требуют
macro/framework. Главный запах — комментарии, которые называют тесты
поведенческими при проверке отдельной модели. Исправлять нужно источник
проверяемых байтов, а не увеличивать число похожих literals.

Отдельная граница совместимости с упомянутым README runner:

- `scripts/paired-ab-runner.mjs:254` превращает в Number только целые токены.
  `emit_f64(..., 1.5)` выдаёт правильный токен `1.5`, но runner оставляет строку.
  Если выбрать её основной метрикой, сумма на строках `:432`/`:433` выполняет
  конкатенацию перед делением, а не числовое сложение.
- Большие u64/u128 печатаются крейтом точно, но Number в потребителе не хранит
  произвольные такие целые без потери точности. Нельзя обещать точный numerical
  round-trip всей цепочки по тестам с небольшими числами.
  [ECMAScript: MAX_SAFE_INTEGER](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-number.max_safe_integer).

Это риски интеграции вне реализации крейта, **не дополнительные P-замечания
к proc-probe**. Не следует ограничивать корректный u128 emitter ради конкретного
потребителя; нужно определить контракт потребителя и добавить interop-проверки.
Сам wire-format является текстовым токеном, не гарантией типа JavaScript.

Лицензии присутствуют; manifest имеет собственные package metadata и обычную
path+version зависимость, без build.rs, proc-macro, git override или новой
сторонней библиотеки. Регистровая разрешимость и сборка упакованного архива
не проверялись. Найденный недостаток release-артефактов — P2-3.
