## Вердикт

**P0=0, P1=0, P2=0, P3=1, P4=5.**

Новых дефектов memory safety или нарушений управления временем жизни в
драйвере при соблюдении `RawAllocator` contract не обнаружено. Исправления
прошлого раунда по своим конкретным контрпримерам приняты. Однако новый hash
сократил различимость коротких префиксов между разными fill-id: некоторые
wrong-source realloc, которые прежний паттерн различал, теперь проходят.
Это P3 к качеству диагностического покрытия, не UB и не неправильное сравнение
байтов. Критерий готовности «без замечаний P0–P3» пока не выполнен.

Из пяти P4 два — новые замечания к документации/CI, три — ранее известные
возможности оптимизации, которые последний коммит явно оставил до измерений.
Их наличие само по себе не означает необходимость усложнять код перед релизом.

## P3-1. Новый hash теряет различимость разных fill-id на коротких префиксах

Места: `crates/globalalloc-model/src/drive.rs:79`, `:238`, `:554`, `:561`;
покрытие нового паттерна: `crates/globalalloc-model/tests/oracle_negative.rs:814`,
`:840`, `:866`, `:888`.

Усечение смешанного значения до u8 не сохраняет инъективность по fill-id
даже в нулевой позиции. Точные значения текущей формулы:

| Fill-id | Байты на offset 0, 1, 2 |
| --- | --- |
| 5 | `cd 36 85` |
| 30 | `cd 35 b3` |
| 60 | `93 7b c0` |
| 92 | `93 7b c9` |

У всех 255 допустимых идентификаторов первый байт принимает только 151
различное значение; первые два байта — 254 различных пары. Здесь нет
переполнения счётчика fill, повторного использования одного id или сдвига
источника: разные id совпадают уже с offset 0.

Конкретный сценарий:

1. Тридцать успешных `Alloc { size: 8, align: 8 }` создают непересекающиеся
   A1…A30 с fill-id 1…30. Никаких повторов id ещё нет.
2. Операция `Realloc { i: 29, new_size: 1 }` выбирает A30. Проверка всего
   старого блока перед realloc проходит: A30 не повреждён.
3. Дефектный аллокатор создаёт новый отдельный диапазон C, потребляет A30,
   но копирует один инициализированный байт из A5 вместо A30.
4. Overlap guard проходит: C не пересекается с другими live-блоками.
   Prefix oracle сравнивает `0xcd` с `0xcd` и также проходит.
5. C получает новый fill-id 31; все остальные блоки неизменны.
   Последующие sweep/teardown не имеют различий, которые могли бы обнаружить.

Диапазоны можно разместить внутри одной достаточно большой заранее
инициализированной тестовой арены без UB. Возврат самого A5 вместо отдельного
C был бы другим сценарием: его обнаружил бы overlap guard.
Аналогичный пример с A60/A92 и `new_size: 2` скрывает копирование двух байтов.

При прежней формуле `fill + offset` нулевые байты этих пар различались:
`0x05 != 0x1e` и `0x3c != 0x5c`. Такие **несдвинутые** wrong-source копии
не проходили. Нынешние отрицательные тесты паттерна используют длинные
префиксы и преимущественно fill 1/2, поэтому этой потери покрытия не закрепляют.

Калибровка: на совпавших значениях возвращённый префикс удовлетворяет
байтовому постусловию realloc; драйвер не ошибается при сравнении. Дефект —
в выборе тестовых данных, скрывающем ошибочный алгоритм копирования.
Это не требование исключить все коллизии конечного паттерна: конкретно
различимость **255 разных id в первом байте** достижима и раньше имелась.

Рекомендация: сохранить для offset 0 взаимно-однозначный ненулевой маркер
fill-id, например сам id, а для остальных позиций — нелинейное смешивание.
Это закрывает показанные несдвинутые wrong-source коллизии без хранения
копии payload. Сохранить прежний shifted-foreign отрицательный контроль;
добавить короткие wrong-source случаи с разными id и соответствующие честные
grow/shrink контроли. Не обещать отсутствия любых сдвиговых/байтовых коллизий.

## P4-1. В четырёх местах остался несуществующий период 256

Места: `crates/globalalloc-model/src/drive.rs:74`, `src/lib.rs:69`,
`README.md:187`, `CHANGELOG.md:121`.

Описание утверждает период 256 и объясняет его `offset as u8`. Но реализация
сначала преобразует offset в **u32**, смешивает старшие биты и только затем
сужает результат. Контрпример к периоду:

```text
pattern(1, 0)   = 0xb7
pattern(1, 256) = 0xd0
```

Гарантированное повторение из-за усечения входа на 64-битной платформе —
через `2^32` позиций: `pattern(f, o + 2^32) == pattern(f, o)` при допустимых
offset. Это не утверждение об отсутствии более ранних локальных коллизий:
они есть, в частности в P3-1. На 32-битной платформе такой шаг внутри
допустимого allocation не достижим.

Обновить все четыре описания. Заодно заменить категорическое обещание
«shift/permutation больше не могут совпасть» на перечисление покрытых
классов и оставшихся ограничений. Приватный комментарий честно называет
устранение любых fixed shifts целью, не доказательством; README звучит сильнее.
Это пример фактического расхождения от копирования одного длинного объяснения
в несколько мест. Лучше держать точные ограничения в одном каноническом
описании, а в остальных — краткую формулировку и ссылку.

## P4-2. После добавления `internals` docsrs job проверяет другой набор features

Места: `crates/globalalloc-model/Cargo.toml:27`, `:55`;
`.github/workflows/globalalloc-model.yml:176`, `:186`;
`.github/workflows/ci.yml:2227`, `:2233`; `CLAUDE.md:893`.

Metadata задаёт `features = ["proptest", "arbitrary"]` и намеренно исключает
`internals`. Это именно список features сборки docs.rs, а не только правило
отображения API. [Документация docs.rs](https://docs.rs/about/metadata).

Однако job «docs.rs configuration» выполняет `cargo doc --all-features`:
теперь он дополнительно включает `internals`. Обычные doc-команды также
проверяют default/all, не точную публикуемую комбинацию. Например, новая
ссылка из feature-gated документации генератора на internal export могла бы
разрешаться при all-features; default docs не включили бы сам генератор.
Публикуемая комбинация такую ссылку не разрешила бы.

Уточнение: standalone consumer действительно собирается с обоими front-end
features **без** internals. Поэтому утверждение «эта комбинация вообще не
компилируется в CI» было бы неверным. Он не выполняет rustdoc с `--cfg docsrs`.
Текущего падения опубликованных docs не установлено; это пробел точности
проверки, не доказанный сломанный релиз.

Добавить doc-lint с features из metadata, предпочтительно извлекая список
при выполнении CI; сохранить отдельный all-features проход для внутренней
конфигурации. Это соответствует уже записанному требованию `CLAUDE.md`.
README:150 и CHANGELOG:68 также стоит уточнить: четыре прежние комбинации
больше не означают полный powerset трёх features. Ради этого замечания
раздувать все test jobs до восьми комбинаций необязательно.

## Ранее известные возможности ускорения

### P4-3. Стоимость побайтового fill/verify после усиления смешивания

Места: `crates/globalalloc-model/src/drive.rs:79`, `:149`, `:167`, `:230`.

Каждый расчёт expected теперь содержит три wrapping-умножения u32 и
xor/shift. В исходнике это повторяется на каждый байт заполнения и проверки;
фактический машинный код и работу оптимизатора здесь не измеряли.
При небольшом live set и крупных блоках эти проходы — первоочередной
кандидат для профилирования. Новая формула делает прежний follow-up актуальнее.

После стабилизации паттерна сравнить текущий вариант с порционной
генерацией/проверкой, сохраняя точный failing offset. Вариант генерации слова
на несколько байтов может уменьшить стоимость смешивания, но меняет схему
данных и требует повторной проверки различимости, включая P3-1.
Не возвращаться к однородному memset и не убирать проверки перед
разрушительными операциями ради непроверенного ускорения.

### P4-4. Overlap scan остаётся O(MK), в худшем случае O(M²)

Место: `crates/globalalloc-model/src/drive.rs:122`.

Каждое создание блока сравнивает его со всеми прочими live-блоками.
Для K последовательных alloc без free получается `K*(K-1)/2` сравнений.
Упорядоченный индекс непересекающихся диапазонов позволил бы проверять
соседей и обновлять индекс за O(log K), сохранив отдельный Vec для семантики
индексов Op. Это дополнительная структура, память и инварианты синхронизации;
сортированный Vec сам по себе не устраняет O(K) стоимость вставки/удаления.
Выбор делать по реальному K и профилю, особенно с учётом цены byte oracle.

### P4-5. Три boxed size strategies на построение `op_strategy`

Места: `crates/globalalloc-model/src/strategy.rs:15`, `:72`, `:74`, `:77`.

Для Alloc, AllocZeroed и Realloc отдельно создаётся `BoxedStrategy`.
Type erasure и соответствующие heap-backed объекты остаются кандидатами
на уменьшение аллокаций/косвенности при частом построении и shrinking деревьев.
Возможен конкретный enum стратегии и ValueTree, но не ценой возвращения
zero-weight ветвей в shrinking. Простая замена disabled arm весом ноль
не эквивалентна нынешнему структурному исключению. Измеренных выигрышей нет.

## Общий обзор текущего кода

- Драйвер проверяет null, alignment и overlap до доступа к новому диапазону.
  При успешном realloc не разыменовывает старый указатель; новая запись
  получает текущий размер/layout. При null сохраняет старую запись.
  Эти переходы согласованы с [контрактом GlobalAlloc::realloc](https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html#method.realloc).
- RawAllocator явно отделяет обязательные extent/provenance/liveness/
  initializedness условия от диагностируемых значений. Safe `drive` не
  обещает безопасно испытать произвольно несостоятельный unsafe impl.
  Live приватен, не выдаёт заимствований наружу, ручных Send/Sync у него нет.
- Проверка всего старого блока перед shrink не теряет испорченный suffix.
  Проверки перед free и каждым teardown free закрывают ранее найденные
  временные окна. Утечки при panic документированы; безусловный RAII-free
  подозрительных указателей был бы опаснее, а не исправлением этого поведения.
- M2 включается только через unsafe token; default выключен. Контракт
  запрещает применять token к blanket GlobalAlloc. Это намеренная граница
  ответственности, не обнаруженный новый безопасный путь к double-free.
- Peak-live prepass стоит O(M), резервирует модель по K, не по длине истории.
  Вместе с overlap и байтовыми проходами стоимость драйвера O(M + MK + B),
  где B — суммарное число обрабатываемых байтов, K — пиковый live count,
  M — число операций. Дополнительная память модели O(K), без копии payload.
- Валидация исключает нулевые веса одновременно и непригодный max_align;
  нулевые/oversized размеры ручных операций нормализуются до allocator call.
  Индексы берутся modulo только для непустой модели. Сумма arbitrary weights
  помещается в u64; bounded decoder ограничен 2048 попытками операций.
- В CI по файлам сохранены default/front-end тесты, i686, MSRV, bare-metal,
  release-profile и Miri; package проверяется после извлечения отдельно.
  Release guard для собственного workflow уже есть и повторно не открывается.
  Его наличие не является подтверждением зелёного CI именно этого HEAD.
