### R17-SEC-01 — H-1 (нижняя граница payload) отсутствует ровно на том пути small-free, который `production` использует по умолчанию

**Места.**
- Дефект: `src/registry/heap_core/free/dealloc_own_base.rs:195-301` (`small_free_guard`) — цепочка охранов: pre-route Large `:219-233`, F7 (A) `:238-252`, F7 (B) `:255-271`, H1 `hardened` `:273-281`, `is_in_magazine` `:287-291`, `off >= bump` (`alloc-decommit`) `:292-295`, `is_free` `:296-298`, `Accept` `:300`. **Сравнения `off` с `payload_start` нет ни в одной ветке.**
- Три родственных пути, где граница есть: `src/alloc_core/small/alloc_core_small/dealloc.rs:73-81` (`dealloc_small`, безусловно, UBFIX-3); `src/alloc_core/small/alloc_core_small_magazine.rs:547-558` + `:571-577` (`flush_run`, hoisted + per-block); `src/alloc_core/small/alloc_core_small_reclaim.rs:38-45` (`reclaim_sidecar_record`, `std::process::abort()`).
- Потребители охрана: `src/registry/heap_core/free/dealloc_own_base.rs:384-402` (скалярный own-thread) и `src/registry/heap_core/free/dealloc_batch.rs:316-332` (`dealloc_batch_small`, `batch-api`).

**Трасса (SOURCE-CONFIRMED).** `GlobalAlloc::dealloc` → `HeapCore::dealloc` (`free/dealloc.rs:219`) → `dealloc_routing` (`heap_core_xthread/routing.rs:10-20`): `canonical_block_of(ptr)` возвращает `(base, block)` для любого адреса внутри зарегистрированного сегмента, потому что ключ — маска `segment_base_of_ptr` (`alloc_core/alloc_core/mem/mem_impl.rs:34-42`), а не геометрия блока → `dealloc_own_thread_with_base(block, layout, base)` (`:341-352`: `canonical_block_of` + сверка `root.addr() == base.addr()`, обе проходят для `ptr = base + off`, `off < payload_start`) → `class_for(size, align)` даёт `Some(c)` для small-раскладки (`:369`) → `small_free_guard(root, ptr, c, layout)`:

- pre-route Large (`:231`): `BlockKind::of(base, Some(c))` читает байт `kind` → для `Small`/`Primordial` сегмента не срабатывает;
- F7 (A)/(B) скомпилированы вне `production`;
- H1 под `hardened` (`:278`) проверяет только `off % block_size(c) == 0` — любое `block_size`-кратное смещение в метаданных (включая `0`, кратное всему) проходит;
- `is_in_magazine(off)`: биты магазинной карты для метаданных никогда не ставятся → `false`;
- `off >= bump`: `bump` ≥ `payload_start` всегда (`set_bump(payload_start)` при reset, `alloc_core_small_pool/decommit.rs:152,216`), значит метаданное смещение всегда `< bump` → не ловится;
- `is_free(off)`: биты alloc-карты для метаданных не ставятся ни одним путём (все три родственных пути отбрасывают такие смещения до `mark_free`), значит бит читается как «занят» → не ловится;
- → `Accept { off }`.

Далее `:409-440`: `mark_magazine(off)`, `slots[cnt] = block`, `count += 1`. Блок **никогда не доходит** до защищённого `dealloc_small`; при следующем `alloc` того же класса сработает горячая ветка магазина `src/registry/heap_core/alloc/hot.rs:289-386`: `let issued = slots[new_cnt]` (`:340`), `clear_magazine_on_issue(issued)` (`:367`; маска даёт тот же `base`, `debug_assert` в release скомпилирован вон), `return issued` (`:385`). Вызывающему выдаётся адрес внутри метаданных сегмента как живая аллокация класса `c`.

**Последствие (SOURCE-CONFIRMED по раскладке).** `payload_start` для `Small` — `[0, small_meta_end())`, для `Primordial` — `[0, primordial_meta_end())` (`segment_header_layout.rs:77-94`). В этом окне лежат: `SegmentHeader` (включая `reservation`/`reservation_len` — токены освобождения ОС, `payload_offset`, `span_usable`, `bump`, `live_count`, `magic`, `kind`), `PageMap`, `BinTable` (головы всех free-list), `AllocBitmap` (32 KiB), `MagazineBitmap` (32 KiB), под `hardened` — таблица генераций; у primordial дополнительно **самохостящийся `SegmentTable`** (массив слотов, hash-таблица, free-list индексов: `primordial_registry_off`/`primordial_hash_off`). Запись приложения в выданный блок переписывает эти байты. Это ровно тот отказ, который UBFIX-3 закрывал в `dealloc_small`, и описанный в `docs/reviews/2026-07-10-ub-memory-audit-summary.md` H-1.

**Модель атакующего и честная оценка эксплуатируемости.** Вход — одиночный вызов `dealloc`/`dealloc_batch` с указателем, не полученным от `alloc`. `GlobalAlloc::dealloc` и `AllocCore::dealloc` — `unsafe fn` с документированным контрактом («exact start pointer of a currently-LIVE allocation … MUST NOT be an interior pointer», `mem_impl.rs:203-209`), поэтому из 100% безопасного кода этот вход недостижим: **нового production-эксплойта из safe-кода нет**, отсюда P3, не P1. Цепочка «вход → примитив» при уже имеющемся произвольном free: `free(base + k·block_size, small layout)` → `alloc(same class)` → запись → подконтрольная перезапись метаданных аллокатора (в primordial — реестра сегментов) → далее произвольные `release_segment`/`contains_base`-десинхронизации. Ценность находки — в асимметрии: три сиблинга на том же логическом шаге отвечают no-op или `abort()`, а дефолтный путь отвечает выдачей метаданных.

**Пробел покрытия (SOURCE-CONFIRMED).** Единственный регрессионный тест H-1 — `tests/regression_dealloc_metadata_region_guard.rs` — ведёт сценарий через `AllocCore::new()` + `AllocCore::dealloc` (`:78-133`), то есть через **субстратную** грань (`dealloc_small`), и поэтому зелёный при дефекте в магазинной грани. Ни один тест не подаёт метаданный адрес в `HeapCore::dealloc`/`SeferAlloc`.

**Рекомендация.** Внести в `small_free_guard` ту же безусловную границу, что в `dealloc_small`: после определения `kind` (он уже читается pre-route'ом через `BlockKind::of`) сравнить `off` с `primordial_meta_end()`/`small_meta_end()` и вернуть `RejectNoOp`. Цена — одно сравнение с compile-time константой на small-free (плюс уже оплаченный читаемый `kind`), это дешевле, чем hardened-`%` рядом. **Oracle исправления (контрфактуальный):** новый интеграционный тест на `HeapCore`/`SeferAlloc`, который (1) делает `alloc` якоря, (2) вычисляет `base` сдвигом от якоря (без int→ptr, как в существующем тесте), (3) `dealloc(base + 0)`, `dealloc(base + PAGE)`, `dealloc(base + 2·PAGE)` с раскладкой класса 0, (4) требует, чтобы следующие N `alloc` не вернули ни один из этих адресов и были попарно различны. На текущем дереве такой тест **красный** (адрес `base + 0` выдаётся обратно), после фикса — зелёный. Тест должен идти в двух конфигурациях (`production` и `production hardened`), потому что hardened-H1 эту дыру не закрывает, и дополнительно через `dealloc_batch` под `batch-api`.

### R17-SEC-02 — интрузивный `next` не аутентифицирован: вне `hardened` его никто не проверяет, `is_free(head)` не проверяется нигде, а в standalone `AllocCore` граница смещения отсутствует и в release

**Места.**
- `src/alloc_core/platform/node.rs:75-102` (`write_next` — безусловная запись слова в тело блока), `:111-119` (`read_next`), `:131-143` (`deref` = `segment_base.add(offset)`, контракт «`offset < segment_len` — обязанность вызывающего»).
- `src/alloc_core/small/alloc_core_small/alloc_core_small_impl.rs:374-465` (`pop_free`): `read_next` `:385`, проверка «тот же сегмент» **только** под `hardened` `:407-412`, вычисление нового смещения вычитанием указателей `:413-420`, `prepare_small_issue` `:421-423`, `set_head` `:424`, `mark_alloc` `:436`.
- `:526-637` (`try_drain_freelist_batch`): probe-проход `:550-577` (та же hardened-проверка `:565-570`), pop-проход `:580-617` (`:598-603`).
- Границы, которые остаются в `production`: `src/registry/segment_route/small_sidecar.rs:50-56` (`prepare`: `offset < SEGMENT` и кратность 16) и `:67-73` (`prepared`).
- `src/alloc_core/segment/bitmap/segment_bitmap.rs:109-117` (`locate`: граница индекса — **только** `debug_assert!`).

**Трасса (SOURCE-CONFIRMED).** Слово `next` живёт в первых 8 байтах освобождённого блока, то есть в памяти, которую пользователь контролирует, пока держит блок (легально) или пишет в него после free (UAF). На pop значение превращается в смещение сырым вычитанием `(next as usize - segment as usize) as u32` без какой-либо валидации вне `hardened`; результат публикуется как голова списка (`set_head`), а следующий pop подаёт его в `Node::deref(segment, off)`.

Что реально ограничивает последствие в разных конфигурациях:
- **`production` (routed table).** `pop_free`/drain вызывают `prepare_small_issue` (`segment_table_impl.rs:316-333` → `small_sidecar.rs:50-56`), и спилл принимается только для `offset < SEGMENT` и 16-кратного. Так как `off` — младшие 32 бита разности, атакующий, контролирующий 8 байт `next`, выбирает **любое** 16-кратное смещение в пределах 4 MiB, включая всю метаданную область (тот же набор структур, что перечислен в R17-SEC-01). То есть containment есть, но он не отделяет payload от метаданных.
- **`alloc-core` без `alloc-global`** (публичная опт-ин конфигурация; `routes` = `None`, `prepare_small_issue` возвращает `IssueTransaction::unrouted`, `segment_table_impl.rs:331-332`). Тогда не проверяется ничего: `Node::deref(segment, off)` с `off` до ~4 GiB — арифметика вне объекта (UB по собственному контракту `node.rs:131-143`), а `mark_alloc(off)` → `locate(off)` даёт `byte_idx` до 32 MiB и пишет байт через `Node::write_u8` вне карты (`segment_bitmap.rs:92-107`) — в release `debug_assert` отсутствует, значит это запись в чужую/незамапленную память.
- **Нигде** на pop не проверяется `is_free(head_off)`: симметричного «голова списка обязана быть помечена свободной» охрана нет ни в `pop_free`, ни в `try_drain_freelist_batch` (оба только `mark_alloc`). Этот бит — готовый, уже существующий и бесплатный по памяти оракул against подделанной головы.
- Кодирования `next` (safe-linking в стиле glibc `PROTECT_PTR`, канареек или XOR-с-ключом-сегмента) нет: `write_next` пишет указатель как есть.

**Отношение к известному.** UBFIX-7 / M-3 (`docs/reviews/2026-07-10-ub-audit-final-synthesis.md`) закрыл именно эту дыру — но **только** под `hardened`, и это решение задокументировано в коде как сознательное («never runs on the production hot path», `alloc_core_small_impl.rs:400-406`). Новое в этом отчёте: (а) в `production` остаётся единственная граница — `SmallSidecar::prepare`, и она пропускает метаданные; (б) в `alloc-core`-only границы нет вовсе, а `locate` — debug-only, то есть в release это OOB-запись, а не ограниченная порча; (в) `is_free(head)` не используется как оракул ни в одной конфигурации, включая `hardened`.

**Модель атакующего.** Требуется запись 8 байт в уже освобождённый блок (UAF) либо переполнение в соседний освобождённый блок. Оба — уже UB в терминах Rust, поэтому это не новый эксплойт из safe-кода (P3). Цепочка: UAF-запись → следующий `alloc` того же класса в том же сегменте возвращает указатель на выбранное атакующим 16-кратное смещение (в `production`) или OOB-указатель + OOB-запись в карту (в `alloc-core`).

**Рекомендация (по возрастанию цены).** (1) Добавить безусловную проверку `is_free(head_off)` на pop — один уже загруженный байт карты, отвергает подделанную голову, которую аллокатор никогда не помечал свободной; (2) снять `hardened`-гейт с проверки «`next` в этом же сегменте» (одна маска + сравнение) либо, что эквивалентно по цене, заменить её безусловной проверкой `off < SEGMENT && off >= payload_start`; (3) безусловную границу в `locate` вместо `debug_assert` (как уже сделано в `gen_at`/`bump_gen`, `segment_header_gen_table.rs:61-64`, `:104-107` — там `assert!` специально release-выживающий, R2-3). **Oracle:** существующий `tests/regression_freelist_next_validation.rs` уже содержит ровно нужный контрфактуал, но весь файл закрыт `#![cfg(all(feature = "hardened", feature = "internals"))]` (`:49`), а используемый им хук `dbg_corrupt_freelist_head_next` скомпилирован только под `hardened` (`alloc_core_small_diag.rs:146`). Для (1)/(2) достаточно расширить гейт хука и теста на `internals` без `hardened`: на текущем дереве такой тест красный в `production`, после фикса — зелёный. Для (3) — отдельный тест с подделанным in-bounds-но-метаданным смещением, проверяющий, что карта не изменилась.

### R17-SEC-03 — own-thread Large-free принимает внутренний указатель и освобождает/кэширует всю резервацию, хотя `payload_offset` уже прочитан строкой выше

**Места.** `src/alloc_core/alloc_core/mem/mem_impl.rs:261-271` (`match kind_at(base)` → `SegmentKind::Large` → `claim_live()`), `:293` (`let stale = SegmentHeader::read_at(base)` — полная шапка, включая `payload_offset`), `:363-384` (допуск в large-cache), `:401-454` (депозит: `unregister`, зануление `magic`, `cache_consumed`), `:470-474` и `:483-487` (ветки освобождения: `unregister` + `release_consumed` + `os::release_segment(stale.reservation, stale.reservation_len)`). Между `:261` и `:487` **нет** сравнения адреса с `base.addr() + stale.payload_offset`.

**Сравнение с сиблингами (SOURCE-CONFIRMED).** Два других пути ту же проверку делают: foreign-путь — `src/registry/segment_route/directory.rs:876-881` (`matches!(entry.kind, RouteKind::Large) && addr != entry.payload` → `None`, то есть ровно точный payload-адрес); OPT-G in-place realloc — `src/alloc_core/alloc_core/mem/realloc_fastpath.rs:292-295` (`if ptr.addr() != base.addr() + payload_off { return None; }`). Достижимость own-thread-ветки: `canonical_block_of` ключуется маской сегмента, поэтому любой адрес внутри Large-сегмента резолвится в его `base` (`mem_impl.rs:34-42`), и `realloc`'s move-leg (`:693`) и `dealloc` (`:241`) попадают в ту же ветку.

**Почему P4, а не P3.** Это нарушение контракта, прямо названное в `# Safety` самого метода: «It MUST NOT be an interior pointer (`base + interior_offset`): … an interior Large free would release the whole reservation of a still-live neighbour» (`mem_impl.rs:203-209`), и README §«Honest limitations» повторяет, что отбрасывание чужих/внутренних указателей — best-effort, а не гарантия. То есть документированный остаток, не расхождение кода с контрактом. Находка в том, что **цена закрытия здесь равна одному сравнению на холодном Large-пути** (значение уже в регистре: `stale.payload_offset`), а два сиблинга его уже платят — то есть асимметрия не обоснована ни ценой, ни архитектурой.

**Рекомендация.** После `:293` (и до `claim_live`, если порядок допускает — иначе сразу после, с отказом вместо порчи) сверить `ptr.addr() == base.addr() + stale.payload_offset` и при несовпадении вернуть no-op (с инкрементом `FOREIGN_OR_UNROUTABLE_FREES`, тогда §R17-SEC-05 «layout mismatch» наконец получит реальный смысл — detected-mismatch-ветку). **Oracle:** тест, который (1) выделяет Large-блок, (2) освобождает `ptr + 64` с той же раскладкой, (3) требует, чтобы `dbg_segments_released_total` не изменился и чтобы исходный `ptr` оставался читаемым, (4) затем освобождает `ptr` корректно. На текущем дереве шаг (3) красный (сегмент освобождён/закэширован), после фикса зелёный. Тест обязан быть подпроцессным либо на отдельном `AllocCore`, потому что в случае текущего поведения он затаптывает живую резервацию.

## 3. Гипотезы оптимизации и поддерживаемости (НЕ ИЗМЕРЕНЫ)

**Ни одна цифра ниже не измерена** — в этом раунде вообще ничего не запускалось. Это не speedup, не RSS-результат, не promotion GO и не повод переоткрывать отвергнутые эксперименты. Судья обязан соблюдать правила R26-4 (config-evidence), R30-8 (path-activation oracle), entry-point и regime из CLAUDE.md.

- **H1 — цена H-1-границы на магазинном free (фикс R17-SEC-01).** Слой: `HeapCore::dealloc` / реальный `#[global_allocator]` (не `AllocCore`). Добавляется одно сравнение `off` с compile-time константой, при уже прочитанном `kind` (его читает pre-route). ГИПОТЕЗА: дельта в пределах шума iai. Oracle активации: число small-free'ов (`dbg_*` счётчика нет — понадобится существующий churn-бенч с подтверждением, что путь `small_free_guard` исполняется, например через `dbg_hardened_large_noop_count` как контроль ветвления). Kill-gate: ±10 Ir на событие, как в perf 84.
- **H2 — safe-linking для интрузивного `next` (фикс R17-SEC-02, вариант «кодирование» вместо «проверка»).** Слой: `AllocCore` free-list push/pop (`write_next`/`read_next` call-sites), но судить — на `HeapCore`/глобальном аллокаторе, потому что в `production` small-путь идёт через магазин и free-list видит только refill/flush. Стоимость в стиле glibc `PROTECT_PTR`: один XOR + один rotate на запись и на чтение. ГИПОТЕЗА: дешевле, чем маска+сравнение из `hardened`-проверки, и покрывает больше (подделка внутри того же сегмента тоже ломается). Oracle активации: счётчик pop'ов из free-list (`refill_class_bump` путь), чтобы не измерять конфигурацию, где free-list не трогается. Жертва: любой внешний инструмент, читающий free-list напрямую (в репозитории таких тестов нет — проверено grep'ом по `read_next`).
- **H3 — удаление X7-таблицы под `hardened` (вариант (а) из R17-SEC-04).** Слой: раскладка сегмента + путь выдачи. Освобождает 256 KiB payload на каждом small-сегменте под `hardened`, снимает 262 144 байтовых записи на резерв и один `fetch_add` на выдачу. ## 5. Проверено — находок нет

### 5.1 Враждебные входы, по которым дефекта не нашлось

- **Переполнения в Large-пути.** `alloc_large`: `hdr_aligned` (`alloc_core_large.rs:143-153`), `needed = hdr_aligned.checked_add(size)` (`:159-162`), округление `div_ceil(SEGMENT) * SEGMENT` (`:192-196`) — при `size <= isize::MAX` (инвариант `Layout`) не переполняется; путь promotion зовёт `alloc_large` с `new_size` до валидации `Layout` (`registry/heap_core/free/realloc.rs:589`), но переполнение там даёт `None`/0 → null, то есть отказ, а не порча. `reserve_biased` использует `checked_add`/`checked_sub` на всех четырёх шагах (`os.rs:184-206`).
- **Move-leg `realloc`.** Чтение ограничено `safe_payload_read_span` в трёх местах (`mem_impl.rs:677`, `realloc.rs:336`, `:558`) — contract-violating `old_layout` не превращается в OOB-чтение.
- **Утечка информации через `alloc_zeroed`.** Все три ветки зануляют, если блок не свежий: Large — по `is_fresh` из `alloc_large`, который под miri withheld (`alloc_core_large.rs:695-699`), и по промаху large-cache; Small под `virgin-zero-skip` — по `payload_virgin` сегмента (`alloc_core_small_impl.rs:314`, `:334`), сбрасываемому при decommit-reset (`alloc_core_small_pool/decommit.rs:277`) и выставляемому только для свежего резерва (`reserve.rs:295`, `bootstrap.rs:410`, оба `cfg!(not(miri))`); блок из магазина/free-list никогда не считается virgin (маска чистится на каждом push и pop: `dealloc_own_base.rs:435-438`, `:538-541`, `hot.rs:352-355`). Путей, где переиспользованная память уходит к вызывающему незанулённой, в прочитанном не найдено.
- **Foreign/cross-thread освобождение.** Директория ключуется адресом и отвергает Large не-точный-payload (`directory.rs:876-881`); `publish_small` передаёт только смещение, байты блока не трогаются; нулевой код класса отбрасывается до RMW (`sidecar_bitmap.rs:110-119`); владелец при reclaim проверяет класс, kind, `off >= payload_start`, кратность `block_size` и `end <= bump` (`alloc_core_small_reclaim.rs:24-45`). Асимметрии, найденные в §2, — исключительно own-thread.
- **`own_cache` (direct-mapped кэш корней).** Заполняется только выигранным `hash_find` (`segment_table_impl.rs:743-757`), очищается по значению при removal (`:866-873`); подделанный ключ не вставляется.
- **TOCTOU в `RouteDirectory::lookup`.** После `find` повторно сверяются и указатель, и `incarnation` под тем же шардовым замком, расхождение → `abort()` (`directory.rs:882-886`).

### 5.2 Ревью src-дельты к базе R16 (безопасность)

`b707d196` (perf 84) заменил на двух местах `canonical_block_of(flushed).unwrap_or_else(abort)` на `os::segment_base_of_ptr(flushed)` + `debug_assert_eq!(canonical_root_for(...))` (`dealloc_own_base.rs:482-494`, `state/tcache_flush.rs:84-95`). Разобрал обоснование: указатели в магазине попали туда через `contains_base`, Small/Primordial корни точны, Large исключён pre-route'ом — для **корректного** содержимого магазина маска и таблица дают одно и то же, и R12-02 уже применил тот же аргумент к выдаче. Что изменилось в худшем случае: если в магазин всё-таки попал адрес, чей корень таблица не подтверждает (ровно сценарий R17-SEC-01, где адрес метаданных принимается осознанно), то в release теперь нет ни abort'а, ни проверки — `clear_magazine`/`mark_magazine` пишут по маскированному адресу. То есть perf 84 не создал R17-SEC-01, но убрал последнюю инстанцию, которая в release могла бы его заметить; это аргумент за фикс SEC-01 в том же месте, а не за откат perf 84. Остальные пять коммитов дельты (R15-01, R15-02, R16-01, R16-03, item 154) по теме безопасности нейтральны: все читаются как сужение паники до abort'а, учёт счётчика, const-assert и правка прозы.
