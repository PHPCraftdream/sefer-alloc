### F1 — **P2** — the table removed every cross-referencing numeral from itself, but left the one in the prose two paragraphs below: *"the third panic site above — an unwinding `init` — is your code"* now contradicts the table's own `#` column **and** its "Whose code" column, which say row 3 is the `align_of` check belonging to **this crate**

**Where:** `crates/racy-ptr-cell/src/lib.rs:165` (`README.md:110` carries the
identical sentence). Contradicted by the table at `src/lib.rs:129-134` /
`README.md:80-85`, specifically rows `| 3 | … | this crate | …` and
`| 2 | an unwinding `init` closure | **yours** | …`.

The paragraph under the table reads (`src/lib.rs:162-168`, emphasis original):

> Only a panic whose message is a bare `&'static str` is fully covered by the
> `set_hook` mitigation. The crate's own two `assert!`s (the sentinel-collision
> check and the `align_of::<T>() >= 2` check) are of that shape and measure 0
> allocations before the hook; **the third panic site above — an unwinding
> `init` — is your code, and its message is whatever you wrote**, so it is
> covered only if you keep it a bare literal.

Against the table directly above it:

| numeral in the prose | what the table says that row is | what the prose says it is |
| --- | --- | --- |
| "the third panic site above" | `#3` = `align_of::<T>() >= 2` in `new`/`default` — **"this crate"** (two rows, both `#3`) | "an unwinding `init` … **is your code**" |

The unwinding `init` is the table's row **`#2`**, and the table marks it
`**yours**` in the same column where it marks both `#3` rows `this crate`.
Under either reading of "third" — the row numbered 3, or the third row down —
the numeral lands on a row the table explicitly attributes to the crate, while
the sentence attributes it to the reader. The two elements cannot both be
right, and they sit four lines apart.

**Provenance — this is the surviving instance of the exact class `a390bfc`
existed to remove.** `git log -S "the third panic site above"` returns a single
commit, `16213de` (task #1380, cycle-5 F1's fix). It introduced the phrase at a
time when the enumeration above it listed the unwinding `init` **second**
("that sentinel-collision `assert!`, an unwinding `init`, and the
`align_of::<T>() >= 2` check"), so the numeral was already mis-bound the day it
landed — it was merely *unfalsifiable*, because the prose enumeration was not
explicitly numbered. Cycle 6 named this exact phrase in its root-cause
diagnosis, listing it as the last of five counting numerals ("three panic
sites … all three … the two … the crate's own two … **the third panic site
above**") and stating that "every edit silently re-binds a numeral to a
different subset". `a390bfc` then replaced the enumeration with the table —
whose commit message says the four rows "contain no cross-referencing numerals,
so a future edit cannot regress this way" — but did not touch this sentence.
The claim is true of the table and false of the paragraph the table was
inserted into. Adding an explicit `#` column converted a latent ambiguity into
a checkable contradiction.

**Concrete failure scenario.** A `std` consumer with a `#[global_allocator]`
reads this section to decide which panic mitigations they owe. The whole point
of the paragraph is the split between *"messages this crate controls, which the
`set_hook` recipe fully covers"* and *"the message YOU wrote, which it does not
if you format it"*. A reader who resolves "the third panic site above" against
the table's `#` column — the only explicit numbering in the section, four lines
up — maps "is your code, and its message is whatever you wrote" onto the
`align_of` check, and by elimination reads the unwinding `init` as one of the
two crate-owned bare-literal sites that "measure 0 allocations before the hook".
That is the dangerous direction: it says a formatted `panic!`/`expect` inside
their own `init` is covered by the `set_hook` mitigation, when the measured
truth (§0.1: 2 allocations for both `panic!("… {}", x)` and `Result::expect`,
*before any hook runs*) is that it is not — and inside a `#[global_allocator]`
those 2 allocations re-enter the cell the thread already holds the sentinel on,
which is the self-deadlock this entire section exists to prevent.

**Honest severity note.** This is the weakest P2 of the seven cycles and I want
to be explicit about why it is still one. The mis-mapping above requires the
reader to override the explicit parenthetical in the same sentence ("the
sentinel-collision check and the `align_of::<T>() >= 2` check"), so a careful
reader recovers the intent; and a reader who applies the FULL recommended recipe
is covered regardless. What keeps it at P2 rather than P3 is not the hazard
width but three facts: it is a statement that is **false as written against the
adjacent table**, it is in the crate's safety contract, it **freezes on the
0.1.0 docs.rs page and the crates.io landing page at first publish**, and it is
the fifth consecutive cycle in which this one paragraph is the finding — the
last four of which were each introduced by the immediately preceding
remediation. The cost of closing it is a five-word deletion in two files.

**Suggested fix.** Delete the numeral rather than renumber it — renumbering
reintroduces exactly the cross-reference the table was built to abolish. In both
`src/lib.rs:165` and `README.md:110`:

> …are of that shape and measure 0 allocations before the hook; **an unwinding
> `init` is your code, and its message is whatever you wrote**, so it is covered
> only if you keep it a bare literal.

(Dropping "the third panic site above — " and the closing dash.) If a pointer
back to the table is wanted, "the caller's own `init` (row 2 above)" is
unambiguous — but the version with no numeral at all is the one that cannot
regress on the next edit.

### F3 — **P3** — the table's `static`-form row is labelled *"`align_of::<T>() >= 2` in `new`/`default`, `static` form"*, but `Default::default` cannot appear in a `static` at all; the route named in that row does not exist, and produces a different error (`E0015`, not `E0080`) if a reader tries it

**Where:** `crates/racy-ptr-cell/src/lib.rs:133`; `crates/racy-ptr-cell/README.md:84`.

Row 3, static form claims the site is reached "in `new`/`default`" via the
`static` form. `RacyPtrCell::default()` is a plain (non-`const`) trait method
(`src/lib.rs:836-840`), so it can never be const-evaluated. Measured, against
the packaged 0.1.0 tarball from a separate crate:

```rust
pub static CELL:  RacyPtrCell<u16> = RacyPtrCell::new();      // compiles
pub static CELL2: RacyPtrCell<u16> = RacyPtrCell::default();  // error[E0015]:
//   cannot call non-const associated function
//   `<RacyPtrCell<u16> as Default>::default` in statics
```

So the two rows do not partition the same pair of entry points: the non-const
row correctly covers `new` (in a fn body) **and** `default`; the static row can
only ever be `new`. A reader who takes the row at face value and writes the
`default()` form expects the documented const-eval diagnostic and gets an
unrelated `E0015` about constness.

This is marginal, and I file it only because the task asked for each of the four
rows to be checked independently against the code — this is what a per-row check
turns up. It is also the only inaccuracy I found *inside* the table.

**Suggested fix.** Two words in each file:
`| 3 | `align_of::<T>() >= 2` in `new`, `static` form | …` (drop `/default` on
the static row only; the non-const row keeps `new`/`default` and is correct as
written).
