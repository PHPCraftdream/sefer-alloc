**F1 — семантика `SIZE2CLASS[k]` сформулирована в ЧЕТЫРЁХ местах; в `segment_layout.rs` — с рождения off-by-one, в шиме — без top-bucket-исключения, которое крейт добавил ещё в run-2 F8.**
Один факт — что лежит в `SIZE2CLASS[k]` — задокументирован на четырёх поверхностях:
1. Крейт, `lib.rs:414–421`: «`size2class[k]` is the smallest class whose `block_size >= (k + 1) * min_block` -- EXCEPT the top bucket `L - 1` … clamped to `table[N - 1]`» — **верно и полно** (EXCEPT-клауза добавлена фиксом run-2 F8, `15888f2`).
2. Корневой тест `tests/size_classes_lookup.rs:91–93`: «the class stored must cover the *largest* size in that bucket, i.e. need = min((k+1)*MIN_BLOCK, SMALL_MAX)» — **верно и полно** (с клампом).
3. Шим `src/alloc_core/size_classes.rs:170–171`: «`SIZE2CLASS[k]` is the index of the smallest class whose `block_size >= (k + 1) * MIN_BLOCK`» — **формула верна, но без EXCEPT-клаузы**: для k = L−1 класса с `block_size >= SMALL_MAX + MIN_BLOCK` не существует, а entry содержит индекс последнего класса (кламп) — т.е. для верхнего bucket'а утверждение шима невыполнимо и не описывает фактическое содержимое. Ровно этот дефект run-2 F8 нашёл и закрыл на КРЕЙТОВОЙ поверхности; копия в шиме синхронизирована не была (шим читался «целиком» в runs 4–8, эта строка ни разу не сверялась с пост-F8 формулировкой — проверено grep'ом отчётов).
4. `src/alloc_core/segment_layout.rs:66–67` (публичный rustdoc `SegmentLayout::SIZE2CLASS`, реэкспорт в `src/lib.rs`): «`SIZE2CLASS[k]` is the smallest class index whose block size **covers `k * MIN_BLOCK` bytes**» — **неверно при любом прочтении, off-by-one**. Контрпример на дефолтной схеме: `SIZE2CLASS[1] = 1` (класс 32 B — наименьший с `block >= 2·16`), но «smallest class covering 16 bytes» — это класс 0 (блок 16 ≥ 16); а при прочтении «класс, обслуживающий запрос в 16 B» — такой запрос индексирует bucket 0, не bucket 1 (`(16−1)>>4 = 0`). Верная формула — `(k + 1) * MIN_BLOCK`, как в трёх остальных местах. Проверено git: формулировка родилась вместе со строкой (`143b8be`, Phase 13.1) при тех же семантиках — неверна с рождения, не дрейф. Grep всех одиннадцати предыдущих отчётов («covers»): не адъюдицировалась ни разу.
Почему P4, не выше: обе неточные поверхности — root-крейт (sefer-alloc), не публикуемый `size-classes`; поведения не касаются (фактическое содержимое таблицы запинено тестами `size2class_table_matches_linear_scan_for_every_bucket` и `sefer_size2class_matches_scan_for_every_bucket`); релиз крейта не блокируют и не сопровождают.
Фикс: в `segment_layout.rs:67` — «…whose block size covers every size in bucket `k`, i.e. `block_size >= (k + 1) * MIN_BLOCK`»; в шиме `:171` — добавить короткое «(top bucket clamps to the last class; see the crate's `build_size2class` doc)».

**F2 — `build_table` `# Panics`: паренфетика достижимости overflow-паники называет не те ручки, противореча собственному panic-сообщению той же функции.**
Где: `lib.rs:204–205`: «if the geometric progression's advance step overflows `usize` **(only reachable with an extreme `min_block`/`growth` combination)**».
Факт: все три `expect`-сообщения этого пути (`lib.rs:342/346/365`) говорят «geometric progression overflows usize -- **reduce geo_count/growth**» — и именно `geo_count` в паренфетике отсутствует. Достижимость через одну лишь `geo_count` при совершенно ординарных `min_block`/`growth` пересчитана вручную: `min_block = 16`, `growth = (5, 4)` (дефолтная SEFER-пара), `geo_count ≈ 182` — накопленный `cur ≈ 16·1.25^k` превышает `usize::MAX / 5` около k ≈ 180, и `checked_mul` паникует; это внутри собственного конверта крейта (N < 256 пинится `build_size2class`). Т.е. «extreme `min_block`/`growth` combination» — атрибуция по неверной оси: экстремальность может целиком жить в `geo_count` (сам по себе запрошенный ряд при этом абсурден — верхний класс за пределами usize — но паренфетика утверждает не «абсурдная схема», а конкретно «extreme min_block/growth»). Родилась в `b970f52` (task #1418, review-1 P2-2); grep отчётов («extreme»): не адъюдицировалась. Тестовое покрытие паники идёт через маршрут «extreme min_block» (`1 << (usize::BITS-1)`), что и замаскировало пропущенную ось.
