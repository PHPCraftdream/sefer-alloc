# План: призрачные проверки, смысловые линтеры под каждое место, линтер сообщений коммитов

Статус: **план принят** (2026-10-27), G0 выполнен (инвентарь и каталог), дальше G1. Пункт в индексе
корректности — `docs/CORRECTNESS_OPEN_ITEMS.md` item 256.

## 0. Зачем

Протоколы между потоками в sefer проверяются loom-моделями. Сегодня
бо́льшая часть этих моделей — **теневые**: тест заново пишет протокол на
`loom::sync::atomic` и в комментарии обещает «production orderings are
mirrored exactly». Механически теневую модель с прод-кодом не связывает
ничего: если в `src/` ослабить `Release` до `Relaxed`, теневая модель
останется зелёной, потому что проверяет копию.

Это не гипотеза. В реестре доказательств `docs/evidence/registry.csv` две
строки уже фиксируют такой провал:

- **R4b-13 INCONCLUSIVE** — мутант L1 (`Release → Relaxed` в Drop-CAS
  `HeapLease`) **не пойман** моделью `tests/loom_r11_ph4b_publish_recycle_drain.rs`;
- **R4b-14 INCONCLUSIVE** — мутант L2 (ослабленный `Acquire` claim-CAS)
  **не пойман** той же моделью.

Часть мест закрыта текстовыми «пинами» исходника — тест через
`include_str!` ищет строку в `src/` (`tests/r11_ph4a_drop_ordering_pinned.rs`,
`r11_ph4b_teardown_ordering_pinned.rs`, `r11_ph4b_local_no_drop_pinned.rs`,
`r11_ph5b_c5_sidecar_ordering_pinned.rs`). Они ловят только ту форму
кода, которую ждут: переименование, перенос в helper или второй вызов
проходят мимо.

Цель плана: у каждого протокола три независимых слоя.

1. **Призрачные проверки (ghost).** Реальный прод-код исполняется под
   loom/miri/kani, а в нём стоят проверки, которые компилируются только в
   проверочных сборках (`cfg(any(loom, miri, kani, sefer_ghost))`) и
   исчезают из прод-сборки целиком. Они превращают нарушение протокола в
   падение там, где модель-чекер перебирает чередования.
2. **Смысловой линтер под каждое место.** Для каждого места, которое
   держит инвариант, своё правило, закрепляющее именно этот инвариант:
   ordering конкретной операции, порядок операций, проверку перед
   действием, единственный путь вызова, наличие ghost-проверки. Линтер
   защищает то, что ghost-проверки не видят: прод-сборку без них.
3. **Линтер сообщений коммитов.** Коммит, задевший код под правилом, обязан
   нести в сообщении обоснование по каждому затронутому правилу: что
   изменилось, почему инвариант держится, каким loom-тестом и
   мутант-фикстурой это закрыто.

Каждое правило и каждая ghost-проверка доказывают, что не пусты:
мутант-фикстура обязана сделать красным **и** линтер, **и** loom (или
miri/kani). Если краснеет только один из двух, правило или модель не
совпадают со смыслом — это дефект плана, а не допуск.

## 1. Границы

Не цели:

- поведение прод-кода не меняется; прод-сборка обязана остаться
  машинно-идентичной (§6);
- существующие проверки не ослабляются и не удаляются: `hardened`,
  `debug_assert!`, `fatal`, текстовые пины, теневые модели остаются, пока
  новый слой не покроет их **строго шире** — с теми же мутантами, которые
  краснеют в новом слое;
- новые атомики и новый `unsafe` в прод-коде не появляются; призрачный код
  без `unsafe`.

## 3. Призрачные проверки

### 3.1 Механизм

- Модуль `src/ghost/` (новый, без `unsafe`; седьмая запись корня `src/` при лимите 7) и `cfg` `sefer_ghost`,
  объявленный в `[lints.rust] unexpected_cfgs`. Проверочный режим:
  `cfg(any(loom, miri, kani, sefer_ghost))`; дальше — «ghost-сборка».
- Макросы:
  - `ghost_assert!(<rule-id>, cond, "...")` — проверка в точке;
  - `ghost_event!(<rule-id>, ...)` — событие в призрачный журнал для
    постусловий уровня протокола (например, «каждое опубликованное
    смещение поглощено ровно один раз»), которые проверяет харнесс в
    конце итерации модели.
  В прод-сборке оба раскрываются в пустоту: аргументы не вычисляются.
- **Призрачное состояние живёт вне прод-структур** — в боковых таблицах
  `ghost::Shadow`, ключ — адрес (например, «сколько pin держит этот
  `Entry`», «какой поток владеет арендой слота»). Поля в прод-структурах
  запрещены: `HeapCore` упирается в пин `size_of <= 9216`,
  `SegmentHeader` — 144 байта; под ghost-сборкой раскладка обязана
  совпадать с прод-сборкой.
- **Призрачный код не добавляет синхронизации.** Боковые таблицы — на
  `std::sync` (не loom), поэтому loom не видит в них рёбер
  happens-before и не может «спрятать» гонку за призрачным мьютексом.
  Призрачный код только читает прод-состояние; запись в прод-данные из
  ghost-макроса запрещена (правило R9).
- Под kani `ghost_assert!` становится `kani::assert!`, то есть
  обязательством доказательства; боковые таблицы под kani не используются —
  только проверки над локальными значениями гарнесса. Под miri — обычный
  `assert!` на реальном исполнении.

### 3.2 Реальный исходник под loom

Шаблон уже есть: `loom_sidecar_bitmap_actual.rs`, `loom_b4_r1_pin_cache.rs`,
`loom_b4_scan_skip_empty_publish.rs` включают прод-файлы через `#[path]`,
прод-файл берёт атомики из `super`, корень теста подставляет атомики loom.
Перевод теневой модели (класс S) — по этому шаблону. Где нужна уменьшенная
геометрия (меньше слов, слотов), её задаёт `cfg(loom)`-константа — это
сам по себе двойник, поэтому он попадает под правило R7.

Где реальный код под loom не собирается (например, `HeapRegistry` целиком
из-за статической инициализации), теневая модель остаётся, но правило R8
связывает её с прод-кодом: каждая её константа ordering и каждый
шаг протокола помечены `// ghost-bind: <rule-id>`, и линтер сверяет их с
прод-местом.

### 3.3 Что именно проверять (по протоколам — заполняется в G0)

Примеры, каким должен быть уровень смысла:

- P5: публикация идёт только при удерживаемом pin; sidecar освобождается
  только на последней ссылке; `lookup` после `remove` не выдаёт pin.
- P1/P3: метаданные аренды мутирует один поток; LIVE→FREE видна
  следующему claimant только после всех записей владельца; проигравший
  CAS не делает drain и drop.
- P12: склад слота пуст в момент LIVE→FREE; к складу обращается только
  текущий владелец аренды.
- P7/P10: каждое опубликованное смещение поглощено ровно один раз;
  кредиты меняет только владелец.

## 4. Смысловой линтер

### 4.1 Инструмент

`crates/ghost-lint` — инструмент в workspace (не публикуется, в пакет
`sefer-alloc` не входит). Разбор — `syn` с `full` и `visit`; `syn 2.0.118`
и `proc-macro2 1.0.106` уже есть в `Cargo.lock` транзитивно, новых версий
не будет, но это новая **прямая** зависимость — нужно согласие владельца
(§10). Запасной вариант без зависимости — расширить стиль
`scripts/verify-*.mjs`; он слабее (текст, не AST) и годится только если
владелец откажет.

Каталог правил — `docs/verification/ghost-rules.json`: на каждое правило
id, протокол, файл, путь функции, вид правила (§4.2), параметры, термины
инварианта (§5.2), связанные ghost-точки, loom/miri/kani-тесты,
мутант-фикстуры, строки реестра доказательств.

Режимы:

- `ghost-lint check` — все правила по дереву, красный при нарушении;
- `ghost-lint selftest` — каждая фикстура: «ok» проходит, каждый мутант
  отвергнут **ровно** ожидаемым правилом;
- `ghost-lint spans --file <path>` — диапазоны строк защищённых мест (для
  линтера коммитов, §5); содержимое файла можно подать со stdin, чтобы
  считать диапазоны на любом коммите без checkout.

### 4.2 Виды правил

| Вид | Что закрепляет | Пример |
|---|---|---|
| R1 ordering | ordering конкретной атомарной операции (success и failure у CAS) в конкретной функции | `Drop for HeapLease`: LIVE→FREE CAS — `Release`, failure-ordering — как в таблице |
| R2 inventory | множество атомарных операций функции равно таблице; новая операция — красный | новый `fetch_or` в `publish_small_borrowed` без обновления каталога |
| R3 sequence | A раньше B на каждом пути (A в доминирующей позиции: раньше в том же блоке или в объемлющем) | `trim_for_recycle`: drain склада раньше Release LIVE→FREE |
| R4 guard | действие только внутри ветки, условие которой совпадает с шаблоном | освобождение sidecar только под `fetch_sub(..) == 1` |
| R5 sole path | функция или запись поля встречается только в перечисленных функциях | публикация удалённого free — только через `RoutePin::publish_*`; поля склада — только в функциях владельца аренды |
| R6 ghost coverage | у каждого правила с `ghost: true` есть `ghost_assert!`/`ghost_event!` с этим id в названной функции | убрали ghost-проверку при рефакторинге — красный |
| R7 twin | `cfg(loom)`- и `cfg(not(loom))`-двойники одного элемента дают одинаковую нормализованную последовательность атомарных операций и ordering; разрешённые отличия — только из явного списка с причиной | `loom_shim::OncePtrCell` против `once_ptr_cell::OncePtrCell`; двойники в `tagged-index-stack` |
| R8 model bind | константы и шаги теневой модели с пометкой `ghost-bind` равны прод-значениям правил R1/R3 | `DROP_ORDERING` в `loom_r11_ph4a_heap_lease.rs` равен ordering в `claim.rs` |
| R9 hygiene | ghost-элементы только под ghost-`cfg`; нет ghost-полей в структурах с пином раскладки; аргументы ghost-макросов не пишут в прод-данные | ghost-поле в `HeapCore` — красный |

Ограничение `syn`: типов нет, поэтому правила привязаны к путям функций,
именам полей-получателей и шаблонам выражений. Неоднозначность (два
метода с одним именем) — ошибка каталога, а не молчаливое совпадение.

### 4.3 Доказательство, что правило не пусто

- `tests/ghost_lint_fixtures/<rule-id>/`: `ok.rs` и `mutant_*.rs` —
  минимальные выдержки реального кода; `selftest` требует, чтобы каждый
  мутант был отвергнут своим правилом.
- Двойное подтверждение на реальном коде: `scripts/ghost_mutants.mjs`
  применяет патчи-мутанты к копии `src/` и требует красного **и** у
  `ghost-lint check`, **и** у связанного loom/miri/kani-теста. Это дорого
  (loom), поэтому идёт по расписанию (nightly) и при изменении правила.
- Текстовые пины удаляются только после того, как их же мутанты
  краснеют в новом правиле; это фиксируется в коммите удаления.

## 5. Линтер сообщений коммитов

### 5.1 Что требуется

`scripts/verify-invariant-trailers.mjs` (по образцу
`scripts/verify-commit-prefixes.mjs`) проходит по коммитам PR
(`base..head`, merge-коммиты пропускаются). Для каждого коммита:

1. По `git diff -U0 <c>^ <c>` и `ghost-lint spans` на дереве этого коммита
   определяет затронутые правила: изменённые строки пересекают диапазон
   защищённого места, либо изменён сам каталог правил, либо фикстура.
2. Требует трейлер на **каждое** затронутое правило:

```text
Invariant-Check: route-pin/last-ref-free
  Change: fetch_sub перенесён в EntryHandle::release
  Why: освобождение sidecar по-прежнему только в ветке fetch_sub(1, AcqRel) == 1,
    ordering AcqRel не менялся, других путей освобождения нет (R5)
  Covered-by: tests/loom_route_pin_unlink.rs, ghost:route-pin/last-ref-free,
    fixture:tests/ghost_lint_fixtures/route-pin/last-ref-free/mutant_free_before_check.rs
```

Трейлер пишет модель (агент), которая меняла код. Это её рассуждение о
том, почему инвариант держится, и оно же — точка проверки для ревью.

### 5.2 Проверки трейлера (максимально близко к смыслу)

- перечислены все затронутые правила; лишние — предупреждение;
- `Why` не пустой, не короче порога (120 символов) и не копия другого
  трейлера;
- `Why` называет **термины инварианта** из каталога (у правила
  `route-pin/last-ref-free` — например «последн* ссылк*», «fetch_sub»,
  «AcqRel»): шаблонная фраза без них не проходит;
- всё из `Covered-by` существует в дереве этого коммита (тест, ghost-id в
  коде, фикстура);
- если изменились параметры правила (ordering, порядок, guard) — в том же
  коммите изменены каталог правил и связанная модель или харнесс, а не
  только сообщение;
- сам линтер закрыт мутантами: коммит без трейлера, трейлер с чужим id,
  ссылка на несуществующий тест, `Why` без терминов — обязаны дать
  красный.

Ограничение: скрипт проверяет, что обоснование есть, привязано к
правильному правилу, говорит в терминах инварианта и ссылается на
реальные доказательства. Истинность рассуждения подтверждают loom/miri/kani
и мутанты, на которые трейлер обязан сослаться; CI в том же PR запускает
именно эти тесты (§7).

## 6. Нулевая цена в прод-сборке — измеримо

На каждом PR, добавляющем ghost-код:

- нормализованная дизассемблировка `.text` прод-бинаря
  (`--features production`, release, те же `RUSTFLAGS`) до и после
  совпадает (адреса и смещения вырезаны);
- `npm run iai`: Δ Ir = 0 на всём наборе;
- пины раскладки (`HeapCore <= 9216`, `SegmentHeader == 144` и др.)
  компилируются и в прод-, и в ghost-сборке без изменений.

Нарушение любого пункта — PR не сливается.
