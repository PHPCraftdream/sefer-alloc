# LM-1 — loss map against mimalloc on `main` after WG-LEAF (measurement only, `bench`)

**Class:** measurement only. No runtime change; no `production` composition change. The
tables below are generated by `scripts/lm1_report.mjs` from the raw data in `docs/perf/lm1/`;
the prose cites them and adds nothing that is not in them.

## 0. Summary

1. **Windows judge (`g1_wild_judge`, 12 blocks × minimum of 3 repeats): sefer is slower than mimalloc
   in all 7 scenarios.** Growth scenarios (grow64, grow1k, regrow, growmix) are known and have owners
   (AO-1 PR #153 on hold, the release policy `Retain`, WG-MLP). `wild`, `large` and `phase` are the
   part of the map that had no attribution; section 2 says what the first attribution attempt could
   and could not show.
2. **`bench:table` (two paired sets): one loss in both sets** — warm bulk burst 16 B. Everything else
   wins in both sets except churn + write 16 B, which is split between the sets (class MIXED).
3. **MT (`malloc_macro`, 6 runs, medians): larson T=1, mstress T=1 and mstress T=4 are losses**;
   larson T=2/T=4 are wins, mstress T=2 is parity.
4. **Release attribution on `wild`/`phase`/`large` is inconclusive:** the `sefer_pool` arm changes
   nothing measurable there, but its path-activation oracle (`seg_released`) shows the arm did **not**
   remove the releases in these scenarios (most likely Large-span releases — the pool holds empty small
   segments only — but this report did not count releases by kind). So "release in `free` does not explain the gap" is **not** a conclusion of this
   report — the lever used cannot reach these releases.

## 1. What was measured

- **Source identity (taken before the measurement):** `main` @ `c495edc9` (merge of PR #155), tree
  `b7a543603713304adfe954ba6677f58df59dcd79`; builds are `--release`, judge with features
  `production internals`, `malloc_macro` with `production`; `rustc 1.97.0`; the binaries' SHA-256 are
  in `docs/perf/lm1/ident.txt`. The `bench:table` manifests (`bt_s1.manifest.json`,
  `bt_s2.manifest.json`) record commit, clean tree, features, binary hash and machine.
- **Machine:** the one in the `bench:table` manifests (11th Gen Intel Core i7-11800H, Windows 10 Pro
  x64). It is shared; each campaign ran with nothing else started by this work.
- **Entry points:** the judge reaches the allocator under test as a static through `#[inline(never)]`
  shims at the `__rust_alloc` boundary (header of `examples/g1_wild_judge.rs`), one arm per process, the
  process global allocator stays `System`. `bench:table` and `malloc_macro` are the repository's own
  harnesses (`examples/bench_table_paired.rs`, `examples/malloc_macro.rs` over `malloc-bench-rs`); they
  are used as they are.
- **Judge statistic:** per block and arm the minimum of `ns_per_op` over 3 back-to-back repeats; per
  block `d = ln(sefer / mi)`; the cell is `exp(mean d)` with a two-sided 95 % t-interval (df = 11,
  quantile 2.201). Scenario order is shuffled per block (fixed seed), the arm order alternates by block
  parity. Both arms run the same op sequence (the script asserts equal checksums).
- **Classes (map conventions, not merge gates):** judge cell LOSS if the interval's lower bound is above
  1 and the mean is at least 1.03, WIN if the upper bound is below 1, otherwise PARITY;
  `bench:table` and MT cells LOSS if the sefer / mi time ratio is at least 1.03 (in both sets for
  `bench:table`), WIN if at most 1/1.03, MIXED if only one of the two sets reaches the loss line.
- **`bench:table`:** `scripts/bench-table-paired.mjs --rounds 200 --processes 3`, run twice back to back
  on the same build (sets s1, s2); the ratio of a cell is read from the printed "× slower/faster" and
  checked by the script against the printed ns/pair columns.
- **MT ratio:** `mi Mops / sefer Mops` (median over runs), i.e. the time ratio sefer / mi.
