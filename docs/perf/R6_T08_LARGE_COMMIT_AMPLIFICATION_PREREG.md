# R6-T08 PREREGISTRATION — Large commit amplification (`exact-span-large`)

Status: **preregistered before measurement**. Every numeric field below is a
prediction or a threshold; actual values are **to be filled by the CI run**
(scripts/r20_r6_t08_large_commit_run.mjs) and are never hand-entered — the
tables in the eventual report are generated by the runner, not written by a
human (CLAUDE.md R31 rules).

## 1. Hypothesis

Without `exact-span-large`, every Large allocation rounds its physical span up
to a whole number of 4 MiB `SEGMENT`s (`src/alloc_core/platform/os.rs:92`,
`pub(crate) const SEGMENT: usize = 1 << 22`; the rounding lives in
`os::Segment::reserve` / the feature-OFF arm of
`src/alloc_core/large/alloc_core_large.rs:248-260`). So N live 260 KiB Large
objects reserve+commit **N × 4 MiB** — an amplification of ~16× over the
requested bytes. On Windows the span is committed eagerly — reserve then
`MEM_COMMIT` over the whole span, so the commit happens at reservation time,
not on first touch — but NOT in one `VirtualAlloc` call for Large:
`Segment::reserve` calls `vmem::reserve_aligned(usable, SEGMENT)` with a 4 MiB
alignment (`src/alloc_core/platform/os.rs:224-294`), which takes the two-call
path in `crates/aligned-vmem/src/os/windows.rs` (first
`VirtualAlloc(.., MEM_RESERVE, ..)` of the aligned address space, then
`VirtualAlloc(.., MEM_COMMIT, ..)` over the span), so commit charge equals the
reserved span immediately.

With `exact-span-large` each Large span is page-rounded only
(`src/alloc_core/large/alloc_core_large.rs:268-279`), so a 260 KiB request
commits ~264 KiB (page-exact `needed = hdr_aligned + size` rounded to the
runtime page size), so the reserved span (Windows: commit charge) scales
~16× lower at equal live object count. RSS is not part of the hypothesis:
the probe touches only the requested bytes, so the untouched rounded tail
need not be resident in either arm (§5).

The feature changes ONLY span sizing. The 4095-simultaneously-live Large
objects-per-heap cap (SegmentTable slots, slot 0 reserved; past it `alloc`
returns null → `handle_alloc_error`) and per-alloc latency are predicted
unchanged.

## 2. Cell

**"N × 260 KiB live"** with N ∈ {16, 64, 256}. One fresh `AllocCore` per N,
allocation sizes `260 * 1024` bytes, align 8 (same shape as
`examples/r12_3_exact_span_measure.rs`).

## 3. Axes and mode rule (R31-1)

Axes: reserved+committed memory and RSS deltas via `proc_memstat::snapshot()`.
The reserved axis is `charged_or_reserved_bytes()`, which is a true commit
charge on Windows but a VA reservation size on Linux/macOS (the r20-gates
workflow runs ubuntu-24.04) — it is reported as `reserved_delta_KiB` /
`reserved_per_alloc_KiB`. The SEGMENT-rounding amplification is visible on
BOTH readings, but only Windows gives the literal commit-limit figure. RSS is
a SECONDARY, informational axis only (see §5): the probe write-touches the
full requested 260 KiB per allocation, but committed-but-untouched tail pages
need not be resident, so a strict RSS inequality is not a valid discriminator.
Plus the allocator-side oracle (§4) and per-alloc median wall-clock
(`std::time::Instant`, single-threaded).

R31-1 (cost AND benefit in ONE mode): each arm is measured in a single
feature mode, and the probe reports per-alloc wall-clock in the SAME run, so
the feature's own latency cost is visible next to its benefit.

Arms (same probe example, two builds):

- **Arm A** = `production internals`
- **Arm B** = `production internals,exact-span-large`

`internals` is in BOTH arms (it gates the `dbg_*` oracle hooks) and changes
nothing measured — the arm's identity is exact-span-large on/off.

## 4. Activation oracle (derived from allocator state, NOT proc-memstat alone)

The oracle must prove WHICH code path ran, from allocator state:

| Hook | Where | Arm A expected | Arm B expected |
|---|---|---|---|
| `AllocCore::dbg_span_usable_of(ptr)` on one live block (`internals`-gated) | `src/alloc_core/alloc_core/alloc_core_core_diag/header_diag.rs:225` | `4194304` (whole SEGMENT) | `262144 < v <= 278528` (page-rounded `hdr_aligned + 266240`; ~264-272 KiB) |
| `AllocCore::dbg_segments_reserved_total()` delta across the N allocs | `src/alloc_core/alloc_core/alloc_core_core_diag/totals.rs:38` (counter `SEGMENTS_RESERVED_TOTAL`, `src/alloc_core/platform/os.rs:52`, bumped in `os.rs:216/234/292/...`) | `== N` (one segment per alloc) | `== N` (still one span per alloc — count is unchanged; only its SIZE differs) |

`dbg_span_usable_of` is the discriminating hook: it reads the segment
header's stored physical `span_usable`, which is exactly what the two
`cfg` arms of `alloc_core_large.rs` compute. Arm A must show a whole multiple
of `SEGMENT` (4194304) and arm B must show a sub-SEGMENT page-rounded value;
either alone is insufficient evidence.

## 5. GO/NO-GO criterion (pre-registered)

**GO** for promoting `exact-span-large` evaluation to a code-change task iff
ALL of:

- (a) arm B `reserved_delta_KiB / (N × 260 KiB)` per cell is ≥ 8× LOWER than
  arm A at every N ∈ {16, 64, 256} (i.e. amplif_B ≤ amplif_A / 8);
- (c) the oracle confirms the exact-span branch taken in B and ONLY in B:
  `span_usable_bytes` is sub-SEGMENT (≤ 278528) in B and == 4194304 in A,
  with `segments_reserved_delta == N` in both arms;
- (d) per-alloc latency in B is within 1.5× of A at every N
  (`alloc_ns_median(B) <= 1.5 × alloc_ns_median(A)`).

RSS is NOT a GO condition: the PRIMARY discriminating axis is the reserved
span (`reserved_delta_KiB`) plus the allocator-side oracle `span_usable_of`.
Because committed-but-untouched pages need not be resident, arm A's rounded-up
tail (~3.75 MiB per object) may never appear in RSS even with full-request
touching — `rss_delta_KiB` is reported per cell for information only and is
never gated on.

Otherwise **NO-GO** (document-only outcome).

**Scope guard:** the run does NOT change allocator code. A GO only opens a
separate code-change task; this gate itself edits nothing under `src/`.

## 6. Reproduction

```
cargo run --release --example r6_t08_large_commit_probe --features "production internals"
cargo run --release --example r6_t08_large_commit_probe --features "production internals,exact-span-large"
```

(Or via the runner: `node scripts/r20_r6_t08_large_commit_run.mjs --measure`.)

### Summary CSV schema (runner-generated)

Header (one row per arm × N):

```
arm,mode,N,reserved_delta_KiB,reserved_per_alloc_KiB,amplif_x,span_usable_bytes,segments_reserved_delta,rss_delta_KiB,alloc_ns_median
```

`arm` is `A` or `B`; `mode` is `production` or
`production+exact-span-large` (the literal feature
comma is replaced by `+` so the field needs no CSV quoting).

### Immutable source identity

The runner records `git rev-parse HEAD` and a full clean-tree check
(`git status --porcelain`) into `manifest.json` BEFORE any measurement, and
refuses to run on a dirty tree. Artifacts go to
`target/r20_r6_t08_large_commit` (a `target/` path is used instead of a
`docs/perf/R20_*` path because the committed `.github/gate-run.json`
`outDir` regex only allows `docs/perf/R20_*` or `target/r20*` names; the
simplest compliant choice is the `target/` form, keeping `docs/perf/` for the
prereg and the eventual human-readable report only).

### Report tables

All tables in the eventual report are generated by the runner
(`summary.csv`, `verdict.txt`) from the same parsed numbers — never
hand-written.
