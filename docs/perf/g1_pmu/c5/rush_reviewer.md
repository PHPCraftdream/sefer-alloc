## Вывод

**Первый кандидат на отгрузку — A: ленивый бюджетированный depot только для расширения класса 64 Б, с сохранением K5 для остальных классов.** Это наиболее прямой способ сохранить механизм P0 с минимальным изменением протоколов. **B — не эквивалент P0:** он сохраняет переходы состояний, credits и поиск свободных блоков; большую часть выигрыша ещё надо доказать.

При этом **P0 сам не достиг паритета bulk16k с mimalloc: 0.873**. Поэтому «сохранить большую часть P0» и «обязательно обогнать mimalloc» — разные требования. Ни один рассматриваемый вариант пока не имеет доказанного пути ко второму.

Ссылки ниже относительно `g1-p0`; префиксы `g1-k5/`, `g1-pmu/`, `g1-p0-meas/` обозначают соответствующие соседние деревья.

## MEASURED / OBSERVED

- **MEASURED, предоставленные результаты:** P0 существенно ускорил bulk16k; callgrind 85.7M → 55.4M Ir и исчезновение flush/drain из топа подтверждают активацию задуманного рычага. Предрегистрация описывает именно потолок, не разрешение на отгрузку: `g1-p0-meas/docs/perf/b4_ablate/G1_P0_PREREG.md:18–43`.
- **Важная поправка к единицам:** анализатор выводит **100 × разность логарифмов времени**, не обычный процент сокращения времени: `g1-p0-meas/scripts/b4_ablate_vs_null.mjs:119–136`. Поэтому −56.13 означает отношение времени **exp(−0.5613) ≈ 0.5705**, то есть **−42.95% времени**, или 1.75×. Аналогично churn64 ≈ −5.73%, bulk64 ≈ −2.72%.

- **OBSERVED:** flush пишет `next` в тело и FREE в metadata, затем снимает credits; drain читает зависимую цепочку и возвращает credits: `src/alloc_core/small/alloc_core_small_magazine.rs:743–795`; `src/alloc_core/small/alloc_core_small/alloc_core_small_impl.rs:562–639`.

**Новых измерений нет. Ниже — ESTIMATE и предлагаемые критерии.**

## A. Большой depot с бюджетом — первый выбор

**Конкретная конфигурация:**

- Существующий K5 оставить; расширять **только 64 Б**. Для остальных классов доказательств пользы большой ёмкости нет.
- Общий лимит паркованных блоков **1.25 МиБ/поток = 1 310 720 Б**, включая K5; class-64 cap — 1024 магазина. Это покрывает весь P0 с небольшим запасом.
- Добавочную pointer storage выделять лениво, например **чанками по 4 КиБ = 32 магазина**. При полном расширении — около 128 КиБ плюс небольшой каталог; неиспользованный registry slot получает только дескриптор, не 128 КиБ.
- Выделение через внутренний нерекурсивный OS-backed seam, не через этот же `GlobalAlloc`; отказ выделения — обычный старый flush, без потери магазина.
- Trim: полный сброс при явном trim и recycle; освобождение пустых pointer-чанков. Предлагаемый decay добавочной ёмкости: после **1 с без её использования** сбрасывать до K5, проверяя время только на редких maintenance/overflow/refill-событиях. Не читать часы на каждом free.

**ESTIMATE:** на непрерывном bulk16k — **85–100% сокращения времени P0**, то есть примерно −36…−43% относительно K5. Это гипотеза близости маршрутов, не линейная зависимость выигрыша от бюджета. Половинный бюджет вовсе не гарантирует половину выигрыша.

**RSS:** до ~1.25 МиБ паркованных блоков плюс ~128 КиБ добавочных указателей на активный поток; для 64 потоков — порядка 80+8 МиБ номинально. **Это не верхняя граница RSS:** MAG удерживает credits, а несколько блоков могут закрепить несколько почти пустых сегментов. Полный flush допускает release/pool только после возврата блоков: `src/registry/heap_core/state/tcache_flush.rs:73–118`.

**Критическая оговорка:** opportunistic decay не освобождает память полностью уснувшего потока. Без внешнего maintenance/явного trim обещать «освобождение через секунду простоя» нельзя.

**Инварианты / размер:** И1–И5 и remote publication не меняются; MAG остаётся MAG. Добавляются бюджетный учёт, владение чанками, OOM rollback и очистка при handoff. P12 должен охватывать и динамическую storage. Объём — **средний**, ориентировочно несколько сотен строк реализации плюс lifecycle-проверки.

## B. FREE-байты + summary по чанкам — разумный второй путь, не бесплатный P0

Горячий magazine и небольшой K5 оставить. Overflow переводит блоки в FREE **без `write_next`**; refill ищет точный `encode(class, FREE)` по summary.

Практичная исходная геометрия: **4 КиБ payload на чанк → 256 state bytes для сканирования**; class-specific summary плюс курсор. Один общий бит «есть какой-то FREE» недостаточен для смешанных классов: возможны повторные безрезультатные сканы.

- На сегмент 4 МиБ — 1024 чанка; summary для 18 классов занимает **2304 Б битов**, для всех классов — больше, плюс курсоры/выравнивание.
- После извлечения неполного набора курсор сохраняется; сбрасывать summary можно только после подтверждения отсутствия FREE нужного класса.
- Ограничить работу одного refill, допускать короткий refill; иначе sparse/mixed сегменты создадут длинный хвост задержки.

**ESTIMATE:** **40–75% сокращения времени P0** на плотном class-64 bulk, примерно −17…−32% против K5; на разреженном смешанном сегменте выигрыш может исчезнуть. Здесь остаются state transitions, credits, directory maintenance и просмотр байтов. Старый прогноз (d) не является новым доказательством: `g1-pmu/docs/perf/g1_pmu/c4/oh.md:45–48`.

**RSS:** нет неограниченной очереди указателей и дополнительного MAG-retention. FREE снимает credits, позволяя вернуть пустой сегмент. Но **«без бюджета» не значит «без удержания»**: частично живые сегменты, существующий pool и metadata остаются. Дополнительная summary требует изменения geometry; существующие 256 КиБ state bytes уже оплачены: `src/alloc_core/segment/bitmap/state_byte.rs:89–91`.

**Инварианты / размер:** И1 сохраняется точным сопоставлением полного байта; **И4 надо переопределить** с «на bin/list» на «в свободном множестве». Необходимо согласованно заменить всех производителей/потребителей FREE, directory emptiness, reset и sidecar reclaim. Объём — **большой, сквозной**, не локальная оптимизация refill.

## C. Сделать перенос дешёвым и body-write-free

**Одного удаления `write_next` недостаточно:** исчезнет способ перечисления FREE. Drain уже не пишет тела, он их читает. Нужен новый индекс.

Лучший отдельный вариант для сравнения с B — **segment-local чанковый стек `u32` offsets**:

- flush добавляет offsets, выставляет FREE, снимает credits;
- drain читает компактный массив, восстанавливает указатели от canonical root, выставляет MAG/LIVE;
- magazine остаётся впереди: не вводить прямой free текущего блока с возможностью немедленного decommit его сегмента.

Для когорты 16 384 блоков индекс — **64 КиБ**, а не 128 КиБ указателей. Но максимальный индекс для мелких блоков значительно дороже; хранение должно быть ленивым, общим для сегмента, с доказанным поведением при OOM. Нельзя сделать FREE и снять credit, не обеспечив перечислимость блока.

**ESTIMATE:** **50–85% сокращения времени P0**, примерно −21…−37% против K5. Потенциально быстрее B на sparse/mixed workloads, потому что нет сканирования; всё ещё дороже park/reload P0.

**RSS / размер:** индекс пропорционален свободным блокам; пустой сегмент можно освобождать вместе с индексом. Риск — нерекурсивное выделение metadata и failure paths. Инварианты затрагиваются почти как в B; объём — **средне-большой**.

Альтернатива — точный free-bitmap, дополнительно **32 КиБ/сегмент** плюс class-summary: детерминированный поиск, но дублирование авторитетного состояния. Начинать одновременно и bitmap, и offsets не рекомендую.

## Обязательные доказательства для всех вариантов

- **Внешние защиты неизменны:** точный LIVE(class), геометрия, never-issued/interior/foreign rejection. И1–И5: `src/alloc_core/segment/bitmap/state_byte.rs:35–56`. Не обещать обнаружения stale free после reissue: существующее ограничение явно документировано в `src/alloc_core/small/alloc_core_small_pool/decommit.rs:202–209`.
- **Remote:** producers не трогают owner-private state/summary. Для B/C owner reclaim должен публиковать FREE в новое хранилище, сохраняя отклонение FREE/MAG и однократное снятие credit: `src/alloc_core/small/alloc_core_small_reclaim.rs:48–78`.
- **Reset/decommit:** обнулять summary, курсоры, offsets/counts до повторного использования; не оставлять адресов в освобождённую reservation. Текущий reset очищает bins и использованный диапазон state bytes: `src/alloc_core/small/alloc_core_small_pool/decommit.rs:212–257`.
- **Ghost:** сохранить P7/P8 publication/pin ordering (`docs/verification/ghost-rules.json:177–225`), P12 flush/owner/bind/handoff (`:1962–2087`), credit allowlists P10 (`:3418–3525`). Для B/C нужны новые правила соответствия FREE↔индекс и отрицательные контроли «потерянный FREE», «повторная выдача», «неочищенный reset»; не просто расширение allowlist.

## Точная предлагаемая предрегистрация

**Одна общая шкала для A/B/C; пороги — предложение, не существующая политика владельца.**

1. **Определить долю потолка по обычному времени:**
   \[
   F=(1-t_X/t_{K5})/(1-t_{P0}/t_{K5}).
   \]
   В свежей совместной кампании требовать **нижнюю 95% границу F ≥ 0.80**. При нынешней точке P0 это примерно **t_X/t_K5 ≤ 0.656**, но исторический P0 не использовать вместо свежего контроля.

2. **J1′ v2:** K5, P0, кандидат и null; 20 процессов × 2000 блоков, все 11 ядер, баланс ABBA/BAAB, фиксированные seeds, affinity, compiler/features/alignment, SHA бинарников и исходников. Bootstrap по процессам, не по отдельным блокам. Два заранее назначенных независимых сеанса; оба должны пройти. Если проверяются несколько кандидатов — поправка Holm; запрещён выбор лучшего случайного прогона.

3. **Неухудшение:** для остальных десяти ядер верхняя односторонняя, скорректированная 95% граница **t_X/t_K5 ≤ 1.01**. CI с нулём — не доказательство равенства. Недопущенные A/A churn1024/vec512 — **нет вердикта**, не «прошли»; повтор по заранее заданному правилу точности.

4. **Против mimalloc — отдельный обязательный gate:** на bulk16k нижняя 95% граница **t_mi/t_X ≥ 1.02**, остальные ядра — неухудшение отношения против свежего K5 более чем на 1%. Старые 0.511/0.873 — контекст, не парный эффект. **С текущим P0=0.873 прохождение этого gate у A маловероятно; без него результат — полезный кандидат, не разрешение на отгрузку.**

5. **RSS — отдельные процессы, не совместное проживание двух allocator arms.** По 20 процессов на allocator: K5/X/mimalloc; T=1/8/64, размеры когорты 4k/16k/64k, dense и sparse-по-сегментам, burst→idle→explicit trim→thread exit. Одинаково трогать payload, измерять peak RSS и private committed bytes, остаток через 1/10/60 с, после trim/exit; metadata, parked bytes и число закреплённых сегментов отдельно. Sampling вне timed regions.

   Предлагаемые RSS-пороги относительно K5:
   - **A:** верхняя 95% граница добавочного peak/idle-before-trim **≤1.5 МиБ × T + 1 МиБ**.
   - **B/C:** **≤max(5% peak K5, 1 МиБ × T)**.
   - **Все:** после explicit trim/exit добавочный остаток **≤1 МиБ на процесс**; без нагрузки на расширение A — также ≤1 МиБ.
   
   Это намеренно проверяет реальное сегментное усиление, а не только счётчик payload. Пороги RSS владелец должен утвердить **до** замеров; фактическое сравнение с mimalloc публиковать даже при прохождении.

## Ранжированная рекомендация

1. **A — ленивый depot 64 Б, общий бюджет 1.25 МиБ/поток:** лучший шанс сохранить ≥80% P0 при наименьшем риске; условно приемлем только с согласованным RSS.
2. **C — segment-local offsets:** следующий кандидат, если RSS A неприемлем; предсказуемее сканирования, но сложнее по metadata/OOM.
3. **B — FREE + class/chunk summary:** перспективный малый индекс, но прежнюю рекомендацию «после P0 сразу строить (d)» теперь считаю слишком уверенной: сохранение большей части потолка не доказано.
4. **Не отгружать ни один только за близость к P0:** при требовании настоящей победы над mimalloc нужен отдельный пройденный gate, которого сейчас нет.
