# U32 — выпуск класса блока по листам в `try_carve_batch`: NO-GO (измерение, прод не меняется)

Вердикт: **NO-GO** по предрегистрации (`u32_carve_range/U32_PREREG.md`,
записана до замеров времени; v2 записана до своего замера). Код в main не
идёт. Отчёт — измерительный (`bench`).

## Что проверялось

U32 — разрыв роста с mimalloc на growth16 (2.23× по Ir при n = 131072 после
U31). Атрибуция callgrind на main: `try_carve_batch` — 6.98 M Ir из 27.27 M,
≈53 Ir на блок; из них проверка листа (`RoutedIssueRun::prepare_for` и
`commit`) и сопутствующие `Option`-сравнения — ≈21 Ir на блок.

Вариант: bump-пробег сплошной, поэтому `try_carve_batch` выпускает его по
4 КиБ листам (`IssueRun::prepare_range` / `commit_range`): одна проверка и
одно разрешение листа на лист, а не на блок. Каждый блок сохраняет свою
Release-запись кода класса, запись байта состояния и запись указателя;
отказ и обратный отсчёт инъекции сбоя — как у поблочного пути (тест
`tests/u32_carve_issue_range.rs` на ветке `u32`: код класса стоит ровно на
начале каждого блока всех малых классов через границы листов, ни на одной
внутренней грануле; отсчёт сбоя уходит ровно на блок; мутанты «шаг 1 вместо
stride» и «пропуск отсчёта» краснеют, «лишний блок в листе» ловит
fatal-проверка).

- v1 (`u32`@`70f48059`): число блоков в листе — `div_ceil`.
- v2 (`u32`@`bb8aacab`): то же без деления — подсчёт шагами.

Путь активен по построению: на свежей куче каждый из 131 072 блоков
growth16 берётся из bump-carve (в базовом профиле `try_carve_batch`
вызывается 8 192 раза по 16 блоков).

## Вывод

Проверка листа на каждом блоке стоит ≈19 Ir на блок, но во времени её цена
не видна: v1 медленнее на 4.2 % (CI 1.4…6.8 %), v2 не отличается от базы.
Медиана фазы alloc у обоих вариантов выше базы (≈+4 %: 996 900 → 1 040 150 нс
у v2), фаза free не меняется. Время alloc на свежей куче, по-видимому,
задают первые касания страниц и записи в холодные метаданные, а не число
инструкций в carve; деление v1 (одна инструкция для callgrind) объясняет
лишь часть разницы — v2 без деления тоже не быстрее. Причина роста alloc не
установлена: для этого нужны PMU-счётчики (промахи кэша, page faults) на
том же зонде, их не мерили. Это второй случай после GR-1, когда −9 % Ir не
дают времени.
