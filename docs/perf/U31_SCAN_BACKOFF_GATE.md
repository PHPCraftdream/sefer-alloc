# U31 — отложенный discovery-скан sidecar на стороне владельца: гейт (perf(runtime))

Статус: **v2 — GO**, v1 — NO-GO, оба по предрегистрации
`docs/perf/u31_scan_backoff/U31_PREREG.md`. Предрегистрация закоммичена до

каждая закоммичена до замеров, которые она регулирует. Пункт OPEN_ITEMS — 90.

Код под замером:
- base — main `29b82b7d` (склад, B1, B2 уже в main);
- v1 — ветка `u31`@`37bf5a10`, v2 — ветка `u31`@`e25e7729`;
- абляции — измерительная ветка `u31-abl` (main `29b82b7d` + харнесс

## Что изменено

Пополнение магазина идёт так: свободный список текущего сегмента → курсор
класса → `find_segment_with_free` → нарезка. При `alloc-global` +
`alloc-xthread` таблица маршрутизирована, отрицательному ответу каталога
не доверяют, и каждый промах пополнения запускает линейный скан. Скан
вычерпывает pending-sidecar каждого маленького сегмента от начала полезной
нагрузки до текущего `bump`. При росте кучи без free каждое пополнение
сканирует весь уже нарезанный диапазон, поэтому работа квадратична.

Сводки, которые помечает производитель, отвергнуты трижды (пункт 82: C′,
C″, C‴): каждая стоила +8 … +16 Ir на удалённый free. U31 меняет только
сторону владельца.

v2 (`src/alloc_core/small/alloc_core_small/find_segment/scan_backoff.rs`):

- скан, все drain которого вернули `Skipped`, удлиняет серию пустых сканов;
  drain, который что-то вернул, сбрасывает серию и закрывает окно;
- на третьем пустом скане подряд открывается окно `(start, end)` по `bump`
  текущего сегмента: `start` — `bump` в момент скана, `end` — `start` плюс
  1/16 вычерпанного диапазона полезной нагрузки;
- пока `start < bump < end` и в текущем сегменте есть место под блок
  класса, линейный скан пропускает drain sidecar. Головы bin по-прежнему
  читаются, поэтому локально освобождённые блоки других сегментов
  переиспользуются;
- повторный discovery без нарезки после пустого скана не откладывается
  никогда; rescue-скан при нехватке памяти (`find_segment_with_free_forced`)
  не откладывается никогда;
- состояние — один `u32` в бывшем хвостовом выравнивании заголовка сегмента
  (`SegmentHeader::sidecar_defer_window`), заголовок остаётся 144 байта.
  В `HeapCore` места нет: под `--all-features` он упирается в пин
  `size_of::<HeapCore>() <= 9216`, пин не тронут. Сброс `bump` при
  retain-decommit сбрасывает и окно;
- производитель, публикация, атомики, `unsafe` не изменены. Новых
  межпоточных состояний нет, поэтому нет и новых моделей loom/kani; miri
  гоняет существующие наборы на CI.

Граница по построению: публикация, ожидающая во время окна, будет вычерпана,
как только владелец нарежет не больше 1/16 вычерпанного диапазона, либо
сегмент заполнится, либо сменится `small_cur`. Каждое отложенное пополнение
нарезает хотя бы один блок, поэтому окно всегда заканчивается.

v1 отличался двумя вещами: окно открывалось после первого же пустого скана
и было 1/8. Он провалил порог памяти (см. ниже); v2 закреплён поправкой 3 до
своих замеров.

Тесты:
- `tests/u31_sidecar_defer_window.rs` закрепляет активацию (сканов меньше
  половины discovery), границу окна (≤ 1/16 вычерпанного диапазона + одно
  пополнение), живучесть (опубликованный free снова выдаётся не позже конца
  окна + пополнение) и сброс серии на возвращающем drain. Мутанты
  «никогда не откладывать», «окно не кончается», «окно на весь диапазон» и
  «серия не сбрасывается» валят его;
- правило «без нарезки не откладывать» держат
  `tests/r10_active_kind_late_publish.rs` и
  `tests/b4_u31_trigger_growth16_oracle.rs` (публикация сразу после пустого
  скана); мутант без этого правила валит `r10_active_kind_late_publish`;
- `tests/r12_o4_routed_miss_counters.rs` по построению режет между пустым
  сканом и публикацией; перед своими этапами он закрывает окно хуком
  `dbg_close_sidecar_defer_window` (`bench-internals`), проверки
  классификации идут на настоящих сканах без изменений.

Локально зелёные четыре набора: `production alloc-stats bench-internals
internals`, `production internals`, `hardened medium-classes internals
bench-internals`, `--all-features`.

## Что меряется

**Allocator layer under test:** реальный `#[global_allocator]` `SeferAlloc` (`HeapCore` → `AllocCore`), путь пополнения магазина `refill_magazine_slow` → `find_segment_with_free` → линейный скан. Решение относится именно к нему: discovery-скан идёт только через этот путь.

- Инструкции: callgrind в WSL2, проба `ut_u31_probe` (зеркало
  `R19Prf01::growth16`: n блоков по 16 Б живы, затем все освобождаются),
  `production bench-internals internals`.
- Время роста: `u31_growth_wall` — то же тело, один рост на процесс, свежая
  куча; два исполняемых файла (base, вариант), 100 четвёрок процессов
  ABBA/BAAB + 50 null-четвёрок, статистика — медиана по четвёркам
  ln(Σ t_B / Σ t_A), 95 % бутстреп по четвёркам.
- Ядра судьи: абляция J1′ v2 — обе копии аллокатора в одном процессе,
  20 процессов × 2000 блоков, эффект = медиана варианта − медиана null.
- Многопоточность: `examples/ph6b_mt_ab.rs` (реальный `#[global_allocator]`,
  larson/mstress, T = 1, 2, 4, 8), 100 четвёрок + 50 null, t = ns/op.
- Память: пиковый RSS (`/usr/bin/time -f %M` в WSL2) — growth16 20 четвёрок,
  `ph6b_mt_ab` 100 четвёрок; `segments_reserved_total` из `ph6b_mt_ab`.

Сборка везде release, `RUSTFLAGS` выравнивания `-C
llvm-args=-align-all-functions=6 -C llvm-args=-align-all-nofallthru-blocks=5`
(кроме callgrind), Windows 10 / i7-11800H; идентичность —
`u31_scan_backoff/run_identity.txt`, хэши исполняемых файлов —
`v1/binaries.sha256`, `v2/binaries.sha256`.

## Выводы

- Рост без free стал линейным: при n = 131072 sefer был медленнее mimalloc в
  8.42× по Ir, стал медленнее в 2.23×. По времени тело роста быстрее в
  2.93×, цикл alloc — в 4.96×.
- На ядрах судьи discovery-скан бывает только на прогреве; v2 откладывает
  сканы лишь в bulk16k (942 из 1024 на процесс) и larson (64 из 98).
  Отложенный скан ничего не нашёл бы и в base, поэтому обе ветки выдают те же
  блоки. Замедление bulk64 (+0.83 %) и bulk16k (+0.67 %) в пределах порога;
  в bulk64 v2 не откладывает ни одного скана, так что это, скорее всего,
  расположение кода, а не U31.
- В многопоточности ни одна ячейка не медленнее; larson T8 быстрее в 1.072×,
  mstress T8 — в 1.045×.
- Память: у v2 пиковый RSS в MT 0.975 [0.935, 1.019] от base; у v1 было
  1.094 [1.028, 1.163] — провал порога 5 и причина v2.

## Не измерено

- Время роста против mimalloc (есть только Ir).
- Ядра с удалёнными free, кроме larson/mstress `ph6b_mt_ab`.
- RSS на Windows (мерился в WSL2).
