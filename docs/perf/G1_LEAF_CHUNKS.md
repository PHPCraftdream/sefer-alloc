# WG-LEAF — листья `ClassLeaves` из чанков вместо одного System-запроса на лист

**Тип работы: `perf(runtime)`** (коммит `perf(runtime): ClassLeaves hands out leaves from 4 KiB System chunks…`): меняется always-on холодный путь `ClassLeaves::promote`/`Drop` в sidecar каждого сегмента мелких блоков. Задача #2490, карточка `docs/perf/OPEN_ITEMS.md` 146 (G1-WJ1), порядок приёма по карточке — «дикий судья + `bench:table` как контроль».

## 0. Вывод

1. **Механизм.** Заполненный сегмент промоутит все 1024 листа по 256 Б, и каждый лист был отдельным `System.alloc` (на Windows `HeapAlloc`), а при освобождении маршрута — отдельным `dealloc`. Листья теперь выдаются из чанков по 16 штук (4096 Б) в порядке промоции: 64 запроса и 64 освобождения на полный сегмент вместо 1024 и 1024. Время внутри этих запросов на росте 1 ГиБ (черновые таймеры, раздел 3): выдача 28–36 мс (3.8–5.9 % времени сценария), освобождение 26–28 мс (2.8–5.5 %).
2. **Windows, судья** (минимум из 3 повторов, 12 блоков, A/A-контроль; первая версия коммита): `leaf / base` grow64 0.971 (0.947–0.995), grow1k 0.939 (0.909–0.969), regrow 0.967 (0.932–1.003), growmix 1.005 (0.966–1.045); wild 0.996, phase 0.994, large 0.966 (ДИ включают 1). A/A в этой кампании: grow1k 0.972 (0.941–1.005), остальные ближе к 1.
3. **Подтверждение** (отдельная кампания, таблица «Confirmation» ниже; арм `base2` — бинарник первой версии, `x` — финальный коммит; 12 блоков × минимум из 3): первая версия против `base` — grow64 0.960 (0.948–0.973), grow1k 0.927 (0.903–0.952), regrow 0.966 (0.945–0.988), growmix 0.965 (0.945–0.986); финальный коммит против `base` — grow64 0.985 (0.970–1.001), grow1k **0.936 (0.908–0.965)**, regrow 0.980 (0.947–1.014), growmix 0.967 (0.936–0.999). **Выигрыш на grow1k воспроизводится во всех трёх измерениях (0.939, 0.927, 0.936; −4…−7 %), на остальных ячейках он меньше и не стабилен**: grow64 0.971 / 0.960 / 0.985, regrow 0.967 / 0.966 / 0.980, growmix 1.005 / 0.965 / 0.967 (основная кампания / первая версия в подтверждении / финальный коммит). Финальная сборка на grow64 медленнее первой версии на 2.6 % (1.007–1.045), на остальных ячейках различие не отличимо от 1; причина не установлена (в сборке изменились типизированный шаг и счётчики; вклад раскладки кода при пересборке не исключён).
4. **Linux (WSL), судья масштаб 0.5:** значимого эффекта нет: все ДИ включают 1, кроме phase 0.976 (0.954–0.999) — единичный номинальный результат, выигрыш на Linux не заявляется (glibc `malloc(256)` дёшев).
5. **Контроль `bench:table` (два парных набора):** новых проигрышей против mimalloc нет, наибольшая согласованная потеря по времени sefer +1.0 % и +1.7 % (порог 3 %), gm по времени sefer −0.0 % и −0.3 %. **По простому правилу величины (`scripts/g1_magnitude_verdict.mjs`) оба набора NO-GO**: gm не достигает −0.5 %, и отношение выигрышей к потерям 5.5/2.9 и 7.4/4.5 пп ниже 2×. Приём по порядку карточки 146 (судья — цель, `bench:table` — контроль без регресса) формально возможен, но достаточен ли такой выигрыш — решение владельца; без явного решения PR не вливается.
6. **MT-контроль** (`malloc_macro`, медианы по 6 запускам): без систематического сдвига (разброс запусков больше эффекта).
7. **Память.** +520 Б на sidecar сегмента (64 указателя чанков + счётчик; 0.012 % от 4 МиБ сегмента), хвост последнего чанка ≤ 15 слотов (3840 Б). Сегмент с одним промоутнутым листом держит 4096 Б вместо 256 Б; полный сегмент — те же 262 144 Б, но без 1024 заголовков кучи. RSS при множестве разреженных сегментов не измерен.

## 1. Что изменено

`src/alloc_core/segment/remote_bitmap/sidecar_bitmap/leaf_classes.rs` (единственный файл `src/`): поля `chunks: [AtomicPtr<u8>; 64]` и `promoted: AtomicUsize` (владелец-приватные, нулевое начальное значение допустимо для `initialize_at`), `next_leaf_slot()` выдаёт следующий слот в порядке промоции (слот не зависит от индекса листа), `Drop` освобождает чанки. Не изменено: публикация листа (`Release`-store `mixed[leaf]`, затем бит присутствия), нулевая заливка листа, срок жизни (листья освобождаются только в `Drop`, после последнего пина), счётчики `system_totals` остаются «запрошенные байты на лист», точки внедрения отказов (до выдачи). Ошибка System на новом чанке даёт тот же отказ промоции, что раньше давала ошибка на листе (курсор не сдвигается).

Находка ревью (`rush reviewer`, `.rush/stdin/g1-leaf-review.out`, только чтение): в первой версии шаг слота считался в байтах, а под `cfg(loom)` `AtomicU8` не однобайтовый, и два листа одного чанка перекрывались бы. Исправлено (`fix(perf)`): чанк хранит и выдаёт типизированный `*mut AtomicU8`, шаг — в элементах `AtomicU8` (в production размер 1 байт, код тот же). Там же: счётчики фактических запросов чанков (`chunk_totals_for_test`); `system_totals_for_test` остаётся логическим «один запрос на промоутнутый лист» и документирован так.

Тесты (запускаются на GitHub CI): `scrambled_promotion_order_keeps_every_leaf_separate` в `tests/class_leaves_publication_miri.rs` (все 1024 листа в перемешанном порядке; у каждого лист-специфичный гранул и один из семи кодов, чтение обратно после всех промоций; перекрытие слотов или неверный шаг дали бы чужой код); `leaves_share_system_chunks_and_drop_frees_every_chunk` в `tests/r6_b4_class_leaves_drop_frees_promoted_leaves.rs` (33 листа = ровно 3 запроса чанка, `Drop` возвращает все три); `loom_actual_two_leaves_of_one_chunk_do_not_overlap` в `tests/loom_sidecar_bitmap_actual.rs` (два листа одного чанка не перекрываются на атомиках loom); существующие `tests/r11_p3_small_sidecar_*` (логический учёт и отказы), `class_leaves_publication_miri.rs` (miri, публикация).

Не покрыто: отказ `System.alloc` на слоте 0 нового чанка (в коде курсор не сдвигается и ничего не публикуется, но точки внедрения такого отказа нет; существующие внедрения срабатывают до выдачи слота).

## 2. Что измерено

- **Точка входа:** `SeferAlloc` как `GlobalAlloc` через прокладки судьи `examples/g1_wild_judge.rs` (WJ-1); `bench:table`/`malloc_macro` — их собственные точки входа.
- **Плечи судьи (один процесс на запуск):** `base` — main `b2796882`; `base2` — побайтно та же `base` (A/A-контроль); `x` — `ade284e0` (первая версия коммита). Сборка `--release --features "production internals"`, rustc 1.97.0; идентичности — `docs/perf/leaf/win_ident.txt`, `linux_ident.txt`. План: 12 блоков, внутри блока три плеча в одном из 6 порядков, минимум по 3 повторам плеча; Windows масштаб 1, Linux масштаб 0.5; вывод `d = ln(x/base)`, среднее по блокам и двусторонний 95 % t-интервал (df = 11).
- **Финальный коммит** (`5416a9e7`) отличается от измеренного `ade284e0` исправлением шага слотов (типизированный указатель), счётчиками чанков и записью двух байтовых литералов; подтверждающие кампании (раздел 3) сравнивают его с `base` и с измеренным бинарником. Основная кампания и Linux измерены на `ade284e0`.
- **`bench:table`:** `scripts/bench-table-paired.mjs`, выровненный код (`-align-all-functions=6`), порядок base, leaf, leaf, base, после отбрасываемого прогрева; два набора.
- **Не измерено:** хвосты задержек и RSS под нагрузкой (оценка памяти — расчётная, раздел 0.6); Linux callgrind/Ir.
