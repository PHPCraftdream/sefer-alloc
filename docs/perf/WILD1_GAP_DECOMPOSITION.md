# WILD-1 — where the `wild` / `phase` / `large` gap to mimalloc sits (measurement only, `bench`)

**Class:** measurement only. The only code change is in the judge `examples/g1_wild_judge.rs`
(an opt-in `WJ_PROF=1` switch and a `burst` scenario); no allocator code changes, no `production`
composition change. Tables and both summary CSVs are generated by `scripts/wild1_report.mjs` from
`docs/perf/wild1/`; the prose cites them.

## 0. Summary

1. **The `wild` gap is the free of small blocks, not Large spans and not release.** On Windows the
   wall-time difference sefer - mi is 68.9 ms (95 % CI 59.7..78.1); the free half of the small LIFO bursts
   (`burst_free`) is 42.5 ms of it (42.5 / 68.9), the alloc half 11.7 ms (11.7 / 68.9). `phase` is
   78.9 ms (45.6..112.2), of which the bursts are 36.6 + 28.9 ms (65.5 / 78.9). `large` is a different
   case: 4.0 ms (2.4..5.5), all of it the free of Large blocks (4.2 ms, sefer 4.9 ms against mimalloc 0.8 ms
   for 3889 calls) plus the final teardown (1.5 ms).
2. **The same gap exists on Linux (WSL2).** `burst_free` is 41.2 ms of a 42.1 ms `wild` difference
   (41.2 / 42.1). Linux `wild` is not a win for sefer: Large allocation is faster in sefer there
   (`large_alloc` -22.7 ms) and that hides most of the loss.
3. **The cost is the context of the heap, not the burst algorithm.** The same bursts on a clean heap
   (scenario `burst`) cost sefer 1.25x mimalloc per freed block on Windows (1.141..1.373); inside `wild` the
   ratio is 2.37 (2.215..2.543), and on Linux 3.06 (2.978..3.134). Inside `wild` the lane that accepts an
   own-thread small free on a one-entry segment memo misses on 88.8 % of the frees (3 804 795 / 4 285 881 in
   the median probe run), against 0.0 % on a clean heap and 3.0 % in `phase`.
4. **What a memo miss costs.** Linux, callgrind, `wild` at scale 0.3: `lane_miss` (the unchanged chain
   `dealloc_routing`) executes 25 495 319 instructions in 278 028 calls, 91.7 per call; sefer executes 168.2 M
   instructions in total against 144.4 M for mimalloc (+23.7 M, +16.4 %), so this one function is about the
   whole instruction gap. Hardware counters (perf stat, median of 5): instructions 1.217x, L1D load misses
   1.738x, cycles 1.539x mimalloc.
5. **A larger `own_cache` removes the hash probes but not the memo misses.** In a throwaway probe build with
   `OWN_CACHE_SIZE = 64` the hash probes fell from 31.6 % to 4.9 % of the lane frees (median of 5 runs);
   memo misses did not change. Whether a cheaper path for the memo miss pays in time is **not measured here**.
6. **What was not found:** no sign of L1 set conflicts between segment headers (a cache simulation with a 12-way
   and a fully associative D1 differs by 2.7 % in total misses), and the `sefer_pool` arm of LM-1 could not
   attribute `wild`/`large` because it does not hold Large spans.

## 1. What was measured

- **Source identity (taken before the measurement).** Windows judge with `WJ_PROF` and the main campaign:
  commit `8df5abcd596dee0b7dba234358b017b8d9c1b9f3`, tree in `ident.txt`; the `burst` scenario campaign:
  commit `12a01097fff75259c7fd30232348a40d21de8eee`, `ident2.txt`; Linux builds are `git archive` tars of the same
  commits (`linux_ident.txt`, `linux_ident2.txt`). The counter probes are throwaway commits `6bfb67b8` and
  `8cef3c9b` on top of `12a01097`; their final patch is `probe.patch` (sha256 in `probe_counts.txt`), the
  size-64 variant adds the one-line edit named in `probe_counts_size64.txt`. Probe builds were used for event
  counts only, never for timing.
- **Machine and toolchain:** i7-11800H, Windows 10 Pro (rustc 1.97.0) and WSL2 Linux 6.18 (rustc 1.98.1);
  shared machine, nothing else started by this work during a campaign.
- **Entry point:** the judge reaches the allocator as a static through `#[inline(never)]` shims at the
  `__rust_alloc` boundary, one arm per process (header of `examples/g1_wild_judge.rs`).
- **Buckets (`WJ_PROF=1`).** The two phases of every small LIFO burst (alloc 1..1000 blocks of 8..128 B, free
  them in reverse) are timed as units; blocks above 256 KiB are timed per call (the alloc timer includes the
  first/last byte write); realloc is timed per call and split by size, with a count of calls that returned a
  new pointer; `free_all` at the end is the teardown; `rest` = wall time minus all buckets. Per-call timers
  cost the same in both arms; the small-block operations outside bursts are not timed individually (a timer
  costs about as much as the operation), they stay in `rest`.
- **Statistic.** Per block (12) and arm the repeat with the smallest wall time of 3 is taken whole, so the
  buckets add up to one real run; per bucket the difference sefer - mi in ms, mean over blocks with a
  two-sided 95 % t-interval (df = 11). The script asserts that the bucket differences add up to the wall
  difference in every block and that both arms ran the same op sequence (equal checksums).
- **Burst ratios** are exp(mean of ln(sefer / mi)) of ns per block, same interval.

## 3. Reading the tables

1. **Windows `wild` / `phase`.** Small LIFO bursts are 79 % of the `wild` difference (54.2 / 68.9: 42.5 free +
   11.7 alloc) and 83 % of the `phase` difference (65.5 / 78.9). Realloc contributes about 0 ms in `wild`
   (0.1 + 0.1 ms) and 5.3 ms in `phase` (2.3 + 3.0 ms). Large calls and the teardown add 2.5 + 4.1 + 3.6 ms in
   `wild`; the teardown is 0.2 ms in mimalloc against 3.8 ms in sefer.
2. **Burst alloc is slower in sefer everywhere, a little** (1.09..1.15 per block in the burst table, on a clean
   heap too); that part is the D16-R family (bulk small blocks), it is not specific to `wild`.
3. **Burst free is where the heap context matters.** The ratio per freed block grows from about 1.2..1.33 (clean
   heap, `phase`) to 2.37 (Windows) and 3.06 (Linux) in `wild`. The probe counters give the first link of the
   cause: 88.8 % of the frees in `wild` leave the memo lane; of those, 2 554 708 hit `own_cache` and 1 256 610 need
   the hash probe (29.3 % of all lane frees, median run; between 1.08 M and 1.35 M in the five runs because the
   segment layout differs from run to run). The chain behind the miss costs 91.7 instructions per call in the
   callgrind profile (the lane's own hit path is not part of that count).
4. **Instruction count and misses both contribute.** Instructions are +21.7 % (perf stat) and L1D load misses
   +73.8 %; the cache simulation (callgrind `--cache-sim`, D1 48 KiB 12-way) does not reproduce the extra misses
   (sefer 640 666 against mimalloc 779 909 simulated D1 read misses), so this report does not attribute the
   miss excess to a cause. The instruction excess is attributed: `lane_miss`.
5. **`large`.** The gap is the free of Large blocks: sefer 1.26 us per call against 0.21 us (4.9 ms and 0.8 ms for
   3889 calls, Windows) and the teardown; allocation of Large blocks is faster in sefer. This points at what a
   Large free does in sefer (decommit/release/cache admission) and was not investigated further. On Linux the
   whole `large` scenario is faster in sefer (14.7 ms against 118.4 ms) because mimalloc's `large_alloc` is
   105.5 ms slower.
6. **Correction of an earlier reading.** LM-1 recorded `sefer_pool` as unable to attribute `wild`/`large`; this
   report confirms it was the wrong lever for them (the dominant part is the small-block free, section 3.3).

## 4. What this suggests (not measured here)

- **WILD-2, a cheaper path for the memo miss.** The lane that accepts an own-thread small free currently returns
  to the unchanged chain on any memo mismatch. A second chance inside the cold exit (probe the direct-mapped
  `own_cache`, then the same acceptance steps) would keep the hit path of the memo untouched. The M1 assessment
  (`docs/perf/M1_SEGMENT_MAP_ASSESSMENT.md`) gave as its return trigger "a target workload with a live set larger
  than one segment and out-of-order frees where the judge shows a gap on free": `wild` is that workload (and
  `growmix`, `regrow` are candidates). A larger `own_cache` is a separate, size-limited lever (the 256-entry
  table does not fit the `HeapCore` size assert; 64 entries did build). Both need a preregistration, a paired
  judge campaign on Windows and Linux and a `bench:table` control before any decision.
- **Large free in `large`.** A separate, smaller item (4.2 ms of 4.0 ms in a 13 ms scenario).

## 5. Limits

- The probe counters are a throwaway build; timing of that build is not used anywhere. Counts differ between runs
  (segment layout); medians of 5 are reported.
- Per-call timers in the judge perturb the small operations they wrap (large blocks, realloc); the bursts are
  timed as units. `rest` contains everything not timed, including the first-touch writes of small blocks outside
  bursts.
- Linux numbers come from WSL2 on the same machine; the Windows and Linux builds use different compilers.
- One machine, one seed (1); the 12 blocks are repeats of the same op sequence, not different workloads.
