# G1-SC — обход всех сегментов при пополнении магазина: предрегистрация счётного замера

Записана до любых данных. Отчёт измерительный (`bench`), прод не меняется.
Задачи SC-1 (эта предрегистрация и проба), SC-2 (рост), SC-3 (граница U31).

## Вопрос

Растёт ли работа поиска свободного блока при пополнении магазина
квадратично по числу сегментов кучи (S), когда у класса нет свободных блоков?

## Механизм (чтение кода, `main` @ `59bca504`)

- Пополнение магазина (`refill_class_bump_impl`,
  `src/alloc_core/small/alloc_core_small_magazine.rs:323`): свободный список
  текущего сегмента → курсор класса → `find_segment_with_free` → нарезка.
  Пополнение — 16 блоков для классов до 4 КиБ.
- В production (`alloc-global` + `alloc-xthread`, таблица routed) отрицательный
  ответ каталога не доверяется (`find_segment/scan.rs:265`), поэтому промах
  каталога ведёт в `linear_scan`, который посещает каждый активный Small-сегмент
  кучи (`scan.rs:540`). Курсор меняет только точку старта.
- U31 откладывает только вычерпывание sidecar (`scan.rs:590`), обход
  сегментов остаётся. Серия U31 хранится в заголовке `small_cur`, поэтому после
  смены текущего сегмента три пополнения подряд вычерпывают sidecar всех
  сегментов (до 4096 слов на сегмент, плоский скан `bitmap_scan.rs:105`).
- Любой вычерпывающий drain с результатом (любого класса) сбрасывает серию
  (`scan.rs:602`): редкие чужие free держат окно U31 закрытым.

Предсказание (вывод из кода, не замер). C — блоков в сегменте, S — сегментов
в конце роста:

| величина | рост до S сегментов | при удвоении n |
|---|---|---|
| вызовы `find_segment_with_free` | ≈ n / 16 | ×2 |
| посещённые сегменты (`full_scan_slots`) | ≈ (C/16) · S² / 2 | ×4 |
| прочитанные слова sidecar | ≈ 3 · 4096 · S² / 2 | ×4 |
| найдено / reclaimed в чистом росте | 0 | 0 |

Формулы — порядок величины, а не точное ожидание: окно U31 может закрыться
внутри сегмента (выросло на 1/16 вычерпанного диапазона), без места под блок
отсрочка запрещена (`scan_backoff.rs:61`), часть пополнений обслуживает текущий
сегмент. Вердикт выносится только по отношениям при удвоении n (ниже), не по
совпадению с формулами; пороги подтверждают поведение на этом конечном
диапазоне S = 8…64, а не асимптотику.

## Проба

`examples/g1_rhythm_probe.rs`, реальный `SeferAlloc` (static, тот же
routed путь, что у `#[global_allocator]`; так же устроена проба U31),
счётная сборка `--features "production bench-internals internals alloc-stats"`
(сборка `production` без этих features нужна только для таймингов RP), release,
одна точка = один процесс. Счётчики (разности до/после фазы):
`dbg_b4_collapse_counters` (find_segment, scans, words, foreign_publish_ok),
`dbg_b4_u31_scan_counters` (discovery scans — drain по сегменту, не по
поиску), `dbg_b4_u31_deferred_scans` (входы в линейный скан с отложенным
drain), `AllocCore::dbg_routed_miss_scans` (входы в линейный скан после промаха
каталога), `AllocCore::dbg_full_scan_slots_examined` (посещённые сегменты); число различных баз сегментов среди
живых блоков (адрес & !(4 МиБ − 1)); время фазы (только для справки, не судит).

Нагрузки:

| id | что | точки |
|---|---|---|
| G64 | рост блоков 64 Б, все живы | S ≈ 8, 16, 32, 64 (n = S · 65 536) |
| G1K | рост блоков 1 КиБ, все живы | S ≈ 8, 16, 32, 64 (n = S · 4 096) |
| T64 | G64 + один чужой free каждые K·16 выделений (поток-освободитель, синхронная передача); подарки нарезаются до замера | S ≈ 8, 32; K = 1, 2, 3, 8 |
| T64c | контроль T64: те же подарки нарезаны, но не передаются | те же |
| B64 | фаза 1: S сегментов живых блоков 64 Б; фаза 2 (меряется): 65 536 блоков 1 КиБ | S ≈ 8, 32, 64 |

Каждая точка — дважды (счётчики детерминированы; расхождение двух прогонов —
дефект пробы, точка повторяется после исправления).

Оракулы активации (иначе точка недействительна):
- routed путь: `find_segment` ≥ 0.9 · (число блоков / 16) в G и B;
- сегментов не меньше заказанного S (по базам живых блоков, подарки T64
  включены);
- T64 и T64c: `find_segment` ≥ 0.45 · (n / 16) (часть пополнений обслуживает
  возвращённый подарок);
- G, B и T64c: `foreign_publish_ok` = 0; T64: `foreign_publish_ok` = числу
  переданных free; T64 и T64c нарезали одинаковое число подарков.

Отчёт отвергает данные, если нет хотя бы одной точки сетки, если у точки не
ровно два прогона, если прогоны расходятся в любом счётчике, если n не
удваивается между соседними точками или любое поле — не неотрицательное целое.

## Правила вердикта (SC-2)

Для G64 и G1K, по каждой паре соседних точек S → 2S, начиная с S = 16:
- «квадрат подтверждён», если отношение `full_scan_slots` ≥ 3.5 на всех парах
  обеих нагрузок;
- «квадрата нет», если ≤ 2.5 хотя бы на одной паре;
- иначе «не решено».
То же правило отдельно для `scan_words` (вторая строка вердикта).

SC-3: для каждого K и S — доля поисков с отложенным drain
`deferred_scans / find_segment` (`routed_miss_scans` не годится в знаменатель:
он считается только при материализованном каталоге, с 32 сегментов) в T64 и в T64c и отношение `scan_words`
T64 / T64c. «Окно U31 открывается в T64 при K», если доля ≥ 0.5; иначе «не
открывается». Вывод «редкие чужие free держат окно закрытым» — если в T64 окно
не открывается, а в T64c при тех же S и K открывается. Задержка reclaim —
число выделений между передачей подарка и его повторной выдачей (по адресу),
делённое на 16 («пополнений-эквивалентов»), — публикуется, порога нет.

B64 публикуется как «стоимость пополнения ~ размер живой кучи»:
`full_scan_slots / find_segment` против S.

Переход к SC-4 (время против mimalloc): только при «квадрат подтверждён» хотя
бы по одной из двух величин; плюс callgrind Ir G64 при S = 8 и 64 для sefer и
mimalloc (WSL) — доля `linear_scan` (inclusive) и рост отношения Ir
sefer/mimalloc с S публикуются, порогов у этой части нет.
