# G1-MT1 — the `malloc-bench-rs` harness inlined one arm and not the other (measurement correction)

**Kind:** `bench`. The harness changed; no allocator code changed. Nothing in this report is
a runtime speedup.

**Entry point under test:** `GlobalAlloc::alloc` / `dealloc` called from
`crates/malloc-bench-rs` (larson, mstress), driven by `examples/malloc_macro.rs` on Windows
and by a single-arm probe (`g1_mt_one`, kept on branch `g1-mt1`) under Linux perf. This is
the layer the README MT tables publish. A real program reaches its `#[global_allocator]`
through `__rust_alloc` / `__rust_dealloc`, which are never inlined into user code. The fix
gives the harness that same boundary.

## 1. Symptom

At T=1 the README's historical numbers have mimalloc 1.28–1.36× ahead on larson and
mstress. The gap was attributed to the cost of the safety checks. The per-op `Ir` gap,
however, was only +19 % (callgrind, 300 000 steps: 76.7 M vs 64.4 M), while cycles were
+38–40 %.

## 2. Mechanism

`perf stat` on larson T=1 counted 2.07 M `ld_blocks.store_forward` events per 2 M
operations for sefer, against 10.5 k for mimalloc. That is one failed store-forward per
operation.

The stall comes from inlining. `<SeferAlloc as GlobalAlloc>::alloc` is a Rust body, so
LLVM inlines it into the generic `alloc_block<A>`. The grown `alloc_block` then stops being
inlined into the workload loop. It returns `Block { ptr, layout }` through an sret slot
written with 8-byte stores. The caller reloads the slot with one 16-byte
`movups 0x78(%rsp)`, and every allocation pays the store-forward stall.

mimalloc's `alloc` is a call to a C symbol, so `alloc_block` stays small and inlines, and
the stall never happens. No real `#[global_allocator]` program has this shape.

## 3. Counterfactual and fix

The counterfactual forces `alloc_block` to `#[inline(always)]` in a lab copy, nothing
else changed. The fix puts each `alloc`/`dealloc` behind an `#[inline(never)]` shim
(`alloc_shim` / `dealloc_shim` in `crates/malloc-bench-rs/src/lib.rs`). Every allocator now
pays one call, and its body inlines into its own shim, as with `__rust_alloc`.

Tables below are generated by `node scripts/g1_mt1_shim_report.mjs` from the raw logs.
Ratios are mimalloc Mops / sefer Mops (> 1: mimalloc faster) or sefer cycles / mimalloc
cycles (> 1: sefer slower).

## 4. Reading

- **larson T=1.** The harness caused most of the gap. Cycles went from 1.409× to 1.165×, and
  the store-forward stall disappeared (2.07 M → 74).
- **mstress T=1 on Linux.** The ratio moved the other way, 1.077 → 1.140. Under the old
  harness sefer's body was inlined into the workload loop, and that inlining helped it. The
  shim removes an advantage no real program has. This is the honest number, and it is a
  remaining target (`OPEN_ITEMS` card 145).
- **T ≥ 2.** Both OSes put sefer ahead. Windows mimalloc arms vary by up to 25 % between
  runs (mstress T=4: 158.1 vs 126.7 best-of-6 across builds), so T ≥ 2 ratios are
  indicative only.
