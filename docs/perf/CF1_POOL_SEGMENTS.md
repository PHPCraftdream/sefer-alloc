# CF-1 — the small-segment pool ("pocket") size: sweep and default (`bench`, measurement-only, default unchanged)

**Class:** `bench` — only the judge `examples/g1_wild_judge.rs` (the `sefer_pool` arm takes `WJ_POOL=<n>` at build time and
reports requested/resolved cap), the report generator `scripts/cf1_report.mjs` and this report changed. No shipping or
opt-in code changed, no default changed. The setting itself already exists
(`SmallSegmentPoolConfig::pool_segments` / `pool_byte_cap`, `SeferAlloc::dbg_current_pool_cap()` since PR #164); this report
measures it and the README now documents how to size it. Tables and both summary CSVs are generated by
`scripts/cf1_report.mjs` from `docs/perf/cf1/`; the prose cites them.

**Entry point under test:** a static `SeferAlloc` instance reached through `GlobalAlloc` shims (the `__rust_alloc` boundary of a `#[global_allocator]` user), with the system allocator as the process's own global allocator: `SeferAlloc::with_config(LargeCacheConfig::DEFAULT.pool(...))` inside
the process judge `examples/g1_wild_judge.rs` (arm `sefer_pool`). It is not the process's registered `#[global_allocator]`; it is the same `GlobalAlloc` methods on the same allocator type, which is the layer the pool ships at.

## 0. Summary

1. **The pocket is a retention knob, not a speed knob, in the seven judge shapes.** In every shape the run fills memory and
   then frees it. The pool never serves a reuse during the run (counter `seg_reserved` is the same for pool 0 and pool 1024 in
   six of seven shapes; `phase` saves 8 reservations of 1099 at pool 4 and 13 at pool 8 and above), and the segments it keeps
   are exactly the ones that would have been released at the end (`seg_released` falls by the pool size: grow64 272 at pool 0,
   268 at 4, 264 at 8, 256 at 16, 240 at 32, 208 at 64, 0 at 1024).
2. **Peak RSS does not move with the pool size** in six of seven shapes on both systems; in `phase` it rises by 6 MiB of
   295 MiB on Linux (pool 8 and above against pool 4) and by 1 MiB of 196 MiB on Windows (peak RSS tables, sections 2 and 3);
   what grows is the RSS left after the run: about 4 MiB per retained segment (Windows grow64: 12 MiB at pool 0, 29 at 4, 46 at
   8, 80 at 16, 149 at 32, 285 at 64, 1172 at 1024 — mimalloc keeps 1031).
3. **Time on Linux (WSL2): indistinguishable from the layout noise floor.** The control pair `sefer`/`p4` (the same configuration in two binaries) differs by
   up to a factor of two between repetitions, so a per-size difference below that is not measured. The deterministic
   mechanism counters (above) and the page-fault counts (fault tables; within 0.6 % across all sizes, the largest step being grow64 69167 → 69547 at pool 1024) are the Linux evidence: the pool size
   does not materially change what the process does during the run.
4. **Time on Windows: a gain exists only when almost everything is retained.** Against the control arm `p4`: pool 1024 is
   0.917 on grow64 (range of the 7 per-repetition ratios 0.84–1.00), 0.757 on grow1k (0.70–0.84) and 0.794 on regrow
   (0.65–0.89); pools 8..64 stay within the control's spread. Pool 1024 is the WG-M0 ceiling (release never happens in `free`);
   it holds the whole burst (1172 MiB after the run in grow64), i.e. it is the "Retain" question that waits for the owner
   decision (OWN-1 / RET-1), not a candidate default.
5. **Verdict:** the default stays `pool_segments = 4`, `pool_byte_cap = 16 MiB`. No size between 8 and 64 beats the measured
   noise on either system, and each retained segment costs about 4 MiB per heap after the burst. The README now states the
   sizing rule and the measured cost (section "Tuning the small-segment pool").

## 1. What was measured

* **Judge and identity.** `examples/g1_wild_judge.rs` at tree `f15038ecb050eae071f89e113671df99308b5b9c` (commit of the
  `bench` change; `tree.txt`), release, `--features production` for time and `--features "production internals bench-internals"`
  for the counters; binary hashes, `rustc`, CPU and OS are in `cf1/linux/ident.txt` and `cf1/windows/ident.txt`.
  Linux: WSL2 on the same host as Windows (11th Gen Intel i7-11800H); Windows 10 22H2.
* **Arms.** `sefer` = `SeferAlloc::new()` (default pool); `p<N>` = `sefer_pool` built with `WJ_POOL=<N>` for N in 0, 4, 8, 16,
  32, 64, 1024 (`pool_segments(N)`, `pool_byte_cap(N * 4 MiB)` so the cap resolves to N: both knobs move together); `mi` =
  mimalloc. `p4` is the control: the default configuration in its own binary. Seven scenarios (`grow64`, `grow1k`, `growmix`,
  `regrow`, `large`, `wild`, `phase`), seed 1, scale 1, each run its own process.
* **Rotation.** Per scenario and repetition the nine arms run in a cyclic rotation (a Latin square over repetitions) so that no
  arm owns a position. Linux: 9 repetitions (a full square); Windows: 7 repetitions of nine arms, so the positional balance is incomplete (two of the nine rotations did not run) and per-arm position effects are not fully cancelled.
* **Config evidence (R26-4).** For every pool size: requested (`pool_req`), resolved (`pool_res`, read with
  `SeferAlloc::dbg_current_pool_cap()` from the allocator's own heap), `config_conflicts` = 0 (`cf1/*/evidence.jsonl`,
  `cf1/*/mech.jsonl`); the script aborts if any resolved value differs from the requested one. Subprocess isolation per run
  (a fresh process has an empty registry).
* **Mechanism evidence (R30-8).** `seg_reserved` / `seg_released` (OS reservations and releases of segments) and, on Linux, the
  process's minor page faults, per pool size, 3 runs per cell. These are exact on Linux; on Windows the median and the range
  are in the mechanism CSV.
* **Layout noise floor.** Two binaries with the same configuration (`sefer` from the 1024 binary and `p4`) are compared in every
  table; every difference smaller than their per-repetition spread is not a result.
* **Statistics.** Ratios are medians of per-repetition ratios against the `p4` control of the same repetition; the range
  is the minimum and maximum of those per-repetition ratios. RSS columns are medians over runs; "end-of-run RSS" is the RSS after
  the scenario freed everything.

## 4. Reading the tables

* **What the pool can and cannot do.** The pool keeps empty small segments of the same size class so that a later
  allocation of that class re-uses them without a fresh OS reservation. The judge shapes never refill what they emptied, so the
  pool has nothing to serve: `seg_reserved` is identical at every size (except `phase`, which has a small refill). The cost side
  is certain and linear: every segment kept is committed memory that stays in the process.
* **Where a gain was measured elsewhere.** R27-4 measured a gain at pool 8 on a different shape (1024-byte allocate/free
  batches of 120 with teardown, Windows, single thread; `docs/perf/R27_4_REAL_DEFAULT_AB_GATE.md`): that is a workload that does
  cross a segment boundary repeatedly. The judge shapes here do not repeat that pattern, so neither result contradicts the other.
* **What pool 1024 shows on Windows.** It never releases a segment (`seg_released` = 0 in grow64, grow1k, regrow), so the time of
  releasing segments in `free` disappears: the WG-M0 ceiling again, now with the grow1k and regrow numbers repeated with the
  control arm. The price is the whole burst staying committed (1172 MiB left after grow64, against 29 MiB at the default).
  That trade is the opt-in "Retain" policy under owner decision (OWN-1 / RET-1); this sweep does not add an argument for a
  bounded size in between.
* **Linux time.** Not decisive: the layout noise floor (the `sefer`/`p4` column) is as large as the largest per-size
  difference. The decision for Linux rests on the counters and fault counts, which do not depend on layout.

## 5. Limits

* One thread per scenario (the judge is single-threaded); the pool is per heap, so the retained size scales with the number of
  heaps (threads that own a heap): N segments of 4 MiB per heap.
* Seven fill-then-free shapes. A workload that re-fills what it empties is the case where a larger pool can pay; use the
  counters (`seg_reserved` / `seg_released` through `dbg_current_pool_cap()` and the judge fields) on the real workload before
  raising the size.
* Windows time was measured with 7 repetitions per cell, Linux with 9; the Windows control spread is the reference for what is
  distinguishable there.
* No default changed, so no `bench:table` / `iai` refresh is owed.
