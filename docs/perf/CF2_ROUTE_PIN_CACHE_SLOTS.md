# CF-2 — the route pin cache slot count becomes a setting (`perf(runtime)`, default unchanged)

**Class:** `perf(runtime)` — the always-on foreign-free path of
`src/registry/heap_core_xthread/route_pin_cache.rs` now reads the thread's slot mask (a word next to the `RefCell` borrow
flag) instead of using a compile-time constant; the default slot count (32) and every default behaviour are unchanged. New setting:
`LargeCacheConfig::route_pin_cache_slots(n)`. Tables and the summary CSV are generated by `scripts/cf2_report.mjs` from
`docs/perf/cf2/`; the prose cites them. Platform: Linux (WSL2) only.

## 0. Summary

1. **The setting.** `.route_pin_cache_slots(n)` on `LargeCacheConfig` (so also on `SeferAlloc::with_config`): the number of
   direct-mapped slots of the per-thread cache of route descriptors used by the foreign-free path. Rounded down to a power
   of two, clamped to `4..=64`, never panics; default 32 (the DZ-3 value). The array is sized for 64 slots; a per-thread
   mask selects the slots in use.
2. **Process-wide, first config wins.** Producer threads usually only free and never bind a heap
   (`current_for_dealloc` does not bind), so the value cannot travel with a heap. The first heap materialised with an explicit
   config publishes it (`Relaxed` `AtomicU8`, from `HeapCore::new_with_config`), each thread adopts it at its first insert
   into its cache, a different value from a later config is ignored (not counted by `config_conflicts_total`: that counter
   lives in `heap_registry`, whose sources are in the scope of many evidence rows).
3. **What a slot count buys (section A).** A direct-mapped cache keeps a cyclic or random order over `m` owner segments
   on the hit path only while the segments do not collide modulo the slot count. Measured hit rate of the cyclic order at
   m = 16 segments: 4: 0.00, 8: 0.00, 16: 0.00, 32: 1.00, 64: 1.00; at m = 32: 4: 0.00, 8: 0.00, 16: 0.00, 32: 0.00, 64: 1.00; at m = 64: 4: 0.00, 8: 0.00, 16: 0.00, 32: 0.00, 64: 0.00. Rule of thumb from the table: reliable up to
   about `slots / 2` owner segments (sparse segment addresses collide), perfect for a sequential order at every size.
4. **Time (section B).** ns per foreign free by slot count — cyclic order, m = 16 segments: 4: 80.3, 8: 85.2, 16: 86.5, 32: 29.0, 64: 30.9 (base 30.0,
   mimalloc 49.3); cyclic, m = 32: 4: 97.5, 8: 99.6, 16: 97.3, 32: 103.6, 64: 36.9 (base 95.9, mimalloc 68.2); random, m = 32: 4: 161.4, 8: 165.1, 16: 153.7, 32: 124.2, 64: 44.9
   (base 115.1, mimalloc 53.4); cyclic, m = 64: 4: 103.0, 8: 115.8, 16: 107.8, 32: 108.6, 64: 112.6 (base 108.7, mimalloc 48.3) — no
   slot count up to 64 serves 64 owner segments in a cyclic order.
5. **Cost of the setting (section C).** On the sequential hit path the 32-slot arm differs from base by -1.10 Ir per free (-0.12 %)
   (-1.32 Ir per free (-0.14 %) at 4 slots, -0.83 Ir per free (-0.09 %) at 64) — not measurable in instructions; time of the sequential order against base:
   0.79-1.07 over every arm and m (noise level of the machine), 0.86-0.99 for the default arm. A first version that wrapped
   the sweep cursor with a run-time modulus was 1.2–1.5 times slower than base in the miss regime and was fixed (section E).
6. **Too few slots are expensive, not neutral.** In the cells where the default hits (hit rate >= 0.99) and an arm does
   not reach the segments (hit rate 0.00), a free costs 554-696 extra Ir and 2.5-3.1 times the time of the default
   (section B, C); a slot count below the producer's owner segments is worse than the default, never better.
7. **Default stays 32** (section 3). Retention is the price of more slots (section D).

## 1. What was measured

- **Identity.** Base: `main` @ `3aab9681` (32 slots, no mask, `SeferAlloc::new()`). Change: git tree `3d5d28192a94e43c1246e499c8596e31eb4d1813` (branch `g1-cf2`), recorded before the run in `docs/perf/cf2/ident.txt`
  with the binary hashes, rustc and CPU. Arms: the change built with `PC_SLOTS` = 4, 8, 16, 32, 64 (the probe's
  `SeferAlloc::with_config(LargeCacheConfig::new().route_pin_cache_slots(PC_SLOTS))`), time builds with `production`, counting
  builds with `production bench-internals internals alloc-stats`; mimalloc through the same probe (`pincycle ... mi`).
  rustc 1.98.1, Linux 6.18 (WSL2), i7-11800H, shared with other sessions.
- **Entry point.** `SeferAlloc` as the `#[global_allocator]` of the probe process; the producer frees through
  `GlobalAlloc::dealloc` on another thread (the real foreign-free path `HeapCore::publish_foreign`); mimalloc through the
  same probe. The setting reaches the producer through the owner's bind, exactly as in a real program.
- **Config evidence per arm (R26-4).** Every counting run prints `slots_req` (the build-time request) and `slots_res`
  (`RoutePin::dbg_route_pin_cache_slots()` read on the producer thread after its frees); the script asserts
  `slots_req == slots_res == arm` for every counting run. One process per run (subprocess isolation; the registry is fresh).
  The conflict counter is not involved: the setting has none, and every process materialises one config.
- **Mechanism evidence (R30-8).** The hit rate itself is the activation oracle: hits + misses = frees is asserted per run,
  and the 32-slot arm must reproduce base's hit rate within 0.01 in every cell (asserted).
- **Shape.** The owner allocates `(m + 2) x 4096` blocks of 1 KiB, `m` segments of 2048 freed blocks each are chosen; one
  producer thread frees them in order `seq` (segment by segment), `cyclic` (one block per segment in turn) or `random`
  (fixed seed). Time per free = producer wall time / (m x 2048).
- **Statistics.** Time: medians of 9 interleaved processes per arm and cell. Hit rate: counting build, every cell twice,
  asserted equal. Extra Ir per free: callgrind program totals, `(total(arm) - total(base)) / (m x 2048)` (the set-up is
  identical across arms).

### E. Design iteration 1 (tree e5e1e9b0, superseded): the sweep wrapped its cursor with a variable modulus

| m | order | extra Ir per free, 32 slots vs base | sweep_dead_slots Ir (m = 32 cyclic), base / 32 slots | ns per free 32 slots / base, fixed order | rotated order |

| 32 | cyclic | 86.2 | 13261346 / 18646786 | 1.36 | 1.24 |

Cause: `self.sweep_cursor % slots` with a run-time `slots` compiles to a division and a bounds check inside the loop of `sweep_dead_slots`, which runs twice per miss. Fix: wrap with the mask and mask the index with the array capacity (section C and B are measured on the fixed tree).

## 3. Reading and the default

- **What the table says about the reach.** Hit rate 1.00 for a cyclic order needs the `m` owner segments to occupy `m`
  different slots, and the measured reach is about half the slot count: 8 slots serve 4 segments (m = 5: hit rate 0.60,
  that is 3 of 5 segments), 16 serve 8, 32 serve 16, 64 serve 32, and at `m == S` the cyclic order already misses on every
  free (section A). Inference, not measured here: on 64-bit Unix a reservation keeps `size + align` of address space
  (`docs/perf/OPEN_ITEMS.md` item 53), so the segments of one owner sit 8 MiB apart, the index `(address / 4 MiB) mod S`
  only ever lands on even slots, and the effective slot count is `S / 2`. On Windows the spacing was not measured. An index
  that spreads such a layout (a fold or a multiplicative hash) would double the reach for one to three more instructions
  on the hit path; it was not evaluated and is recorded as a follow-up. A sequential order never needs more than one slot.
- **Why the default stays 32.** 32 slots reproduce the shipped behaviour exactly (the 32-slot arm matches base's hit
  rate in every cell, asserted) and serve the shape that was measured to matter (a producer freeing into up to ~16 owner
  segments in any order, DZ-3). 64 slots add the m = 32 cyclic and random cells (section B) for twice the worst-case
  retention (section D); 16 slots and below lose the m = 16 cyclic cell (and part of the random one). A workload that fans in from more than ~16 owner
  segments per producer thread should set 64; a workload with few owner segments per producer and many producer
  threads can set 8 or 16 to cut the retention bound (sections A, D).
- **What does not work.** m = 64 in a cyclic order is not served by any count up to 64; at that size the cache is a
  loss of the lookup it was meant to save, with or without the setting.
- **The cost of the setting.** One more load on the hit path and none measurable: -1.10 Ir per free (-0.12 %) at the default against base
  (section C), the time of the sequential order moves by 0.86-0.99 of base (noise of this machine). In the miss regime
  (every free misses) the 32-slot arm is 1.00-1.08 of base in time (section B, cells m = 32 and 64, cyclic and random).
  The runtime-configurable count is therefore paid for with nothing the harness can see; the array grew from 768 B to
  1,536 B of thread-local storage per thread.
- **Safety.** Every site that stores or drops a pin keeps its ghost event (`pin-cache/held` +1 / -1 at the same places;
  the catalog counts per function are unchanged), the mask is written only while the cache holds no pin and never changes
  afterwards, the index is masked with the array capacity so it is in range for every value, and the sweep and `Drop`
  walk the slots in use or all of them respectively. `tests/route_pin_cache_slots.rs` pins the resolution (rounding,
  clamping, default) and the effect through a real `#[global_allocator]` built with 8 slots (a producer that only
  frees adopts the value and cannot hold more than 7 of 16 colliding segments hot; with the default 32 it would hold
  all of them).

## 4. Limits

- Linux only (WSL2), one machine shared with other sessions; the foreign-free path was not measured on Windows.
- One owner segment shape (1 KiB blocks, 2048 freed per segment), one producer thread; the retention column is the
  DZ-3 worst case (every class in use), not a measurement of this run.
- The MT controls of DZ-3 are not repeated: the arm with 32 slots differs from base by the mask load only.
- Section C counts instructions of the whole probe process; the set-up phase is identical across arms, so the difference
  is the frees plus the start-up noise of the process.

  base from `git archive` tars of the two trees, writes `counters.txt`, `ir.txt`, `time.txt` (kept gzip-compressed as
  `time.txt.gz`) and `ident.txt`.
- Tables and CSV: `node scripts/cf2_report.mjs` (writes `docs/perf/cf2/tables.md`,
  `docs/perf/CF2_ROUTE_PIN_CACHE_SLOTS_summary.csv` and this file from `doc_head.md`, `doc_tail.md` and the tables).
