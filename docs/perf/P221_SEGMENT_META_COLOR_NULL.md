# P221 — segment-metadata coloring against cache-set aliasing: NULL

`bench` — measurement only. No shipping or opt-in code changes; the probe's
code is not merged (its patch is kept as evidence in `docs/perf/p221/`).

## 0. Verdict

**NULL.** Spreading the hot per-segment metadata of 4 MiB-aligned segments
across 64 cache-line colors removes the simulated conflict misses that P220
blamed for the `growmix`/`wild` user-time gap, but it does not change process
CPU time on the real host. In all 24 measurable scenario×metric cells, the
95 % interval of x/base contains 1. The gap to mimalloc is the same with and
without the feature: `growmix` user is 1.465 base/mi and 1.469 x/mi.

The cache-simulator evidence that motivated the probe was real *in the
simulator*, but it does not carry over to this CPU. The probe is closed. The
`growmix`/`wild` user-time gap stays open, without a confirmed mechanism.

## 1. Hypothesis and probe

P220 (`docs/perf/P220_TEARDOWN_MISS_ATTRIBUTION.md`) found that on `growmix`
Sefer incurs 5.54× mimalloc's simulated LL read misses, almost all of them on
per-segment metadata reads on the free side. Every segment is 4 MiB-aligned,
so its header, bin table and state bytes sit at the same offset modulo every
power-of-two cache geometry.

Step 0 (`docs/perf/p221/cachesim_assoc.log`) kept the cache sizes and raised
associativity to 96 ways, on the same P220 binary and scenario (`growmix`,
seed 1, scale 0.25):

| arm | config | D1mr | DLmr |
|---|---|---|---|
| sefer | LL 96-way | 2,439,408 | 411,960 |
| sefer | D1 + LL 96-way | 1,668,388 | 411,968 |
| mi | LL 96-way | 1,687,353 | 288,638 |
| mi | D1 + LL 96-way | 1,667,028 | 288,636 |

Against P220's default geometry, where Sefer's DLmr is 1,613,864, the misses
fall by about 4×, and Sefer's D1 misses fall to mimalloc's level. In the
simulator, then, the excess misses are conflict misses.

The probe was an opt-in Cargo feature, `segment-meta-color`, implemented over
base `b7eed3cc`:

- Metadata placement: each segment's hot metadata block moves to
  `base + ((base >> 22) & 63) * 64`. That is 64 distinct line colors per 4 MiB
  stride, applied through the header/bin/state choke-point accessors.
- Large payloads: the payload start is pushed past the worst-case colored
  bound.
- Patch: `docs/perf/p221/segment_meta_color.patch.gz` (tracked diff plus 4 new
  files).

## 2. Measurement

- **Source identity.** The measured tree is recorded in
  `docs/perf/p221/identity.json` as base `b7eed3cc` plus a tracked diff with
  sha256 `02c93a4d…`. That hash was written to `measure_ident.txt` *before* the
  builds, and the same value was re-read after the run.
- **Binaries.** `examples/g1_wild_judge.rs` was built `--release` twice:
  - `base`: `--features production`;
  - `x`: `--features "production segment-meta-color"`.
  The two executables differ (sha256 `8ffc7da0…` / `90251ff2…`).
- **Arms.** `mi` is the base binary's mimalloc arm.
- **Schedule.** 7 scenarios × 3 arms × 12 blocks × 3 repeats = 756 runs. The
  arms are interleaved within each block. Every build and run was under
  `capc 10`.
- **Primary axis.** The primary axis is process CPU time (user + kernel), as
  P220 established. Under the 10 % cap, wall time is mostly throttle.
- **Statistic.** For each block, the per-arm minimum over its 3 repeats. Over
  the 12 blocks, the geometric mean of the per-block ratio, with a 95 % paired
  t interval. The tables are generated by `docs/perf/p221/report.mjs` from
  `ab.jsonl.gz`. The summary is `P221_SEGMENT_META_COLOR_NULL_summary.csv`.

### 2.1 Mechanism evidence and its limits

Coloring is a compile-time layout change. It is active in every segment of
the `x` binary, and the differing executable hashes are the evidence that the
arm ran it. No runtime counter was read from the judge.

The probe's own tests (accessor agreement, derivation, e2e round trip) were
never run. Its review was still open when the measurement finished: test
oracles were judged insufficient, and the anchor contract was restated. That
does not weaken a NULL verdict, because a correct-but-ineffective layout and
this one cost the same. It is the reason the code is **not** merged.

The planned cache-simulation rerun of the colored binary was not performed.
The WSL distribution disk came up read-only because the host volume was full,
and its recovery needs elevation.

## 4. Interpretation

1. **The simulator's geometry is not this CPU's.** callgrind models a
   modulo-indexed LL with the host's sizes. On the i7-11800H, L1D is 48 KiB
   12-way and L2 is 1.25 MiB 20-way. L3 is sliced by an address hash, so
   4 MiB-strided lines do not land in one L3 set the way they do in the
   simulator's LL. The 4× LL-miss excess that P220 attributed to aliasing is
   therefore, for the most part, a property of the model.
2. **The L1/L2 aliasing that does exist on the real CPU is not a measurable
   cost here.** Even where 4 MiB-aligned lines share real L1/L2 sets, removing
   the collision moves no cell outside noise. The interval half-widths are
   about ±3–12 % on the CPU axes.
3. **What stays open.** The `growmix`/`wild` user-time gap (1.47 / 1.24
   base/mi) remains, without a confirmed mechanism. Untested candidates:
   - the per-free touch of a distinct 4 KiB header page for each segment (TLB
     reach, which callgrind does not model);
   - fresh-block first writes (557 K vs 237 K simulated misses, P220 §3).
   Testing either needs hardware counters, which xperf cannot configure on
   this host, or a probe that changes the access pattern itself.

## 5. Reproduction

1. Base: `git worktree add <dir> b7eed3cc`.
2. Measured tree: apply `docs/perf/p221/segment_meta_color.patch.gz`
   (`gunzip -c … | git apply`). `git diff | sha256sum` must print
   `02c93a4d…`.
3. Build `examples/g1_wild_judge.rs` twice under `capc 10`, as in §2.
4. Run the paired runner from `docs/perf/p218/run_ab.mjs` with
   `--scenarios growmix,regrow,wild,grow64,grow1k,phase,large --blocks 12 --repeats 3`
   and the three arms.
5. Regenerate the tables: `node docs/perf/p221/report.mjs --csv <out.csv>`.
