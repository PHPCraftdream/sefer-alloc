## 2026-11-08 #48 source implementation amendment

This dated amendment records the current source state of the #48 control-sampling integration; it does not rewrite earlier amendments or the original preregistration. Status: **source implementation partial; tests and CI acceptance pending**. No local runtime behavior was observed, no J13b measurement exists, and there is NO GO. Do not describe #48 as fully accepted or as establishing valid remote-control sampling.

1. **Fresh-path controls are wired, but there is still no learner.** In the existing Linux/Android, `alloc-decommit`, non-`numa-aware`, fresh Large path with `align < SEGMENT`, an eligible `Auto` request takes exactly one process-global ordinal from `ThpRuntime::next_control`; the fixed process seed and aligned cohorts of eight choose exactly one control per complete cohort, including at share zero. Only a selected control calls `try_disable_transparent_huge_pages`, before the fresh header is written. `Auto`'s `auto_share` remains zero, so non-control requests also receive no THP advice. Selection has no thread, task, request identity, or per-request seed. This does not extend eligibility to cache hits, in-place growth, high-alignment (`align >= SEGMENT`) allocations, NUMA-aware builds, or other platforms.
2. **Owner-free sampling is wired before cache/decommit/release.** A selected control's mapping token is consumed by the owning Large free after its live credit is claimed and before cache deposit or unmapping. The runtime validates the header and samples only complete base pages inside the requested payload, excluding the header and leading/trailing partial pages. The planner places at most 16 disjoint, stratified windows, each no larger than 2 MiB; this is bounded observation, not full-payload observation. The resulting resident/sample counts are recorded, but no estimator consumes them and no learned share is produced.
3. **Spatial selection is deterministic and correlated.** The ordinal selects the control; the sampler's seed is instead fixed by request group (`group token XOR OBSERVATION_SEED`), not varied per request. Equal geometries in the same request group can therefore use the same window positions. The planner itself documents that clustered fill/reclaim can correlate with its contiguous windows and that this is not a representativeness guarantee. Sampling sparsity (at most 16 windows) and reclaim/swap bias of UNKNOWN direction remain explicit limitations.
4. **Mapping reuse and realloc invalidate first-life evidence.** Cache reuse clears the token through the targeted header update; `large_size`/`span_usable` updates clear it as well. A successful moving own realloc clears the old Large mapping's token before copying. A second cache life is not selected or sampled. Live mappings reached only by allocator teardown are not sampled.
5. **Remote owner reclaim is UNKNOWN, not a valid sample.** The foreign producer does not mutate the plain owner-only token. On owner-side remote reclaim, a pending control token is consumed and counted as invalidated (a failed no-THP premise is counted separately); the mapping is not sampled. This conservative skip is required because a foreign realloc/copy may leave the owner-only token stale. No claim of valid remote-control sampling is made, and no foreign-header protocol or producer mutation was added.
6. **Acceptance boundary.** The integration is partial while remote controls are skipped and tests/CI remain pending. The preregistered campaign, real judge acceptance, performance results, and any GO remain outstanding. Defaults, `Always`/`Off` semantics, production feature composition, dependencies, and unrelated allocator protocols are unchanged.
7. **Fresh-premise ordering proof.** The fresh OS reservation receives `MADV_NOHUGEPAGE` BEFORE the header write, terminal-word init and payload use, so no huge backing can pre-exist when the policy is applied. A failed premise yields an UNKNOWN token that is never sampled. The never-touched oracle `tests/j13b_control_premise_fresh.rs` asserts a fresh control mapping reads `resident == 0`.
8. **Reason-separated invalidation accounting.** Invalidated remote-reclaim consumption is recorded in telemetry field 3 and invalidated realloc in field 4 (token-derived group, exactly-once), with premise failures counted separately, so downstream #49 can quantify invalidation/lifetime bias. `tests/j13b_control_invalidation.rs` pins the in-place invalidation count; `tests/j13b_control_moving_realloc.rs` pins the move-leg invalidation and the OOM-preserved boundary. `tests/j13b_control_oom_shrink_invalidation.rs` pins the successful registry OOM-shrink fallback's exactly-once token consumption (a success token becomes realloc-invalidation, a failed-premise token becomes premise failure, a consumed token is never recounted) and the truly failed growth realloc's byte-identical preservation.
9. **Bounded alignment-slack owner geometry is accepted.** A reservation root strictly below the SEGMENT-aligned usable base is valid ordinary-backend geometry; pointer equality between root and base is NOT required. The oracle `tests/j13b_control_owner_geometry.rs` is a production-binding pure validator with exact-variant rejections; native slack presence is address-luck, which is why the oracle is pure. The owner-free sampler adopts the reservation contract-faithfully (usable base/span plus SEGMENT creation alignment per `from_raw_parts`' documented base-vs-reservation distinction, with the untouched root pair); unknown-token fail-closed accounting remains source-verified only — a native malformed-token injection oracle would require a raw-header token setter, which is a forbidden safe raw-pointer metadata mutation API.
10. **Concurrent competing-ordinal coverage.** `tests/j13b_control_concurrent_ordinal.rs` drives 64 competing eligible 16 MiB allocations through the installed GlobalAlloc on 4 barrier-synchronized threads. The oracle reads what the runtime actually consumed through the bounded bench-internals diagnostic ticket log (`dbg_thp_control_ticket_log`, reset per scenario) (bounded at 128 fresh records; entries are packed `ordinal << 2 | selected << 1 | valid`, so ordinals below 2^62 pack losslessly; an ordinal at or above 2^62 is stored as the explicit invalid marker 0 and a record count past the cap leaves the raw cursor above 128 — either condition makes the diagnostic hook return `None` instead of masquerading as complete evidence; this scenario's fresh window is 64 records captured between a pre-spawn reset and a post-join snapshot): the captured `(ordinal, decision)` records must be exactly the consumed window `[before, after)` with pairwise-distinct tickets — a lost, duplicated, or folded ticket (e.g. a selector fed the fetch_add return divided by the cohort length, which repeats ordinals 0..7 across cohorts while leaving the counter delta, the aggregate selection count, and any independent pure replay unchanged) turns the captured multiset red; every captured decision must equal the fixed-seed pure selector evaluated at that captured ticket; the per-cohort census over the actual captured decisions holds exactly one control per complete aligned cohort; and the true-decision count closes against telemetry selections (g2[0] == 8). Aggregate telemetry alone still proves neither property. A sliding 8-window may legally hold 2 controls and is never asserted per-window; pure selector tests and sequential allocations do not cover the competing-RMW property. The capture bounds themselves are regressed by `tests/j13b_control_ticket_log_capture_bounds.rs` (dedicated matrix row): the production packer and validity gate are exposed as pure diagnostic hooks, the asserts cover the 2^62 threshold (lossless round-trip at 2^62 - 1; marker 0 at 2^62 and above), marker-0 and over-cap windows rejected by the gate and hook, and a real 129-record window through the installed GlobalAlloc rejected as over-cap.
11. **Reserved-capacity invalidation captures the token BEFORE the helper.** The helper's span setter would otherwise clear it; success accounts exactly once, and failure preserves the token so the moving leg accounts exactly once. Dedicated activating row: `test-j13b-control-reserved-capacity-invalidation` (production large-reserved-capacity internals bench-internals).
12. **Remote consumption is asserted at the explicit guaranteed owner drain.** Only after `dbg_trim_current_thread`, with an exactly-once second-trim assertion; before the drain only the foreign-publication guarantees are asserted (telemetry field 3 is deliberately unconstrained).
13. **Failed-premise-through-realloc discrimination.** A failed-premise token (9..=14) consumed by a moving realloc is counted as a premise failure exactly once — never as realloc-invalidation, never double-counted (`tests/j13b_control_premise_recovery.rs`).
14. **VM activation evidence is two-layered.** Layer 1: the kernel VMA policy record (`/proc/self/smaps` `VmFlags: nh`) is REQUIRED on native Linux/Android (an unreadable smaps is a loud failure, never a silent pass). Layer 2: the mincore granularity oracle proves base-page fault granularity under any backing but cannot alone distinguish the no-THP operation from a no-op on an already-base-page host; unsupported backends return typed errors. HugeTLB rejection coverage is environmental.
15. **Unknown control tokens fail closed.** An unknown token is an observation error attributed to the recorded request size — never a token-derived group, never out-of-bounds (`tests/j13b_control_remote_unknown.rs`).

## 2026-11-06 #47 implementation amendment

This amendment records what the allocator-side implementation of task #47 actually does and supersedes only the statements named below; every older amendment and the original text stay as dated history. Status: implementation, CI pending. No test was executed locally, no J13b measurement exists, and there is NO GO of any kind. PR #224 (static J13 whole-mapping 8 MiB hint) is OPEN and ABSENT from this tree; nothing was merged or cherry-picked from it.

1. **Default mode is `Off`, not `Always`.** With no THP knob set nothing is published, the tuple reads as `(Off, 8 MiB, budget 0 = unlimited, CAUTIOUS)` and no Large mapping is ever advised: exactly today's behaviour. Supersedes the §2 table default (`huge_page_mode` = `Always`), the §0/§2(b) statements that the defaults reproduce PR #224, and the `d` arm "behaviourally identical to `base`" until a static baseline exists in the tree. `Always` here is a NEW range-advice implementation, not a J13 identity.
2. **Advice is issued before registration.** The aligned-vmem arm needs the live `Reservation`, so advice runs right after `Segment::reserve*` and before `forget(segment)`; the charge is a local until the header is written. The registration-failure release CAN therefore hold a charge locally and returns it through the release funnel after the unmap. Supersedes the §6 ordering sentence ("reserve OS → `register_payload` → … advise") and consequence (a) "the registration-failure release can never hold a charge". Covered by `tests/j13b_thp_registration_failure.rs` through the `internals` injection flag `dbg_set_inject_large_register_fail`, which forces the fresh-path registration failure only; a registration failure on the cache-reuse path is not injectable.
3. **Range primitive in ALL cases.** `Reservation::try_advise_huge_pages_range` over `floor(min(usable span, share × span, budget left) / 2 MiB) × 2 MiB` bytes from offset 0, including `Always` with an unlimited budget (a charge is taken only when the budget is not 0). No whole-mapping advise, no widening. Supersedes §2(b).
4. **The charge is returned AFTER the unmap**, by `release_large_mapping` at every terminal release site (the caller reads the charge first; storage is never read after the release). A freed budget therefore cannot be handed out while the old mapping is still advised. Supersedes "returned right before the terminal release". The charge is held through cache deposit and reuse; a cache hit neither re-advises nor re-charges.
5. **Explicit-only publication.** The process-wide tuple is published (first-wins as a WHOLE) only by a config that sets at least one of the four knobs; unset knobs take their defaults inside the published tuple. A config with no THP knob neither publishes nor conflicts.
6. **Conflict counting.** `AllocStats::thp_tuple_conflicts` counts a differing publication only at heap materialisation (`new_with_config_and_owner`); a re-claim of a recycled heap and the fallback heap are NOT conflict-checked (documented limitation). A loser that meets the winner mid-publication (`PUBLISHING`) never spins and counts one conflict, which over-counts a same-tuple race by one; readers in `PUBLISHING` see the default tuple.

**Explicit observable contract (supersedes §2's clause "a racing loser adopts the winner's published tuple"):** a racing loser does NOT adopt the winner's tuple — it counts exactly one conflict and no readable surface ever shows anything but the winner's whole tuple or the default; readers meeting `PUBLISHING` see the default tuple; a same-tuple race over-counts by one.
7. **`Auto` is a seam only.** The tuple is stored, published and readable, but the learned share comes from `auto_share`, which returns ZERO until scopes #48/#49 land: `Auto` advises nothing. Auto learning is NOT implemented.
8. **Charge storage: `SegmentHeader::thp_charge`** (bytes, `usize`), chosen over a `CachedLarge` field and a side table. A `CachedLarge` field alone is insufficient: a live mapping (after a cache hit, before its next deposit) has no `CachedLarge`, so the charge would need a second home plus copy-in/copy-out (two owners instead of one mapping-owned charge), and every cache slot would grow 48 → 56 bytes. A reservation-keyed side table needs a new sidecar with its own `unsafe` seam, atomics and model, and carries a stale-entry/ABA hazard once the keyed mapping is freed. The header field already travels with the mapping through deposit (only the magic word is cleared) and reuse (targeted field writes; the hit path debug-asserts the charge is unchanged), so no second copy or lookup exists. The header grows 128 → 136 bytes; the iai Ir effect of that and of the extra Acquire load on the fresh path is UNKNOWN until CI.
9. **Budget semantics.** The budget bounds ADVISED bytes (charged), not process RSS.
10. **UNKNOWN prerequisites (not established here):** the CI host's THP mode; real `madvise` partial failure cannot be forced in tests (classification is a pure function: validation error or error without an OS code ⇒ charge returned, error with an OS code ⇒ charge held); the aarch64 64 KiB-page huge-page size is not derived (granule 2 MiB plus a runtime `GRANULE % page_size() == 0` guard only); actual-source loom models of the cell and the ledger exist (`tests/loom_thp_tuple_cell.rs`, `tests/loom_thp_ledger.rs`), wired into the loom CI row (`scripts/loom.mjs`, ci.yml `loom (alloc-core alloc-xthread)`), executed only on CI; a kani harness remains open.

11. **Classifier-aware controls (clarified 2026-11-07, before measurements):** the 1 MiB cycle is a below-THP-threshold control, not necessarily a Small-class allocation. In the current `production` bundle, medium classes are disabled and the Small table ends below 1 MiB, so this request uses the Large path. Opt-in medium-class bundles may classify it differently. This corrects the older "small-path control" label without changing the cell or its numerical gates. The separate Small-hot-path Ir obligation must use an actually Small request under the exact measured feature set, with a classifier/path oracle. The runtime judge must verify the fresh-Large activation of each churn cell rather than infer it from its name.

## 1. What J13 left open (corrected cost model)

- **Accepted state** (J13 owner decision `docs/perf/J13_OWNER_DECISION.md`, on `g1-j13-go`/PR #224): every fresh Large reservation with request ≥ 8 MiB is advised `MADV_HUGEPAGE` over the whole mapping — WHEN GRANTED; a hint is advisory, the kernel may decline or partially grant, and `madvise` success ≠ huge backing. Measured there: cold first-round ratios 0.43–0.57 of base, page faults of a 1 GiB block 262505 → 874, cold cost +2 MiB of RSS per hinted-and-touched reservation (the huge page also holds the header page), a sparse two-page touch of a 128 MiB block costs ~0.4 ms instead of ~56 µs. The preregistered T2 RSS limits were exceeded by 2–142 KiB (granularity, not mechanism); accepted by the owner with the residual recorded: extra resident memory over many live, barely touched hinted blocks — 2 MiB per touched 2 MiB region, NO ceiling.
- **Why a count cap is not a bound:** the owner-decision line once described this follow-up as "a counter of live big reservations, cap 128". A count cap bounds nothing: one sparse 1 GiB block touches up to 512 separate 2 MiB regions, so even ONE hinted block can add hundreds of MiB; 128 such blocks add tens of GiB. Superseded by a byte budget on hinted ranges (§2).
- **Why "extra RSS ≤ budget" must NOT be claimed process-wide** (this corrects the earlier draft): the budget bounds the allocator's ADVICE — total bytes of ranges this allocator advised `MADV_HUGEPAGE` and has not released. It does not bound process RSS: with system THP `always`, the kernel backs memory regardless of hints (and `khugepaged` collapses outside our advice); the small-segment hint (`huge_page_after_segments`, shipped CF3) is a separate axis; kernel reclaim/swap changes residency under memory pressure; and madvise is advisory — the kernel may grant a hint partially or not at all. What IS true on a `madvise`-mode host for OUR mechanism: a hinted region, when granted, becomes resident as a whole 2 MiB page when any part is touched, so the hint-attributable extra RSS of one block is bounded by its advised prefix, and process-wide by the budget — the campaign checks exactly this bound in controlled cells (§8 B) on hosts recording `madvise` mode; on `always`-mode hosts those gates read NULL (invalid, not failed). With system THP `never` the budget still BINDS: madvise succeeds (advisory) and advice bytes are charged while no huge pages materialize — the campaign's budget counters remain valid there; Auto converges on true base-page residency and changes nothing observable — harmless but pointless.

## 2. Design: settings and hint computation

Settings table (Linux/Android; process-wide, each knob first-config-wins; see the coherent tuple publication contract below; defaults reproduce PR #224's RUNTIME BEHAVIOUR for successful allocations — not byte-identical .text, see §6/§12; a no-op elsewhere; forced `Off` under `numa-aware`):

| setting | default | meaning |
|---|---|---|
| `huge_page_mode(m)` | `Always` | `Off` — never hint Large blocks (the "never" switch); `Always` — hint every fresh eligible reservation, whole-mapping advise when the budget is unlimited, exactly as PR #224; `Auto` — the hinted share is learned per size bucket (§5) |
| `huge_page_block_min_bytes(n)` | 8 MiB | a fresh Large reservation whose **request** is at least `n` is eligible; the threshold compares the REQUESTED size (the `Layout` size), never the rounded span (`span_usable`); `0` = EVERY fresh Large reservation is eligible (it is NOT an alias for "never" — `Off` is the never switch) |
| `huge_page_budget_bytes(n)` | 0 | at most `n` bytes of advised range outstanding process-wide (`0` = unlimited); applies in BOTH `Always` and `Auto`; distinct from `LargeCacheConfig::budget_bytes` (the cache's own per-shard ceiling) |
| `huge_page_gradient(g)` | `Cautious` (used when mode is `Auto`) | the learning gradient: named `Cautious` / `Eager` / `Steady` or a raw parameter set (§5) |

Eligibility buckets (REQUEST size, MiB): `[0,1)`, `[1,8)`, `[8,32)`, `[32,128)`, `[128,512)`, `[512,∞)` — six, with no bucket undefined; the sub-8 buckets are reachable only when `min_bytes < 8` (default 8 MiB leaves them empty).

Hint computation for a fresh eligible block (request `S`, usable span `span` — SEGMENT-multiple in default builds, page-rounded under opt-in `exact-span-large`):

```text
share = 1                                  // Always; in Auto: bucket_share(bucket(S)) from §5
units = floor(min(span, share x span, budget_left) / 2 MiB)   // 2 MiB-aligned prefix of the MAPPING, floored, never beyond it
given = units x 2 MiB
hint  = MADV_HUGEPAGE on [span start, span start + given)   // given = 0 (units < 1) => no hint
charge := given                             // the ACTUAL bytes passed to madvise
```

Notes:

- (a) eligibility requires `S >= min_bytes`; the advised range is a 2 MiB-aligned prefix of the mapping, floored, never beyond it; `given = 0` when `units < 1` → no hint, no charge;
- (b) with mode `Always` and budget `0` (the identity branch) the implementation calls the SAME whole-mapping `Segment::advise_huge_pages()` PR #224 calls, and NO charge is taken — the mapping length may be a non-2 MiB multiple (under opt-in `exact-span-large`), which is fine there because the budget is unlimited; the identity gate (§8 D) depends on it;
- (c) whenever a budget is in force the range form above is used and accounting matches REALLY-ADVISED bytes; the span's un-advised tail keeps 4 KiB pages;
- (d) the prefix is a HEURISTIC: many programs fill blocks from the start (arrays, buffers), but NOT all programs do — no fill-pattern detection is claimed or attempted; the `stride` and `tail` cells (§7) measure what the prefix misses, and the learned share is the volume control that adapts.

**Coherent tuple publication (contract).** The knobs are published as ONE coherent resolved tuple — (mode, min_bytes, budget_bytes, gradient params) — with a single compare_exchange on first heap materialisation: the first publisher wins WHOLE; a racing loser adopts the winner's published tuple and counts ONE tuple-level conflict; per-knob conflicts disappear (per-knob separate first-config-wins could mix knobs from different racers into an incoherent config). Bounded: one CAS attempt + one read of the published tuple; no spin loops; safe under reentrant initialisation — publication must not allocate and must not re-enter the allocator. Publication contract: publish a FULLY INITIALIZED, IMMUTABLE, VALIDATED tuple with Release/Acquire pairing; no allocation, no re-entry, no unbounded spin. No arbitrary parameter set is promised to fit a single `AtomicU64`; the concrete representation and its proof are integration-scope decisions (loom/kani) made later. Tuple conflicts are counted by a DEDICATED THP tuple-conflict diagnostic delta counter `thp_tuple_conflicts`; it may optionally ALSO feed the existing global `config_conflicts_total` only in a way that does not change that counter's existing semantics for other knobs — an integration decision, NOT a wholesale redefinition of the global counter.

## 3. Shared state, cost, concurrency

- Process-global state follows the `THP_AFTER`/`publish_huge_page_after` template (`src/alloc_core/small/alloc_core_small/reserve.rs:31`–`:63`) — upgraded to the coherent tuple of §2: the published tuple (first-wins-whole CAS, relaxed reads), the budget word, per-bucket estimator words (§5), the control pseudo-random state, and `bench-internals`-gated observers SPLIT into `charged_bytes` — the strict ledger (advised bytes now/peak/total), which exists ONLY when a budget is in force — and `advised_bytes` — the observation counters (advised-bytes now/peak/total, observations per bucket, controls issued/observed, share per bucket, mincore errors), ACTIVE in EVERY mode including the unlimited identity branch. The unlimited branch needs no charge ledger, but its observers stay honest and active. Estimate words are updated with relaxed load/store — a lost update is a statistical error, not a safety one; statistics may aggregate. The budget is different: it is STRICT — a compare-and-swap reserve/rollback loop (never overshoots, never negative; a concurrent return between read and CAS only fails the CAS and retries with a fresh read; transient under-estimation of available budget is conservative and allowed).
- Hot paths untouched: small alloc/free never reads or writes any of this state; large cache hits touch only their own charge metadata (§6); the budget CAS and share computation run only on the fresh-reservation slow path. Justification for adding a process-wide synchronization point (answering perf-index item 30's earlier decline of exactly this shape for cache retention): (1) this budget is the treatment under test — the mechanism J13b exists to validate, not infrastructure built in case; (2) HYPOTHESIS (tested, not assumed): fresh reservations of ≥ 8 MiB are rare events and CAS contention is negligible — the threshold is configurable and churn frequency can be huge, so §7 carries `churn` (default threshold, parity asserted) AND `churn-small` (every fresh Large reservation eligible — this cell MEASURES the CAS/branch cost at maximal eligibility frequency; no parity promise, kill only on an invariant violation); (3) the no-background-thread constraint is respected — charges return only at existing release events (§6), nothing shrinks back on a timer (item 13's unsolved idle-shrink problem does not arise: the budget gates NEW hints, it never reclaims).
- Every new atomic/ordering site added at implementation time needs a catalog scope in `docs/verification/ghost-rules.json` (+ rule, fixture, `Invariant-Check:` trailer) per CLAUDE.md's ghost rules; ghost code adds no fields, writes no production data, allocates nothing.
- Bounded cost summary (constants named here, fixed analytically, re-checked by pure-function tests in the implementation phase, never presented as measured sweeps): observation of one freed eligible block = at most `K = 16` evenly spaced 2 MiB regions, one `mincore` call each (the primitive returns resident/sample COUNTS per call, not raw vectors — §0/§12.2); control reservations: rate `R = 1/8` of eligible fresh blocks when the bucket share is > 0, by STRATIFIED SYSTEMATIC selection: eligible fresh requests are grouped into consecutive blocks of 8; within each block the control index is drawn by the bounded PRNG once per block — at most 1 control per 8 eligible requests is a HARD deterministic bound, the expected rate stays 1/8 (a bounded PRNG alone gives no per-window hard cap; this does). This is bounded decorrelation, still NOT a representativeness guarantee. Nothing else ever reads `/proc` or calls `mincore`; there is NO live sampling of still-mapped blocks (§4).

## 4. Signal acquisition (residency), with its defects defined

- **Observation `o`:** the fraction of RESIDENT BASE (4 KiB) pages in the sample. Each `mincore` call over one 2 MiB region returns a 512-entry vector (one entry per 4 KiB page); `o = (resident entries summed over the ≤ K = 16 sampled regions) / (entries sampled)`. Taken ONCE per freed eligible block (at free/deposit, before the block is cached or released), and ONLY for VALID UNHINTED observations — see below. Rationale: a region-level metric ("fraction of regions with at least one resident page") reads ≈ 1.0 even on unhinted controls for one-byte-per-region fills; the base-page fraction separates dense (≈ 1) from sparse (≈ 1/512 per stray touch).
- **Input discipline (who feeds the estimator):** ONLY valid UNHINTED fresh observations feed the estimator. When a bucket's share is 0, every eligible fresh block is unhinted, and the SAME stratified selector throttles observations to ≤ 1 of every 8 eligible frees (NOT mincore on every free) — each throttled observation is clean. When share > 0, ONLY control reservations (drawn unhinted by the stratified selector of §3) feed the estimator; every NON-control eligible fresh block follows the policy (hinted per share) — a control is NEVER hinted in its first life. NO hinted residency feedback EVER: a hinted region reads fully resident on any touch, so 63 self-confirming signals against 1 clean control cannot learn dense-vs-sparse.
- **Control selection:** STRATIFIED SYSTEMATIC (§3): eligible fresh requests grouped into consecutive blocks of 8; the control index within each block drawn by a bounded PRNG (32-bit xorshift/LCG seeded at tuple publication, one draw per block) — at most 1 control per 8 eligible requests is a HARD deterministic bound, expected rate 1/8. Explicitly a bounded-cost + bounded-decorrelation mechanism, NOT a representativeness guarantee; a plain deterministic every-Nth counter was rejected (it correlates with periodic workloads, §11). The rate `R = 1/8` is analytic and revisable only via the constants phase (§5). Rationale: the estimator's ENTIRE input is controls, so the rate sets learning speed and the hint-benefit cost (1/8 of eligible blocks give up the hint).
- **Defect 1 — self-confirmation (metric rationale, kept):** an advised region, when granted, becomes fully resident when ANY byte is touched, so for hinted blocks any region-level signal reads ≈ 1 whenever the program touched anything at all. The base-page metric plus the unhinted-only input discipline are the mitigations.
- **Defect 2 — history contamination:** a cached, reusable block carries residency history from its previous life (the cache keeps pages mapped; J14 C2 §5 confirms reused spans stay faulted in). Its `o` is NOT a clean observation of the current occupant: only FIRST-life blocks (fresh-reservation lineage, one flag at hand in the reuse path) are observed; second-life blocks are never observed and never counted as controls. Reused blocks are also never re-hinted (§6), so they never re-enter the hint state.
- **Defect 3 — reclaim bias:** `o` is an ESTIMATE with bias, not an exact record of program behaviour: kernel reclaim/swap lowers measured residency (swapped-out anonymous pages read as not resident), `MADV_FREE`-style drops and `MADV_DONTNEED` decommit clear residency the program did logically touch. DIRECTION IS UNKNOWN, not assumed downward — no exactness and no sign claim anywhere; recorded as UNKNOWN.
- **Defect 4 — never-freed blocks:** a long-lived block is never freed and never observed. For v1 this is accepted explicitly: learning WAITS FOR FREES; long-lived blocks are unobserved until freed (their control, if ever drawn, applies at their free). There is NO live sampling, NO sampling of other/foreign mappings, NO background threads, NO pinning, NO live-block registry, NO locks on mappings: without pinning, `mincore` on a concurrently unmapped range races unmap, and a per-free-rate sampler observes nothing when there are no frees. `mincore` runs ONLY on the free/deposit path under the existing guarantee that the mapping is live and owned by the allocator at that point (before `os::release_segment`).
- **Errors and unknowns:** `mincore` can fail (`ENOMEM` unmapped, `EFAULT` buffer, partial vectors). Defined handling: single attempt, no retry; on failure the observation is UNKNOWN — the estimator is not updated and an error counter increments; the block's lifecycle proceeds unchanged. UNKNOWNs recorded explicitly (labelled, not directional): reclaim/swap bias; sampling sparsity (≤ K regions of a possibly large block); THP-`always` hosts — where even unhinted mappings get huge pages and the base-page metric reads ≈ 1 regardless. The metric is valid ONLY where the mapping is base-paged (madvise-mode hosts for unhinted ranges). On a THP `never` host hints are no-ops; observations still flow (they measure true base-page residency), learning converges but changes nothing — harmless by construction.
- **What no estimate can see:** a "one byte per 2 MiB region" touch pattern reads ≈ 1/512 in the base-page metric on a clean control — the metric is chosen exactly to expose it. Where sampling misses it (≤ K regions), the UNKNOWN above applies. The budget (§2) remains the answer to invisible fill.

## 5. Learning and gradients (corrected semantics)

- Buckets are by REQUEST size groups — the six of §2: `[0,1)`, `[1,8)`, `[8,32)`, `[32,128)`, `[128,512)`, `[512,∞)` MiB (sub-8 buckets reachable only when `min_bytes < 8`). The learned quantity is the HINT VOLUME (share), grouped by size; the allocator never learns or identifies "which allocation", thread, task or business process made it — two workloads of one bucket are indistinguishable, and the budget plus the `Off` switch are the escape hatches. Frequency is not a learned axis: a block served from the Large cache is not a fresh reservation and is not hinted again, so a reuse-heavy workload does not touch this state.
- **Input source:** the estimator consumes ONLY valid unhinted observations per §4 — when share > 0, controls at rate `R = 1/8` (stratified systematic selection, §3/§4); when share = 0, throttled observations at ≤ 1 of every 8 eligible frees (NOT mincore on every free). Learning latency is explicitly acknowledged: the input rate IS the control rate, and long-lived blocks are unseen until freed — the estimator's clock is frees, not wall time or allocations.
- Per bucket, two fixed-point words (named scale; exact width is an implementation decision pinned by pure-function tests), both starting at 1 (a fresh process behaves as without learning): `e` follows the observation asymmetrically — `e += (o - e) >> down_shift` when `o < e`, `e += (o - e) >> up_shift` when `o >= e`; `m` is the slow long-run mean, `m += (o - m) >> mean_shift`. Estimate `est = e + anchor x (m - e)`, `anchor` in `[0,1]`. Bounded curve to share: `share = 0` if `est < floor`, else `min(1, gain x curve(est))`, where `curve` is an EXPLICIT bounded fixed-point curve ENUM `{ SqrtGenerous, Linear, SquareStrict }` (generous ≈ the old gamma < 1, Linear = gamma 1, strict ≈ gamma > 1), chosen per gradient — NO float pow, no_std-friendly; shares are always in `[0,1]`.
- Named gradients (the program picks one, or writes its own numbers; historical names `Cautious`/`Eager`/`Steady` and their shift/floor/gain/anchor parameters are KEPT — each named gradient now also names its curve: Cautious → Linear, Steady → Linear, user sets pick the curve): `Cautious` (default): `down 2, up 5, mean 5, anchor 0, floor 0.10, gain 1.25, curve Linear` — falls fast, rises slowly; `Eager`: `down 5, up 2` (other parameters as Cautious) — gives the hint up slowly, regains it fast; `Steady`: `down 3, up 3, mean 6, anchor 0.5, curve Linear` — a smoothed middle. Shifts are rates `2^-shift` per observation. Expected public types: `LargeThpGradient` (parameters + curve choice) and `LargeThpEstimator` (per-bucket words). Closed form: after `n` same-class observations of value `o` from `e0`, the final word is `e_n = o + (e0 − o)·(1 − 2^-shift)^n` — deterministic per exact stream (fixed-point arithmetic only, no float pow).
- **CORRECTED comparative semantics** (this fixes the earlier draft's gate): Eager falls more slowly and rises faster than Cautious; under the same observation stream Eager's estimate stays ≥ Cautious's throughout (both maps are monotone in the current estimate and Eager's retention factor `(1 - 2^-down)` is larger, its recovery factor `(1 - 2^-up)` larger; a one-line induction over identical `o` streams proves the inequality — the implementation's pure-function tests pin it). CONSEQUENTLY there is NO claim, gate or expectation that Eager ≤ Cautious during dense recovery: Eager grows fast and can legitimately stay ABOVE Cautious while both recover. The `Eager ≥ Cautious` monotonicity is a PURE-FUNCTION property tested on identical synthetic streams (§8 decision), NOT a campaign gate — real arms have different control draws and feedback histories, so no pathwise relation between measured Auto arms is asserted.
- All constants (buckets, `K`, `R`, the three named gradients and their curves) are fixed here analytically; they are validated by pure-function tests (§8 decision) and may be revised later only through a separate constants phase (pure functions, no OS) with reasons — they are never presented as measured or tuned.

## 6. Lifecycle invariants (the charge protocol)

- Charge = the block's `given` (bytes ACTUALLY passed to madvise; 0 in the Always-with-unlimited-budget identity branch). Charge storage is NOT decided here: the charge is mapping-owned metadata whose lifetime is bounded by the mapping. Candidate locations, decision deferred to the implementation scope: (a) a `SegmentHeader` field — with a MANDATORY explicit review of every cached-header overwrite/reinitialisation site (cached headers get rewritten: magic zeroed at deposit, targeted rewrites on reuse, fresh init, `begin`/`finish_large_reuse`); (b) a `CachedLarge` field carried at deposit and back at reuse; (c) a reservation-keyed ancillary slot. Mandatory obligations whichever is chosen: enumerate and review every cached-segment header overwrite/reinit site; invariant "no charge access after `os::release_segment`" with a test; layout pins/mirror tests re-checked. Zero-cost and layout-pins claims are NOT pre-confirmed — they are verification items of this scope.
- Ordering at reservation: reserve OS → `register_payload` → compute eligibility/share → CAS budget reserve → advise range → on a validation or injected pre-syscall failure return the unused charge; on an OS error whose partial effect cannot be excluded, retain the full reserved charge conservatively until mapping release (unless a separately verified rollback proves the advice removed) → store the surviving charge → return. Success confirms accepted advice, not physical huge backing. Failed OS advice is not assumed all-or-nothing. Consequences: (a) the registration-failure release (`alloc_large_slow`'s `os::release_segment` at `src/alloc_core/large/alloc_core_large.rs:687`) can never hold a charge — asserted in tests; (b) relative to PR #224 the only behavioural difference on a FAILED allocation is that the mapping is not advised before being released — unobservable to the program.
- The charge is held across the whole life of the mapping, through cache deposit and reuse: a cache hit does NOT re-hint and does NOT re-charge (the hint is a property of the mapping; re-faults after decommit do not re-charge either — MADV_DONTNEED splits huge pages back but the advice and its charge persist once for the mapping's lifetime); the charge is returned EXACTLY ONCE, at the mapping's single terminal `os::release_segment`, riding the existing `LargeReservationState` single-release invariant.
- The definitive list of charge-return sites (every `os::release_segment` a Large mapping can reach): own-thread dealloc not-admitted eager release (`mem_impl.rs` `dealloc` Large tail, both the deposit-reject and the no-`alloc-decommit` arms); remote-free `reclaim_large_segment` not-admitted release; `evict_one_oldest` victims (deposit eviction loop, decay/trim drain); `release_cached_on_drop` for base and `large-cache-extended` cache slots at teardown; the live-segment walk in `Drop for AllocCore`; the two cached-slot fallback releases inside `alloc_large` (`begin_large_reuse` failure; `register_payload` failure on reuse). `numa-aware` builds have no mechanism and no charge. Realloc is covered (the old block frees through the normal dealloc path); remote free through `reclaim_large_segment`; teardown/Drop through `lifecycle.rs`. Tests must assert: `budget_left >= 0` always; Σ outstanding charges ≤ budget always; charges return to 0 only after full teardown of any cell (NOT after frees — cached blocks keep their charge); no double return (one return per mapping).
- No user callbacks exist or will exist inside the allocator; all observability is via counters read from outside.

## 8. Gates (fixed now)

- **D, identity of the defaults.** `d` vs `base`: the cold interval of every cell contains 1 (A/A included), faults within 5 %, end and peak RSS within 256 KiB. Behavioural identity of successful allocations (same whole-mapping advise as PR #224) is the PRIMARY D claim — NOT byte-identical .text — plus an iai DEFAULT-PATH probe with the SAME compiler/flags: the preregistered expectation is target 0 Ir delta on the small hot path; ANY nonzero Ir delta is recorded and individually reviewed before acceptance — NO blanket/unspecified tolerance, no pretend evidence.
- **T0, mechanism (hard asserts per arm; primary oracle = the allocator's own targeted counters).** (a) `n`: the advised (observation) counters read 0 (PRIMARY; the charged ledger does not exist without a budget, the observation counters are active in every mode). `Off` disables only LARGE hints — small-segment THP (CF3, from the 16th segment) and foreign mappings still raise `AnonHugePages`, so `AnonHugePages` is used ONLY as a corroborating DELTA vs the `Off` arm (baseline subtraction), never as an absolute-zero assertion. (b) `b` and `ab` in `sparse`: advised peak ≤ budget and ≥ 90 % of it; after the cell's frees, advised-now equals the charge held by cached hinted blocks (counter-consistency assert: advised == charged in budget arms) — NOT 0; advised-now == 0 only after explicit trim/teardown of the cell's allocator. Post-free non-zero advised-now is NORMAL. (b-i) identity branch (`Always` + budget 0): the charged ledger is NOT required — no claim that advised == charged there; the advised counters stay ACTIVE (peak ≈ advised spans). (c) `a` in `phased`: a TRAINING-CRITERION design — per bucket, the training phase collects valid observations of its window class (sparse: o < 0.1; dense: o > 0.9) until ≥ 96 valid observations or the 1536 cap; judged by the ACTUAL ATTAINED SHARE after training: sparse-trained share < 0.5; dense-trained share ≥ 0.9; cap hit before 96 → the gate reads INCONCLUSIVE explicitly, DISTINCT from FAIL/NULL-by-mechanism. NO analytic gate of the form "mean o > 0.9 implies share ≥ 0.9": window order is not bounded by a mean; the windows are constructed single-class by the cell design, and the final word after n same-class observations has the closed form e_n = o + (e0 − o)·(1 − 2^-shift)^n (deterministic per exact stream; fixed-point, no float pow). Honesty about the arithmetic (why training to ≥ 96, not 12): Cautious up-rate is 5 → 1/32 per observation, so after 12 dense obs from e ≈ 0.08, e ≈ 1 − 0.92·(31/32)^12 ≈ 0.37 — the earlier "≈ 0.97 after 12" claim was WRONG (it used up-rate 1/4); e ≥ 0.92 needs ~80 clean dense observations; e ≥ 0.72 (needed for share ≥ 0.9 on the Linear curve) needs ~38. Exact synthetic streams get a formula/rounded oracle in PURE tests only (§8 Decision, §12.3); the prose carries NO per-round analytic promises. In `mixed`: the sparse `[32,128)` bucket — trained share < 0.5 after its training criterion (≥ 96 valid o ≈ 0.02 observations), else INCONCLUSIVE; the dense `[8,32)` bucket trained as in `phased` (buckets do not mix). (d) Direction of change, per arm, for `a` and `ab` only: each Auto arm's share decreases across the sparse training phase and increases across the dense training phase (strict in at least one window of each kind). NO `ae` arm and NO pathwise inter-arm gradient relation (§5). Failing T0: no claim, NULL.
- **B, the budget bound (madvise-mode hosts; NULL elsewhere).** `b` in `sparse` 128×16 MiB: end and peak RSS at most `n`'s + budget + 256 KiB; in `many` 128×16 MiB the same bound; `b`'s cold vs `n`'s wholly below 1 (the advised prefix, when granted, still helps) — this benefit gate applies ONLY when the mechanism counters show activation and the cell is readable; `b` vs `base` (unlimited Always): lost speed is REPORTED descriptively, NEVER gated — with a 256 MiB budget on 2 GiB dense a ceiling such as 1.40 can be mathematically unattainable (almost everything legitimately falls back to unhinted speed), and this prereg does not pretend otherwise.
- **L, the learning adapts both ways.** `a` in `phased`, TRAINED windows only (cold/training/trained never pooled): after the sparse training criterion passes (≥ 96 valid o < 0.1 → sparse-trained share < 0.5; else INCONCLUSIVE): sparse-trained peak RSS at most `n`'s + 25 % of (`base`'s − `n`'s); after the dense training criterion passes: LEARNING EFFECT — on dense TRAINED windows `a` vs `f` is margin-equivalent: pre-declared margin ±5 %, the 95 % CI wholly inside the margin; a noisy window → NULL/unreadable (statistical nonsignificance is NOT equivalence). `mixed`: the sparse huge-bucket RSS at most `n`'s + 25 % of (`base`'s − `n`'s) once its training criterion passes (per-sub-window RSS only, never pooled); the dense part: policy-vs-Always overhead at EQUAL budget — `a` vs `base` on dense trained cells carries a DECLARED ceiling ≤ 1.20.
- **C, the three compose.** `ab` meets B's bounds and L's share behaviour in the same runs; on dense trained cells and in `many` 128×16 MiB: policy-vs-Always overhead at EQUAL budget — `ab` vs `b` carries a DECLARED ceiling ≤ 1.20 (there is NO "ab vs b interval contains 1 / learning costs nothing" claim — the declared 12.5 % expected exploration cost forbids it); `ab` vs `n` wholly below 1 (the hint still helps under budget+learning). Learning effect is judged `a` vs `f` (identical exploration/observation cost), NOT vs an instrumentation-free arm. No comparison to unlimited `base` tighter than the declared ceiling is required.
- **S, the cost of observing and of the shared state.** Free time of a 128 MiB block with the cache off: `a` − `d` ≤ 0.5 ms (≤ 16 `mincore` calls; per-call cost reported); control overhead reported and bounded (≤ R of eligible fresh reservations); `churn` (default min 8 MiB): the budget invariants of §6 hold (never negative, Σ ≤ budget, one return per mapping) — a correctness kill, not a timing gate — and `a` vs `d` is judged margin-equivalent (pre-declared margin ±5 %, the 95 % CI wholly inside; a noisy window → NULL/unreadable; otherwise the measured cost is reported — CI non-significance alone is never equivalence) (the rarity hypothesis asserted at default threshold); `churn-small` (`min_bytes` 0, cache disabled): reports the a-vs-d throughput ratio AND the measured span traffic (≈ 4 MiB/op ≈ 64 GiB total — counted, reported as data) and asserts the budget invariants — NO parity promise, this cell MEASURES the CAS/branch cost; kill only on an invariant violation.
- **Kill.** Any gate above failed; any benefit cell (`cycle` 128 MiB, `cycle` 1 GiB, `grow` 1 GiB, `many` 128×16 MiB) whose `d`/`base` interval lies wholly above 1.10 (the default arm only; Auto is subject to its explicitly declared exploration-cost gates, not this contradictory 10 % kill); `cycle` 1 MiB (control) faults differing by more than 5 %; any §6 invariant violated (in `churn`, `churn-small`, or tests).

## 10. What this does not claim

Windows is unchanged by construction; `numa-aware` builds exclude the mechanism; system THP `always`/`never` arms are not measured (on `never` the hint is a no-op BUT the budget still binds — advice is charged while nothing is granted; on `always` the budget neither removes nor adds kernel-backed memory); a hint's effect is described only as "when granted" — the kernel may decline or partially grant, and `madvise` success ≠ huge backing; residency is an estimate with UNKNOWN-direction bias and ≤ K-region sampling sparsity, not an exact record; on THP-`always` hosts the base-page metric reads ≈ 1 regardless and the metric is invalid (recorded UNKNOWN); the rarity of ≥ 8 MiB eligible reservations is a HYPOTHESIS measured by the churn cells, not a fact; control sampling is a bounded-cost + decorrelation attempt, NOT a representativeness guarantee; learning latency until frees is acknowledged — long-lived blocks are unobserved until freed; the charge storage location is NOT decided here — only candidate locations and mandatory verification obligations; two workloads of one size bucket are indistinguishable — no thread, task or business-process identity exists, and the async scheduler is untouched; the prefix heuristic is not assumed to fit all programs (stride/tail cells measure the gap); constants are analytic, not tuned or measured; the budget bounds advised bytes, not process RSS and not kernel behaviour; J13's measured benefit is cited, not re-claimed; no mimalloc-parity claim is made through the magnitude rule (that rule governs `bench:table` GO decisions; this campaign carries its own preregistered gates); defaults are behaviourally identical to PR #224 for successful allocations, not byte-identical in .text.

## 11. Decided against (with reasons)

Per-thread or per-block overrides (a program's business processes are abstract; async tasks move between threads; a per-thread rule could crowd some threads and starve others — runtime-wide settings, the allocator learns inside them); count caps on hinted blocks (bounds nothing — §1); billing the hint by measured residency (self-confirming signal, reclaim bias, bounded-cost violation — the budget bounds advice instead); LIVE SAMPLING of still-mapped or foreign mappings (without pinning, `mincore` on a concurrently unmapped range races unmap; and a per-free-rate sampler observes nothing when there are no frees — learning waits for frees instead); TAIL-SAMPLING of partly-hinted blocks (technically unhinted, but tail position correlates with the prefix heuristic and fill order — not a clean instrument); DETERMINISTIC every-Nth control selection (correlates with periodic workloads — stratified systematic selection instead: fixed blocks of 8, PRNG-drawn control index per block, a hard ≤ 1-per-8 bound with bounded decorrelation); PER-KNOB independent first-config-wins (mixes knobs from different racers into an incoherent config — coherent tuple publication instead); PRE-DECIDED header storage of the charge (cached headers get rewritten/reinitialised at multiple sites — candidate review + obligations instead); user callbacks inside the allocator; async-scheduler integration; kernel-cooperation modes (THP sysfs) — outside the allocator's control. Also superseded from the earlier draft: the RSS ≤ budget process claim (§1), the cap-128 lineage, and the recovery-order gate `Eager ≤ Cautious` (§5).
