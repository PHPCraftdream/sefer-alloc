# iai-callgrind Ir baseline — no-LTO row (user-default codegen)

Second perf-gate row for `benches/perf_gate_iai.rs`. The existing
`iai-callgrind` row measures the workspace's own tuned build
(`[profile.bench]`: `lto = "thin"`, `codegen-units = 1`); a downstream LIBRARY
USER of the published crate compiles with THEIR profile — Cargo's defaults
(`lto = false`, `codegen-units = 16`). After the planned crate extractions
(`docs/plans/2026-11-15-workspace-restructure-plan.md`, P1/P2),
cross-crate inlining in such a user build is limited to `#[inline]`/generic
functions; workspace-local thin-LTO can no longer glue crates together. P1.0
therefore records this row's `Ir` base on the UNSPLIT tree, BEFORE the first
extraction; step P1.6 (inline audit) expects delta 0 against it, and every P1
extraction PR compares its run against this row.

## How the CI row is built

- Job `iai-callgrind-nolto` in `.github/workflows/perf-gate.yml`
  (workflow_dispatch-only today, like the whole gate).
- Same bench (`perf_gate_iai`) and feature set
  (`production bench-internals internals`) as the existing `iai-callgrind`
  row.
- Profile overridden by env vars, not manifest edits:
  `CARGO_PROFILE_BENCH_LTO=false` + `CARGO_PROFILE_BENCH_CODEGEN_UNITS=16`
  (cargo env-overrides-manifest precedence). `lto = false` is the user default
  itself — cargo's "thin local LTO", NOT `off`.
- Baseline name `main_nolto` — iai-callgrind baseline names accept only ASCII
  `[A-Za-z0-9_]` (a hyphenated `main-nolto` made the job's first CI run fail)
  — with cache keys `iai-baseline-nolto-main-*` (kebab-case is fine for cache
  keys; the prefix deliberately doesn't start with `iai-baseline-main-`, so
  the two rows' caches never mix).
- CI threshold identical to the existing row (inherited
  `IAI_CALLGRIND_REGRESSION: 'Ir=10'`); the plan's "delta 0" for P1.6 is the
  audit expectation read from recorded numbers, not a CI threshold.
- The baseline numbers come ONLY from GitHub CI runs — local iai/valgrind
  execution is forbidden by CLAUDE.md.

Raw benchmark output: `docs/perf/_raw_iai_nolto_baseline_20261115.log` (setup and build steps cut, marked `# TRUNCATED`; the full log is `gh run view 43712417106 --log --job 132806673508`). Summary CSV: `docs/perf/IAI_NOLTO_BASELINE_summary.csv`. The CSV and the section below were generated by `scripts/iai-nolto-summary.mjs` from that log; no number here is typed by hand. The first two attempts of the row failed for reasons found only by real CI logs (a baseline name with a hyphen, then ANSI colors the script did not strip) and are fixed in the history of this file's PRs.

Instruction counts are deterministic; these are not wall-clock measurements.

## Functions at risk on future crate boundaries (annotation, not a measurement)

- `os` helpers used on the free path (extraction step P1.4,
  `sefer-platform`): every cross-crate call not inlined in a no-LTO build
  adds its call overhead to the free hot path.
- Config reads on the Large path (extraction step P1.3, `sefer-policy`).

This row is how those costs will be detected — `Ir` delta of a later
extraction run vs this baseline. No code is changed by this task.

## Comparison discipline

- Compare only same-row runs: this row against its own `main_nolto` baseline;
  never against the thin-LTO row's numbers — different binaries.
- Bench-name sets must match exactly between the runs being diffed (the
  summary script enforces it).
- `Ir` is deterministic per binary+input (callgrind), so any nonzero delta is
  a real code/codegen change to explain.
