## Decisions

- Trusting a `run_in_background` wrapper's bare exit-code/status summary
  without reading the actual log content is unsafe — established as a hard
  rule for the rest of this session after the rustfmt incident. Every
  verification log in #2003/#2004 was read/grepped directly before treating
  it as evidence.
- #2001's `required-features` fix for the Sol-F1 negative probe was reverted
  because it was diagnosed against a command (`--all-targets --features
  production`) that doesn't match any row the real check matrix runs —
  chose to fix the DIAGNOSIS (revert to the narrower, already-correct state)
  rather than patch around the symptom a second way.
- #2003's regression test: chose a standalone fixture-crate (mirroring
  `tagged-index-stack`'s established pattern) over a root `[[example]]`,
  specifically because this probe's failure is UNCONDITIONAL once a feature
  is on (unlike the narrowly-conditional Sol-F1 probe), so no
  `required-features` string could both satisfy the oracle's own build and
  stay invisible to every real `--all-targets` row simultaneously.
- #2004's bound placement: per-method `where T: Send + 'static`/`T: Sync`
  clauses on the specific destructive/shared-read operations, NOT a blanket
  bound on the whole `EpochRegion<T>` struct or impl block — verified
  `Drop`/`with_capacity`/`len`/`is_empty` genuinely don't need it
  (`drop_value` is a synchronous same-thread drop, no collector deferral),
  and this sidesteps Rust's Drop-impl-bound-mismatch restriction (E0367)
  entirely rather than needing to reason through it.
- Both #2003 and #2004 used an EMPIRICAL PROBE-FIRST methodology before
  writing any fix: reproduce the claimed defect with a minimal repro,
  confirm it actually behaves as the review claims (catching one case,
  R2-01, where an existing code comment claimed the OPPOSITE), only then
  design and apply the fix, then re-run the SAME probe (now as a permanent
  regression test) to confirm the fix closes it. This is now the working
  pattern for the remaining P1 tasks too (several of which — R2-03, R2-05,
  R2-06 — make similarly strong empirical claims worth verifying before
  editing).
