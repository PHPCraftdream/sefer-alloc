## Disputed / interesting points (the user explicitly asked these be preserved)

- **`@fh` vs. the eleventh review's own filed recommendation, on the doc-hidden decision.** Task #1267's card (item 101's addendum, and independently item 102's own re-confirmation of it) recommended option (c): promote `cpumap` to real documented API, on the grounds that "stable but hidden" is an incoherent contract. `@fh` read the same source and reached a different conclusion: promoting `cpumap` would freeze a parser that `docs/perf/OPEN_ITEMS.md` item 59 already flags as a candidate for a `getcpu(2)`/reverse-index redesign — i.e., (c) trades away exactly the refactoring freedom the perf backlog wants to keep. `@fh`'s counter-framing: the "incoherent" half of (c)'s critique was aimed at the wrong contract — "guaranteed forever but undocumented" is incoherent, but "hidden AND explicitly exempt from SemVer" (the `serde::__private` / `cargo-semver-checks`-recognized convention) is not. The user picked `@fh`'s (d) over the filed (c) — **this is a live disagreement between two independent reviewing agents that the human resolved by picking the later, more specific argument**, not by deferring to whichever was "first" or "official."
- **`@fh`'s honesty correction on the `mock`→cfg framing.** `@fh` flagged that describing the cfg conversion as "shrinking the blast radius" (language used in earlier task descriptions this session, including my own) is imprecise: `RUSTFLAGS="--cfg numa_shim_mock"` still applies build-graph-wide once set. What actually changes is *who* can set it — only the top-level build invoker, explicitly, never a transitive dependency via Cargo's additive feature-unification, and never accidentally via `--all-features`/docs.rs/`cargo add`. Recommended the eventual CHANGELOG entry say this precisely rather than repeat the "scoped"/"shrunk" framing.
- **A concrete implementation trap `@fh` caught that the earlier task descriptions this session did not anticipate**: `crates/numa-shim/Cargo.toml`'s `[[bench]] numa_bench` has `harness = false, required-features = ["mock"]` — a Cargo `required-features` entry cannot reference a `--cfg` flag, only a Cargo feature. Converting `mock` to a pure cfg without addressing this will either leave the bench permanently unbuildable-and-silently-skipped or produce a hard compile error (no `main` if the whole file gets cfg'd out). `@fh`'s suggested fix: a `#[cfg(not(numa_shim_mock))] fn main() {}` stub, or equivalent.
- **A CI-correctness risk `@fh` flagged by name, citing repo history**: converting a Cargo feature to a `--cfg` flag risks a "vacuous green" CI row if the cfg is typo'd or the RUSTFLAGS step is misconfigured — the row would silently compile the mock tests *out* rather than fail, and CI stays green while testing nothing. `@fh` cited `docs/perf/OPEN_ITEMS.md`... actually cited **task #1070's "Breakage B"** and the `expectTest` sentinel machinery already built into `scripts/check-all.mjs:603-638` for exactly this defect class, and recommended the numa-shim conversion reuse that sentinel pattern rather than trusting a bare `RUSTFLAGS=` CI step.
- **Whether the two decisions are coupled**: `@fh`'s answer was "separable in outcome, but should land as one 0.2.0 wave" — mechanically, the `linux` module's own cfg gate (`not(feature = "mock")`) needs rewriting to `not(numa_shim_mock)` regardless of the doc-hidden decision, so doing the two waves separately touches the same lines twice; semantically, if `mock` had stayed a Cargo feature (rejected option (c) above) *and* `cpumap` had been promoted to "stable" (rejected option (c) on the other decision), enabling `mock` would have deleted a "stable" module — a second, compounding non-additivity. Both rejections removed this coupling risk, but it's worth remembering if either decision is ever revisited independently later.
