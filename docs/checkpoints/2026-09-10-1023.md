**G1 (P1, the sole NO-GO blocker) — CLOSED, commit `24552cb`.** A
genuine use-after-free: `HeapCore::push_with_overflow_retry`
(`src/registry/heap_core_xthread.rs`) called
`set_dirty_bit_for_segment(base, packed)` AFTER a successful
cross-thread-free ring publish — but that helper's first two
statements read the segment header at `base` to resolve the owning
`HeapSlot`, and by the time it ran, the segment's owner could already
have drained the just-published record and released (unmapped) the
segment. Fixed by splitting into `resolve_dirty_bit_target` (called
BEFORE the publish, while the block is still counted in the owner's
`live_count` and the segment cannot have been released) and
`apply_resolved_dirty_bit` (called only after a successful publish,
touching nothing but a process-lifetime `&'static HeapSlot` and
pre-computed bitmap arithmetic — no segment pointer at all). New
`tests/g1_dirty_resolve_apply_split.rs` pins this structurally (a
source-text drift guard: the apply function's one-parameter signature,
the resolved-target struct's absence of any raw pointer, and
resolve-before-publish ordering at both call sites) — verified
non-vacuous by reverting the fix and confirming the guard actually
fails. Also independently confirmed a pre-existing, unrelated Windows
linker failure (`tagged_index_stack_ab_runner_scratch_guard`) via a
throwaway baseline worktree, so it wasn't mistaken for a regression.

**G3 (P2) — CLOSED, commit `f949211`.** The batch allocation API
(`alloc_batch`) bypassed `drain_large_deferred_free` for Large
requests — the scalar `HeapCore::alloc` always drains before a Large
request, but both the fastbin batch's Large branch
(`alloc_batch_large`) and the non-fastbin `alloc_batch` never did,
so a batch-only owner whose blocks are freed by another thread would
accumulate O(cycles) held segments/table slots with no bound, headed
for OOM. Fixed by adding the drain to `alloc_batch_large` (the shared
Large-only helper) and having the non-fastbin `alloc_batch` classify
once per call and delegate Large requests to that same helper. New
`tests/batch_large_deferred_reclaim.rs` runs 64 batch-only
alloc/cross-thread-free/ack cycles and asserts the table high-water
mark stays bounded — verified non-vacuous (reverted fix reproduces the
O(cycles) growth exactly: `baseline=1, max_hwm=65, final=65`) and
incidentally confirmed the fix also silences one of four pre-existing
clippy dead-code warnings in the non-fastbin config (via a throwaway
baseline-commit worktree comparison).
