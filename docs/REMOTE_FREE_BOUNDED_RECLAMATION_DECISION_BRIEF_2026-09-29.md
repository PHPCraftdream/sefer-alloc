# Решение по bounded reclamation для remote free

Дата: 2026-09-29, Europe/Berlin. Статус: вопрос к владельцу проекта; это не утверждённый дизайн.

## Зачем нужно решение

Независимый [обзор `src`, раунд 6](reviews/2026-09-29-150233-src-review-xxs-sol-round-6.md) поднял два связанных замечания:

- **R6-01 / P1.** Если поток-владелец вышел, а другой поток позже освободил ещё живой блок его heap, note остаётся в очереди прежнего слота. Освобождение памяти зависит от будущего claimant именно этого слота; гарантированного события дренирования нет.
- **R6-03 / P2.** `trim_current_thread()` может вернуться, не обработав remote frees, завершённые до вызова: текущие очереди дренируются на других slow paths, а один проход overflow/spill имеет ограниченный бюджет.

Ранее выбранное направление — **полный bounded snapshot и scavenger**, а не только уточнение документации. Однако этот выбор не определяет цену по памяти, горячему пути и объём переработки. Прежде чем делать крупный патч, требуется зафиксировать именно эти решения.

## Почему существующие очереди не дают строгий snapshot

В intrusive spill producer сначала публикует `spill_head.swap(block)`, а потом записывает `next` и Release-пометку `ready`. Возможен порядок:

1. Узел A полностью опубликован до начала `trim`.
2. Producer B ставит себя в head и останавливается до записи `B.next`.
3. `trim` видит неготовый B. Он не может ждать B без верхней границы и не может добраться до готового A без ещё не опубликованной ссылки.

Значит, повторение текущего drain не превращает его в bounded snapshot. Похожее окно есть у reservation-before-payload в кольцах и у `PUBLISHING`-состояния Large deferred stack. Перенос обхода в отдельный поток без изменения ingress не устраняет эту причинную цепочку.

## Контракт, который нужно получить

Предлагаемая строгая формулировка: для всех valid frees, **публикация которых завершилась до начала `trim_current_thread()`**, вызов выполняет owner-side reclaim за конечное число шагов независимо от приостановленных других producers и непрерывных новых frees. Незавершённый producer не обязан входить в snapshot, но его block/segment остаётся живым и его note нельзя потерять.

Для ownerless слота scavenger должен получать исключительное владение через существующий tagged `free_slots.pop`, а не читать чужой `HeapCore` как `&mut` из producer-потока. При одновременном `claim`, `recycle` и новом remote free ни одна запись не теряется и индекс возвращается в free stack ровно один раз. Сам `GlobalAlloc::dealloc` остаётся неблокирующим и не выделяет память через глобальный аллокатор.

Release/decommit сегмента допустим только после исключения in-flight доступа producer к header, bitmap или block. Граница snapshot должна быть точкой завершения публикации, а не только reservation. Нужны доказуемые Acquire/Release-пары, правила ABA/provenance и обработка unwind.

## Кандидат A: per-segment pending bitmap

Один рассматриваемый дизайн оставляет per-segment ring как быстрый путь, а переполнение отправляет в заранее подготовленную bitmap сегмента вместо heap-wide overflow/spill stack. Для Large предлагается per-segment pending state вместо связанного стека; owner находит сегмент через существующий table. Чтобы ready note за reservation-hole не прятался за пустым слотом ring, owner сканирует фиксированный tail-snapshot и продвигает head лишь через обработанный непрерывный префикс. Dirty-segment bitmap должна быть доступна всем нужным `alloc-xthread` конфигурациям, не только directory-профилю.

Оценка **до реализации и измерений**: 4 МиБ / 16 Б = 262 144 возможных small slots, то есть 32 КиБ основной bitmap на сегмент; двухуровневый summary добавляет около 512 Б. При 4096 сегментах **только одна bitmap + summary** теоретически занимает около **128 МиБ + 2 МиБ на heap**. Это не измеренный RSS и не утверждение, что все страницы будут физически committed. На обычном пути изменятся атомарные операции и, возможно, layout/metadata footprint; выигрыш по скорости не доказан.

Для reclaim нужен исходный size class: mixed-class page map не является достоверным источником. Если packed `(offset, class)` удастся безопасно держать в теле ещё не reclaim-нутого блока, отдельная class table не требуется, но её отсутствие надо доказать вместе с lifetime pin. Если хранить class вне блока по **6 бит на каждую 16-байтовую гранулу**, class table занимает 192 КиБ на 4-МиБ сегмент. Вместе с bitmap это **224 КиБ на bank**; две полные bank — около **448 КиБ на сегмент**, теоретически **1,75 ГиБ на heap** при 4096 сегментах (без остальных metadata). Реальный расход зависит от выбранного кодирования, materialization и числа сегментов. Бюджет «32,5 КиБ на сегмент» не является полной ценой до выбора class storage и числа bank.

Кандидат пока **не доказан**. Например, если producer поставил pending bit и остановился до dirty publication, а owner видит старый dirty bit того же сегмента, owner может обработать note и попытаться отпустить сегмент до последней записи producer в его metadata. Простая последовательность `payload → pending bit → dirty bit` этого не исключает. Реализация должна явно закрыть этот interleaving (admission/in-flight pin, отдельное commit-состояние с повторной публикацией либо иной доказанный протокол), не превращая `trim` в ожидание paused producer.

Независимый adversarial design-аудит выявил дополнительные обязательства:

- Стабильный slot-sidecar для dirty/admission нельзя просто заменить metadata в освобождаемом сегменте: producer может писать туда после decommit/reuse без явного lifetime pin.
- OOO-обход ring требует sequence/tag у каждого слота. Неготовую reservation нельзя переписать при wrap или считать завершённой только потому, что более поздние слоты готовы.
- Large pending-state без поколения не отличает старый free от новой выдачи того же VA/cache entry с тем же layout. Нужны проверка generation и политика исчерпания без wrap.
- При panic между reclaim и очисткой pending запись может потеряться или быть обработана дважды; callback должен иметь terminal/no-unwind либо доказуемо идемпотентный контракт.

Аудитор предложил две publication bank со stable slot-sidecar, admission-счётчиками и закрытием старой bank при snapshot. Это направление для pin/reuse, **но ещё не доказательство строгого `trim`**: если producer старой bank остановился, ожидание `writers == 0` не имеет верхней границы. Если `trim` возвращается, не дренируя bank, он может пропустить frees, уже завершённые до вызова за незавершённой записью. Прототип обязан объяснить, как независимо discoverable READY-записи обрабатываются при таком paused writer, а сам writer удерживает segment lifetime до своей последней записи. Нельзя объявлять «две bank» решением без этой части.

## Альтернативы для сравнения

- **B. Иная bounded ingress-структура.** Допустима, если она позволяет обходить незавершённую публикацию без ожидания, не хранит stale pointer после OS reuse, не выделяет память в `dealloc`, даёт конечный snapshot и имеет меньшую измеренную цену. Название «очередь» без доказательства этих свойств недостаточно.
- **C. Сохранить текущие очереди и сузить контракт.** `trim` остаётся best effort, ownerless frees могут удерживать память до будущего claimant/конца процесса. Это меньший патч, но **не** закрывает R6-01/R6-03 по выбранному строгому контракту; выбрать C следует только явно как изменение продуктового требования.

## Что требуется решить владельцу

1. Подтвердить ли строгий контракт snapshot и scavenger выше для всех `alloc-xthread` feature-наборов, включая `production`, `hardened` и минимальные сборки? Если нет — какую точную гарантию и предел удержания памяти обещаем?
2. Разрешить ли исследовательский прототип bitmap/admission с **открытым** бюджетом памяти (от ~32,5 КиБ на сегмент для одной bitmap + summary до существенно большего при class table/двух bank; оценки выше), без обещания сохранить прежнюю производительность до замеров? Либо сначала искать B с меньшим footprint?
3. Должен ли `trim_current_thread()` при непрерывном потоке новых frees обрабатывать только completed-before-call snapshot (предлагается) или ещё и появившиеся во время вызова? Второе может лишить вызов конечной границы.
4. При каком измеренном ухудшении RSS, p99 `dealloc`, alloc throughput или idle retention прототип считается неприемлемым? Нужны базовые и новые замеры на одинаковой конфигурации, без hard gate по шумному wall-clock.
5. Допускается ли менять layout small-segment metadata и внутренний remote-free протокол сразу для всех `alloc-xthread` профилей? Если нет, какую минимальную совместимую границу требовать от прототипа?

## Критерии приёмки выбранного дизайна

- Детерминированные модели producer pause на каждом шаге reservation/publish для small ring, bitmap и Large; завершённая до cut запись обрабатывается, более поздняя сохраняется.
- Loom/эквивалентная модель гонок claim–scavenger–recycle, producer–snapshot и dirty-clear; ровно один owner mutator, отсутствие потерянных/двойных frees.
- Реальные регрессии для backlog больше `HEAP_OVERFLOW_CAP`, позднего free после owner exit, `trim` при уже завершённых remote frees, continuous producers, decommit/reuse и минимальных block sizes.
- Проверка unsafe/provenance, Miri где применимо, feature matrix и целевых ОС/архитектур; отдельные throughput/RSS/p99 замеры до заявления об оптимизации.
- Обновление API-документации и старых тестовых oracle только после подтверждённого изменения поведения; никаких версий и публикации без отдельного решения.

**Вопрос:** разрешить прототип A с обязательным доказательством lifetime/admission и последующими замерами, потребовать сперва вариант B с меньшей ценой или явно отказаться от строгой гарантии по варианту C? До ответа кандидат A и двухbank-вариант не следует считать утверждённой реализацией.
